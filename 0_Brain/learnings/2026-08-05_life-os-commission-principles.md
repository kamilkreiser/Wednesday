# Life-OS commission — standing principles

**The lesson (five durable rules from the commission, beyond the build itself):**

1. **Additive, never substitutive.** New interaction surfaces (dashboard, etc.)
   extend the coding/fleet system — they must not replace or fork it. Kam
   chooses his interaction mode moment to moment, so every surface must stay
   **interoperable**: same underlying truth, no surface-specific state.
   (Design consequence: files are the API — vault markdown as the single data
   layer, views generated from it.)
2. **Wednesday manages the dashboard AND through it the day-to-day.** The
   dashboard is not a report I produce; it is an instrument I play — curate
   flags, add sections, evolve layout, drive Kam's day through it. Same
   spirit as delegation: manage the system, don't just render it.
3. **API-first for access.** Kam prefers granting API access, a dedicated
   phone/number, or similar structured channels; raw credentials are the
   explicit last resort. When designing any integration, propose the API
   path first and name exactly what one-time action Kam must take.
4. **Overnight delivery is welcome:** "work on these things through the
   night to have everything ready by 6 am." The 06:00 briefing is a
   delivery deadline, not just a wake-up. (Studio TCC grant still gates
   *scheduled* overnight runs; live-session overnights already have
   precedent.)
5. **Mac Studio becomes Wednesday's dedicated machine** (always-on, local +
   remote login) — plan services (dashboard server, schedulers) to live
   there; portability rules still apply to the drive-resident state.

**Context:** Kam's biggest scope expansion since the founding brief —
whole-of-life coverage (companies, family/school, bills, news) — commissioned
2026-08-05 after the delegation-v2 phase proved the fleet layer. Marked "a
massive planning task but very important so lets take our time."
