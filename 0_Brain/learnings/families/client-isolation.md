# Client isolation

**The one idea.** Nothing of one client may appear in another client's work: not names, code, context, credentials, mail, or even how the product looks. Kam marked this "very important" and said it would be "embarrassing or worse" if one client's work carried the other's name, so any leak is treated as the most severe kind of event. The leaks that actually happened were never deliberate: a filter that was one clause too loose, a palette nobody constrained, a command that looked like a read. So the protection has to be built into the path, not left to care.

## The rules

1. **Treat any cross-client leak as severity-max, and take extra care exactly where patterns travel:** briefs, templates, and anything generated for one client from something learned on another. Client names are used here because the rule cannot be stated without them: Datasec must never see Secuura's names, code, context or credentials, and the reverse. `2026-08-03_role-beyond-code-three-priorities.md`
2. **The role this protects is wider than code.** The coordinator's help covers Kam's whole life (personal matters, his two children, turning ideas into reality, coordination, and whatever grows from there); coding is about 60% of it, and code-centred methods must not narrow her into a coding orchestrator. His three "very important" things are: no scope creep or leak between projects; seamless integration (one great way for him to interact, with her managing everything downstream, so he is not answering agents' questions, stepping through approvals or switching between sessions); and constant learning, by the system and not only by her. His approach constraints: try several approaches and reject most to find the right one; prefer Anthropic-native mechanisms, with messaging and mail as options; productivity is the limit, not money. This is a statement of who she is for him, kept as such. `2026-08-03_role-beyond-code-three-priorities.md`
3. **When a script or agent reads the shared mail bus automatically: filter on its own project tag before touching any message's subject or body.** The tag is the exact `[<Client>/<Project> ->` or the inbound `-> <Client>/<Project>]` for that project. A filter on message class alone (QUESTION, ANSWER, wrap) is necessary but never enough on a shared bus: the first matching message may be another client's. Prefer the project's own inbox wherever one exists. The coordinator's own pollers filter on the intended recipient too; reading the whole shared inbox is acceptable only in a seat that coordinates those clients, and it is exactly the unsafe pattern inside a single-client agent. Put the tag filter in the poller template so it does not depend on someone remembering to write it. `2026-08-13_shared-bus-tag-filter-or-leak.md`
4. **A fleet-wide fix to a shared protocol file is Kam's call.** A file shared across clients (the workspace rules, the fleet-comms section) is amended only on his decision, raised as a decision item, never edited unilaterally by the coordinator or a project session. `2026-08-13_shared-bus-tag-filter-or-leak.md`
5. **When an agent catches, contains and discloses its own breach unprompted: protect that.** Score the honesty; penalising disclosure teaches hiding. Ask whether the cause is structural (every agent with the same exposure) before treating it as one agent's mistake. `2026-08-13_shared-bus-tag-filter-or-leak.md`
6. **When I brief, accept, score or rule a deploy on any visual change for a client project** (theme, colour, component, layout): the brief names that project's style guide or brand-token source first, as a file the agent reads before anything else. If none exists, item zero of the round is to write one from the project's own brand tokens (its existing theme, its logo, the customer's own guide where the work is a client deliverable), and no invented colour ships until it exists. Standing line for every such brief: palette from this project's guide only; a colour that does not resolve to the guide is a Major whatever its contrast. `2026-09-02_style-guides-never-mixed.md`
7. **Brand conformance is a completion check beside contrast.** The QA pass lists every colour a change introduces against the guide (value to token, or off-guide); an off-guide colour is a Major at any contrast ratio and there is no allow-list for it. Before scoring, ask the negative test: would Kam recognise this as this client's product at a glance? If I cannot answer, the pass gets a brand check and I do not score until it lands. Passing contrast says nothing about whose product it looks like. `2026-09-02_style-guides-never-mixed.md`
8. **A palette is a brand decision and it is Kam's.** A theme derived from the guide is shown to him as a rendered proposal (screenshots, every mode) before it ships: the derivation is the agent's, the approval is his, and no themed surface is deployed without that approval on the record. `2026-09-02_style-guides-never-mixed.md`
9. **When running `git -C` on another project's checkout: read verbs only.** Reads: `diff`, `merge-base`, `rev-list`, `show`, `cat-file`, `ls-tree`, `ls-remote`, `log`, `grep`. Writes into its `.git`, and therefore forbidden from my hands however harmless the objects: `fetch`, `pull`, `push`, `merge-tree --write-tree`, `worktree add` or `prune`, `checkout`, `reset`, `stash`, `commit`, `tag`, `gc`. Before any `git -C` on a path outside my own project, read the verb against that list. `2026-09-06_other-projects-repos-are-read-only-git-verbs-that-write.md`
10. **To verify or predict a merge in another project:** use the agent's own receipt (parents, tree id, stat, authenticated) plus `ls-remote` from my seat. If a commit is not in the local objects, the agent re-derives it on request, or I clone into my own scratchpad and run the write verbs there. A merge prediction in a brief names the instrument and the seat that ran it. If a write has already happened in someone's checkout: disclose it in the artefact it was made for ("run in the builder's checkout, a write; re-derive it, do not trust it"), record it, and tell the owning seat if anything could be observed. `2026-09-06_other-projects-repos-are-read-only-git-verbs-that-write.md`

## What a tool already enforces

- `2_Project_Files/fleet/inbox_digest.sh` withholds other-client messages on the shared bus for the Tuesday seat (Datasec only), before any subject or preview is printed. The Friday seat works both clients, so no client filter applies to it there. It covers reads made through that script; an ad-hoc poller an agent writes for itself is not covered, and the lesson records the fleet-wide fix (per-project inboxes, or a tag-filter line in the shared rules) as Kam's decision.
- `2_Project_Files/fleet/hooks/pretooluse_no_cd.sh` refuses a git write verb pointed outside the seat's own tree, whether the target is named by `-C`, `--git-dir`, `--work-tree` or a `GIT_DIR=` prefix (the lesson text still calls this a candidate; the hook has since been built). It checks the coordinator seat's own Bash calls only: it does not cover a GUI tool or a script that runs git internally, so the verb list is still read every time.
- Nothing enforces the style-guide rules; they live in the brief's standing line and the QA pass.

## The mistakes this family keeps catching

- A filter that checks what kind of message it is but not whose it is.
- A check that keeps passing (contrast, tests) on a question that was never the one Kam cares about (whose product this looks like).
- A builder with nothing to constrain it inventing a look, and the look belonging to another client.
- A command classed as reading that writes into another project's files.
- Treating a structural exposure as one agent's slip, or punishing the agent that disclosed it.
- A pattern, template or phrase learned on one client reused for the other.
