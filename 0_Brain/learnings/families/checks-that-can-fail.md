# Checks that can fail: a verification is only evidence if it could have come out the other way, about the thing I am claiming

**The one idea.** A check can be performed carefully and still prove nothing: it could never have failed; it returned an empty result because the measurement did not happen; it ran correctly on a neighbouring question; it was complete over a smaller world than the claim; or its control ran in a different mode from the judge. All of these feel like diligence from the inside. So the question is put to the check, not the result: what would make it fail, what did it actually look at, and is that the property my sentence needs? Most near-misses are in the checking, not the doing.

## The rules

1. **Before I trust any check:** ask "what would make this fail?" If there is no concrete answer it is decoration. A zero, an empty result, "clean" and a silent success are suspects, equally consistent with "nothing wrong" and "never ran". Never let an error exit be swallowed. Prefer checking the artefact (the rendered file, the served page, the value inside the failing process) over the intent. Be as suspicious of a surprising pass as of a failure. `2026-08-07_a-check-that-cannot-fail.md`

2. **When a suite asserts that things are rejected, blocked or absent:** it carries at least one case that MUST succeed, and the suite fails if that case does not pass; otherwise "refusing everything" looks like "rejecting correctly". Prove a search can find something before reporting that it found nothing. A red-proof needs a green baseline too, and a subject that actually builds; a test's name is not its coverage; a helper that reimplements the product is a mock. `2026-08-07_a-check-that-cannot-fail.md`

3. **When a check returns zero, empty, no match or all-fail, before that absence enters a sentence anyone will rely on:** run, in the same action, a control that would return non-zero, and read stderr. The control must be able to fail independently of the suspect case (different file, syntax or code path; best taken from something I did not write) and should answer a different type from the query, so an error string cannot pass as a count. If every case fails identically, the negative control included, test the instrument, not the subject. Ask whether the answer is even possible given what I know. On any authenticated service the first question about a zero is "was I allowed to ask?". A zero from a command whose invocation I did not verify (a truncated name, an abbreviated commit id, a wrong path) measures nothing. A control is owed when the absence becomes a claim, not for every read. `2026-09-08_a-false-absence-is-usually-my-own-instrument.md`

4. **When I extract something from a structured file or check a tool:** ask the resolver, not the text (the tool that consumes the format: `docker compose config`, `git config --get`, `jq`); never re-implement a tool's method to verify that tool, since two implementations disagree by default. Before searching a file I did not write, check its record separator (compare line count with byte count), search a single distinctive token in wrapped prose, and name any truncation (`head`, a limit, a column cut) as a frame. A search that returns a line has answered PRESENT, whatever the visible part shows: never read a mail body through a column cut, and write an absence about an agent's mail only from a count on the untruncated text with a positive control from the same text. The more small checks I run in a sitting, the more each must use the tool's own interface. `2026-09-08_a-false-absence-is-usually-my-own-instrument.md`

5. **When a control fires:** that proves the instrument runs, not that it answers my question. Read the control's hits, do not just count them, and when a zero would change a decision go to the source the artefact is derived from (the authored schema, not the generated file). `2026-09-08_a-false-absence-is-usually-my-own-instrument.md`

6. **When I run or write a pass/fail or there/not-there check:** name the third state first ("the measurement did not happen": skipped, wrong workspace, not started yet) and run a positive control before I want the answer. Ask at the level where "did not happen" is visible (step, not job). Enumerate the full set; do not verify a list I was handed. In briefs that offer two options, add "or tell me it is neither". `2026-09-10_a-two-answer-question-hides-a-third-state.md`

7. **When a gate, test or guard returns green:** say which property it tested and whether the claim needs that one ("the gate proved the cited mail exists", when the claim needed that it carries the content). Build checks against the failure to be prevented, not the artefact in front of me. A green on the first attempt at a recurring failure is a prompt to re-read the check. When a control returns the hoped-for answer, plant a violation, confirm it fires, restore byte-identical. In code keep "is there a result?" apart from "did the operation succeed?". `2026-09-08_the-check-ran-and-was-not-checking-the-thing.md`

8. **When I trust or report a control:** it must run in the same mode, by the same invoker, over the same set of refs as the judge: write down the exact command the judge runs and run that, and name the mode in the report. Check an ignore or suppression entry's key format against the mode that will read it. A canary must be a value the ruleset is known to detect (name the rule); a control that does not fire is unresolved between "instrument dead" and "canary wrong" and must be resolved, not reported. Read the population a clean result covered (files, bytes, commit count against `git log`; assume a merge commit unscanned until shown otherwise). A remedy for a skipped control is itself a control. `2026-09-20_a-control-in-the-wrong-scan-mode-buys-confidence.md`

9. **Before any instruction naming a path, a file or a dependency:** complete "this will behave as I expect because ___" with a property I have read (the config governing that path, the file's contents, the clause stating the dependency). Existence, size and location do not fill the blank. Before commissioning a file into a scanned or built repository, ask what the tooling will see in it. A branch push is an action on the shared board wherever CI scans history. A destructive control runs against a committed tree or a scratch copy. When unsure, commission the measurement, not the action. `2026-09-20_a-control-in-the-wrong-scan-mode-buys-confidence.md`

10. **When I write "the complete set" (all writers, all accounts, none left):** state the frame in the sentence ("three writers in `backend/`", "the account per `hosts.yml`"), ask what would live outside it (another language, directory, repository, file type, credential store), and look there once. Where a census underpins a decision the frame goes in the provenance line. Suspect a tidy census most. `2026-09-07_a-census-complete-over-a-frame-that-is-not.md`

11. **When a measurement surprises me, or before a step consumes a derived set:** print what the selector picked (field, file, resolved path, row count, the time of sampling) before re-reading the logic, and use a positive control or a second independent measurement. An index, a glob, `head -1`, a home-directory path, a pattern and the sampling moment are all selectors; one that encodes a location is seat-specific. A selector that omits an item gives no surprise at all, only a smaller consistent world: so check by hand that the one item the step exists to act on is in the set. Where a prediction keeps being wrong, replace it with a mechanism that halts cleanly. `2026-09-10_surprising-measurements-are-selector-errors.md`

12. **When browser verification of someone's work surprises me:** suspect my own selector or a stale handle first. Target the exact control by stable id, re-query just before interacting, confirm the click landed, reproduce a second way (keyboard, direct call, fresh load) before calling it a defect, and report my own test-side errors in the receipt. `2026-08-06_selector-discipline-in-ui-verification.md`

13. **Before I call a cross-cutting change done:** list every render path (subpages, print views, exports, emails) and search the whole output tree for the OLD pattern; the closing check is its absence everywhere, not the new thing's presence where I looked. Depth of a check says nothing about its coverage. A request to "double check" is a real hypothesis that something is wrong. `2026-08-07_enumerate-every-surface-before-done.md`

14. **When I verify a multi-hop sync or copy:** pick a file known to have changed today and confirm its content at the FINAL destination. Leg exit codes prove only that two roots match. Do this before promising Kam freshness. `2026-08-05_verify-the-chain-not-the-legs.md`

15. **When a credential fails:** verify it at the point of use (print its length inside the failing process), not at rest. Sourcing a bare-assignment `.env` without `set -a` works for same-shell expansion and breaks any child process reading the environment; check how the value is consumed. A plausible cause is not a diagnosis: reproduce the failure, off-schedule, before shipping a fix. `2026-08-07_valid-is-not-delivered.md`

16. **When I deploy a config file a container mounts as a single FILE:** verify by the served behaviour, with a positive control, never by the steps. The mount binds the inode: copy or rsync orphans it, and checksum, config test, reload and health can all be green while nothing changed. Use an in-place write plus reload, a restart of the same container, or a recreate (which may swap the image); afterwards compare host and container inode and checksum. If the cheap path was the premise of an authorisation and it fails, the authority does not widen: stop and ask. `2026-09-10_a-single-file-bind-mount-binds-the-inode.md`

17. **Before I arm any script, watcher, hook or flow:** run it in its real environment and prove both the fire path and the quiet path; walk interactive branches with real keystrokes, Enter included; assume the oldest shell on target machines (macOS bash 3.2: no associative arrays, no `timeout`); recheck executable bits after a drive sync. `2026-08-06_exercise-mechanisms-before-arming.md`

18. **When I build a redacted or client-safe artefact:** run the redaction mode and inspect the OUTPUT for what should be gone, across every carrier the format has (speaker notes, metadata, comments, alt-text, revisions, embedded objects, filenames). Fix the mechanism with a verifier that fails on a leak, not the wording. A containment control never run is a claim. `2026-08-13_containment-never-run-is-a-claim.md`

19. **When I write a guard on identity, target, tenant, branch or recipient:** besides absent and malformed, ask how the value could be well-formed and still wrong (stale, inherited). Refuse on disagreement with an independent second source that cannot go stale the same way (environment against the checkout folder), only where both sources know, and test with a discriminating pair (same operation, suspect value and forced value, compare the destination). `2026-09-09_a-guard-refuses-malformed-input-and-the-real-failure-is-stale-input.md`

20. **When I rely on or write a guard:** read its exclusion list against its subject; each exclusion is a claim needing evidence. Plant the defect in an EXCLUDED file type; exclude by what the tool cannot read (true binaries), not by what is assumed safe; test a feared false positive instead of honouring it. A hook in an untracked machine-local path is delivered only when each seat has installed it. `2026-09-09_a-guard-whose-exclusion-list-contains-its-own-subject.md`

21. **When I specify or ratify red-proof arms for a checker:** list every legitimate shape of the real event (first push, fast-forward, re-push; first deploy, redeploy, rollback) and give each a CLEAN arm; each defect class gets a failing arm. If the failure path is destructive (restore, revert, delete), add a false-alarm arm, and until it exists the instruction on alarm is STOP and ask. Put every shape through the brief's rule text clause by clause. Ratifying an agent's arms is writing them. `2026-09-11_red-proof-arms-cover-every-legitimate-shape-of-the-real-event.md`

22. **Before filing a finding:** a control proving the failure pre-dates my work answers "is it mine?", not "is it already filed?". Search the board by symbol, file path or error string (never my own phrasing), state the search in the ticket, and if it is filed add the evidence there. Whenever a control's conclusion must be silently widened to justify the next action, the defect is in the widening. `2026-09-07_a-control-proving-it-is-not-yours-does-not-say-who-filed-it.md`

23. **Never commission "recognise the safe cases" of a shell, query language, template language or any interpreter as a security boundary:** commission the conservative rule (all of it is the dangerous class). If gate round 2 fails on a different dimension from round 1, ask "can this be made sound at all?" and remove the mechanism; removal is not a third round. The usability cost goes to Kam on a card with the safe default already applied, and the removed attempt is quarantined with both verdicts. `2026-11-17_a-recogniser-of-safe-shell-commands-cannot-be-finished.md`

## What a tool already enforces

- `2_Project_Files/fleet/send_brief.sh` refuses to send when the seat named in the environment disagrees with the checkout folder (rule 19). It covers that one identity field only.
- `2_Project_Files/fleet/hooks/pre-commit` refuses conflict markers, now including `.json` files (rule 20). It protects only seats that have copied it into their own `.git/hooks/`.
- The lessons also name an advisory hook that flags any `grep ... | cut -c` pipeline (rule 4); it warns and does not refuse.

## The mistakes this family keeps catching

- A zero or "clean" reported from an instrument that never ran, was not allowed to answer, or could not see the file.
- A green from a real check aimed at a neighbouring property.
- A complete answer over a frame the sentence never states.
- A control that shares the blind spot, or the wrong mode, of the thing it controls.
- Step-level successes (exit codes, checksums, reloads) taken as proof of the outcome.
- A guard whose exclusions or single source leave out exactly the case it was written for.
