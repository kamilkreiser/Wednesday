# Shell and script hygiene

**The one idea.** The shell does things I did not ask for, quietly: it runs text meant as prose, returns an empty string where I expected an exit code, re-reads a script I am editing, overwrites the file I just fixed, and writes when I only meant to look. Each rule here closes one silent path, and each has the same test: make the thing actually run and read all of what it printed.

## The rules

1. **When writing any script: never send stderr to `/dev/null`.** Errors go to a log, the console, or a variable printed on failure. If a command is expected to fail harmlessly, capture stderr and branch on its content; do not silence it. A failure message says what failed, the real error, and the next step. Tell "failed" from "not ready yet": freshly created cloud resources (a new secret, DNS record, role assignment) are eventually consistent, so retry with backoff (about ten seconds was the measured case) before declaring failure. When a fix like this lands, ask whether it is a bug in this file or in how I write files, and if the latter write the rule at once. `2026-08-06_never-discard-stderr.md`
2. **In a Bash tool call (the tool runs zsh): never branch on or print a piped command's status through `PIPESTATUS`.** It expands to the empty string in zsh, so the guard cannot fail. Redirect to a file and read `$?` (`cmd > out 2>&1; rc=$?`), then tail the file. If a pipe is unavoidable, zsh's form is `$pipestatus[1]`. Never chain a destructive step behind a guard that reads a piped status. `2026-08-26_zsh-has-no-pipestatus.md`
3. **When writing a brief, answer, note or lesson body through a heredoc: use a quoted delimiter (`<<'EOF'`).** An unquoted heredoc runs backticks and `$(...)` and expands variables, leaving a silent hole where the instruction was. Put live values (date, time, SHA) in afterwards with a second step, or build the body in Python. Before sending, grep the written file for the phrases that were meant to be there. Any stray tool error printed by a write-only command means a substitution ran: re-read the file. `2026-08-29_unquoted-heredoc-executes-backticks.md`
4. **The same defect from two more sides.** (a) Prose inside a double-quoted bash string needs every inner quote escaped, or the string ends early and silently; `bash -n` passes anyway. Safer: no prose in a double-quoted string, use a quoted heredoc into a variable, and check by sourcing the block and asserting the variable ends where it should. (b) A quoted heredoc protects only the first shell: text bound for a second interpreter (ssh, `bash -c`, a container exec, a script written for another box) carries no backticks or `$(...)` in prose, or escapes them for that layer. A "command not found" from a write or echo step means some layer interpreted it. Count the shells a body passes through. `2026-08-29_unquoted-heredoc-executes-backticks.md`
5. **At boot, before any greeting, voice, or "morning" or "overnight" framing: run `date '+%H:%M %Z'` and read the day-phase from it.** Never infer the time from mail timestamps or from the date having rolled over. Fleet mail times are UTC and the local offset is seasonal (plus 10 in standard time, plus 11 in daylight time): read it from `date +%z`, convert before reasoning about "how long ago". 23:00 to 06:00 is quiet hours: no voice, no greeting; a boot inside them is an overnight seat, not a morning one. A duration ("idle overnight", "waiting three minutes") is a measurement computed from two clock reads. `2026-09-07_read-the-clock-at-boot.md`
6. **Before editing a file to make a change stick: ask what else writes that file.** Grep the launcher and the generators for its name; a hit in a copy, a redirect, a template render or a dump means the file is an output and editing it is editing a cache. Put the fix in the generator, or in a seam the generator does not own (a wrapper beside it, a new file the launcher points at), never in the artefact. Prove it by making the overwriter run once more and checking the change survived. A present value that never moves (a frozen number, timestamp or status) is this failure's fingerprint: suspect a dead writer before the reader. And before reporting a UI change done, grep the identifying markup across every page: two renderers of one control is the standard hiding place. `2026-09-09_a-fix-in-a-generated-file-lives-until-the-next-boot.md`
7. **When writing a string detector that triggers a remedy: key it on the condition, never on the remedy's name.** Tools print their remedies (`--skip`, `--force`, `--abort`, `--hard`) as hints exactly in the failures where that remedy is wrong. Test a fact about the system (for a rebase: is anything conflicted, by an empty unmerged-files diff). If a string test is unavoidable, exclude the tool's advice vocabulary. Order the checks so the dangerous branch cannot be reached from the dangerous state. A recovery path never runs in normal operation, so induce the failure against the real script before trusting it. `2026-09-10_a-detector-keyed-on-remedy-text-matches-the-hint.md`
8. **Before editing any shell script: check whether it is running (`pgrep -fl <name>`).** Bash reads a script lazily by byte offset, so an in-place edit under a running instance kills or corrupts it, and appending is not a loophole. If it is running: stop it, edit, run the new code once (its `--once` or dry run), then re-arm, in that order. After any edit that might have disturbed a background mechanism, confirm the mechanism is alive (process list, pane list, launchd list): a watchdog that has stopped looks exactly like a quiet night. `2026-09-16_never-edit-a-bash-script-that-is-currently-running.md`
9. **Never run a write verb (`add`, `post`, `create`, `send`) with dummy values to read what it would say.** A refusal seen once is not a read-only mode; it depends on the inputs. To learn what a tool knows, use a read path: its header, its `show` or `list` verb, or its store file through an inclusion filter. Before piping any command through `grep`, `head` or `tail`, ask whether it can write; if it can, run it unfiltered or not at all, because the filter hides the one line that says it wrote. Never cut a write command's output with `tail` or `head` on its first run; to see a refusal whole, re-run the same real call with `2>&1 | head -40`. `2026-10-31_never-invoke-a-write-command-to-read-what-it-would-say.md`
10. **When writing a daily-note entry, a re-sent note, or a ledger edit that records a slip: it is the only tool call in its message.** The order is: act (one or more calls), read the output, then the note alone in a new message, then any ledger edit in another. A note written beside another call is composed before that call's output exists, so it states results it has not seen. Never bundle a note with a wake acknowledgement, a read, a launch, a board post, a delivery mark or a pane close to save a turn. `2026-11-01_a-note-is-its-own-message.md`

## What a tool already enforces

- `2_Project_Files/voice/speak.sh` refuses speech in quiet hours (override only for a genuine fire). It does not stop a wrong "morning" framing in text, a greeting in chat, or a misread duration.
- `2_Project_Files/tools/decision_queue.sh` refuses an `add` whose title, summary, default or option label is under four characters, which blocks placeholder probes. It does not stop a probe written with longer junk, and does not cover other tools' write verbs.
- `2_Project_Files/tuesday/tools/note_alone.sh` refuses a note sent beside another tool call (nothing is written). The lesson records that the refusal holds while the habit does not: every refusal is a wasted turn, and a ledger edit beside a note is not yet refused.

## The mistakes this family keeps catching

- A guard or check that reads an empty string and therefore can never fail.
- A document that reads as complete with a silent hole where the shell ate the text.
- A fix applied to an output, a copy or a running file, gone or lethal at the next boot.
- Tidying or truncating output and hiding the one line that mattered (the error, the "added").
- Using a write path as a cheap read because it refused last time.
- Fixing the instance and not adopting the rule, so the same bug is written again the same day.
