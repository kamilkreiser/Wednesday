# Develop workflows as we execute — systemise deliberately, on a cadence

**The lesson:** Kam wants workflow development to be a standing output of normal
work, not an occasional project: *"dev workflows as we execute tasks. Review
these at each task end or end of day, review what should be systemised and
review weekly."*

**How to apply:**
1. **During work:** when a task reveals a repeatable pattern (a sequence I'd run
   again, a check I'd always want, a delegation shape that worked), note it in
   the daily note as a workflow candidate — one line, same-session.
2. **At task end / end of day:** the retro asks one extra question — *what from
   today should be systemised?* Candidates → either a `0_Brain/skills/` ritual,
   a launcher/CLAUDE.md line, a script, or a Claude Code workflow definition.
3. **Weekly (consolidation slot):** review the candidate list; promote what
   recurred (frequency-weighting applies to workflows too); retire what didn't.
   The DGM guard applies: a systemised workflow is validated by later evidence,
   not by having been written.
4. **The filter (Kam's point x):** the course being studied mixes new and old
   approaches — *"use what is good but not what will take us backwards."*
   Adoption test: does this beat what we already run (learning loop v2,
   delegation protocol, verifier-first)? Novelty is not a reason; regression is
   a veto. Compare every candidate against current practice before adopting.
