**What the 08-13 session proved and what it now means.** Deleting an inbox-scoped API key
returns **204**, the key **disappears from the listing (count 0)** — and **keeps
authenticating**. Reproduced twice with two independent keys, one created solely to time it,
still working several minutes after its own deletion returned 204.

🔴 **The operative consequence, and it is a posture change rather than a bug report:
DELETION IS NOT REVOCATION on this platform, and the vendor will not commit to when it will
be.** Every AgentMail key we have ever issued must be treated as **permanently valid**.

**Three things follow, and they are Kam's to weigh:**
1. **Key rotation is not available to us as an incident response.** The per-project inbox
   migration's stated security premise was *"a compromised key can be revoked and
   replaced."* **Half of that is not true.** The isolation itself works exactly as
   advertised — own inbox 200, others 404 — and that half is unaffected.
2. **WED-107 changes shape.** Five legacy org-wide keys span every inbox; **the plan was to
   delete them.** Deleting them will make them vanish from the listing while leaving them
   live — **strictly worse than leaving them visible**, because the board would then say we
   had no org-wide keys while five kept working. *An inventory that cannot be made true by
   deletion is an inventory that must be made true some other way.*
3. **Issuing a key is now a one-way door**, so the bar for creating one rises: fewer keys,
   narrower scope, and no casual test keys.

⚠️ **And a genuine catch-22 worth recording: re-testing whether this is still broken
requires issuing a key that may never be revocable.** So I am NOT re-testing casually, and
the 08-13 evidence stands as the basis. **The cost of verifying the defect is an instance of
the defect.**
