### Secuura s29 — #686 blocked by CI infrastructure, not by its change (KS-628)
- **Two consecutive `pr` runs failed on the same shared boot step for the same
  reason with a DIFFERENT victim suite each time** — GitHub **secondary rate
  limit** (403) on the GHCR pull, after `Login Succeeded!`. Root cause: four
  suites each boot their own isolated stack, so one `pr` run does four full
  ~30-image pulls from the same namespace within minutes; whichever suite is
  pulling when the limit bites goes red. **That is why the re-run moved the
  failure instead of clearing it.** #686's own change is green — my diff-relevant
  suites all passed on one run or the other.
- **They asked rather than acted, and I agreed: LEAVE the shared workflow.**
  Their reasoning was right; I added the sharper version — a CI change made at
  01:00 that goes wrong is **discovered by Peter or Stuart in the morning, in a
  repo where neither knows a change happened.** Shared CI is technically inside
  my v1.3 scope (reversible, in-project), but *permitted* and *right* are
  different questions, and the payoff was one PR landing a few hours earlier.
  **#686 stays honestly red and un-merged; the B queue does not depend on it.**
- **My addition, verified from my own brain before asserting it: this is the
  SECOND occurrence, not the first.** 2026-08-05, PR #646 — same mechanism,
  stack-boot image pull dying on a GitHub secondary rate limit with the suites
  recorded `outcome=skipped`. **And that time it cost me a wrong root cause**: I
  read those reds as real Schemathesis/Akto findings when no test had run, and a
  Secuura session caught it (my ledger, 08-06). So KS-628's true cost is
  investigation time and at least one wrong conclusion, twice — that goes on the
  ticket and makes it a recurring fragility rather than a nuisance.

### Lesson extended — the third and fourth members of the family
[[../learnings/2026-08-07_a-check-that-cannot-fail]] now carries, from the same
agent in one night: **a check that cannot see**, and **a check that MISREPORTS
what it saw** — one rate limit wearing three disguises (Docker rendering a 403 as
*"repository does not exist or may require 'docker login'"*; the enforce step
rendering a **skipped** suite as *"k6 smoke failed"*; a re-run relocating the
failure so the second red reads as a different problem). Plus the nastiest
variant: **a remedy that hides its own ineffectiveness by moving the symptom.**
When a fix relocates a failure rather than removing it, suspect a shared resource,
not a flaky test.
