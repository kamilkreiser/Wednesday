===== TICKET =====
KS-1536 — One role vocabulary, seven divergent lists: platform_admin is a super-role to the gateway and an ordinary tenant user to the key policy [Backlog]

## BLUF

**The same question — "is this caller a platform role?" — is answered by at least seven separate hard-coded lists that do not agree.** The one that matters most: `platform_admin` is accepted as a super-role by the api-gateway in six places, and is **absent** from the key policy's `PLATFORM_ROLES`, so `decideTenantAccess` treats it as an ordinary tenant user.

Found while building KS-1533 arm 1 (the mint's organisation arm). It is **not** folded into that ticket: arm 1 is one call site, this is a repo-wide vocabulary problem. KS-1535 records the *policy* question of which roles may cross an organisation boundary; **this ticket is the engineering problem that there is no single answer to consult.**

## The seven lists, read at source

```
services/api-gateway/src/routes/audit-export.ts:105  adminRoles            …includes platform_admin AND ORG_ADMIN
packages/shared/src/security/keyRevokePolicy.ts:59   PLATFORM_ROLES        SYSTEM_ADMIN SUPER_ADMIN            <-- no platform_admin
services/auth/src/routes/users.ts:193                PLATFORM_ADMIN_ROLES  SYSTEM_ADMIN SUPER_ADMIN admin super_admin   <-- no platform_admin, but `admin`
services/auth/src/routes/oauth.ts:1156               OAUTH_PLATFORM_ADMIN_ROLES  the same four as users.ts, duplicated because
                                                     "neither list in routes/users.ts is importable" (its own comment, :1138)
```

`services/auth/src/routes/oauth.ts:1138` already says the quiet part: the lists are duplicated **because they cannot be imported**.

## The measured consequence

Running the real predicates over the vocabulary (caller in org A, target a different organisation in the **same tenant**):

| role | `isPlatformRole` | `isOrgBoundedRole` | `decideTenantAccess` verdict |
| -- | -- | -- | -- |
| `SYSTEM_ADMIN` / `SUPER_ADMIN` / `super_admin` | true | false | ALLOW `platform-admin` |
| `platform_admin` / `PLATFORM_ADMIN` | **false** | **false** | **ALLOW** `same-tenant` |
| `ADMIN` / `admin` | false | false | ALLOW `same-tenant` |
| `ORG_ADMIN` / `ISSUER_ADMIN` / `issuer_admin` | false | true | DENY `cross-organisation` |

Both predicates upper-case the claim (`keyRevokePolicy.ts:84`, `:123`), so this is not a casing bug — the role is in neither set. A `platform_admin` therefore passes the gateway's platform guards and then lands in the key policy as an unbounded tenant user.

**Stored roles are lower-case** on Kintsugi (J's count, 16:44Z), which is why the upper-casing in those predicates is load-bearing and why a new list written without it would be wrong on real data.

## Why it is worth a ticket rather than a shrug

* A role added to one list and not the others is a **silent authorisation difference**, and nothing fails when the lists drift — there is no test that compares them.
* KS-1283 already fixed one instance of this class ("a widened `SUPER_ROLES` would admit a tenant `ADMIN` role on six routes"). That was the symptom; this is the cause.
* The erasure path reached through KS-1533/KS-695 is irreversible, so "which list did this route consult" is a security question, not a tidiness one.

## Recommendation

One exported vocabulary in `packages/shared` (it already owns `keyRevokePolicy`), each role set named for the question it answers, and **a guard test that fails when any service re-declares one of them inline** — the KS-764 call-site-guard shape, which already works in this repo. The lists cannot simply be merged: they genuinely differ today, and reconciling them is an authorisation change per route, so the first step is a census with the differences stated, not a rename.

**Not in scope here:** whether `ADMIN` and `platform_admin` *should* be organisation-bounded. That is Kam's policy call on KS-1535 and his board card.

## ⚠ CORRECTION to the "measured consequence" above

The table above shows `platform_admin` as ALLOW `same-tenant` from `decideTenantAccess`, and says "for arm 1 that reads as unbounded". **That is true of the function and false of the route.** On the running mint route, `decideMint` runs first and refuses `platform_admin` 403, because `PLATFORM_ADMIN` is not in `KEY_ADMIN_ROLES`. So at the mint, this vocabulary split makes a gateway super-role **over**-restricted (it cannot mint keys), not under-restricted.

**This strengthens the ticket rather than weakening it.** The same role is a platform role to the gateway, an ordinary tenant user to `decideTenantAccess`, and not an admin at all to `decideMint` — three different answers to one question across three lists on one request path. That is exactly the problem this ticket names; I had just picked the wrong one of the three as the consequence.
