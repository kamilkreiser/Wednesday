===== TICKET =====
KS-1219 — OAuth /authorize answers 500 server_error for an array-valued scope (repeated query param or JSON array) - should be 400 invalid_request [Backlog]

## BLUF

**Minor, pre-existing:** `/api/oauth/authorize` answers **500** `server_error` when `scope` arrives as an ARRAY: a repeated query parameter (`?scope=a&scope=b`) on GET or POST, or a JSON array in the POST body. The request is malformed, so it should be refused 400 `invalid_request`. Measured by the tier-1 round-2 gate on PR #1026 (finding F-10) on all 53 apps, with develop equal to the PR head; not introduced by that PR.

## Recommendation

Refuse a non-string `scope` (and, by the same shape, any other non-string authorize parameter) with 400 `invalid_request` before the resolver runs, rather than casting the query. Add a cell per carrier (repeated query param on GET, the same on POST, JSON array body on POST) asserting 400, plus a control that a single string scope still resolves. Not built; `Refs KS-839` as its source.

## Detail

* **Cause, as the gate read it and re-read at develop** `20ab16f9a`**:**
  * `routes/oauth.ts:473-478`: GET `/authorize` destructures `scope` from `req.query as Record<string, string>`. The cast is compile-time only, so express/qs still hands over an array for a repeated parameter.
  * The resolver passes that `scope` to `parseScopeString` (`services/oauth.ts:357-360`), which calls `scope.split(/[\s,]+/)`. An array has no `split`, so the resulting TypeError reaches the handler's catch and answers 500 `server_error`.
  * POST `/authorize` (`routes/oauth.ts:619`) reads the same parameters from the query or body. The gate measured the POST query and JSON-array body carriers giving the same 500. Not re-measured here.
* **Why it matters:** a malformed client request is reported as a server fault. That is noise for monitoring and fuzzing (the `not_a_server_error` class), and it is the wrong contract for an integrator.
* **Not the same as KS-283** (Done): that was a 500 on malformed Unicode in authorize query parameters, a different input and cause.
* **Searched before filing** (Linear, literal matches, archived included): `server_error` (47 hits, the Schemathesis `not_a_server_error` family; the only authorize one is KS-283, above); `array-valued` (2: KS-256, KS-677, unrelated); `as Record<string, string>` (0); `invalid_scope` (3: KS-839, KS-840 on authorize error delivery, KS-822); `parseScopeString` (0).
* **Source:** gate report `2026-09-17-ks839-1026-df97c0def-tier1-r2` (F-10), relayed in Wednesday's GO for #1026 (2026-09-17 10:51Z).

265:     return { ok: false, message: 'invalid_client', description: 'Unknown client_id' };
266:   }
267: 
268:   if (redirectUri && !app.redirectUris.includes(redirectUri) && !app.redirectUris.includes('*')) {
269:     return { ok: false, message: 'invalid_redirect_uri', description: 'redirect_uri not registered for this app' };
270:   }
271: 
272:   // RULE 2c — KS-822 F-7: WHEN `redirect_uri` MAY BE OMITTED, decided here so all
273:   // three entry points agree.
274:   //
275:   // The disagreement F-7 names was three-way, not two-way: GET passed an absent
276:   // `redirect_uri` to this resolver and got the fallback; the POST DENY branch
277:   // did the same; and only the POST APPROVE path refused it, at a pre-resolver
278:   // required-field guard that never reached this line. So the fallback was dead
279:   // on exactly one of the three, which is the KS-804 shape again — a rule
280:   // enforced by a handler instead of by the resolver every handler shares.
281:   //
282:   // RFC 6749 3.1.2.3 makes the omission legal only when the ambiguity does not
283:   // exist: with more than one registered URI the client MUST send one. The old
284:   // fallback took `redirectUris[0]` no matter how many were registered, so with
285:   // two registered it silently picked the first — a choice nobody made, and the
286:   // same shape as F-5's empty filter. Now the omission is allowed only when the
287:   // app registers EXACTLY one, and refused otherwise.
288:   //
289:   // `invalid_request` is an existing message and so is invisible to F-8's
290:   // message-set guard — the RULES row for this rule is hand-added in the same
291:   // commit, as with F-6.
292:   if (!redirectUri && app.redirectUris.length !== 1) {
293:     return {
294:       ok: false,
295:       message: 'invalid_request',
296:       description: 'redirect_uri is required unless the app registers exactly one',
297:     };
298:   }
299: 
300:   const effectiveRedirect = redirectUri || app.redirectUris[0];
301: 
302:   // RULE 2b (KS-804 Q4) — the scheme. Applied to the EFFECTIVE target, so a
303:   // dangerous URI is refused whether the client supplied it or it came from the
304:   // app's own registration.
305:   let parsed: URL;
306:   try {
307:     parsed = new URL(effectiveRedirect);
308:   } catch {
309:     return {
310:       ok: false,
311:       message: 'invalid_redirect_uri',
312:       description: 'redirect_uri must be a valid absolute URL',
313:     };
314:   }
315:   if (REFUSED_REDIRECT_SCHEMES.has(parsed.protocol)) {
316:     return {
317:       ok: false,
318:       message: 'invalid_redirect_uri',
319:       description: 'redirect_uri scheme is not permitted',
320:     };
321:   }
322: 
323:   // RULE 3 — PKCE for public clients. This is the one whose absence on POST was
324:   // not merely a skipped check: a code minted with no challenge is redeemable
325:   // with no verifier, because exchangeCode only verifies inside
326:   // `if (row.code_challenge)`.
327:   if (app.appType === 'public' && !codeChallenge) {
328:     return {
329:       ok: false,
330:       message: 'invalid_request',
331:       description: 'code_challenge is required for public clients (PKCE)',
332:     };
333:   }
334: 
335:   // RULE 3b — KS-822 F-6: `code_challenge_method` must be one the verifier
336:   // understands, checked HERE rather than trusted downstream.
337:   //
338:   // `exchangeCode` selects the method with `row.code_challenge_method === 'S256'
339:   // ? sha256(verifier) : verifier` — an exact string match with the PLAIN
340:   // comparison as its else branch. So every value that is not exactly `S256`
341:   // verifies as plain, and the two that matter are:
342:   //   · `s256` — a client that believes it asked for S256 and got it. The
343:   //     challenge it computed is a sha256 digest; the server compares the raw
344:   //     verifier to it, so the code is simply unredeemable — but nothing tells
345:   //     the client its protection was never applied, and a client that instead
346:   //     sends the verifier as the challenge redeems with NO protection at all.
347:   //   · anything else — silently plain.
348:   // RFC 7636 4.3: the method must be a registered value. An unregistered one is
349:   // an error, not a default.
350:   //
351:   // Refused with `invalid_request`, an EXISTING message, deliberately: it is the
352:   // same class as RULE 3's refusal, and inventing a message for it would be a
353:   // published-contract change this ticket has no grant for. Note the consequence,
354:   // named because F-8's guard depends on it — a new rule reusing an existing
355:   // message is invisible to that guard, so the RULES row for this rule is added
356:   // by hand in the same commit and that is the only thing making it driven.
357:   //
358:   // NOT covered, and stated rather than implied: rows ALREADY stored carrying a
359:   // bad method still verify as plain. That population drains with the 5-minute
360:   // code TTL and no migration is attempted here.
361:   if (codeChallengeMethod !== undefined && !PKCE_METHODS.has(codeChallengeMethod)) {
362:     return {
363:       ok: false,
364:       message: 'invalid_request',
365:       description: 'code_challenge_method must be S256 or plain',
366:     };
367:   }
368: 
369:   // RULE 4 — scopes, against the app's own allow-list. POST used to store the
370:   // raw `scope` string from the body straight onto the code.
371:   //
372:   // KS-822 F-4 — OMITTING `scope` IS A DEFAULT, AND THE DEFAULT IS THE WHOLE
373:   // ALLOW-LIST. Named here deliberately rather than left to be re-derived.
374:   // RFC 6749 3.3 gives a server exactly two options when the client omits the
375:   // parameter: use a pre-defined default, or fail the request. This is the
376:   // first. Before KS-804 put GET and POST on this one resolver, POST stored the
377:   // raw body string, so omitting `scope` minted NULL — which is NEITHER of the
378:   // RFC's options. So the consolidation did not widen a correct behaviour; it
379:   // replaced a non-conforming one with a conforming and wider one.
380:   //
381:   // The asymmetry that makes this worth writing down: omitting the parameter
382:   // grants EVERYTHING the app may hold, while explicitly asking for only things
383:   // it may not hold grants NOTHING (`validateScopes` filters rather than
384:   // refuses — that is F-5, and it is a separate item). Asking for less than
385:   // nothing is therefore stricter than asking for nothing at all.
386:   //
387:   // Bound by `ks804-authorize-get-post-agree-per-rule.test.ts`, describe
388:   // "KS-822 F-4", four cases: the two no-scope cases plus a narrow-request
389:   // control (an explicit `openid` must NOT be widened to the allow-list) and
390:   // the all-unpermitted contrast. Removing the `?:` below reds exactly the two
391:   // no-scope cases. Narrowing this default is a decision to be made in those
392:   // cases first, not here.
393:   // KS-1219: a repeated query parameter (?scope=a&scope=b) or a JSON array body reaches this resolver as an ARRAY whatever the compile-time cast at the handler says, and
394:   // parseScopeString below would throw on it (an array has no split) and the handler would answer 500 server_error. A malformed request is a 400 invalid_request, the same
395:   // existing message RULE 3 uses, so no published message changes.
396:   if (scope !== undefined && typeof scope !== 'string') {
397:     return {
398:       ok: false,
399:       message: 'invalid_request',
400:       description: 'scope must be a single space- or comma-separated string',
401:     };
402:   }
403:   const requestedScopes = parseScopeString(scope);
404:   const grantedScopes = validateScopes(
405:     requestedScopes.length > 0 ? requestedScopes : app.allowedScopes,
406:     app.allowedScopes,
407:   );
408: 
409:   // RULE 5 — KS-822 F-5: rule 4 FILTERS, and a filter that removes everything is
410:   // not a decision anybody made. A request naming only scopes the app may not
411:   // hold used to reach `ok: true` with an EMPTY grant: on GET that renders a
412:   // consent page asking the user to approve a list of nothing, and on POST it
413:   // mints a code carrying scope ''.
414:   //
415:   // RFC 6749 4.1.2.1 registers `invalid_scope` for exactly this. Partial overlap
416:   // is left as a filter — that IS permitted, and §3.3's obligation to tell the
417:   // client what it actually got is already met by the token response's `scope`
418:   // field. Only the all-or-nothing case refuses.
419:   //
420:   // Deliberately conditioned on `requestedScopes.length > 0`, so this is about a
421:   // request that ASKED and got nothing. An app registered with an EMPTY
422:   // `allowedScopes` still takes RULE 4's default path unchanged and is not
423:   // refused here — whether such an app should be able to mint at all is a
424:   // different question and not this one.
425:   //
426:   // `invalid_scope` is a NEW message, and that is load-bearing twice over: it is
427:   // the RFC's own code for this condition (answering with `invalid_request`
428:   // would misreport a scope problem as a malformed request, the same species of
429:   // error F-1b corrected in the published contract), and unlike F-6's reused
430:   // message it IS visible to F-8's message-set guard — which reds until the
431:   // RULES row exists. That red was observed before the row was written.
432:   if (requestedScopes.length > 0 && grantedScopes.length === 0) {
433:     return {
434:       ok: false,
435:       message: 'invalid_scope',
436:       description: 'none of the requested scopes are permitted for this client',
437:     };
438:   }
439: 
440:   return {
441:     ok: true,
442:     app,
443:     redirectUri: effectiveRedirect,
444:     grantedScopes,
445:     codeChallenge,
446:     codeChallengeMethod: codeChallengeMethod || 'S256',
447:   };
448: }

458: /**
459:  * KS-799 — deliver the post-consent redirect target in a way the consent page
460:  * can actually act on.
461:  *
462:  * The gateway CSRF guard is double-submit-cookie: it requires the `X-XSRF-TOKEN`
463:  * *header* (csrf.ts), which a top-level `<form>` POST cannot set — so the consent
464:  * page must submit via `fetch` with the header (the XSRF-TOKEN cookie is
465:  * httpOnly:false for exactly this). But a browser `fetch` cannot follow this 302
466:  * to NAVIGATE the page, so an XHR caller is handed the target as JSON and
467:  * navigates itself; every other caller keeps the native 302.
468:  *
469:  * This is the whole of Option 2 (KS-799 ruling, 2026-09-07): no CSRF exemption
470:  * and no change to the CSRF middleware. It is additive and backward-compatible —
471:  * a request without `X-Requested-With: XMLHttpRequest` behaves exactly as before,
472:  * which is why every existing authorize test still sees a 302. Error responses on
473:  * this path were already JSON, so the fetch client reads those unchanged.
474:  */

476:   if ((req.get('x-requested-with') || '').toLowerCase() === 'xmlhttprequest') {
477:     res.status(200).json({ success: true, redirect: url });
478:     return;
479:   }
480:   res.redirect(url);
481: }

811: /**
812:  * KS-820 — read the client secret from either place RFC 6749 2.3.1 allows.
813:  *
814:  * HTTP Basic first, because the RFC says a server MUST support it and SHOULD
815:  * prefer it. The body form is accepted too: it is what most SDKs send.
816:  *
817:  * The Basic credentials are only honoured when the userid half MATCHES the
818:  * `client_id` the request is exchanging under. Without that check a caller
819:  * could authenticate as one client and redeem another's code.
820:  *
821:  * Per the RFC the two halves are form-urlencoded before the base64, so they are
822:  * decoded here; a secret containing `:` is not mangled because only the FIRST
823:  * colon separates the pair.
824:  */
825: /**
826:  * KS-823 — the client a token request is made under: `client_id` in the body
827:  * (what public clients send, RFC 6749 §6) or the userid half of an HTTP Basic
828:  * header (a confidential client authenticating per §2.3.1 need not repeat it in
829:  * the body). Body wins when both are present; readClientSecret() then refuses a
830:  * Basic userid that does not match it.
831:  */
832: function readClientId(req: Request): string | undefined {
833:   const fromBody = (req.body as Record<string, unknown> | undefined)?.client_id;
834:   if (typeof fromBody === 'string' && fromBody.length > 0) return fromBody;
835:   const header = req.get('authorization');
836:   if (header && /^Basic /i.test(header)) {
837:     try {
838:       const decoded = Buffer.from(header.slice(6).trim(), 'base64').toString('utf8');
839:       const sep = decoded.indexOf(':');
840:       if (sep > 0) return decodeURIComponent(decoded.slice(0, sep));
841:     } catch {
842:       // malformed — not an identification
843:     }
844:   }
845:   return undefined;
846: }
847: 
848: function readClientSecret(req: Request, clientId: string): string | undefined {
849:   const header = req.get('authorization');
850:   if (header && /^Basic /i.test(header)) {
851:     try {
852:       const decoded = Buffer.from(header.slice(6).trim(), 'base64').toString('utf8');
853:       const sep = decoded.indexOf(':');
854:       if (sep > 0) {
855:         const user = decodeURIComponent(decoded.slice(0, sep));
856:         const pass = decodeURIComponent(decoded.slice(sep + 1));
857:         if (user === clientId && pass) return pass;
858:       }
859:     } catch {
860:       // A malformed Authorization header is not a credential. Fall through to
861:       // the body rather than 500 on it.
862:     }
863:   }
864:   const fromBody = (req.body as Record<string, unknown> | undefined)?.client_secret;
865:   return typeof fromBody === 'string' && fromBody.length > 0 ? fromBody : undefined;
866: }
