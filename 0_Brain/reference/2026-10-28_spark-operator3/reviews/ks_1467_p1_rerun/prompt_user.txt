===== TICKET =====
KS-1467 — AppError resets every subclass to the base prototype: `instanceof <subclass>` is always false and ValidationError `details` (password-strength feedback) never reaches the client [Backlog]

## BLUF

`AppError`'s constructor ends with `Object.setPrototypeOf(this, AppError.prototype)`, which resets every subclass instance to the **base** prototype. So `err instanceof ValidationError` (or any other subclass) is **always false**, and `errorHandler` never adds `details` to a 422. The password-strength `feedback` that registration, password reset and password change build is silently dropped. The same constructor line is in `packages/shared`, which twelve other services mount.

## Recommendation

Make the constructor `Object.setPrototypeOf(this, new.target.prototype)` in both places, with a cell per subclass, and decide deliberately that 422 responses now carry `details` (a visible response change; check the published 422 shape first). Until then, code that needs to recognise an error by type must use `statusCode`/`code`, as the tests do.

## Detail

218: export async function assertAccountMayReceiveCredential(
219:   user: User,
220:   input: CredentialIssueGateInput,
221: ): Promise<CredentialIssueGateResult> {
222:   const { mfaCode, sourceIp, route, lockoutAlreadyChecked } = input;
223: 
224:   // Normalised HERE — see the header. The identifier is the account's own, not
225:   // one the caller supplied, so a caller cannot key the counter differently
226:   // from the account it resolved.
227:   const email = String(user.email ?? '').toLowerCase().trim();
228: 
229:   const { isLockedOut, recordFailure, recordSuccess } = await import('./accountLockout');
230:   const { getRedisClient } = await import('./session');
231:   const lockoutRedis = getRedisClient();
232: 
233:   if (!lockoutAlreadyChecked && (await isLockedOut(lockoutRedis, email, sourceIp))) {
234:     logger.warn(`${route}: blocked by account lockout`, { email: maskEmail(email), ip: sourceIp });
235:     return { ok: false, reason: 'refused' };
236:   }
237: 
238:   if (accountStatusForbidsCredential(user)) {
239:     logger.warn(`${route}: blocked by account status`, { userId: user.id, status: user.status });
240:     await recordFailure(lockoutRedis, email, sourceIp);
241:     return { ok: false, reason: 'refused' };
242:   }
243: 
244:   if (user.mfaEnabled) {
245:     if (!mfaCode) return { ok: false, reason: 'mfa_required' };
246: 
247:     if (!user.mfaSecret) {
248:       // MFA on with no secret is a configuration fault, not a credential the
249:       // caller can supply. Refuse rather than fall through — falling through
250:       // issues a credential without the factor, which is the whole defect.
251:       logger.error(`${route}: MFA enabled but no secret found`, { userId: user.id });
252:       return { ok: false, reason: 'refused' };
253:     }
254: 
255:     if (!verifyTotpCode(user.mfaSecret, mfaCode)) {
256:       const backupResult = user.mfaBackupCodes
257:         ? await verifyBackupCode(mfaCode, user.mfaBackupCodes)
258:         : { valid: false, index: -1 };
259: 
260:       if (backupResult.valid && backupResult.index >= 0 && user.mfaBackupCodes) {
261:         // Single-use: burn it before it can buy a second credential.
262:         //
263:         // KS-1052: the burn is CHECKED. It was discarded, and on a write that
264:         // did not land the code stayed valid while this function went on to
265:         // recordSuccess() and returned ok:true — a single-use credential
266:         // surviving the login it just bought. updateUserOrThrow refuses instead,
267:         // so the code cannot be spent without being spent.
268:         //
269:         // The 503 is not a credential oracle: it is reachable only AFTER a
270:         // backup code has already verified, so it tells an attacker nothing
271:         // they did not supply. An invalid code still takes the uniform
272:         // refusal path below.
273:         user.mfaBackupCodes.splice(backupResult.index, 1);
274:         // KS-1188 F3: a 503 around the burn does not mean "nothing happened". The burn can have LANDED while the
275:         // read-back inside updateUserOrThrow failed (measured by the #1013 gate: codes 2 -> 1), so "please retry" sent
276:         // the user back with a SPENT code: 401 and a lockout increment. A fault before the burn gives 503 then 200 on
277:         // retry, so the response alone cannot tell the two apart. Wording only (ruled option A, 2026-10-12): same 503,
278:         // same code, text that is true in both cases. It is conditional ("if you signed in with a backup code") so it
279:         // does not confirm the code was valid. Any other failure passes through untouched.
280:         try {
281:           await userRepo.updateUserOrThrow(
282:             user.id,
283:             { mfaBackupCodes: user.mfaBackupCodes },
284:             'Backup-code sign-in',
285:           );
286:         } catch (err) {
287:           // `statusCode`, not `instanceof`: this reads the same for an AppError from any package. (KS-1467: AppError's constructor used to end with
288:           // Object.setPrototypeOf(this, AppError.prototype), which reset every subclass instance, so `instanceof ServiceUnavailableError` was always false here.)
289:           if ((err as { statusCode?: unknown } | null)?.statusCode === 503) throw new ServiceUnavailableError(BACKUP_CODE_UNCONFIRMED_MESSAGE);
290:           throw err;
291:         }
292:         logger.info(`${route}: MFA verified via backup code`, { userId: user.id });
293:       } else {
294:         logger.warn(`${route}: MFA verification failed`, { userId: user.id });
295:         // KS-622: reached only when BOTH checks failed, so a legitimate backup
296:         // code never increments the lockout counter.
297:         await recordFailure(lockoutRedis, email, sourceIp);
298:         return { ok: false, reason: 'refused' };
299:       }
300:     }
301: 
302:     // KS-158: self-heal a legacy-plaintext secret after a successful verify.
303:     await userRepo.reencryptMfaSecretIfLegacy(user.id);
304:   }
305: 
306:   await recordSuccess(lockoutRedis, email, sourceIp);
307:   return { ok: true };
308: }
