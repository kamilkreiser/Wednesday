===== TICKET =====
KS-1467 — AppError resets every subclass to the base prototype: `instanceof <subclass>` is always false and ValidationError `details` (password-strength feedback) never reaches the client [Backlog]

## BLUF

`AppError`'s constructor ends with `Object.setPrototypeOf(this, AppError.prototype)`, which resets every subclass instance to the **base** prototype. So `err instanceof ValidationError` (or any other subclass) is **always false**, and `errorHandler` never adds `details` to a 422. The password-strength `feedback` that registration, password reset and password change build is silently dropped. The same constructor line is in `packages/shared`, which twelve other services mount.

## Recommendation

Make the constructor `Object.setPrototypeOf(this, new.target.prototype)` in both places, with a cell per subclass, and decide deliberately that 422 responses now carry `details` (a visible response change; check the published 422 shape first). Until then, code that needs to recognise an error by type must use `statusCode`/`code`, as the tests do.

## Detail

* **Measured 2026-10-12** by driving the real `errorHandler` in `services/auth`: `next(new ValidationError('New password is too weak', { feedback: ['add a number'] }))` answers 422 with the body `{"success":false,"error":{"code":"VALIDATION_ERROR","message":"New password is too weak"}}`. No `details`. And `new ValidationError('x', { a: 1 }) instanceof ValidationError` is `false`.
* **The dead branch:** `services/auth/src/middleware/errorHandler.ts:296`, `if (err instanceof ValidationError && err.details) { errorPayload.details = err.details; }`. The outer `err instanceof AppError` works (the base), the inner one cannot.
* **What is dropped today** (`new ValidationError(..., { feedback })`): `routes/auth.ts:201` (register) and `:819` (reset-password), `routes/users.ts:981` (change-password). I have not checked the other services' use.
* **Where the constructor line is:** `services/auth/src/middleware/errorHandler.ts:25` and `packages/shared/src/errors/index.ts:44`. Whether the shared handler has the same `details` branch is unmeasured.
* **How it bit me:** a new `err instanceof ServiceUnavailableError` check in the KS-1188 F3 change never matched. It was caught only because the new test went red against the fix; the fix keys on `statusCode === 503`.
* **Not established:** whether any client depends on `details` being absent; whether any other `instanceof <subclass>` exists outside `services/auth` (the one grep covered `Blockchain/Dev/services` and found only the two above).

Found by Seat V 3rd while building KS-1188 F3, 2026-10-12. Related: KS-1188, KS-253 (the 503 class).
