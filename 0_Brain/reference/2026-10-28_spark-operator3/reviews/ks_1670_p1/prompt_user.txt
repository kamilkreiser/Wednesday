===== TICKET =====
KS-1670 — m365-integration: three more reflection sites from gate AM1 - an unencoded connectionId in the success redirect, and two uncapped error texts in JSON bodies [Backlog]

**BLUF:** Gate AM1, reviewing #1622 (KS-1641 finding 2), found **three more places in** `services/m365-integration/src/index.ts` **that put text the service does not control into a response.** None is the crash #1622 fixes. One is an **unencoded** value in a redirect; two are **uncapped** error texts in JSON bodies, one of them an internal error message in a 500. All three need a valid session or a server-issued id to reach, so none is reachable by an anonymous request today.

Filed as one ticket because AM1 found them in one review pass. Measured by Seat R 55th at develop `115797747cb60009e781d80e9059dbbed69e1ac3`, file blob `1d9ea9df234832ceb8d04de116be10ee3bf421d3`. **Line numbers are develop's.** #1622 inserts 52 lines above them, so on that branch each is +52.

## The three sites

**1.** `:508` **—** `connectionId` **goes into the success redirect unencoded (AM1 N4).**

```ts
res.redirect(`…/admin/integrations?m365=success&connectionId=${connectionId}&tenant=${encodeURIComponent(connection.tenantName || '')}`);
```

`tenant` in the same template **is** encoded and `connectionId` is not. `connectionId` is `String(state)`, and it only reaches this line after `memConnections.get(connectionId)` hits. So it has to equal an id the server issued, and **it is not exploitable today.** It is fragile: if the id format ever admits `&`, `#` or `%`, the redirect's query changes shape. Fix: `encodeURIComponent(connectionId)`, the same as its neighbour.

**2.** `:742` **— an internal error message in a 500 body, with no guard at the site (AM1 N5).**

```ts
res.status(500).json({ success: false, error: { code: 'INTERNAL_ERROR', message: 'Token refresh failed', details: err?.message } });
```

This is the **KS-1410 class** (thrown text in a 500 body), but in a file KS-1410 does not cover. m365 reads `NODE_ENV` 5 times, **all at** `:1536` **or later** (the PII-key fatal-start block). There are **zero** `NODE_ENV` reads before `:742`, so nothing guards this site. The route is authenticated.

**3.** `:1026` **— Graph's own error text, passed back uncapped (AM1 N5).**

```ts
return res.status(resp.status).json({ error: (err as any).error?.message || 'OneDrive API error' });
```

This is **provider** text, not an internal error: it is the same kind of thing as the OAuth `error_description` KS-1641 capped. It is authenticated, uncapped, and it forwards Graph's status code unchanged.

## Why the third one matters beyond itself

The callback's `:515` already reflects MSAL's `err.message` into a redirect: encoded, uncapped, and reachable only with a valid `state`. KS-1641 calls that **a decision, not a cap**: bound the internal message, or map it to a code and keep the detail server-side. `:742` and `:1026` are the same decision in JSON bodies, so they should be decided together with `:515`, not capped one at a time.

## Neighbours read before filing

The search's negative control (`xkqvzzpholmdrf`) returned **0** hits, so the search does discriminate.

* **KS-1410** (In Progress): same class as site 2, but it lists **six files** by name, and m365 is not one of them.
* **KS-730** (Done): lists five files, with **0** m365 mentions.
* **KS-840**: about auth's own OAuth error envelope, not m365.
* **KS-1641**: owns `:465` (the cap, #1622) and the `:515` decision. These three are AM1's notes on that PR, carved out by Wednesday's ruling so they would not widen it.

## How to fix

Site 1 is a one-line change and can ship on its own. Sites 2 and 3 should wait for the `:515` decision on KS-1641, so that one rule covers all three.

Each fix needs a cell that sends **non-ASCII text across the boundary**. KS-1641's round 1 shipped a crash because every cell was ASCII; gate AM1's B1 is that crash.

+// KS-1670 site 1 (m365-integration src/index.ts, GET /api/callback success redirect): the redirect put `connectionId` into the query string unencoded, while `tenant` in the same template was
+// encoded with encodeURIComponent. The id only reaches that line after the server's own connection lookup hits, so it is not exploitable today, but an id format that ever admitted `&`, `#` or `%`
+// would change the shape of the query. This file reads the route's source text (no app boot, no database) and pins that every `connectionId=${...}` interpolation in the file is wrapped in
+// encodeURIComponent, and that the success redirect still encodes the tenant. C1 to C3 prove the instrument finds the route and the redirects it must not disturb.
+import { describe, it, expect } from 'vitest';
+import { readFileSync } from 'node:fs';
+import { join } from 'node:path';
+
+const SRC = readFileSync(join(__dirname, '..', 'index.ts'), 'utf8');
+const NEEDLE = 'connectionId=${';
+
+/** Every interpolation that follows `connectionId=${` in the source, as the text up to the closing `}` of the template expression. */
+function interpolations(): string[] {
+  const found: string[] = [];
+  let at = SRC.indexOf(NEEDLE);
+  while (at !== -1) {
+    const start = at + NEEDLE.length;
+    let depth = 1;
+    let i = start;
+    while (i < SRC.length && depth > 0) {
+      if (SRC[i] === '{') depth++;
+      else if (SRC[i] === '}') depth--;
+      i++;
+    }
+    found.push(SRC.slice(start, i - 1));
+    at = SRC.indexOf(NEEDLE, i);
+  }
+  return found;
+}
+
+describe('KS-1670: the m365 success redirect encodes the connection id', () => {
+  it('RED KS-1670 R1 every connectionId interpolation in a redirect query is wrapped in encodeURIComponent', () => {
+    const unwrapped = interpolations().filter((expr) => !/^encodeURIComponent\(.*\)$/.test(expr.trim()));
+    expect(unwrapped).toEqual([]);
+  });
+
+  it('RED KS-1670 R2 the success redirect carries the encoded connection id and the encoded tenant, in that order', () => {
+    expect(SRC).toContain('m365=success&connectionId=${encodeURIComponent(connectionId)}&tenant=${encodeURIComponent(connection.tenantName');
+  });
+
+  it('control KS-1670 C1 the instrument finds exactly one connectionId interpolation (the success redirect)', () => {
+    expect(interpolations()).toHaveLength(1);
+  });

387: // =============================================================================
388: // ORGANISATION BINDING (KS-1673)
389: // =============================================================================
390: //
391: // Every m365 resource below is owned by exactly one organisation, and the
392: // caller's organisation comes from their signed token — `req.user.organizationId`,
393: // set by @secuura/shared's `authenticate()` mounted on /api below — never from the
394: // request body or the query string. There is NO bypass for any role: an operator
395: // who needs to see another organisation's connections gets its own ticket and its
396: // own design.
397: //
398: // Two shapes of refusal, deliberately different:
399: //   * a route that NAMES a resource answers the SAME 404 it gives an unknown id,
400: //     so a caller cannot learn that the id exists (`ownedConnection`, `ownedSite`);
401: //   * a route that LISTS or CREATES has no id to hide behind, so a token carrying
402: //     no organisation is refused visibly with 403 rather than served an empty list
403: //     that reads like "you own nothing" (`requireCallerOrg`).
404: //
405: // A row with no organisation recorded is owned by NOBODY, including whoever created
406: // it. So is a site or document whose connection is no longer in the warm map. Both
407: // are fail-closed on purpose: there is nothing left to prove ownership with.
408: 
409: function callerOrg(req: Request): string | null {
410:   const raw = (req as unknown as { user?: { organizationId?: unknown } }).user?.organizationId;
411:   if (typeof raw !== 'string') return null;
412:   const org = raw.trim();
413:   return org === '' ? null : org;
414: }

416: function requireCallerOrg(req: Request, res: Response): string | null {

527: // =============================================================================
528: // REFLECTED TEXT BOUNDING — KS-1641
529: // =============================================================================
530: 
531: // Both helpers are exported so the guard below can be exercised DIRECTLY. With the
532: // code-point cap in front of it the guard's fallback is unreachable over HTTP, so a
533: // request-level cell cannot prove it; only a direct call can.
534: 
535: /** Code points of provider-controlled text this service will reflect or log. */
536: const REFLECTED_TEXT_MAX = 200;
537: 
538: /**
539:  * Cap provider-controlled text by CODE POINT, never by UTF-16 code unit.
540:  *
541:  * `String.prototype.slice` counts code units, so a cut at a fixed index can land
542:  * between the two halves of a surrogate pair and leave a lone surrogate behind.
543:  * `encodeURIComponent` throws `URIError: URI malformed` on one of those — and on
544:  * the OAuth callback below that throw happens inside an `async` Express 4 handler
545:  * on an UNAUTHENTICATED route, in a service that registers no `process.on`
546:  * handler, so it takes the process down rather than returning 500. Capping by
547:  * code point cannot split a pair, so the throw has no source here.
548:  */
549: export function capCodePoints(value: unknown, max: number = REFLECTED_TEXT_MAX): string {
550:   return Array.from(String(value)).slice(0, max).join('');
551: }
552: 
553: /**
554:  * `encodeURIComponent` that cannot throw — the second defence, not the first.
555:  *
556:  * With `capCodePoints` in front of it this fallback is unreachable through the
557:  * HTTP surface, and that is the intent: it is here so a later caller on this
558:  * route cannot turn a malformed string back into a dead process. The replacement
559:  * targets LONE surrogates only, so a valid pair survives intact.
560:  */
561: export function encodeReflectedText(value: string): string {
562:   try {
563:     return encodeURIComponent(value);
564:   } catch {
565:     const wellFormed = value.replace(
566:       /[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/g,
567:       '\uFFFD',
568:     );
569:     return encodeURIComponent(wellFormed);
570:   }
571: }

596: /**
597:  * KS-1677: why a callback is refused, for the log only. The caller sees one redirect whatever the reason.
598:  * The binding was already checked by the consume itself: a wrong or missing cookie never reaches here
599:  * with a record.
600:  */
601: function refuseOAuthCallback(pending: PendingOAuthState | null, connection: M365Connection | undefined): string | null {
602:   if (!pending) return 'no_matching_state';
603:   if (pending.expiresAt.getTime() <= Date.now()) return 'expired_state';
604:   if (!connection) return 'connection_gone';
605:   if (connection.status !== 'pending') return 'connection_not_pending';
606:   if (connection.organizationId !== pending.organizationId) return 'organisation_mismatch';
607:   return null;
608: }

610: /**
611:  * GET /api/callback
612:  * OAuth2 redirect handler — exchanges auth code for tokens
613:  * Note: No auth required — this is called by Microsoft's redirect
614:  */
615: app.get('/api/callback', async (req: Request, res: Response) => {
616:   const code = stringParam(req.query.code);
617:   const state = stringParam(req.query.state);
618:   const oauthError = stringParam(req.query.error);
619:   const error_description = stringParam(req.query.error_description);
620: 
621:   if (oauthError) {
622:     log('error', 'OAuth callback error', {
623:       error: capCodePoints(oauthError),
624:       description: error_description === undefined ? undefined : capCodePoints(error_description),
625:     });
626:     return res.redirect(`${process.env.FRONTEND_URL || 'http://localhost:6882'}/admin/integrations?m365=error&message=${encodeReflectedText(capCodePoints(error_description || oauthError))}`);
627:   }
628: 
629:   if (!code || !state) {
630:     return res.redirect(`${process.env.FRONTEND_URL || 'http://localhost:6882'}/admin/integrations?m365=error&message=missing_code_or_state`);
631:   }
632: 
633:   // KS-1677: `state` is an opaque single-use value bound to the browser that started the sign-in (its cookie),
634:   // to the initiating user and organisation, and to one connection. Every refusal changes nothing, exchanges no
635:   // code and answers with ONE redirect, so an unknown, spent, expired, unbound or no-longer-pending state cannot
636:   // be told apart (this also closes the old known-id vs unknown-id oracle).
637:   const stateHash = sha256Hex(String(state));
638:   const presentedBinding = readCookie(req.headers.cookie, oauthBindingCookieName(stateHash));
639:   const pending = presentedBinding ? await consumeOAuthState(stateHash, sha256Hex(presentedBinding)) : null;
640:   const connection = pending ? memConnections.get(pending.connectionId) : undefined;
641:   const refusal = refuseOAuthCallback(pending, connection);
642:   if (refusal !== null || !pending || !connection) {
643:     log('warn', 'OAuth callback refused', { reason: refusal, connectionId: pending?.connectionId });
644:     return res.redirect(`${process.env.FRONTEND_URL || 'http://localhost:6882'}/admin/integrations?m365=error&message=invalid_state`);
645:   }
646:   res.clearCookie(oauthBindingCookieName(stateHash), { path: OAUTH_BINDING_COOKIE_PATH });
647:   const connectionId = connection.id;
648: 
649:   try {
650:     const redirectUri = process.env.ENTRA_REDIRECT_URI || `${process.env.FRONTEND_URL || 'http://localhost:6882'}/api/m365/callback`;
651:     const tokenResult = await exchangeAuthCode(String(code), redirectUri, connection.scopes, pending.codeVerifier);
652: 
653:     connection.accessToken = tokenResult.accessToken;
654:     connection.refreshToken = tokenResult.refreshToken;
655:     connection.tokenExpiresAt = tokenResult.expiresAt;
656:     connection.status = 'connected';
657:     connection.connectedAt = new Date();
658:     connection.tenantName = tokenResult.tenantName || connection.tenantId;
659: 
660:     // Fetch tenant display name from Graph
661:     if (connection.accessToken) {
662:       try {
663:         const orgResp = await fetch('https://graph.microsoft.com/v1.0/organization', {
664:           headers: { Authorization: `Bearer ${connection.accessToken}` },
665:         });
666:         if (orgResp.ok) {
667:           const orgData = await orgResp.json() as { value: Array<{ displayName: string }> };
668:           connection.tenantName = orgData.value?.[0]?.displayName || connection.tenantName;
669:         }
670:       } catch { /* keep existing name */ }
671:     }
672: 
673:     connection.updatedAt = new Date();
674:     await dbSaveConnection(connection);
675:     log('info', 'OAuth callback: connection completed', { connectionId, tenantName: connection.tenantName });
676: 
677:     res.redirect(`${process.env.FRONTEND_URL || 'http://localhost:6882'}/admin/integrations?m365=success&connectionId=${encodeURIComponent(connectionId)}&tenant=${encodeURIComponent(connection.tenantName || '')}`);
678:   } catch (err: any) {
679:     connection.status = 'error';
680:     connection.errorMessage = err?.message || 'Token exchange failed';
681:     connection.updatedAt = new Date();
682:     await dbSaveConnection(connection);
683:     log('error', 'OAuth callback: token exchange failed', { error: err?.message });
684:     res.redirect(`${process.env.FRONTEND_URL || 'http://localhost:6882'}/admin/integrations?m365=error&message=${encodeURIComponent(err?.message || 'token_exchange_failed')}`);
685:   }
686: });

1375:     // m365-integration.openapi.ts). The old truthiness check only caught a

1379:     if (!parsed.success) {

1381:         success: false,
1382:         error: { code: 'BAD_REQUEST', message: teamsNotifyErrorMessage(parsed.error) },
1383:       });

1385:     const { event, documentTitle, documentId, actor, details } = parsed.data;
1386: 
1387:     // KS-934: this SELECT had no LIMIT and the loop below no aggregate bound, inside
1388:     // the request handler. safeOutboundRequest's own deadline defaults to 10 s and
1389:     // this call site passes none, so the worst case was rows x 10 s with the HTTP
1390:     // request held open throughout. Two bounds are needed and neither is sufficient
1391:     // alone: the LIMIT bounds the row set and the memory it costs but still allows
1392:     // LIMIT x 10 s of wall-clock; the aggregate deadline bounds the wall-clock but
1393:     // would still load an unbounded row set.
1394:     //
1395:     // KS-934 F-1274-1 — CORRECTING THIS COMMENT, which used to end "Paging is
1396:     // deliberately NOT added ... The un-attempted remainder is reported instead of
1397:     // being silently dropped". The first half still holds: cursor paging on the
1398:     // request path is more request-path work, which is the opposite of the fix. The
1399:     // second half was FALSE as written and was measured to be false: with a plain
1400:     // `LIMIT` over a FIXED `created_at ASC` order, rows past the limit were neither
1401:     // attempted NOR reported, and because the order never changed, "call again"
1402:     // re-notified the same first MAX_ROWS for ever. The newest webhooks were starved
1403:     // permanently and silently. Two changes, and each fixes a different half:
1404:     //
1405:     //   1. fetch MAX_ROWS + 1. The extra row is NEVER notified; it is read only so
1406:     //      the answer can say `truncated`, rather than presenting a bounded run as a
1407:     //      complete one. An exact "how many remain" would need a second COUNT(*) on
1408:     //      the request path, which is the work this bound exists to avoid.
1409:     //   2. order by `last_sent_at ASC NULLS FIRST, created_at ASC`. This ROTATES the
1410:     //      window: a row just notified sorts last, so the next call reaches the rest.
1411:     //      NULLS FIRST keeps never-notified rows at the head, so a newly registered
1412:     //      webhook is served first rather than last.

1414:     // KS1335, the limit this used to record: ordering on `last_sent_at` starved any
