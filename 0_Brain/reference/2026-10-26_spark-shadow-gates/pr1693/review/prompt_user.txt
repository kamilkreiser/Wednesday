===== TICKET =====
KS-1391 — No frontend declares a `test` script — six package.json files, none with one, so the issuer's vitest setup and its 12 component assertions are unreachable from any runner [In Progress]

## BLUF

`Blockchain/Dev/frontend/` has nine directories, six of them with a `package.json`, and **not one declares a** `test` **script**. The root workspace runner is `"test": "npm run test --workspaces"` (`Blockchain/Dev/package.json:17`), so it cannot reach them. The issuer went further than the others — it has `vitest` + `@testing-library/react` + `jsdom` in devDependencies, a `test:` block in `vite.config.ts:8-12`, and two real spec files carrying 12 assertions — and none of it can be run without typing a `vitest` invocation by hand. This is unit/component coverage only; the portals themselves are covered by the e2e-v2 browser tier, which has its own problem (`KS-1390`). Read from the tree on `develop` `8ba2da02d`, 29 Sep 2026.

## What was seen

Every `scripts` block under `Blockchain/Dev/frontend/*/package.json`:

| Frontend | `scripts` | Test files present |
| -- | -- | -- |
| `admin` | `dev`, `build`, `preview`, `lint` | 0 |
| `issuer` | `dev`, `build`, `preview`, `lint`, `check:bundle` | **2** (`blockchain-card.test.tsx`, `provenance-timeline.test.tsx`) |
| `verifier` | `dev`, `build`, `preview`, `lint` | 0 |
| `website` | `dev`, `build`, `preview`, `lint` | 0 |
| `outlook-addin` | `dev`, `build`, `preview`, `lint` | 0 |
| `demo-overlay` | `build`, `dev` | 0 |
| `status`, `gmail-addon`, `shared` | no `package.json` | 0 |

So the two issuer specs are dead weight: present, maintained-looking, and executed by nothing. `frontend/issuer/vite.config.ts:8-12` configures the vitest environment for them, which makes it look deliberate rather than abandoned — the missing piece is one line in `package.json`.

## Why it matters

* **It is a silent zero.** `npm run test --workspaces` at `Blockchain/Dev` looks like it covers the workspaces, and `frontend/*` is a workspace glob (`package.json:6-10`). A reader has no signal that the frontend leg of that command is empty.
* **It is the same class already ticketed one layer down.** `KS-634` (Backlog) — *"No CI gate runs the services' unit suites — a 73-test suite sat dead on develop and every PR stayed green"* — and `KS-652` (Backlog) — *"1219 tests across 23 services are ungated"*. Those are about services having suites nothing runs; this is frontends having no suite to run, plus one that exists and cannot be reached. Same failure mode, opposite end.
* **The precedent for cost is in the repo.** `KS-649` had 31 auth tests dead since 6 Aug because two suites failed at module load and reported "no tests"; `KS-718` had golden-master snapshots gitignored, so a fresh clone wrote its own expectations and passed. Tests that cannot fail are worse than absent — they read as coverage.
* Four shipped admin pages import types from `frontend/admin/src/__mocks__/` (`DocumentTypes.tsx:20`, `DocumentTypeDetail.tsx:22`, `VerificationQueue.tsx:11`, `Workflows.tsx:12`) — a `__mocks__` directory on the production path, in an app with no test framework to justify the name. Worth a look in the same pass.

## Suggested shape

1. Add `"test": "vitest run"` to `frontend/issuer/package.json` so the 12 assertions that already exist can run and fail. One line; it is the whole fix for the unreachable half.
2. Decide for the other five whether a unit tier is wanted at all. "No unit tests for admin/verifier, the browser tier covers them" is a legitimate answer — but it should be written down rather than inferred from an absence, because today the two states are indistinguishable.
3. If the answer is none, make `npm run test --workspaces` honest: `--if-present`, or a note in `Blockchain/Dev/package.json` saying the frontend leg is intentionally empty.
4. Rename or relocate `frontend/admin/src/__mocks__/` if it is production data, so the name stops implying a test fixture.

## Acceptance

* `npm test -w frontend/issuer` runs and reports 12 passing assertions.
* A planted failure in one of those specs turns the command red (the `KS-718` lesson — prove the suite can fail before trusting it).
* The intended unit-test posture for the other frontends is stated in the repo, whatever it is.

## Note to Kamil — please scan before fixing

Suggest checking the same shape across every workspace in one pass rather than ticket by ticket: which `package.json` files declare `test`, which declare it and are never invoked by a gate, and which have test files with no script. `KS-634` / `KS-652` already hold the services half, so a single audit would close the family. The `sdk/javascript` and `sdk/python` client SDKs are a third instance — no tests at all, and not workspace members, so nothing would reach them even if they had some.
