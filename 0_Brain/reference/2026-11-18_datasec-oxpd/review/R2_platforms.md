## BLUF (five lines at most: is this part buildable as written; the worst three findings)

1. The platform part is buildable in shape (one core, two adapters, LAN server, off-panel sign-in): 63 of 77 load-bearing claims traced, and no Blocker found. Phases 0 to 2 are NOT buildable exactly as written: five Major corrections are needed first.
2. Worst 1 (F1): "CoreWCF for the agent side, HP's own advice" is not what the library says. The thread is about OXPdLib 1.8.4 CLIENT proxies failing TLS on .NET 8, unresolved by the partner; HP's reply is to use Core WCF "rather than" the OXPd library. D3 and spike S2 rest on it, and S2 tests only the agent side.
3. Worst 2 (F3, F4): the OXPd 2 release gate is understated. The documents say only HP's signing turnaround can delay OXPd 2; the library also shows every platform version "Not Supported" for VAV, beta firmware not distributable to customers, and the documents' own rule that OXPd2Lib ships only after a production SDK. E1.9 (first signing round after phase 1) needs seven device groups; phase 0 supplies one printer.
4. Worst 3 (F2): "all registrations non-critical" is contradicted: HP defines the OXPd 2 USB reader target as a critical target, whose undelivered data is retried later, not discarded. A card tap made during a server outage may arrive after recovery; nothing in the design drops stale taps.
5. Also Major: phase-0 inputs miss blocking items the library names (F5), and the HA pair contradicts the TPM / non-exportable key store and rests on unmeasured device DNS behaviour (F6, F7).
