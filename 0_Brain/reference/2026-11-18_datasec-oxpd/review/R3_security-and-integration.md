## BLUF (five lines at most: is this part buildable as written; the worst three findings)

1. The security and integration design is buildable in outline, NOT as written: 144 of 160 load-bearing claims trace, no Blocker, but 12 Major findings change what phases 0, 1 and 4 must build or prove.
2. Worst 1 (F1, F2): the card-blob key is ALSO the QR key (same literal at both library lines, compared by equality only), so the server needs it to draw every QR; and the claim that the library copy is "old and rotated" rests on C-3 alone, while that key sits in the 4.4.1 source the fielded apps are built from. One question to Kam settles it.
3. Worst 2 (F3, F4): the session handle is put in OXPd 2 custom attributes, which the contract says flow to other agents and job statistics, and its "bound to the device" property is not given by the mechanism (panel page requests carry no per-device credential in the design).
4. Worst 3 (F5, F6): OXPd 2 `reissueInstallCode` is admin-only in the OpenAPI contract, so recovery after a reboot that kills the solution token needs the stored admin password (open reading Q7); and onboarding steps 4 to 6 of section 8.2 are in an order that cannot deliver the install code (cross-lane, R2 owns 8.2).
5. Also Major: No-MFA token write-back can break Workpath printers (F7), non-exportable Universal Print keys conflict with the HA pair and the backup (F8), Universal Print deregistration and `CLIENT_ID_UP` reuse have no source or ruling (F9, F10), the gateway's publisher rule is unknown (F11).
