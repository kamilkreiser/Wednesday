Lane C2 of the Datasec OXPd analysis, written 2026-11-18. Library root for all relative paths: `/Volumes/Laptop-DEV/!CODING/Datasec/OXPd/`. Leads from an earlier cut-off agent (scratch notes) were re-verified against the threads before use.

## 1. BLUF
This lane holds ten years (2017-2026) of OXPd 1.x field experience (HP JetAdvantage forum, Pro forum, KB), the legacy OXPd JavaScript SDK, and HP's general partner material (card-reader SDK, roadmaps, portal pages, firmware notes, PJL). Five facts that shape the port:
1. OXPd 1.x is an on-premises, server-reaches-device platform (fixed port 7627, no NAT, no failover, HP: "not a cloud-based SDK"; cloud → Workpath), and **OXPd2 runs only on FutureSmart 6+**, so FS4/FS5 devices without Workpath can only be served by OXPd 1.x (SF 360002980048; SF 49815561950611; SF 360046654334).
2. Card sign-in on OXPd 1.x works but is the most failure-prone area in the record: Concurrency faults, wake-from-sleep races (10-22 s), lost/partial HID reports, regenerated accessory context ids, sign-out notifications missing; the server must implement a defensive state machine (4.1, 4.2).
3. The panel browser is a constrained WebKit (≤ 2-3 MB per solution, cookies unreliable on FS5, no SVG/pop-ups, 10 s JS cap); Microsoft's login page inside it already failed for a partner (45.00.33, 45.00.CB) — Entra login must happen off-panel (4.4).
4. Firmware generation matters more than SDK version: TLS 1.3 (FS 5.5), browser/cookie changes (FS5), and many fixes land only in later or interim firmware; certificates must be CA-based with the full chain on every device (4.3, 4.8).
5. "OXPd JavaScript" is a legacy client-side library set (print, scan, discovery, device info only) running in the device browser over CORS on FS 3.7+; it has no auth, card-reader or statistics services, so the project does not need it (4.9).

### 4.1 Authentication agent, session, sign-out, kiosk and timeouts (OXPd 1.x)

**Sign-in mechanics and what HP will not change**
- HP (2018-11-28, HP-official 2018-12-07): authentication status messages on the panel cannot be suppressed or modified; non-UI-initiated authentication (server calls `ReserveAuthenticationContext`) always resets the UI at least once; a solution cannot query the state of the device browser and the device does not say why it requested a URI; a Default Homescreen Application ("kiosk mode") loads the guest context on first load and sign-out and the signed-in context on sign-in, and the app must handle the switch. SF 360020763713 :23, :59, :102. A partner notes the `UiContextId` arrives in the HTTP header of the request (:41).
- HP (2018-06-12): the device sends `UIContextId` in the HTTP header of the agent's prompt page together with `OXPd.AuthenticationContextId`; only one context at a time, so a card swipe while the sign-in prompt is open gives a Concurrency fault (SF 360003006187 :32, :65). `ReleaseUIContext` with that id was rejected; HP workarounds: `EndUserSession(uiContextId)` (:112) or `ReleaseAuthenticationContext(authContextId)` (:140). HP (2024-07-26): `ReleaseUIContext` cannot be used on an authentication prompt; use the authentication context id (SF 31612889326483 :35).
- Concurrency fault on `ReserveAuthenticationContext` is thrown when a user is signed in, an authentication is pending, or the device is not at the home screen ("UI is not idle") — HP-official 2018-11-08 (SF 360019351633 :45) and HP 2019-08-13 (SF 360033652974 :72-78). Consequence (HP 2018-07-31): a card swipe while a walk-up user is inside a native menu (e.g. Scan) cannot sign in; HP's workaround is to revoke all guest permissions so no menu is reachable before sign-in (SF 360014560793 :52, :65); an enhancement was "resolved for future release" with no date (2019-01-31, :236).
- HP (2024-10-08 to 10-30, X57945 on FS 5.7.1.1/5.8): intermittent Concurrency faults were finally traced to the partner discarding the `AuthenticationContextId` when `SignOutNotification` arrived, so the later sign-out used an invalid id and the device still believed a user was signed in (SF 33960974483859 :135, :161, :261). The partner's fix: keep the id and always `ReleaseAuthenticationContext` before a new `Reserve…` (:261). This is a direct design rule for the port.
- HP (2024-06-14): authenticating from a custom unlocked web button (instead of the device Sign In button) is "not supported by the OXPd .NET/Java SDK"; UI-initiated authentication must start from the device Sign In button (SF 30193638510995 :35). HP (2024-08-05): the grey "all apps locked" screen cannot be changed via OXPd; leave one app unlocked or use kiosk mode, in which case the solution handles authentication itself (:117-121).
- UI-initiated sign-in with the agent's own prompt page: the page calls `window.close()`, which triggers `GetPostPromptResult`; a partner's earlier failures came from an invalid PostPromptResult (2022-02-22, SF 4416997899283 :187-191). Double prompts: when a card is swiped while the agent's prompt page is open (user had touched a locked app), the device runs two authentication requests and calls `GetPostPromptResult` twice; HP (2020-11-04): the solution must merge the two (SF 360040940153 :511-521); a partner saw an error screen on some firmware (2406048 fine, 2410028/2408071 not, :115).
- `GetPrePromptResult` can be called twice with the same context id when the user touches a locked app just as a non-UI authentication wakes the device (partner 2019-10-23, HP could not reproduce; SF 360037191933 :11-22, :76).
- HP (2022-12-19/2023-02-23): a HID report from the Accessories service does NOT itself cause `GetPrePromptResult`; the server must call `ReserveAuthenticationContext` ("Non-UI Initiated Authentication with User Prompt") (SF 12060994970003 :108).
- User identity to apps: the signed-in user reaches an app only through Initial Post Query Format String (IPQFS) macros in `BrowserTarget.initialPostQueryFormatString`, POSTed on app launch — HP-official 2018-06-28 and 2019-03-29 (SF 360003268548 :18; SF 360029167053 :25-30). `AuthenticationInfo.browserCookie` was ignored by the device browser (E87640, FS 4.6.4); HP 2019-11-18: setting a cookie through authentication is "regarded as a new feature … no estimate" (SF 360033520394 :131); use IPQFS + KeyValuePair (:159-161). SAML: HP labs 2021-03-17 — not supported directly; the auth agent can put an `OpaqueToken` on the security context, delivered to apps as POST data via IPQFS (SF 360051964174 :47, :74-76).
- CAC/PIV on FS5 is a wholly embedded firmware agent, not OXPd (HP 2020-05-28, SF 360045100354 :48).
- `UserPreferences.autoLaunchAppAccessPointId` launches an app after sign-in (HP-official 2018-08-06, SF 360014554714 :46-50); it failed after a cancelled sign-in on FS 4.10, fixed in FS 4.11.0.1 (SF 360044268893 :40, :123).
- No API lists only third-party apps or their ids; the Authorization agent manages ALL device apps (least privilege) and is notified when a top-level button is registered; `GetTopLevelButtonRecords` lists non-native buttons (HP 2025-11-18/27, SF 46592259029779 :35-49, :84).

**Sign-out**
- HP-official 2019-10-24: no guaranteed order between `SignOutNotification` and the reload of the default app; notification only if `EnableSignoutNotification` is true (SF 360036970654 :39, :70). HP-official 2019-03-20: sign-out and browser refresh are two separate workflows, either may come first; refresh the page from JS after sign-out completes (SF 360028756694 :66-68).
- `SignOutNotification` not delivered on FS 5.7.1.1 (E78625, SDK 1.8.4) even by the SDK example; HP 2024-07-18: R&D fixed, firmware "25.9" planned spring 2025 (SF 30255164600851 :113). In 2025 a partner reported no notification on inactivity-timeout logout on "all models" with 1.8.4; HP could not reproduce in ~85 attempts and the thread closed without a fix (SF 42381631056659; SF 43070912507539 :153, :195).
- No JavaScript sign-out; must be a server-side SDK call (HP 2020-08-10, SF 360049212253 :18). Own Home button + `EndUserSession(uiContextId)` (HP-official 2019-10-07, SF 360036657913 :25). Server-initiated logout from the cloud: HP 2022-04-19 points to `UIConfiguration.EndUserSession` (SF 4620109272339 :92); the partner says a cloud server cannot reach the device (:127); HP 2022-05-02: "If you are creating a cloud workflow then It would be better to work using Workpath and not OXPd" (:142); HP 2022-11-25: the general requirement "was never prioritized and is not even planned" and a restricted SDK might be discussed with the alliance manager (:280-285).
- Once the server has lost a context id (e.g. after server restart) it cannot force a logout; HP cites security checks (2020-03-13, SF 360039960393 :29-31; 2020-03-30, SF 360042044694 :61).
- Fast reserve-then-release before `Authorize` arrived left the user logged in until a ~5-minute `SignOutNotification` (partner 2021-05-03, unreproduced by HP; SF 1500000937002 :14-24).

**Kiosk / default home application**
- Login page as the default screen = register it as a top-level app and `UIConfiguration.SetDefaultApplication` (CopyKiosk demo) (HP 2019-09-10, SF 360034820514 :56). `OXPd.launchApplication(null)` returns to the native home (HP 2020-10-14, SF 360051458813 :64); the default app can be cleared on sign-in and re-set on `SignOutNotification` (:68).
- A kiosk app never times out to the home screen (HP 2020-04-21, SF 360043936453 :38). `window.OXPd` exposes `AuthenticationContextId`, `QuotaContextId`, `UIContextId`, `signInEnabled`, `resetEnabled`, `homeButtonVisible/Enabled`, `footerCollapsed`, `uiInactivityTimeoutPeriod`, etc. (:77-98). `signinEnabled` only acts in a home application (HP-official 2019-01-15, SF 360024304133 :71). The Sign In button cannot be hidden outside an app: by design admins must always reach the device (HP 2020-07-14/20, SF 360048448773 :49-51, :73).
- Mandatory sign-in page replaced the native menu when the guest permission set is null (FS4 fw 2406048); a custom login page there was "planned for future release" (HP-official 2018-06-27, SF 360003276867 :30-32, :71).
- Bricked-panel risk: kiosk + unreachable server + "Enable HP home screen if OXPd app fails to load" off = device stuck on the loading screen with EWS unreachable when the IP changed; only a partial clean recovers (partner 2019-05-14, HP 2019-05-16: use DNS names, keep the fallback enabled) (SF 360029579094 :16-22, :154). That fallback switch cannot be set through the SDK; it must be set in the EWS (HP 2025-09, SF 44554949772819 :46-52). Home-screen app randomly reverting to the native menu (E877, FS 5.7.2) was reported and not reproduced (SF 30889910344595 :10, :78).

**Timeouts, sleep and wake**
- Device UI inactivity timeout: no OXPd API to read/write or override it; `window.OXPd.resetUIInactivityTimer()` resets it temporarily only (HP 2026-03-24, SF 50168695633939 :122-126); no public MIB OID for it either, only sleep/power-state OIDs (HP 2025-05-21, SF 41012591095443 :56-60). A server-side `ResetUIInactivityTimer` exists from SDK 1.8.1.0 (HP 2020-02-03, SF 360038531173 :86). Solutions must not override the timer indefinitely (HP 2018-06-12, SF 360003006187 :69). The timer applies to the sign-in page unless the solution resets it (HP-official 2019-09-24, SF 360035736314 :33-35).
- Card sign-in from sleep is slow and variable: HP-official 2019-06-20 — the delay between `ReserveAuthenticationContext` and the context id is expected in sleep mode and differs by model (SF 360029714493 :151-153; 10-16 s seen on M725/M651). E62655 FS 4.10: 18-20 s vs E60155 5-8 s vs M527 3-4 s; HP measured ~4 s (2020-01/02, SF 360038531913 :170, :226, :257-261); partner "about to lose 500 MFP devices contract" (:86). E62655 FS 5.2.0.2: 7-12 s, up to 22 s; resolved by customer configuration (2021-11-10, SF 4409371931411 :149). E50145/E60145 20 s+, resolved by newer firmware (2020-11-02, SF 360051981353 :96); HP suggested `SetHomescreenMessage("Please wait")` meanwhile (:34).
- After deep sleep the first `ReserveAuthenticationContext` often returns Concurrency ("UI is not idle"); HP reproduced 50-70 % on M630 FS 4.8 and labs concluded there "has always been a risk … particularly on older devices" with no deterministic fix: retry (2019-08-16, 2020-02-05; SF 360033652974 :131, :188).
- After a reboot, OXPd services come up ~1-2 minutes after the panel is shown (HP 2021-02-23, SF 1500000457262 :43); Authentication can be ready before Authorization so a user can sign in with nothing unlocked; there is no readiness API — retry (HP 2021-05-24/28, SF 1500001144742 :60, :83).

**Server availability**
- With `EnablePrePromptCheck=true` and the agent server down, users could not choose another sign-in method ("Sign-In failed, Server or network problems are preventing sign-in", FS 4.7) — confirmed by HP 2019-05-07, workaround `EnablePrePromptCheck=false`, fixed in FS 4.10 (SF 360029556993 :92, :124-126, :161). The agent record there shows `connectionTimeout=30`, `responseTimeout=30` for authentication and 5/5 for authorization (:112, :117).
- "The default sign-in method is currently unavailable" = the device could not reach the agent server (HP 2023-12-01, SF 23029758166547 :22); in one case only a reboot cleared it (SF 360039198874 :24).
- An undersized solution server (1 core VM shared with Web Jetadmin) starved `GetPrePrompt` replies; some devices never reloaded the browser until rebooted; HP: size the server, adjust the inactivity timeout (2024-03/04, SF 26673063881235 :111, :154-158).
- "Sign-In failed" + event 49.38.02 on E87740/E82660 FS 5.7.1.1 while the same solution worked on FS4-era models; closed without root cause (2024-04, SF 28384130764563 :26-32, :111).

(Further session threads read: SF 360000826207 — `UIContextId` valid until return to Home, job ids reused, `serverContextId` for statistics (HP-official 2018-10-30 :104-108); SF 115008774068 — the agent page masthead cannot be removed, title = HTML title (HP 2017-09-14 :28); SF 360034208394 — `footerCollapsed`/`headerBackgroundColor` ignored on the auth prompt, fixed in FS 4.10 (:179), `dateTimeVisible` unsupported on Omni (:74); SF 360027100173 — panel timing out during long keyboard entry on M527 FS 4.7, HP could not reproduce (:347); SF 26412662443923 — `AuthorizeUser` not called on E87750, fixed by factory reset (:65); SF 360017881554 — "HP Access Server API" is not an OXPd component (HP-official 2018-10-26 :31).)

### 4.2 Card readers at the device (OXPd 1.x Accessories service)

**What the device accepts**
- Only USB HID-class readers: "Oxpd currently only supports HID card readers" (HP 2024-02-08, SF 25993660383507 :20). Devices report accessory classes HID, CCID, MassStorage (HP 2019-07-16, SF 360033417613 :42; partner output SF 360021397554 :98) but there is no OXPd method for CCID and no announced plan (HP-official 2019-02-25, SF 360027647553 :46, :64). HP gives no list of working non-HP readers (HP 2024-03-08, SF 26961068302483 :20) and says "there is no guarantee of compatibility with all USB accessories" (HP 2025-07-17, SF 42591455837075 :50). There is no white-list of reader VID/PIDs in firmware (HP 2018-12/2019-01, SF 360021397554 :153, :187).
- A reader must be registered (Owned or Shared accessory, VID/PID in decimal, serial number null is safest) before the device stops showing a USB error / "Attached USB device will not be used because it is not supported" (HP-official 2019-03-20, SF 360027745193 :117-121; HP 2023-02-23, SF 14210705659667 :30; HP 2025-07-17, SF 42591455837075 :46). An empty `EnumerateAccessories` after registration = the device does not see a matching HID interface (SF 14210705659667 :63, :90); in that thread the partner had the wrong PID (40106 vs 40101) for the reader mode (:190, :213). Registering with an empty string serial instead of null broke recognition after reboot (HP 2020-01-30, SF 360038402413 :128).
- HP readers: VID 1008 / PID 69 (X3D03A family, HP-official 2018-05-25, SF 360002659247 :30); VID 1008 / PID 21 seen on P57750 (SF 360049055993 :16). The device offers no way to list attached USB ids (same thread :12). X3D03A is an RF IDeas OEM; its only firmware is 16.0 (HP 2023-09-22, SF 12056036124691 :28, :138). The HP Card Reader Configuration Utility is documented as tested with X3D03A, 4QL32A, Y7C05A only, not 2FG93A (HP-official 2020-01-06, SF 360037953474 :55-57).
- An accessory is either Owned (events to one solution, survives without UI) or Shared (reserved per UI context); "it can't be both" (HP 2022-02-21, SF 4416997899283 :148-152).
- Reserving a shared accessory context over plain http fails: "OXPd does not allow http without ssl" (HP 2023-12-01, SF 23068526599315 :19).

**Data format and reliability**
- Readers deliver 8-byte HID keyboard reports (usage code in byte 3) that the solution decodes itself; start/stop characters are up to the reader maker (HP 2022-09-19, SF 9472274448147 :40; partner data SF 26786563597331 :12; HP :26). NUM LOCK / CAPS LOCK artefacts and truncated numbers appeared after FS3→FS4 on YSoft readers (2017, SF 115008774088 :20-24); the reader's key-press timeout mattered (:57).
- HP (2022-10-10): HID report delivery is not guaranteed; use the ordinal numbers, queue and re-sequence within a time window and reject a read with a missing ordinal; empty reports must be tolerated (SF 9890511134099 :80-88). Empty `HidReportEventData` interleaved with card data appeared only on FS 5.5 with Elatec TWN4; the partner's fix was ordinal-based assembly from ordinal 1 after registration (:145-151). HP recommends a ~1000 ms read window from the starting ordinal (SF 9472274448147 :52). `HidStopReading`/`HidStartReading` after each card to reset the ordinal is acceptable on a stable network but costs extra calls per device (HP labs 2020-09-08, SF 360049555754 :87-89).
- Field defects with reader data: one digit short now and then on a third-party reader, undetectable by the solution, unanswered (2025-11, SF 46912775231507 :10-12); 4QL32A sends 8 characters from sleep but 7 in ready mode on E786xx FS 5.5.0.3/5.7, unanswered (2023-11, SF 22781463374739 :16-20); X3D03A + MIFARE inconsistent values, fixed by Configuration Utility Card Type 1 = Mifare DESFire CSN (7F01), types 2-4 None, "Include Card Type With Data" enabled (HP 2023-05-23, SF 15864398937107 :117-119); partial card numbers FS 4.4-4.5.5, fixed in FS 4.6.0.1 (SF 360001107527 :69, :87).

**Context lifecycle**
- The device can and does regenerate owned-accessory context ids; the solution must handle `OwnedAccessoryEvent` and update the stored id (HP-official 2024-10-01, SF 33700121315475 :27; partner fix :51). After the device sends the context id the solution must bind with `HidOpen` + `HidStartReading`; a swipe wakes the device only when the accessory has a reader bound (HP 2026-01-12, SF 47393431346323 :47-51). There is no known interval at which these calls must be repeated; network interruptions can lose data (HP 2026-03-26, :109). In that case (E87740, events stopped after hours/days on a subset of devices; reboot did not help, re-registering did :13-16) HP R&D built a custom bundle; the customer on FS 5.9.2.3 saw it rarely and closed as "sufficiently mitigated" 2026-06 (:421-425).
- A 2020 case of X3D03A/Elatec readers silently not delivering swipes on E77650 (FS 4.7-4.10) was fixed by the partner moving to "strict SSL/TLS" callbacks (2020-10-15, SF 360039187694 :315; SF 360039153913 :88); timeouts were 10 s (:137).
- `ResendOwnedAccessoryEvent` failed after reboot ("No matching owned accessory record") on P77940; HP reproduced, fixed in FS 4.11 (2020, SF 360038402413 :205, :227, :315); accessories are unavailable for 2-3 minutes after reboot and there is no restart event (HP 2020-01-13/15, :47, :91). On a Pro/PageWide P57750 `ResendOwnedAccessoryEvent` returned 403 while Enterprise returned OK (SF 360049055993 :28-30).
- Firmware regressions fixed later: shared HID record lost on power cycle (FS 4.3-4.5.x, fixed 4.6.0.1, SF 360000144288 :119); duplicate `OwnedAccessoryRecord`s after 4.6.0.1 upgrade, card reader stopped after several records (HP-official 2018-08-09 with three workarounds, SF 360014373753 :115-121); 49.38.03 blocking the panel after reboot with YSoft reader on FS 4.5.5/4.5.6 (fixed 4.6.0.1, SF 360001107527 :30, :69); YSoft reader with two HID interfaces (hidraw0/hidraw1) dead on E42540/M430/M480 FS 5.3 (fixed ~summer 2022, SF 4411066461587 :106, :404); persistent "USB services are loading. Please wait." with a registered shared accessory on FS 5.7 (fixed FS 5.8, HP-official 2024-10-02, SF 21919456093587 :67); "failed to send USB data" panel error = device could not deliver the owned-accessory context id to the server (HP 2024-12-05, fixed by FS 5.8.1.1, SF 35440760154643 :100, :303); Y7C05A unreachable over MFP-8 on "Ballpark" E4000/E47528 FS 5.2-5.3, fixed in FS 5.4 (SF 4405977900563 :330, :342).
- Swipe while the network is down: nothing is shown; the Accessories service has no user-notification mechanism and none is planned (HP 2019-09-23/25, SF 360034919713 :39, :61). No way to block the UI immediately at swipe before the server round trip (HP 2021-01-22, SF 1500000228041 :37).
- Wake on swipe: a HID report alone does not wake the device; `ReserveAuthenticationContext` does (HP-official 2019-04-02, SF 360029003994 :27). FS 4.9 added wake-on-badge (cannot be disabled, HP 2020-01-10, SF 360038371533 :29); from 4.9/4.10 the wake clashes with `ReserveAuthenticationContext` ("device is not waking from sleep within 8000 milliseconds" / Concurrency); HP: detect that error and retry; the risk "has always" existed and no further enhancement is planned (HP 2020-01-21/29, SF 360038350394 :21, :64, :86-88).
- Network ports: OXPd 1.8 libraries use 80, 443 and 7627 inbound to the device; the device calls the solution from ephemeral source ports; port 1057 is firmware error reporting (HP 2025-06-05, SF 41867286054035 :57-61).
- Old HP proximity readers on M527 fleets (850 units) detaching (SF 30627514576787 :28-30; SF 4408601099667, unresolved 2022-01).

### 4.3 TLS and certificates across firmware generations

**Trust model HP prescribes (unchanged 2017-2024)**
- HP-official 2018-08-30 and 2019-04-17: create a Certificate Authority and install it on both device and server for bi-directional trust; for the device-as-server direction, generate a CSR in the EWS (Networking > Authorization > JetDirect certificate > Create Certificate Request), sign it with the CA, install the result (SF 360015026093 :134-160; SF 360029458853 :20-44). Devices "may re-issue the self-signed certificate and certificate authority at any time", most often after a partial clean or disk format (SF 360029458853 :46). Self-signed certificates in the OXPd CA store are "not recommended/supported" and several IIS-generated ones were incompatible (HP 2017-11, 2019-04-28, 2019-05-23: SF 115009586248 :28; SF 360029458853 :77; SF 360030260213 :40).
- The device validates the server against its CA store; install the issuing CA, not the server certificate (HP-official 2019-08-15, SF 360034060133 :34-39; partner's steps :65-75). HP 2019-03-15: there is "no possibility to know the CA's trusted by the device as they change during the time" (SF 360028756693 :195) — this bit a partner's Microsoft login page in the panel browser (45.00.33 "SSL certificate … not OK" until the GoDaddy CA was added, :143, :184). Typical JDP errors: `UnableToGetIssuerCert` (partial chain) and `HostNameMismatch` (HP 2018-08, SF 360002972068 :252-264).
- Error codes seen: 45.00.33 / 45.00.3C untrusted server certificate (SF 360028756693; SF 13580334058515 :9); 45.00.23 WebKit SSL connect error after importing a certificate in the same HTTPS session in which buttons are then registered — close the session after `ImportCertificate` (HP-official 2019-05-14, SF 360027182413 :112, :554); 45.00.34 empty packets from the solution server (SF 360003518808 :255).
- The SDK's discovery-tree call is HTTPS-only: `GetOXPdDiscoveryTree(hostname)` fetches over 443 with SSL; the `useHttps=false` overload is for internal testing only (HP 2018-07, SF 360003567947 :33, :87). The SDK examples include a certificate-validation override because devices ship self-signed certificates (SF 360051949494 :47-50) — a weakness to avoid copying.
- Client certificates: devices support TLS client authentication with their identity certificate, but there is no API to install identity certificates (HP 2021-07/08, SF 4403971370131 :37, :88). The OXPd CertificateManagement service handles the trust store only; identity certificates and SCEP are managed through HP Security Manager, no public API (HP 2024-11-22, 2024-12-06; SF 35440516114451 :49, :86).
- Cipher suites are managed per device at EWS > Networking > Secure Communication (HP 2025-08-07, SF 43146442117907 :55-61). Devices on recent firmware only enable TLS 1.2 by default (HP 2021-11-10, SF 4408601099667 :248).

**TLS 1.3 (FutureSmart 5.5 onwards)**
- 2020-06 and 2021-10: TLS 1.3 not supported, no schedule (SF 360047182614 title; SF 4408156338579 :21).
- FS 5.5 (2022) enabled TLS 1.3. .NET OXPd SOAP calls then failed with HTTP 400 or timeouts until `ServicePointManager.Expect100Continue = false` (HP 2022-12-01/08, SF 11492088428819 :80-85, :144; SF 11512914133139 :223). The KB article `OXPd1-NET-Java/Knowledge-Base/Issues--11899822165011-TLS-1-3-HTTPS-Requests-with-100-Continue-May-Result-in-400-Bad-Request.md` documents it.
- Device-to-server HTTPS scan upload with TLS 1.3 failed with 49.38.03 on E731xx/E786xx FS 5.5-5.7 (TLS 1.2 fine); HP: fix in FS 5.8, released on hp.com 2024-09 (SF 10530536296979 :8, :54; SF 17413087339667 :207, :231, :255).
- HP 2023-02-23: partners report callbacks working better with TLS 1.2 than 1.3; on FS 5.5+ consider limiting TLS max to 1.2 (SF 12060994970003 :125).
- "Ballpark" devices (E40040/E42540 class) FS 5.2-5.3.0.1: loading a corporate root CA broke all OXPd page loads ("Problem reading the SSL trusted root certificates"); fixed in FS 5.5 (2022-07, SF 4415520887315 :10, :244). "Enable extended signature verification" exists only on "L1Classic" FS5 devices (:107). E42540 FS 5.7 failed when two certificates from the same server were installed; not reproduced by HP (SF 27885097125011 :10, :195). FS 5.3.0.1 caused timeouts on CertificateManagement/UIConfiguration calls for one partner (E77660, M577), unresolved (SF 4412869470611 :11-24).
- Panel performance: every image over HTTPS costs a TLS handshake on parallel streams; HP recommends sprite maps and avoiding CSS image resizing (HP-official 2019-04-02, SF 360029003754 :43-47; HP 2019-12, SF 360037854173 :22-49); a partner measured felt response ~4.5 s with SSL vs ~2 s without on an M575 (:73-81).

### 4.4 Practical limits of the embedded browser (OXPd 1.x, FutureSmart 3/4/5)

- **Engine**: a WebKit build that cannot be upgraded or downgraded on the device (HP 2021-09, SF 4407694677267 :30). FS4-era user agent `AppleWebKit/534+` (WinCE); newer FS5 Linux devices report `AppleWebKit/605.1.15` (partner traces 2022-11, SF 11066887439891 :46, :99). HP-official 2024-04-19: "some" HTML5/CSS3 is supported; read the version from `navigator.userAgent` (SF 28314939713939 :20-22). The KB browser model lists JavaScript/AJAX, HTML4 (Windjammer), HTML5 (Omni), CSS3/CSS4, DOM2, cookies, images under 1,920,000 pixels, and a fixed MIME list; disabled: pop-ups (`open()` does nothing), plugins, SVG, alpha blending, XPath, file input, "Save As" downloads (`OXPd1-NET-Java/Knowledge-Base/UI-Configuration--115009332187-OXPd-1-6-Browser-Use-Model-and-UIConfiguration-Service.md:519-615`).
- **Memory**: HP-official 2020-01-15: solutions should use no more than 3 MB of device memory, 2 MB recommended (SF 360038344494 :23); the limit applies to the solution as a whole including third-party pages loaded in it (HP 2019-04-11, SF 360028756693 :372). Microsoft's login page inside the panel browser triggered 45.00.CB "insufficient memory" on an M681 (FS 4.7.0.1) when the user tapped an edit box (SF 360028756693 :208-231) and 49.DE.11 (unhandled JavaScript exception) on E77822 in the same OneDrive login flow (SF 360029155873 :10, :32). On FS 5.5 several long-stable apps started hitting 45.00.CB; HP's explanation: the newer browser keeps JavaScript objects alive across app switches, so the app must release listeners and objects on `unload`/`pagehide` (HP 2022-12, SF 11734241487507 :47-53, :312-330; KB article 21485043028883 cited at :353). Same advice for 45.00.CB / 49.DE crashes on old FS4 devices with 4.3-inch panels in 2026 (SF 49092012007059 :134-144, unresolved). 49.DE.05 during release of 25 retained jobs on E52645 FS 5.8/5.9 traced by the partner to an extra backend request at the browser's memory limit; fixed by rendering at most 15 documents (10 on 4.3-inch panels) (2026, SF 48618937868691 :214-238).
- **Cookies and session state**: on new-generation devices (E87740, WebKit 605) a server-set session cookie was not sent on the next AJAX request while older devices did send it (partner 2022-11, SF 11066887439891 :10-31); HP could read a cookie via `document.cookie` (:471, :502). Similar model-dependent cookie loss on E62655/E55040/E52645 FS 5.5-5.6; HP R&D treated it as a defect and suggested session cookies (2023-08 to 2024, SF 19349347465491 :160, :340). Per the KB, all cookies are deleted on UI timeout, successful login and logout (KB Browser Use Model :575-587). `AuthenticationInfo.browserCookie` is not honoured (4.1).
- **Other runtime limits**: WebSocket — a top-level button must be http/https; HP says the browser supports WebSockets (HP-official 2018-10-03, SF 360016736974 :87-89) but WSS from a page failed and labs said it was "not currently supported functionality" (2018/2019, SF 360018016773 :185); a partner replaced long-poll AJAX with STOMP and the browser became fast (SF 360018565194 :300-302). A SignalR connection in the page is lost when the app goes to the background (SF 4620109272339 :10). JavaScript console log costs ~250 ms per line on device (KB Best Practices `OXPd1-NET-Java/Knowledge-Base/General--115006143068-OXPd-Best-Practices.md:41`). Device JavaScript console log is at `/hp/device/oxpd/oxpdlog.txt` (admin) (SF 360029155873 :216). Screen sizes: no complete table; `GetUIAttributes` returns `controlPanelId` and screen resolution per device; new X58045/X67765 panels (1280×652, 1240×620, 1024×620 claimed) were missing from the Look and Feel guide (HP-official 2024-06-05, SF 27604834883859 :202-204); there is no programmatic touch/non-touch flag except the panel id (2022, SF 7937594141203 :146, :171). FS4 = Omni UI only; Windjammer = FS3 (HP 2026-01, SF 47291814491923 :96, :162).
- **The panel needs the server for every screen**: if the server is slow, the browser shows a loading page and some devices never recover without reboot (SF 26673063881235); when unreachable in kiosk mode the panel can lock (SF 360029579094). SSL makes every asset slower (4.3).

### 4.5 Pull print, IPP and job release (OXPd 1.x)

- Mechanism: the server submits via the device IPP service (`IIppProxy.PrintURI` / `PrintJob`), with HP IPP extensions: `priority-print-auth-cookie` = the current `UIContextId` reserves the printer for the walk-up user and lets priority jobs through; the device leaves priority mode at UI inactivity timeout; `print-uri-cookie` and `print-uri-username/password` let the device fetch the document URI with credentials; HTTPS document URIs are validated against the OXPd CA store (`OXPd1-NET-Java/Knowledge-Base/General--115009511148-IPP-Extensions-for-OXPd-Fleet-Specification.md:96, :189-195, :214-216, :275-301`).
- IPP queue depth is set by firmware, "up to five jobs" and varies by device; partners saw `IPP_PRINTER_BUSY` on the second job on an M577; the solution must queue on its server and poll job state (HP 2024-06/07, SF 30719996101779 :158, :176, :192; HP 2021-03, SF 1500000475661 :80-82, :108). "The HP firmware only supports receiving one print job at a time" in the walk-up flow; submit jobs individually, keep the session alive with `resetUIInactivityTimer` (only works while the solution page is shown, not on the native home screen) (HP 2024-09/10, SF 33239992368531 :50, :151, :171, :210).
- No API to list pending jobs (SF 30719996101779 :108). IPP `job-id` is an integer and reused; `job-uuid` comes from `GetJobAttributes` (2020, SF 360043970913 :204). Jobs > ~500 pages via PrintURI failed with `document-access-error` (2024, SF 32182709446675 :68). `PrintJob(byte[])` loads the whole document into server memory (2025, SF 41589099186067 :36). Page ranges via IPP are possible; Workpath's API has none (HP 2019-12, SF 360037760373 :41-43). A finishing value reported in `finishings-supported` can still come back `IPP_OK_SUBST`/unsupported depending on the installed finisher (2026-04, SF 51103054889235 :21-30, :72).
- Users can cancel other users' jobs unless permissions ("Job Log and Active Jobs" etc.) are managed through the Authorization agent (2021, SF 4408298050451 :28, :152).
- For Universal-Print-style secure release on OXPd 1.x the only device-side primitives are this IPP path plus the Statistics service (inferred from the above; see 4.6).

### 4.6 Scan destinations and statistics (OXPd 1.x)

- Scan destinations are HTTP(S), CIFS `file:////…`, local file and FTP; there is **no e-mail destination** — HP 2024-07: "this is a limitation from OXPd side" (SF 30723479464083 :30-90, :165, :222). A Mailflow-type app must therefore receive the scan over HTTP(S) and send the mail from the server (inferred).
- HTTP uploads > ~2 GB fail at IIS (`maxRequestLength` caps at 2,097,151 KB) (HP-official 2026-06, SF 51934837047187 :144-166); IIS must allow large payloads (`OXPd1-NET-Java/Knowledge-Base/General--115009224267-OXP-Device-SDK-User-Guide.md:896`). SMB destinations leave a processing overlay unless the `ProgressDialog` option is used (same thread :92, :162). ScanService unavailable right after wake (FS 4.3-4.5.5, SF 360002630948 :14, :102). Scan with TLS 1.3 to HTTPS failed until FS 5.8 (4.3). ID-card scanning exists in ScanTicket3 (`captureMode=IDCapturePromptBothSides` requires duplex) but validation errors are generic (2025, SF 38413778664979 :184-229). `AuthenticatedUserInfo.userDomain` was not passed to Scan to Network Folder on FS4 until a fix (HP-official 2018-09-28, SF 360000911307 :139); the KB "Send to Network Folder" article lists the attributes an OXPd agent must set, including a custom `homeDirectory` key (`OXPd1-NET-Java/Knowledge-Base/Authentication--115011791508-Configuring-Authentication-Agents-for-Send-to-Network-Folder.md:91-135`).
- Statistics: a Statistics agent registered as **critical** must acknowledge every `EndJobNotification`; one unacknowledged notification eventually locks the device with **48.A1.01** ("no further jobs … from any source") — HP 2021 (SF 1500000013202 :37, :539, :593). The device caches up to 256 unacknowledged notifications and resends after reboot (:843, :452). A 2021 field case (100+ printers, FS 4.10-4.11) where devices silently stopped sending notifications ended with HP blaming network instability and the partner declining HP's suggested ordinal-based recovery (:683, :1074-1096). The EWS "Job Statistics Service" shows Connected only for a critical agent with `ackRequiredForDelete=true` (HP-official 2026-07-20, SF 53113677705235 :89, :140). Security-context key/value attributes appear in statistics data (SF 360052309533 :77-97). `serverContextId` is the hook to correlate jobs with sessions (SF 360000826207 :108).

### 4.7 Registration, fleet deployment, network and server

- **Deployment model** (HP staff 2026-03-04): OXPd 1.x solutions "sit on a server and register with the devices by using each service's registration method"; for OXPd 1.8 and "the soon to be released OXPd 1.9, no HP approval is required"; OXPd 2 "will require a validation and verification step and HP signing" (SF 49615404208147 :26, :30). OXPd .NET/Java uses no solution bundles (HP-official 2019-08-13, SF 360033652994). (Note: no OXPd 1.9 SDK is in this library; 1.8.4.1 is the newest — C1 lane.)
- **Network**: all OXPd .NET/Java services listen on device port 7627, not configurable; NAT port remapping not supported; "not a cloud-based SDK and is expected to be run from a server in the customer's environment" (HP 2018-06-14, SF 360002980048 :33). Device inbound 80/443/7627; outbound to the solution from ephemeral ports (SF 41867286054035 :57-61). A non-secure web-services port 57627 exists (SF 23170253306515, title). Discovery is HTTPS on 443 (4.3). Registration needs the device IP reachable from the server (HP 2017-11-27, SF 115009575008 :22). Cloud server calling back into devices: HP recommends Workpath instead (SF 4620109272339 :142).
- **Admin credentials**: proxies are created with the device admin password; after a factory reset the admin password must be set again before registering (HP 2018, SF 360003485328 :34-36); "HTTP request was forbidden with client authentication scheme 'Basic'" = no admin password set (HP 2019, SF 360031579474 :417). FS4 adds account lockout (default 5 attempts, 10 s) and password complexity on the EWS/remote admin passwords, which a registration tool hammering bad passwords will trip (`OXPd1-NET-Java/Knowledge-Base/General--115005970107-FutureSmart-4-Security-Features.md:34-64`).
- **Fleet tooling**: Web Jetadmin can install "OXPd configuration" packages from repositories (Tools > Options > Device Management > Configuration) and create panel icons, but cannot call OXPd APIs itself (HP-official 2019-03-12, SF 360028592914 :42, :61-71). OXPm 1.7 / Button Manager tools are in the library (C1 lane). The M406 had no EWS OXPd configuration upload page (2025, SF 45188318198675 :8-10, unanswered). WJA picked wrong button images on some models (titles SF 44271651371795, 360049361113, 10750119635091 — not read). FS 5.9.0.2 duplicated OXPd buttons after upgrade; fixed FS 5.9.2.3 (SF 45779311787411 :10, :99).
- **Capability detection**: devices have no "OXPd SDK version"; use the DiscoveryTree and each service's revision/minor revision; HP recommends against model lists (HP-official 2019-08-22, SF 360031579474 :96-100, :460; SF 360034838013 :85). UIConfiguration 1.3 does not guarantee other 1.8 services (:409). Callback binding Soap12 = Enterprise, Plain (REST) = Pro (KB Best Practices :77-81; HP 2022-05, SF 5761278787731 :145). "All devices that support OXPD 1.0 are also compatible with OXPD 1.8.4" (HP 2024-09, SF 33700366559891 :26).
- **Boot and readiness**: the only boot-time event is the owned-accessory notification; OXPd2 is to add boot events (HP-official 2025-02-04, SF 37428987693075 :72-78). See 4.1 for 1-2 minute readiness after boot.
- **Resilience to IP change** (FS "25.8" = 5.8): put the `$DEVICE_IP_ADDRESS$` macro in every callback's `serverContextId`; the firmware substitutes the current IP (`OXPd1-NET-Java/Knowledge-Base/General--28823565805331-Resiliency-when-device-s-IP-address-changes-but-DNS-does-not-reflect-i.md:8-63`). KB Best Practices: one server serves many devices; correlate every UI request (IPQFS on first POST, then session) and every web-service callback (`serverContextId`, max 256 chars) to a per-device environment; persist accessory context ids; cache DiscoveryTree and proxies until firmware changes; retry transient network errors (KB Best Practices :124-174, :202-414).
- **Scaling and failover**: no dual/failover server per agent (alternative sign-in only) (SF 360036415893 :43); NLB "not something we support" (HP 2024-01, SF 24843001539475 :19); a 1-core VM starved devices (SF 26673063881235). Low-cost failover was a 2017 roadmap promise for OXPd 1.9 that never shipped (4.8).
- **Server stack**: OXPd 1.8.3 added .NET 6 and .NET Framework 4.8; WCF/SOAP unchanged (HP 2023-06, SF 17859541410195 :30-32, :73-77). 1.8.4 Java uses Jakarta namespaces; examples need namespace edits (KB `Issues--33938497568275` :8-28; SF 31382161387411 :151). .NET 8 + 1.8.4 proxies failed TLS validation where the certificate lacked a proper SAN; HP points to CoreWCF and a CA-issued certificate (2025, SF 37773710045075 :114-136). No lifecycle policy for OXPd libraries (HP 2019-03, SF 360028606394 :22). Linux server: HP-official 2019-03-14 — the OXPd .NET libraries "would generally require" Windows IIS; for Linux use the Java libraries (SF 360026575153 :158; referenced from SF 360029629873 :24) — dated, before the 1.8.3 .NET 6 build. SDK 1.8.4.0 (2024-05-03) moved to OpenJDK 21 / JAX-WS 4.0.1 and .NET Framework 4.8 / .NET 8 and split the simulator out; 1.8.4.1 (2025-06-30) only adds IPP duplex options; both state FutureSmart 4.7 is the first fleet release with the full 1.8 feature set (`General/Release-Notes/release-note-228356.md`, `General/Release-Notes/release-note-287186.md`).

### 4.9 What "OXPd JavaScript" is, and whether the project needs it

- **What it is**: "OXPdJS is a set of JavaScript libraries" that a web app loads into the **device's embedded browser**; the page itself is served from the partner's web server and registered as a top-level button; the JavaScript then calls the device's own OXPd web services directly from the panel browser using CORS (`OXPd-JavaScript/Knowledge-Base/General--226812527-System-and-Device-Requirements.md:8-30`; `OXPd-JavaScript/Knowledge-Base/General--226812287-SDK-Architecture.md:10-14`, where it is called "OXPd Express"). Only dependency jQuery ≥ 1.11.0; FutureSmart 3.7 or later; CORS must be enabled per device (EWS Security > Web Services Security, or WJA) (`…System-and-Device-Requirements.md:8, :16, :24-28`).
- **Scope**: SDK 2.6.0 (2023-05-15, adds ScanTicket3; `General/Release-Notes/release-note-155021.md`) ships four libraries only: `oxpddeviceinfo`, `oxpddiscovery`, `oxpdprint`, `oxpdscan` (`OXPd-JavaScript/SDK/oxpd-javascript-2.6.0/lib/`; API index `…/doc/index.html`: print = PrintUri, PriorityPrintEnter/Exit/Uri, GetJobAttributes, CancelJob; scan = StartScanJob/StartScanJob3, profiles, validation). **No authentication, authorization, accessories (card reader), UI configuration, statistics or quota** — those exist only in the server-side .NET/Java SDK. The `uiContextId` arrives once in the `OXPd.UIContextId` header of the first request and the server must inject it into the page (`…SDK-Architecture.md:322-347`).
- **Relation to OXPd 1.x and OXPd2**: it is a client-side wrapper over the same OXPd 1.x device services (Discovery Tree, IPP, Scan) on FutureSmart devices (inferred from the API set and the shared DiscoveryTree). The "OXPd Demos 1.4" filed under `OXPd-JavaScript/Demos/` are in fact .NET server demos built on `OXPdLib-1.8.0.dll` (AuthnAuthz, CopyKiosk, PullPrint, Quota, Statistics, ScanPreview…) (`OXPd-JavaScript/Demos/hp-ext-oxpd-demos1.4/Manifest.txt`; grep of `*.csproj`). Nothing in this lane's material ties OXPdJS to OXPd2 (the OXPd2 SDK has its own JS client library — B lanes).
- **Status**: legacy but still downloadable (portal lists SDK 2.6.0, 2023-05-15; `General/Portal-Pages/developer-packages.md:56`); the KB articles date from 2016-2024; JS-side runtime limits are the same browser limits as 4.4 plus a 10-second JavaScript execution cap and a RAM cache cleared only at power cycle (`…SDK-Architecture.md:96-100, :233-235`).
- **Does the project need it?** Not as a dependency. The suite needs authentication agents, card-reader accessories and statistics, which OXPdJS lacks, and CORS-enabled panel-to-device calls add a per-device setting and a cross-origin surface (inferred). Its one useful idea — the panel page itself calling `oxpdprint`/`oxpdscan` so print/scan do not need the server to reach the device — was cited by HP for an isolated-network case (SF 4408198636947 :18, :53) and could be kept as an option for sites where the server cannot reach devices on 7627 (inferred; would still need the server-side agents).

## 5. What this means for the port

### 5.1 Requirements and design rules that follow from the field record (OXPd 1.x side)
1. **Run the OXPd 1.x server inside the customer network, close to the devices.** Port 7627 is fixed, NAT remapping is unsupported, the server must reach every device IP, and HP says cloud workflows belong on Workpath (4.7; SF 360002980048, SF 4620109272339). Kam's "localised server" matches HP's model; an Azure-hosted OXPd 1.x server would need a site connector/VPN per site (inferred).
2. **One agent per device, owned by one server.** No failover, no NLB support; size the server (not 1 vCPU); plan HA as fast restore with persisted per-device state (accessory context ids, auth context ids, registrations) (4.7; KB Best Practices :402-414).
3. **Card login state machine must be defensive**: keep the `AuthenticationContextId` until a confirmed sign-out; always `ReleaseAuthenticationContext` before a new `Reserve…`; retry on Concurrency/"not waking within 8000 ms"; tolerate double `GetPostPromptResult`/`GetPrePromptResult`; never rely on `SignOutNotification` ordering or delivery (4.1). This replaces HPAM's on-device card listener (inferred).
4. **Card reader input must be assembled server-side** from ordinal-numbered 8-byte keyboard reports with a ~1 s window, start/stop characters per reader, re-binding on every `OwnedAccessoryEvent`, re-registration as recovery, and per-reader configuration (e.g. X3D03A card-type settings) (4.2). HPAM's current readers (Elatec TWN4, RFIDeas, HP 35H11B per `START-HERE.md:56`) are all keyboard-wedge HID, so they fit; **BLE badge flows have no OXPd 1.x path in this material** (4.10) — they would have to stay app/QR-based (inferred).
5. **Entra sign-in cannot reasonably run inside the OXPd 1.x panel browser.** Microsoft's login page in that browser hit 45.00.33 (CA trust) and 45.00.CB / 49.DE.11 (memory, JS) in 2019 (4.4); the 3 MB budget applies to the whole solution including third-party pages. Design: QR/device-code or card → server-side token handling, with the panel showing a lightweight server page (inferred from 4.4).
6. **Panel UI budget**: ≤ 2-3 MB per solution, explicit teardown on `pagehide`/`unload`, small DOM (≤ 10-15 list items on 4.3-inch panels), sprites instead of many images, no SVG, no pop-ups, no file input, 10 s JS cap; cookies are unreliable on FS5 → carry state in the URL/POST (`UIContextId`, IPQFS) not cookies (4.4, 4.9).
7. **Token hand-off to apps**: on OXPd 1.x the only supported channel from the auth agent to the app pages is IPQFS POST data (and `OpaqueToken`/KeyValuePairs), not cookies (4.1). The shared token store (today Entra CSAs + on-device sharing) must move server-side and be keyed by device + `UIContextId`/auth context (inferred).
8. **Mailflow cannot use an OXPd e-mail destination** (none exists); scan to the server over HTTPS and send via Graph from the server; mind the ~2 GB IIS limit and TLS 1.3 scan failures before FS 5.8 (4.6).
9. **Universal Print release on OXPd 1.x** = server fetches the job (Graph) and pushes it via IPP `Print-URI`/`Print-Job` with the walk-up `UIContextId` as `priority-print-auth-cookie`; queue ≤ 5 jobs (often 1); poll job state; keep the session alive only while the solution page is shown (4.5). The 2026 forum report of Graph-registered Universal Print jobs not printing on M406/M507 (4.10) is a warning for the "_Direct" variant.
10. **Statistics/logging**: if a Statistics agent is used for audit (HPAM logs jobs to Log Analytics today, `START-HERE.md:55`), registering it as critical risks 48.A1.01 device lock on any missed acknowledgement; prefer non-critical unless audit completeness is contractual (4.6).
11. **Certificates**: ship a CA-based PKI per customer (server cert with FQDN and IP in SAN, full chain uploaded to every device's OXPd CA store), never the SDK examples' "accept all certificates" override; plan for devices regenerating their own certificates after partial clean/firmware events; validate TLS 1.2 vs 1.3 per firmware and `Expect: 100-continue` off in .NET (4.3).
12. **Deployment tooling**: registration needs the device admin password and reachable IP; WJA can push OXPd configuration packages but cannot call OXPd APIs; a Datasec deployment utility must register agents/buttons per device, record what it registered, keep the "Enable HP home screen if OXPd app fails to load" fallback ON (EWS only), and set the `$DEVICE_IP_ADDRESS$` macro in callback `serverContextId` (4.7, 4.1).
13. **Capability detection, not model lists**: decide OXPd 1.x vs OXPd2 vs Workpath per device from discovery (DiscoveryTree/service revisions for 1.x; FS6 for OXPd2) and keep a firmware-defect table (4.7, 4.8).

## 6. Contradictions and doubts
- **OXPd 1.9**: promised in 2017 decks (Email, Fax, REST, failover; `…Technical Roadmap S.Banning.pdf` p4) and called "soon to be released" by HP in 2026-03 (SF 49615404208147 :30); the library's newest SDK is 1.8.4.1 (2025-06-30). Treat 1.9 as not existing.
- **WebSockets**: HP-official 2018-10-03 says the browser supports WebSockets (SF 360016736974 :89); labs later said the reported WSS use was "not currently supported functionality" (SF 360018016773 :185). Unverified on FS5; assume no WebSocket/SignalR on the panel.
- **HTML5**: OXPd JavaScript KB says the browser does **not** support HTML5 (`…SDK-Architecture.md:72`), the KB Browser Use Model says HTML5 on Omni (`…UI-Configuration--115009332187-…:533`), HP-official 2024 says "some" HTML5 (SF 28314939713939). The JS article describes the pre-Omni (FS3) browser — stale.
- **Pre-installed CAs**: OXPdJS KB says devices ship with popular CAs so you may not need to install one (`…System-and-Device-Requirements.md:50`); HP support said 2019 there is no way to know which CAs are trusted (SF 360028756693 :195) and partners in 2025 insist the full chain must be uploaded. Assume upload always.
- **Inactivity reset from the server**: HP 2020 says server-side `ResetUIInactivityTimer` exists from 1.8.1 (SF 360038531173 :86) and "either the browser or server method should work" (SF 33239992368531 :151), but a partner calling the Java proxy saw no effect (:142), and HP 2026 says resetting does not "extend or bypass" the timeout (SF 50168695633939 :126).
- **SignOutNotification on inactivity**: partner says never delivered on all models (2025); HP could not reproduce in 85 tries (SF 43070912507539 :153); a related FS 5.7.1.1 defect was fixed for "25.9" (SF 30255164600851 :113). Status on FS 5.8/5.9 unproven.
- **TLS guidance**: HP 2021-11 says latest firmware enables only TLS 1.2 by default (SF 4408601099667 :248) while FS 5.5 (2022) enabled TLS 1.3 support; HP 2023 suggests capping at TLS 1.2 (SF 12060994970003 :125).
- **"All devices that support OXPd 1.0 are compatible with 1.8.4"** (SF 33700366559891 :26) conflicts with "full 1.8 feature set from FS 4.7" (release notes) and with service-revision checks (SF 360031579474 :409): the library loads on old devices, the features do not.
- **Forum dates of HP statements** range 2017-2026; e.g. Linux guidance (Windows IIS for .NET) predates .NET 6/8 support. Every rule in section 4 carries its date for this reason.
- **Coverage doubt**: my selection favoured authentication, card readers, TLS, browser, print/scan/statistics and registration; copy, fax, quota, accessibility (screen reader) and SNMP threads were deliberately not read (see Coverage).
