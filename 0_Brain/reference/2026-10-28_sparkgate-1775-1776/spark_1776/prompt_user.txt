===== TICKET =====
KS-1591 — Security (nit, pre-existing): isPlatformRole's toUpperCase admits a dotless-i, a long-s and an ARRAY role as SUPER_ADMIN [In Progress]

## BLUF

`String(role).toUpperCase()` **is not an identity test.** `packages/shared/src/security/keyRevokePolicy.ts:139-140` (`isPlatformRole`) and `requireKeyAdmin`'s own `toUpperCase` admit three spellings as `SUPER_ADMIN`:

* `super_admın` — **dotless i** (U+0131), which upper-cases to `I`;
* `ſuper_admin` — **long s** (U+017F), which upper-cases to `S`;
* a role **array** `["SUPER_ADMIN"]`, because `String(["SUPER_ADMIN"])` is `"SUPER_ADMIN"`.

**Measured by the pull request 1539 gate** (verdict sha256/16 `91e8da4021c40661`, finding **n4**): `PUT /api/keys/admin-scopes/:userId` answered **200** and the mint answered **201** for all three.

## Reachability is NOT established, and that is the first thing to settle

This needs a token the auth service **signs** with such a role. **The gate did not test whether any issuer, user-management path or seed can store or sign one**, and nor have I. So the severity here is a nit until someone measures that; if any path can, it is a privilege escalation and should be re-rated immediately.

## Recommendation

Not built. Compare against an exact ASCII-folded string and **reject a non-string role** outright, in the one shared definition so every caller inherits it.

## Where

* `packages/shared/src/security/keyRevokePolicy.ts:139-140` — `isPlatformRole`.
* `services/security/src/index.ts` — `requireKeyAdmin`'s `toUpperCase`.
* Worth a sweep for other `toUpperCase()` role comparisons rather than fixing only these two.

## Dedupe

Linear's `searchIssues` is **fuzzy** — it returned 12 hits for a deliberately nonsensical control term, so it is not a membership test. Deduped with a literal `containsIgnoreCase` filter over title and description, controlled both ways (0 for the nonsense term, non-zero for a real one): `toUpperCase` **0 hits,** `dotless` **0,** `ASCII-folded` **0.** Related but NOT the same: KS-1536 (one role vocabulary, seven divergent lists) is about which role strings each list contains, not about the folding admitting lookalikes.

321:     if (predecessor) {
322:       const waitMs = rotateChainWaitMs();
323:       let timer: NodeJS.Timeout | undefined;
324:       const timedOut = await Promise.race([
325:         predecessor.then(() => false),
326:         new Promise<boolean>((resolve) => { timer = setTimeout(() => resolve(true), waitMs); }),
327:       ]);
328:       if (timer) clearTimeout(timer);
329:       if (timedOut) log('warn', 'KS-1556: a rotate waited the whole chain timeout for its predecessor and proceeds', { key, waitMs });
330:     }
331:     return await fn();
332:   } finally {
333:     release();
334:     if (rotateChains.get(key) === mine) rotateChains.delete(key);
335:   }
336: }

338: /**
339:  * KS-1549. A rotate's INSERT and its retire, as ONE transaction on ONE pooled client, serialised per
340:  * connector. Returns how many prior keys were retired, or null if the retire FAILED (KS-577's contract:
341:  * the new key still stands and the failure is reported). Throws if the key itself could not be saved,
342:  * which the caller answers 503/500 with no key (KS-888's contract).
343:  *
344:  * Before this, the INSERT and the retire were two autocommit statements, each on its own pooled
345:  * connection, with an await between them. Two interleaved rotates each retired the OTHER's new key, so
346:  * the connector was left with ZERO active keys and both callers held dead ones: 0 active in 9 of 10
347:  * double-submits on real Postgres (the #1521 gate). Ruled (decision D): the last rotate wins, exactly as
348:  * two sequential rotates behave.
349:  *
350:  * Every step here is load-bearing:
351:  *  - the per-connector in-process chain above, so that this process applies its in-memory changes in
352:  *    commit order, and waits without holding a pooled client;
353:  *  - READ COMMITTED, pinned on the transaction itself (KS-1556 m2). Under REPEATABLE READ the snapshot is
354:  *    taken before the lock is granted, so a rotate that waited cannot see the key the previous one
355:  *    committed, and its retire fails to serialise: more than one active key. It must be the FIRST
356:  *    statement: once the transaction has run a query, Postgres refuses to CHANGE the level (setting
357:  *    the level it already has is a no-op). So a late pin passes silently under a READ COMMITTED
358:  *    default and fails every rotate under a REPEATABLE READ one;
359:  *  - the tenant GUC on THIS client: svc_api_keys is FORCE row-level security and fail-closed, so a
360:  *    transaction without it inserts nothing and retires nothing, silently;
361:  *  - a TRANSACTION-scoped advisory lock on (tenant, connector): pgbouncer runs pool_mode = transaction,
362:  *    where a session lock would leak to the next client. It serialises rotates of one connector across
363:  *    processes;
364:  *  - the INSERT on the SAME client as the lock. KS-757 measured the trap: an INSERT on a second pooled
365:  *    connection, made while holding the lock, deadlocks the pool once the waiters fill it;
366:  *  - the retire under a SAVEPOINT, so a failed retire rolls back alone and the mint stands;
367:  *  - the in-memory changes ONLY AFTER COMMIT, and never undone (KS-1556). The design this replaces
368:  *    (#1527) changed memory before COMMIT and undid it on failure. Restoring the captured object let a
369:  *    concurrent validate leave the prior key refused while the database held it active (m1, the #1527
370:  *    gate's A8). Restoring by id instead RESURRECTED a revoke whose own save had failed (KS-888 R2),
371:  *    measured by its author on #1529. After COMMIT there is nothing to undo, and before it, memory and the
372:  *    database agree. A crash between COMMIT and this update leaves memory stale. Validate re-reads the
373:  *    stored row for a key in memory, and finds a key that is not in memory by its hash (KS-1370), so it
374:  *    still answers from the database.
375:  */
376: export async function saveKeyAndRetirePriors(k: ApiKey, connectorId: string): Promise<number | null> {
377:   if (!isDbAvailable()) {
378:     // In memory nothing awaits between the two steps, so there is no window to close.
379:     memApiKeys.set(k.id, k);
380:     return revokePriorConnectorKeys(connectorId, k.tenantId, k.id);
381:   }
382:   return withConnectorChain(`${k.tenantId}:${connectorId}`, async () => {
383:     const grace = rotationGraceSeconds();
384:     const retiredIds = await runWithTenantId(k.tenantId, () => transaction(async (client) => {
385:       await client.query('SET TRANSACTION ISOLATION LEVEL READ COMMITTED');
386:       await applyTenantGuc(client);
387:       await client.query('SELECT pg_advisory_xact_lock(hashtext($1), hashtext($2))', [k.tenantId, connectorId]);
388:       const ins = apiKeyInsertStatement(k);
389:       await client.query(ins.text, ins.values);
390: 
391:       const ret = retirePriorStatement(connectorId, k.tenantId, k.id, grace);
392:       await client.query('SAVEPOINT ks1549_retire');
393:       try {
394:         const ids = (await client.query<{ id: string }>(ret.text, ret.values)).rows.map((row) => row.id);
395:         await client.query('RELEASE SAVEPOINT ks1549_retire');
396:         return ids;
397:       } catch (err) {
398:         await client.query('ROLLBACK TO SAVEPOINT ks1549_retire');
399:         log('error', 'KS-577: revoke-on-rotate FAILED — the prior credential is still valid', {
400:           connectorId, tenantId: k.tenantId, keepKeyId: k.id, error: err instanceof Error ? err.message : String(err),
401:         });
402:         return null;
403:       }
404:     }));
405: 
406:     // COMMITTED. Only now does memory change, so nothing is ever undone, and the new key is in memory
407:     // before the 201 leaves.
408:     memApiKeys.set(k.id, k);
409:     for (const id of retiredIds ?? []) {
410:       const current = memApiKeys.get(id);
411:       if (current) retireInMemory(current, grace);
412:     }
413:     return retiredIds === null ? null : retiredIds.length;
414:   });
415: }

441: async function dbSaveApiKey(k: ApiKey, opts: { rethrow?: boolean } = {}): Promise<void> {
442:   memApiKeys.set(k.id, k);
443:   if (!isDbAvailable()) return;
444:   try {
445:     // KS-33: write tenant_id (the load-bearing scoping field) on every
446:     // INSERT. organization_id is now NULL-able. ON CONFLICT updates
447:     // the volatile usage fields, but tenant_id is immutable per key —
448:     // a key minted for tenant A never moves to tenant B.
449:     // KS-869: connector_id is written too. The column has existed since
450:     // migration 018 and NOTHING wrote it or read it, so a key's connectorId
451:     // lived only in memApiKeys and died with the process. That made the
452:     // KS-843 grace log record `connectorId: null` for every Platform S key
453:     // after a restart, collapsed every connector's userId to
454:     // `connector:api-key`, and left revoke-on-rotate (KS-577) with no durable
455:     // way to find a connector's prior keys.
456:     // KS-458: pin the RLS GUC to the key's own tenant — callers include the
457:     // pre-session validate route (no request ALS at all) and admin flows
458:     // whose request tenant may differ from the key's; fail-closed
459:     // svc_api_keys requires the GUC to match the row being written.
460:     const st = apiKeyInsertStatement(k);
461:     await runWithTenantId(k.tenantId, () => query(st.text, st.values));
462:   } catch (err: any) {
463:     logger.error('DB save API key failed', { error: err?.message });
464:     // KS-888: re-throws only for a caller that opts in, and each caller that opts in catches it in its own try.
465:     // Any other caller keeps this log-only swallow: a throw into a handler that takes no next is an unhandled
466:     // rejection, and that ends the process.
467:     if (opts.rethrow) throw err;
468:   }

471: // KS-1370 half (i): validate's usage write must NOT carry is_active.
472: // The shared dbSaveApiKey upsert above sets `is_active = EXCLUDED.is_active`, and it is the ONE
473: // statement every caller uses — mint, revoke and validate's usage bump. That is what let a stale
474: // in-memory copy REVIVE a persisted revoke: validate resolved the key from memApiKeys (a boot-time
475: // snapshot), saw isActive=true there, and its usage write then wrote that true back over the
476: // revoked row. Measured on real PostgreSQL before this change: usage_count 1 -> 2 and
477: // is_active false -> TRUE.
478: //
479: // Deleting `is_active = EXCLUDED.is_active` from the shared upsert is NOT the fix: the revoke route
480: // persists its revoke THROUGH that same upsert (`apiKey.isActive = false` then
481: // `dbSaveApiKey(apiKey, { rethrow: true })`), so removing it would stop a revoke of an existing row

544: export async function loadFromDb(): Promise<void> {
545:   if (!isDbAvailable()) return;
546:   // KS-458: boot-time cache warm is deliberately cross-tenant — there is no
547:   // request context, and the in-memory caches must hold EVERY tenant's rows
548:   // (the API surface re-filters per caller). Under fail-closed RLS the full

558:       memAuditLogs.reverse();

560:       const eventsResult = await query(
561:         'SELECT * FROM svc_security_events ORDER BY created_at DESC LIMIT 10000'
562:       );
563:       memSecurityEvents.length = 0;
564:       for (const row of eventsResult.rows) memSecurityEvents.push(rowToSecurityEvent(row));
565:       memSecurityEvents.reverse();
566: 
567:       const keysResult = await query('SELECT * FROM svc_api_keys');
568:       memApiKeys.clear();
569:       for (const row of keysResult.rows) {
570:         const key = rowToApiKey(row);
571:         memApiKeys.set(key.id, key);

574:       logger.info('Loaded persisted data from DB', {
575:         auditLogs: memAuditLogs.length,

578:       });
579:     } catch (err: any) {
