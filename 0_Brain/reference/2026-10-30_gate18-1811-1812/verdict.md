## Gateway-validation answer for #1811 (the deciding question): the feature is reachable

Path read at the head `d7d3a6e3` for `POST /api/anchors`:

1. **api-gateway/src/index.ts:402** `express.json({limit:'1mb'})` runs for this path because `/api/anchors` is NOT in `proxyPaths` (L383-396 lists `/api/anchoring`, which does not prefix-match `/api/anchors`). It parses only; no schema.
2. **index.ts:441** `rejectNulBytes()`; **L447-448** `sanitizeInput` (HTML-entity-escapes strings; `middleware/security.ts:76-93`) and `detectSuspiciousRequests` (400 only on `../`, `<script`, `union select`, `exec(`; `config/services.ts:70-75`). A 64-hex value trips neither.
3. **index.ts:1054-1089** the spec-aware gate (`specRouteMap.ts`) checks **method and bearer presence only** (405 / 401). It never reads the body or the request schema.
4. **routes/proxy.ts:898-902** `router.post('/api/anchors', authenticateToken(true), attachScopes, requireScope('anchors:write'), proxy('anchoring', ...))` - auth and scope, nothing about the body. **proxy.ts:80-82 `proxyBodyToWrite`** re-serialises the parsed body whole: `JSON.stringify(parsedBody)`.
5. `api-gateway/package.json` declares no validator (`ajv`/`express-openapi-validator` are absent; `batch.ts:46` says "api-gateway does not depend on zod"). `ajv` exists in the root `node_modules` only as someone else's transitive dependency.
6. **anchoring/src/index.ts:256-264** `express.json`, `rejectNulBytes`, emitter-signature guard (strips its own headers), then **L469** `jwtAuthenticate()`; **L475-477** `anchorDocumentSchema.parse(req.body)`.
7. **anchoring/src/anchorSchema.ts** `anchorDocumentSchema = z.object({...})` and its `metadata: z.object({...})` carry **no `.strict()` or `.passthrough()`**: zod's default strips unknown keys (the file's own comment at the `metadata` block and the `onBehalfOf` comment say so; `grep strict()` over anchoring/src non-test code: none).

Measured, not only read (scratch cells kept in `evidence/scratch_tests/`, run in my own worktree, removed from it afterwards):
- **Real gateway app** (ks1195 recipe, loopback stub as anchoring, API key with `anchors:write`): `POST /api/anchors` with `{documentId, contentHash, zzTopUndeclared, onBehalfOf, metadata:{documentType:'sign', signatureHash:<64 hex>, zzMetaUndeclared}}` -> **202**, the stub received exactly one request whose body `toEqual` the sent body (hash and both undeclared keys intact). `evidence/measure_gateway.logs`.

Control M3: `documentType:'upload'` + hash -> **400** `metadata.signatureHash is only accepted with metadata.documentType "sign"`. `evidence/measure_anchoring.logs`, 3/3 pass.
- Not composed in one process (gateway stubbed to a recorder; anchoring driven directly). The two measurements meet at the proxied body, which the gateway cell proves unchanged.

Conclusion: a caller (Platform S) can send `metadata.signatureHash` today through the gateway; the spec omission is documentation debt (KS-1826), not a functional block. **No fix-before-merge finding.**
