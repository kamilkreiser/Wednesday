## Plain answer for Kam
Today, if the credential database hiccups while someone checks a credential, the service answers from an in-memory copy that can be out of date, so a credential revoked elsewhere can come back as valid. After this merge, a check that cannot read the database says "not verified" instead, on both verify endpoints, and nothing more permissive happens anywhere I measured (0 of 30 cases). The price is the one the PR states: during such a hiccup every credential checked on that server, good ones included, reads "not verified", and the message says the store could not be read rather than giving the revocation reason. No database error text reaches the caller. A separate older hole stays open and is already ticketed (KS-1959): if saving a revoke fails, the user is told it worked and the credential still verifies.
