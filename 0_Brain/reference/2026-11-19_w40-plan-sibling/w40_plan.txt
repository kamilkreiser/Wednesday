OPTIONS
(i) A claim token is mailed when the stub is made and required on register.
  - Invitee: gets a mail at issue time with a link that carries the token. Register with the token claims, and can set emailVerified true.
  - Someone else first: refused without the token; the stub stays INVITED and the invitee claims normally later.
  - Issuer and connector flows: POST /api/users/stub gains a side effect, a mail to the recipient for every new stub, including Platform S's certify and transfer-custody calls. Idempotent resolves must not re-mail. S may already tell its users through its own channel (not read).
  - Cost: a token store (migration), a new register field and a client that passes it (no in-repo page reads a URL token; census d), a resend path for lost or expired tokens, and a backfill or fallback for the stubs that exist today without a token.
  - Cells: no token, wrong token, expired token: refused, row untouched. Right token: 201, ACTIVE, verified. Squatter then invitee: the squatter is refused, the invitee gets 201.
(ii) The claim leaves the row INVITED (or pending) until the verification link is followed; no session to an unverified claimant.
  - Invitee: register answers "check your email" with no session; the click activates.
  - Someone else first: the squatter never gets a session. BUT if the password is chosen at register, this is a pre-account hijack. The squatter registers first with their own password, the invitee receives a "verify your email" mail for a sign-up they did not make, clicks it, and so activates the account with the squatter's password. It is safe only if each register's password is bound to that one mailed token and held off the row until the click; even then, an invitee who clicks an older mail activates the squatter's attempt.
  - Issuer and connector flows: unchanged.
  - Widened to every account (no session until emailVerified): it closes the SIBLING as well. But every new user must verify before their first login, and on a deployment with no mail provider nobody could finish registering. That is a larger product decision.
(iii) Register never claims; the invitee gets a claim link instead.
  - Invitee: register on an INVITED address answers with no session and mails a single-use link. The link's page lets the invitee set their own password; the row turns ACTIVE with emailVerified true, and they log in.
  - Someone else first: the squatter's register changes nothing on the row and only mails the real address. No password is chosen before the proof, so there is no pre-hijack. The invitee may get one unexpected mail.
  - Issuer and connector flows: unchanged; stub creation is not touched.
(iv) My shape: (iii) built on the reset flow that already exists.
  - Register on an INVITED address: no write to the row and no session. Store a reset-style token (the existing hashed store), send a claim mail to the stub's address (a NEW template in auth's email.ts, inside services/auth), and answer with no session (status code and wording are Kam's; see the sub-choice below).
  - reset-password on an INVITED row: set the hash AND flip status to ACTIVE with emailVerified true, because the token proves the mailbox. Nothing else in reset changes; ACTIVE rows behave as today.
  - Cost: two routes in auth, one template and their OpenAPI entries; no migration and no originate or gateway change. The mobile register-then-login (AuthContext.tsx:146) fails on the new answer and needs its own change, outside services/auth. The link lands on FRONTEND_URL/reset-password (or a claim path), which, like today's verify and reset links, is not a page in this repo.
  - Red-first cells (form body AND JSON for each register cell; gate 381 F1):
    - R1 no proof: register on an INVITED address gives the no-session answer: no access token and no refresh cookie, the row still INVITED with no hash, updateUserOrThrow never called, and exactly one claim mail, to the stub's address.
    - R2 wrong proof: reset-password with an unknown or expired token gives 404 or 400, and the row stays INVITED.
    - R3 right proof: reset-password with the mailed token on an INVITED row gives 200; the row is ACTIVE with emailVerified true and the hash set, and login with that password succeeds.
    - R4 invitee after a squatter: the squatter registers (R1 shape), then the invitee follows the link and sets their password, so the row is ACTIVE. Login with the squatter's password gives 401.
    - Controls: a fresh register still answers 201 with a session; an ACTIVE address still gets 409; reset-password on an ACTIVE row changes only the hash (status and emailVerified unchanged).
    - Rewritten by ruling, not weakened: auth.integration.test.ts:1583, ks1460 R1, R2, C1 and C3, and PR 2259's R3 and C2.
- Enumeration sub-choice (for Kam): today a register on an invited address answers 201, indistinguishable from a new address. (iii) and (iv) make "invited" visible unless the answer for INVITED matches the one for a registered address (409 "Email already registered", which already reveals existence), with the mail sent only for INVITED. So the choice is a 409 like a registered address (no new enumeration, but confusing to an invitee) or a 202 "check your email" (clear, but it reveals "invited").
- Mail flooding: anyone can make register mail an invited address again and again, as forgot-password already can today. Existing auth rate limits apply (not measured).

RECOMMENDATION: (iv).
- It sets no password before proof, so there is no pre-hijack (unlike (ii)).
- It leaves Platform S, issuer and connector flows untouched (unlike (i)).
- It reuses the hashed single-use token store, the route and the sender auth already has.
- It fits inside services/auth plus its tests, docs and spec.
It is a PRODUCT decision: what an invitee sees on register changes (no instant session, a mail to follow), the mobile auto-login breaks for that case, and the 202-or-409 wording is user-facing. Please put it to Kam as a card. The SIBLING needs its own ruling and its own seat.
