-Source of truth in code: [`packages/shared/src/security/scopes.ts`](../packages/shared/src/security/scopes.ts). Both the api-gateway's `requireScope` middleware and originate's `isAllowedByRoleOrScope` helper import from there so the vocabulary can't drift between services.
-Filed under [KS-71](https://linear.app/secuura/issue/KS-71). User-facing labels for the admin portal's API-key issuance UI come from this doc.
-Platform K has two authorisation paths:
-1. **Role-based (humans)** — a logged-in user has a `role` claim on their JWT (`ISSUER_ADMIN`, `ORG_ADMIN`, `VERIFIER`, `SYSTEM_ADMIN`, etc.). Every write route in originate has a role allow-list. JWT users skip scope checks at the gateway (they get an implicit `*`).
-2. **Scope-based (machine clients)** — an `sk_*` API key or OAuth client has `role: 'connector'` and an explicit `scopes: string[]` claim. The gateway validates each request against the route's required scope; downstream services additionally honour the same scope via `isAllowedByRoleOrScope`.
-Both paths can pass a single check — the helper returns `true` if **either** the role is allowed **or** the scope is present. Defence-in-depth is preserved: human callers still need the right role, scoped tokens still need the right scope.

-Two wildcard shapes are supported:
-**OAuth grants are the exception (KS-839).** KS-839 (2026-09-17): option E, "'*' grants no scopes". An OAuth app whose registered allow-list contains `*` (including an entry that only becomes `*` once split on spaces or commas) is granted nothing: a request naming scopes is refused 400 `invalid_scope`, and an omitted `scope` yields an empty grant. The wildcard satisfying scopes above applies to API keys, not to OAut
-Wildcards are **validated at API-key issuance time**, not at request time, to keep per-request scope checking fast. The admin portal's UI rejects unknown wildcards before storing them.
