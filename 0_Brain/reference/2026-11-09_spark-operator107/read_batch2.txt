##### KS-1338 entrypoint-corpus guard: a parenthesised return of a guarded call reads `guarded:false`, and the file's own rule-3 comment claims both return shapes are covered Backlog 2026-09-26T02:40:11.437Z
**BLUF: the guard reads** `guarded:false` **for call shapes the file's own comment says it covers.** Its rule-3 comment states *"Both return shapes are covered: a concise arrow body, and an explicit* `return`*"* — yet `return (() => g())` and `() => (() => g())`, when called, both read `guarded:false`, while the truth and `develop` both read **true**. `(() => g()).call(null)` reads false as well, and is not named anywhere.

This is the residue of a capped round. Nothing shipped for it; the pull request that attempted it stays open and its disposition sits with the repository owner.

## What is wrong, precisely

The defect is **parenthesisation**. A guarded call wrapped in parentheses — whether returned explicitly or as a concise arrow body — is not recognised, so a correctly-guarded call site is reported as unguarded. The reading is wrong in the **unsafe-looking** direction: it accuses safe code.

Three shapes, measured at runtime:

| shape | guard reads | truth / develop |
| -- | -- | -- |
| `return (() => g())` then called | `guarded:false` | true |
| `() => (() => g())` then called | `guarded:false` | true |
| `(() => g()).call(null)` | `guarded:false` | true |

The third came from a call-shape table the round was commissioned to make **"read as the truth or be NAMED"**. It does neither: it reads false and is unnamed.

**Evidence produced by the gate:** `evidence/1268/probe_readings_head.jsonl`, rows 23, 40 and 41.

## Why this is its own ticket

It is the same defect **class** as the round's first attempt, which is why the round capped. The fix is a reader change: recognise a parenthesised expression as transparent when deciding whether the inner call is guarded, and either read `.call`/`.apply` invocation forms as the truth or name them as unsupported. **A guard whose own comment claims coverage it does not have is worse than one with a stated limit**, because the comment is what the next reader trusts.

## Not in this ticket

The round's other work — the `entrypoint-corpus.test.ts` change at blob `8a4ce36a3a96` — is sound and is being re-raised separately by its author. This ticket is only the reader defect.
