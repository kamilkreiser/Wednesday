## Method
I wrote my own recorder (`scripts/gate172-recorder.test.ts`, 70 cells), separate from the builder's file. It drives the REAL `routes/auth.ts` register and reset-password handlers and the REAL `isPasswordBreached` over HTTP on 127.0.0.1. It uses a STATEFUL in-memory user and token store, so I can read the store after each request. `hashPassword` and the session, email, event and db modules are counting stand-ins.

Global fetch is a forwarder: 127.0.0.1 goes to the real fetch, `api.pwnedpasswords.com` goes to a stub that records URL, method, headers and body, and any other host is refused and counted (0 in every run).

Every run, including the suite and every mutant, went under my own outbound guard (`scripts/hibp_guard.mjs`, loaded with `NODE_OPTIONS=--import`). It blocks and counts the breach host at four layers: global fetch, dns.lookup / dns.promises, net.connect and tls.connect.

- **HOW:** recorder cells `Q3 <route> timeout`; `runs/mutants_raw.tsv` rows m11 and m12 (PR file 0 of 28 failed).

### G172-F3 — INFO: only the exact value `false` turns the check off
- **FOUND:**
  - With `HIBP_ENABLED` set to `FALSE`, `0`, `off`, the empty string or `true`, the lookup runs and a breached password is refused (both routes). This fails safe: the check is on.
  - The setup default applies only when the variable is UNSET. An exported empty `HIBP_ENABLED=` therefore stays empty, and the check is ON in tests.
  - Any test that does not stub fetch would then reach for the real service. In this gate the guard would block it; elsewhere nothing would.
- **TESTED:** 6 values × 2 routes. The setup file was imported with unset, `true`, `''` and `FALSE`.
- **HOW:** recorder `Q3-switch` and `Q3-setup` cells.

### G172-F4 — INFO: the logged "type" is the thrown value's constructor name, which is code, not data

## Plain answer for Kam
After this merge, someone signing up or resetting a password with a password that appears in a known public breach gets your sentence, "This password has appeared in a data breach, choose another", and has to pick another. Nothing is saved, and a reset link still works afterwards. Only the first 5 characters of a scrambled fingerprint of the password are sent to the breach service, never the password. If that service is down, slow (over 2 seconds) or answers with an error, the password is accepted, as you chose. Changing a password from inside the account, and accounts an admin creates, are not covered yet; that is the next piece. One small gap: the PR's own tests do not check the 2-second limit (I checked it separately and it works).
