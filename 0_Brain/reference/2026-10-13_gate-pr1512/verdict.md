### (b) Client-supplied data in the log line

- What is logged exactly: `{ error: <message or string or 'thrown <Type> with fields [..]' or 'thrown <typeof>'> }` under the fixed context; no request object, query or header is passed. The fixed context carries no client data (O2 shows adding the query is caught by L2-L4).
- Does client data reach `err.message`? Schema in `docker/init-platform/01-platform-schema.sql:209-218`: `content_hash VARCHAR(255)`, `document_id VARCHAR(255)`; both queries compare with `= $1`, so a malformed value is not a type-syntax error and Postgres does not echo it (the builder's 'invalid input syntax for type uuid' example needs a uuid column; the deployed schema could differ: unmeasured, no DB). Measured with a stub that DOES echo the caller's value into the Error (worst case): see below.
- Real winston logger, driven through the real route with a CR/LF/ESC payload in `?documentId=` that the stub echoes into `Error.message` (`probe_real_logger_crlf.txt`, logger Console transport's final formatted string captured):

Lines starting with the forged timestamp or the forged JSON: 0.
  - `NODE_ENV=development`: also one physical line per call; the meta goes through `JSON.stringify` (`\r\n` and `\u001b` escaped inside `{"error":"..."}`); forged-start lines: 0. (The `colorize()` ESC codes around `error` are the logger's own.) NUL was stripped from the URL for that run (Node's HTTP parser path); the `%00` request in cell F reached the handler and logged normally, content echoed: unmeasured.
  - So a newline cannot forge a line in either mode. No truncation anywhere: logged line lengths with echoed hashes of 8000 and 15000 characters: 8201 and 15201 bytes (dev 8166/15166).
