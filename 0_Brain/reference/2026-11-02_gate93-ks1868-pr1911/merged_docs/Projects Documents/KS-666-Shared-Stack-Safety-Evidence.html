Shared-Stack Safety Evidence

Four isolated stack slots, a destructive-rebuild guard, and per-slot test artifacts — verified by running, not by reading.

Commit 91df72c03 Branch feature/ks-666-… (1 ahead of develop, 0 behind) PR #729 — open, not merged Verified from an empty Docker Host Mac, arm64, Docker Desktop 6 CPU / 31.3 GiB Date 2026-08-20

Bottom line. Before this change, one Docker project, one set of ports, one database volume and one set of result paths were shared by every platform-k branch — so a routine --rebuild or --fresh-db on one branch silently destroyed another's stack and overwrote its results. That is now fixed: four slots, each with its own compose project, ports, volumes, network and <ticket>-slot<N> artifacts, behind a guard that refuses destructive operations against a stack it does not own.

5a. A LOCAL run must name its slot (KS-1016, 2026-09-11)

The isolation above only holds for a run that said which slot it wanted. An unset slot used to mean slot 1 silently — another ticket's stack on a shared machine — so every harness (Schemathesis, k6, Playwright, Akto and the shared provisioning step) now refuses to start against a local target when neither SECUURA_STACK_SLOT nor the platform-s alias STACK_SLOT is set, and prints the command to run:

No stack slot named. Every LOCAL system-test run must say which Docker stack it targets.
  SECUURA_STACK_SLOT=2 python3 scripts/run.py pr
  or: systemTest/run-in-slot.sh 2 python3 scripts/run.py pr

Local only. Remote targets carry no slot and are left alone; CI is exempt because its isolated per-suite stacks are local by construction and deliberately unslotted (CI=true). Measured on slot 2, 2026-09-11: no slot → exit 2, 0 docker calls, nothing provisioned; STACK_SLOT=2 → 1,759 requests, all to :6982, run validity OK.

Serial within a slot, parallel across slots

systemTest/run-in-slot.sh permits one suite at a time per slot, using an atomic mkdir lock released by a trap on EXIT/INT/TERM, with a 30-minute bounded wait. The cause is the per-IP login rate limiter: a second concurrent suite in the same slot trips it and poisons both runs. This applies to Schemathesis, Playwright, Akto and k6 alike — and after 429s appear, wait 15 minutes before retesting.

6. Defects this work surfaced

Found by running rather than reading. Five belong to one class — state or configuration pinned to slot 1 — and each was invisible until something ran on a slot other than 1.

In the platform tooling

  • stop-secuura.sh had no slot awareness — reproduced live: 35 containers survived a teardown that exited 0.
  • A COMPOSE_PROJECT_NAME leak into the Akto harness joined it to the platform project; a down --remove-orphans then deleted 33 containers.
  • Slot targeting had three root causes, not one. The dominant was runner/cli.py’s --base-url argparse default: argparse always supplies it, so the resolved config was overwritten every run. A slot-3 sweep sent 508 of 509 requests to slot 1 and still stamped its report -slot3.
  • Akto endpoint labelling had two sources — the HAR Host header and the OpenAPI servers[] entry, both hardcoded to slot 1.
  • .auth/ (Playwright) and .env (Schemathesis) were single shared paths holding bearer tokens; two slots overwrote each other’s credentials, so the loser authenticated against the wrong stack.
  • Akto’s preflight.ts and engineDiagnostics.ts hardcoded the container akto-testing; on slot 4 that container does not exist, and the failure was reported as “the Secuura target is not reachable” — blaming the platform for a name the harness got wrong.

In my own gates — two that could not fail

  • The container-name tests asserted a locally redefined helper instead of the real module, and passed with the bug restored.
  • The cross-slot count check filtered on project names matching secuura_slot[0-9]+, which excludes slot 1 — its project is the worktree basename. It compared one stack against itself: vacuously true, incapable of failing. Non-vacuity guards now make an empty or single-item corpus a failure.
  • A port collision I introduced: Akto Mongo Express based at 9090, head-on with observability Prometheus — re-opening a clash fixed on 2026-06-18. The crossover gate could not see it because only slotted platforms were modelled. Re-homed to 9490; observability is now in the registry.

In the orchestration — three that fabricated results

These produced output that read as genuine. On a project where the Mac is the evidence host, a GNU-only assumption does not fail loudly — it manufactures evidence.

  • timeout does not exist on macOS: eight gates reported FAIL without one of them running.
  • A background watchdog inherited stdout; inside $( ) command substitution waits for every writer, so each gate cost its full 600s — measured: echo hello under a 20s limit took 20s.
  • grep -E "^. (tests|pass)" against node’s 3-byte ℹ prefix: BSD grep matches . per byte, so a passing 45/45 suite printed blank.

All three are now checked by check-script-portability.sh (21 unit tests, mutation-proven), which also found two pre-existing defects nobody knew about — see §7.
