KS-1384 R2b: one resolver decides every anchor reader; confirmed is terminal; the retry route asks own-create first

What to know.Every reader of a document’s anchor state (the poller, the failure writer, the GET reconcile, both verifies) calls one resolver and writes through one conditional UPDATE. confirmed is never written over. A confirmed anchor row heals the document only when its transaction is bound to the document’s own create (its payload timestamp is a recorded create attempt). Anything else asks anchoring’s new POST /api/anchors/own-create, which scans the platform wallet for that create.
POST /api/documents/{id}/anchor asks own-create before it pays. If the create is on chain: 409 “already anchored on chain (<txHash>)”, and the document is confirmed. If another transaction carries the document’s id and hash: 409 for an operator. If own-create cannot answer: 503 Retry-After 60 with error.kind. Only “none” goes on to the POST. The whole route is bounded at 30 s.
A v2 verify, or an anonymous v1 verify, heals nothing now: it shows the stored state until the GET reconcile (an authenticated read after 15 minutes of silence) or the poller (at most 600 s after a POST) heals it. A bound bearer-less variant is KS 1918.
A pre-R2b fail-closed document has no create attempt to bind to, and waits for the operator path (KS 1907). An old document’s own-create scan can be truncated every time (KS 1908). The retry route no longer compares anchoring’s network with its own (QA gate 68, G68-F1): anchoring writes its own network into every row. Deploy hold: R2b deploys only with F0, F-b, R1 and R2a, after the census, box by box, and only where the deploy seat has read CARDANO_NETWORK of originate and of anchoring on that box and found them equal.
Not measured here.A real anchoring service and a real wallet scan, real chain state, the poller’s real heal latency, the four platform suites, a running stack, Node 24 (LTS), any chain or box.
