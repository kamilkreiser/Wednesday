The SQL-injection guard reads multi-line templates, filters by path only, and carries an allow list — KS-1867, KS-1865

What to know. scripts/check-no-sql-injection.sh now finds a $queryRawUnsafe / $executeRawUnsafe call whose first argument is a template literal holding ${, wherever the call, the template and the ${ sit (multi-line, with a generic, in .ts .tsx .js .jsx .mjs .cjs .mts .cts). Its path filter reads the file path only, by whole segment. A failed scan (unreadable file, missing root, grep or awk error) exits 2 instead of reading as clean. Sites that were traced safe, or are tracked as open, live in scripts/check-no-sql-injection.allow: four tab-separated fields (path, opener line, the ${...} expressions, reason); a reason starting OPEN: is counted apart as ALLOWED-OPEN. If the guard fails after you touch a listed site, the site's opener or interpolated expression changed: fix the site, or re-trace it and update the entry; an entry whose site is gone must be deleted.
Not measured here. A query built in a variable or by concatenation first is not read. GNU grep and gawk (Linux) were not run. The optimization.ts entry is OPEN against KS 1929 until that change lands. The four platform suites, a booted stack and any deploy were not run.
