A suspended or archived tenant is refused by originate, and tenant status moves follow the documented order — KS-1860

What to know. Where MULTI_TENANCY_ENABLED is true, originate now answers 403 “Tenant is suspended” or “Tenant is archived” to a request made as that tenant, within one successful 60-second refresh of the status change, per originate process. If the platform database is unreachable at start-up, no status is known and every tenant is served until a read succeeds; if it goes down later, the statuses last read stay in force (this change does not alter it, and Kam ruled to keep it: card secuura-ks1860-status-refresh-fails-at-startup-1101, “a — Keep it as built and say so”). With the flag off (the compose default) nothing changes. Public verification of that tenant’s documents, the admin document lookup and the template clone behave as before, because getPool still falls back to the default pool for that tenant (the shared database; with per-tenant databases on, that is not the tenant’s own). Sign-in and the other services are not touched.
PATCH /api/platform/tenants/:id/status allows provisioning → active, active → suspended, suspended → active and suspended → archived (KS-1861 later adds archived → suspended). Anything else answers 409 CONFLICT and changes nothing, with no audit row: archived → active, active → archived (suspend first), and a same-status request. An unknown well-formed id answers 404. The admin portal discards the answer, so a refused move looks like no change after the reload.
