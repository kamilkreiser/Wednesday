An unreadable connector allow-list fails closed — KS-1256

What to know. The connector allow-list is read from platform settings to decide whether a caller may create a restricted document type.
When the read failed, the parse left connectorConfig = {}, and an empty config reads as no restriction — so every restricted connector became unrestricted exactly when the platform could not see its own restrictions.
It now answers 503 and refuses the create. Two unreadable states, two different mechanisms. A THROWN read (the client’s MaxRetriesPerRequestError, or JSON.parse on malformed stored bytes) is closed in the catch.
But when Redis is UNAVAILABLE, getNotificationSettings resolves null without throwing out of an empty in-memory store — a catch can never see that, so the availability test must run BEFORE the read. Redis up and the key absent is still “no restriction”, by Kam’s ruling b: a fresh install has no key, and failing closed there would refuse every connector create on a new deployment.
A malformed container still answers 403, unchanged. The cost is accepted, not hidden (Kam, card …-1006 = a): while K’s Redis is down, Platform-S cannot create documents through a connector. Watch out: fallbackMode is set by retryStrategy at services/redis.ts:78 with no NODE_ENV guard, so production reached the old fail-open state on a runtime blip despite refusing to START without Redis.
One cell pins that under NODE_ENV=production.
