api-client.ts declares the error body the gateway sends — KS-1767

What to know. The MCP server’s api-client.ts typed a response’s error as a string at three sites (registerDocument, getWorkflowInstance, getConnectorInfo), while the gateway’s published error body carries an object { code, message }. Nothing checks the declared type at run time, so the type and the wire had drifted apart unseen. The three sites now share one alias, string | { code?: string; message?: string }, and the as unknown as cast in tools/info.ts that worked round the old type is gone.
Read from source: the routes’ own refusals are objects. A flat string exists only in the brute-force limiter’s 429 branch (429 { error: 'Too many failed attempts', ... }), which KS-1372 records as unreachable today because nothing calls its recordFailure. The string arm is kept for the old declaration, for tools/info.ts’s own string test, and for that branch if it is ever wired. The info.ts edit changes no behaviour: its emitted JavaScript is identical line for line.
The new test reads the types, because vitest does not type-check: it compiles a probe against the real api-client.ts through the TypeScript compiler API. 10 cells: per site T1 (the object is assignable), T2 (a string is assignable), C1 (a number is refused), plus C2 (the probe resolved the real file). Red-first: 3 failed / 7 passed on the unfixed file, 10 of 10 fixed. Eight one-line mutants each fail exactly their own cells.
Not measured here. A run on an LTS Node: the host carries only v26.8.1 and nothing was repeated on Node 24. Nothing calls a gateway; the wire reading is from source files, and the reverse proxy in front of the gateway was not read.
The four platform suites (Schemathesis, Akto, Playwright, Performance). Three other places that read data.error and relay it (tools/info.ts once, tools/register.ts twice) are not changed.
