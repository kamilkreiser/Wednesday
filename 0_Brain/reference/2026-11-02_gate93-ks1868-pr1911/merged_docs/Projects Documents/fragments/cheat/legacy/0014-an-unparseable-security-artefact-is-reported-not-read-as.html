An unparseable security artefact is reported, not read as clean — KS-1136

What to know. 09-aggregate-report.sh read each job's artefact with jq -r … 2>/dev/null (08 with a bare jq), so an artefact that EXISTS but does not PARSE — a job that aborted mid-write — gave zero findings and rc 0, which is indistinguishable from a clean scan.
KS 878 had guarded 04's artefact only.
Each present, unparseable artefact across the seven other jobs (01 02 03 05 06 07 08) now emits its own HIGH finding.
The insertion sits before ALL_FINDINGS reads $TMP, so the findings land in the aggregate rather than after it.
Pure insertion, numstat 14 0; no threshold, baseline, exit-code path or report writer is touched.
Gotcha when you run this locally. Two of them. (1) git apply drops the executable bit. 09-aggregate-report.sh is 100755; after applying the patch git ls-files -s still reads 100755 while the file on disk is -rw-r--r-- and [ -x ] is FALSE.
Re-assert it with chmod 755 on that one file — authorised by the index mode, and prove it changed no byte (cmp rc 0).
Never checkout-index -a. (2) jq -e . takes its exit status from the output VALUE, not only from parseability, so a valid JSON null or false also reads as unreadable.
That is the chosen behaviour, named rather than discovered later.
