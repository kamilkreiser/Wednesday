api-gateway fail500 logs a thrown object's type and field names, so a non-Error throw is no longer [object Object] — KS-1346

What to know. Three api-gateway routers share one fail500() helper (routes/notifications.ts, routes/batch.ts, routes/audit-export.ts). Its log line was String(err), so a thrown non-Error object became "[object Object]" and its content was lost. It now logs the thrown value's type and field names.
Read the LOG, not the response. The 500 body is the constant INTERNAL_ERROR body and always was, so the response is not evidence either way. Throw a non-Error from one of those routes and read what logger.error wrote.
Still true after the fix, deliberately. A thrown Error logs its .message; thrown text is logged verbatim. If you are hunting secrets in logs, those are the two shapes to look at — they are tracked on this ticket, not closed by it.
How to run it. cd Blockchain/Dev/services/api-gateway then npx vitest run src/__tests__/ks1346-apigw-fail500-logs-type-and-field-names.test.ts — 15 cells (G1 plain object, G2 class instance, G3 number, times three routers). They read 9 failed / 6 passed of 15 against the unfixed product and 15 of 15 with it.
What was not run. The four platform suites need a booted local stack; none of their numbers appears above. A live run is owed before the ticket moves, because this is runtime logging behaviour and offline green does not settle it.
