The published OAuth authorize contract names the OAuth token and the role-or-scope door — KS-1472

What to know. The sentence in both /api/oauth/authorize descriptions now says “An OAuth token with no scopes” (a plain login JWT passes requireScope on RBAC, so only an OAuth token is refused), adds “unless the route also admits the caller by role” (requireOrgProvisioner admits SUPER_ROLES with no scope), and says “requires no scope” where it said “requires none”. The wording lives in auth.openapi.ts; the yaml is regenerated, never hand-edited.
The route that requires no scope “does not refuse it for want of one, though a role check on that route can still refuse it”. The first wording said such a route “accepts any valid token”, which the QA gate flagged as false for a role-gated route: requireSuperAdmin answers 403 outside SUPER_ROLES, and GET /api/platform/tenants has no requireScope.
The pin is STATES_THE_TOKEN in ks839-contract-states-the-wildcard-allow-list-rule.test.ts; the false-claim guard beside it is unchanged and still red when the claim “the gateway answers 403 on it” is added. The ks1210 header now names redirectUris only, which is all its control reads.
Not measured here. A request through a running gateway: the cells read the yaml text and send nothing. What the sentence says about the gateway was read from scopes.ts and platform.ts, not run.
The four platform suites (Schemathesis, Akto, Playwright, Performance/k6) are not claimed as passing, and Node 24 was not run. The new text is served only after a deploy and a gateway restart.
