Transfer-custody: newHolderId is declared a uuid in the published contract — KS-591

What to know. TransferCustodyRequestSchema in services/originate/src/originate.openapi.ts declared newHolderId: z.string().optional() — a plain string for what is a user id — so the published spec advertised any string as valid and Schemathesis scored the operation as accepting bad data.
Now z.string().uuid().optional(). This registry schema is the contract (the spec is generated from it), so declaration and document cannot drift.
The narrowing is the format, never the presence: optional() is kept and newHolderEmail is untouched, so the email-resolution path is unaffected.
KS-591 is a REGISTER (734 failures across 64 operations). This is one operation's one field, so it is a narrowing and the ticket does not move to Done.
Gotcha when you run this locally. Three of them. (1) This service is jest, not vitest. A vitest invocation against services/originate reports 96 failed (96) with Tests: no tests — 0 executed. That is a load failure, and it looks exactly like a catastrophically red suite if you read only the exit code.
(2) Run check:openapi BEFORE regenerating. With the product change in and the YAML untouched it exits 1 with CHECK FAIL: generated YAML differs from on-disk version. That is the only cheap way to prove the later rc 0 is a comparison that ran rather than a gate that cannot fail.
(3) generate-openapi rebuilds packages/shared first (it is npm run build --workspace=packages/shared && tsx scripts/generate-openapi.ts), so a stale dist silently changes what the spec is generated from.
