Tenant creation says when the vault key was not confirmed: a keyPending flag on the 201 — KS-1240 option b

What to know. Kam ruled decision card secuura-ks1240-key-fail-answer-measured-1028 as option b. POST /api/tenants still answers 201 when the tenant’s vault key cannot be generated, but the body now carries keyPending (false when the key service confirmed the key; true when it was unreachable, did not answer in time, or answered not-ok) and, only when true, a keyPendingMessage. The server logs the not-ok answer, which it never did before.
Only these additions. Every existing field of the success body is byte-identical (the new field is appended); the writes are unchanged; a failed metering mint does not set the flag. A 503 and a rollback of the key row the key service writes after the caller gives up are not part of it.
Scope. The ticket text names only the api-gateway key-validate fetch; this part was added by the coordinator’s brief, not by the ticket.
Not measured here. A real tokenisation or security service, a real database row (the writes are read at a recording stub), a real gateway in front (the body is forwarded by a spread, read from the code), the admin UI, and a running stack.
