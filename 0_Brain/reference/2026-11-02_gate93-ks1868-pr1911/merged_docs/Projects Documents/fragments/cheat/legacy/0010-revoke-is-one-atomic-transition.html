/revoke is one atomic transition — KS-1278

What to know.POST /api/documents/:id/revoke decided “already revoked” on a READ and then ran an unconditional UPDATE, so two overlapping revokes could both pass the read: 200 + 200, two updates, two action_provenance rows, two anchor calls.
The decision now lives IN the UPDATE — updateDocument’s new ifStatusIsNot option adds AND (… IS NULL OR status IS DISTINCT FROM …) to the WHERE, and a guarded write that changed no row returns null.
The loser answers the same 400 and returns before recordOnBehalfOf, so it records nothing and anchors nothing. Refs KS-1278; the row-lock alternative is not taken.

Round 2 (this commit). The guarded UPDATE still keyed on external_id, but both reads fall back to the primary key for a UUID-shaped id (documentRepo.ts:244-251) and the API hands clients that key as documentUuid (:172).
So a sequential, non-race revoke of a live, owned, unrevoked document addressed by its documentUuid matched 0 rows and answered 400 “already revoked” (gate65 N-1393-1).
The guarded write now keys on the row the read resolved (:616), mirroring the read’s own precedence.
Only the one opted-in caller changes key; the other 12 production updateDocument( callers take a byte-identical statement.
