A backup code can no longer be spent twice by two sign-ins at once — KS-1848, KS-1849

What to know. The MFA backup-code burn in services/auth is now one conditional UPDATE (userRepo.consumeBackupCode): it removes exactly the stored hash that matched, and only while it is still stored. Before, the gate wrote its own snapshot of the array, minus the code, back over the row by id.
Behaviour change on POST /api/auth/login, the OAuth password grant and wallet verify: of two sign-ins racing with one backup code, the second now gets the uniform refusal (the answer a replayed spent code gets) and one lockout count, instead of a second credential. A burn that cannot be confirmed (a blind write, a NULL set, no row) still answers 503 with the KS-1188 F3 wording. The burn still comes before the credential.
New cells: ks1848-backup-code-burn-is-conditional.test.ts (18 unit cells over a stateful db stub; 9 are red at develop) and integration/ks1848-backup-code-burn-concurrency.integration.ts (13 cells on a real Postgres, run as secuura_app so RLS is live; 8 are red at develop). The two ks781 files gain the new function in their userRepo mock.
Not measured here. The four platform suites, a running stack, Node 24 and any deploy were not run. The integration file needs a throwaway Postgres (see its header); it is not part of vitest run.
