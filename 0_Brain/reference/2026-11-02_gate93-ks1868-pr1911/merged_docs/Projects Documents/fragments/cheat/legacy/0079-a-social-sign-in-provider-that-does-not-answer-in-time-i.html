A social sign-in provider that does not answer in time is classified as unavailable; every provider fetch is bounded — KS-1240

What to know. The six social provider adapters (GitHub, Google, LinkedIn, Apple, Facebook, Microsoft) bound each of their 12 fetches at 10 s. A call that does not finish in time (a hang, or a body that stalls) surfaces as the existing ServiceUnavailableError: POST /social/link answers 503 SERVICE_UNAVAILABLE, and the login callback answers its 400 “OAuth authentication failed: <Provider> did not answer in time; please try again.” Both used to hang.
A refused or unresolvable provider is classified the same way (“<Provider> could not be reached; please try again.”: 503 on the link route, was 500). A token refusal no longer carries the provider’s own error body to the client: the error says “<Provider> token exchange failed (HTTP 400)” and the body is logged server-side, first 200 characters. The OAuth state is still spent before the exchange, so a timed-out sign-in needs a fresh one.
routes/auth.ts and middleware/errorHandler.ts are unchanged; the classification is thrown from the adapters.
Not measured here. Node 24 (host Node 26.8.1 only, no Docker in this lane); any real provider (the endpoints are a local stub, the state store an in-memory map); any running stack.
The four platform suites (Schemathesis, Akto, Playwright, Performance/k6) are not claimed as passing. The change is not deployed.
