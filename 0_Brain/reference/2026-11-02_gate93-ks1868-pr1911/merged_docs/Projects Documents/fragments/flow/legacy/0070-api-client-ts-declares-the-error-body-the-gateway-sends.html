81. api-client.ts declares the error body the gateway sends: a string or an object { code, message } at all three sites (KS-1767)

What this changes. KS-1767 records that the MCP server’s api-client.ts typed a response’s error as a string at three sites (registerDocument, getWorkflowInstance, getConnectorInfo) while the gateway’s published error body carries an object { code, message }. Nothing was failing: nothing checks the declared type at run time, because apiRequest only casts the parsed body to it. The type said one thing and the wire said another, and a caller that trusted it could relay [object Object] or the whole object.
A type-only change. The three declarations now use one alias, GatewayErrorField = string | { code?: string; message?: string }, and the as unknown as cast in tools/info.ts that worked round the old type is dropped. The emitted JavaScript of info.ts (comments removed) is identical, line for line, so no behaviour changes.
details, optional in the published ErrorResponse, is not declared because no caller reads it. Three other places read data.error and relay it into a JSON error field (tools/info.ts for the workflow instance, and tools/register.ts twice). They are not changed: they compile under either type, and whether they should relay an object is a behaviour question this ticket does not ask.
