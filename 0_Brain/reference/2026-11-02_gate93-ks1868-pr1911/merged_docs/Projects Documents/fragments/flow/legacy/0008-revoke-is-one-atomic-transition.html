15. /revoke is one atomic transition (KS-1278)

What this pins.POST /api/documents/:id/revoke decided “already revoked” on a READ (routes/documents.ts:2374) and then ran an unconditional UPDATE.
Two overlapping revokes could both pass that read, so both answered 200, both wrote an action_provenance row and both emitted an anchor call.
The decision now lives IN the UPDATE: updateDocument takes an ifStatusIsNot option that adds AND (${guardStatus}::text IS NULL OR status IS DISTINCT FROM ${guardStatus}::text) to the WHERE, and a guarded write that changed no row returns null.
The loser of the race answers the same 400 BAD_REQUEST “Document is already revoked” as a sequential caller, and returns before recordOnBehalfOf — so it records no provenance row and emits no anchor.
Scope. This completes the ticket’s scope — the atomic transition, the 400 for the loser, and provenance and anchor only for the winner.
The PR says Refs KS-1278, not Closes. The row-lock alternative is not taken.
What a null from the guarded write means, and what each meaning is pinned by.updateDocument already returned null for a missing document (documentRepo.ts:543 at 4a1620588819; :538 at the branch base 32e058975d4e), so null is not a single condition and the route must not read it as one.
On the guarded path it can arise three ways:
A genuine raceanother revoke changed the row between this request's read and its write.
The write refuses in the UPDATE, so exactly one of two overlapping writers wins. Instrument: cell R1, which also asserts 0 anchor emissions on the losing path, not only 0 provenance rows.
The guard itself is pinned by cell R2, which asserts the guard clause by exact text and the guard’s own two parameters by position — a weaker assertion on either half is satisfied by a vacuous guard, or by the SET clause’s new status standing in for the guard value.
The row was deleted inside the windowthe answer is 400 where 404 belongs.
This is unchanged by round 2 and is tracked as KS 1419. Instrument: none live — unmeasured against a real database.
A revoke addressed by the platform UUIDfixed in round 2. Both reads fall back to the primary key for a UUID-shaped id (documentRepo.ts:244-251) and the API hands clients that key as documentUuid (:172), but the guarded UPDATE keyed on external_id. At the branch base and at round 1 a sequential, non-race revoke of a live, owned, unrevoked document addressed that way matched 0 rows and answered 400 "Document is already revoked" with 0 provenance rows and the status never written. At round 2 the guarded write keys on the row the read resolved (:616, mirroring the read's own precedence: external_id first, then the primary key), so it answers 200, writes the status and records exactly one provenance row. Instrument: cell N1, red at 4a1620588819 and green at the round-2 head.
The route still 404s at :2367 and 403s at :2371 before the write, so a missing or unowned document never reaches it. Only the opted-in revoke path changed key: the other 12 production updateDocument( callers pass no ifStatusIsNot and take a byte-identical statement (instrument: cell N3).
A non-UUID external id never reaches the ::uuid cast, which would otherwise raise 22P02 (:590; instrument: cell N2, green at both ends).
The remaining residual cases are recorded under Not covered below.
