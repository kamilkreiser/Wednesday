128. The single-use MFA backup-code burn removes exactly the matched stored hash in one conditional UPDATE, so two concurrent sign-ins cannot spend one code twice (KS-1848, KS-1849)

What this changes. Blockchain/Dev/services/auth/src/repositories/userRepo.ts gains consumeBackupCode(id, storedHash): one UPDATE users SET mfa_backup_codes = array_remove(mfa_backup_codes, $1), updated_at = NOW() WHERE id = $2 AND $1 = ANY(mfa_backup_codes), run under the tenant updateUser resolves. A row count above 0 is read back under the same scope, as updateUserOrThrow did. A row count of 0 is re-read through the pre-auth carve-out: a stored set that still exists and lacks the hash means another request spent the code or replaced the set (a regenerate); no row, a NULL set, or the hash still stored is the 503 it always was. updateUser itself is unchanged.
services/passwordLoginGate.ts, the burn block only: the gate burns the stored hash that matched, never an index; a burn that lost the race answers the uniform refusal and counts once in the lockout, which is what a replay of a spent code answers; the request’s own copy of the codes is trimmed only after a confirmed burn. Before KS-1848 the gate spliced the code out of its snapshot and wrote the whole array back by id. Gate 38 F1: the comment above that refusal used to say a lost race “is no oracle”; it now says that status, body and lockout count are identical to a replay of a spent code but time is not (a lost race answers about 30 ms sooner, because verifyBackupCode returns at the first matching hash). 128.3 What this does not prove

The burn, not every writer of the column. In the forced races L1c and L2c the writer reached the row lock first in all 20 rounds; the reverse order (the burn’s UPDATE queued first, then the regenerate or the disable) is L3 and L4, 20 of 20 rounds each, and the burn is correct in that order. A lost race still answers about 30 ms sooner than a wrong or spent code (gate 38 F1); the comment now says so and the timing is unchanged. A connection fault on the burn UPDATE itself is still unclassified (a 500, as from updateUser today); only faults in the tenant lookup and the read-back become the 503.
Not touched: routes/users.ts stores /me/mfa/verify codes unhashed, and services/account-recovery.ts accepts any string of eight or more characters as backup-code evidence (it is not wired to a route). Both are reported for filing.
Not run: the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), a running stack, Node 24, any deploy. The pre-push hook’s leg count is stated in the pull request.
