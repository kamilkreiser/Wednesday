98. The m365 callback’s success redirect encodes the connection id, as it already encodes the tenant (KS-1670, site 1)

What this changes. KS-1670 site 1 (the other two sites of the ticket wait for a separate decision and are not here): in services/m365-integration/src/index.ts the GET /api/callback success redirect put connectionId into the query string unencoded, while tenant in the same template line was already wrapped in encodeURIComponent. The id only reaches that line after the server’s own connection lookup hits, so it is not exploitable today; an id format that ever admitted &, # or % would change the shape of the query. The template expression now reads encodeURIComponent(connectionId). For every id the server issues, the redirect is byte for byte the same. A local model (the Spark, DeepSeek V4 Flash) wrote the patch (pass ks_1670_p1); its checker passed 7 of 7 and the patch is byte-identical to the drafter’s golden. It was applied here strictly and unchanged.
One product line changes (+1 / −1). The first new test is services/m365-integration/src/__tests__/ks1670-the-success-redirect-encodes-the-connection-id.test.ts (vitest, 5 cells), a source-text pin: it reads index.ts as text and boots nothing, so it proves the text of the template. The second, added at prep on the tier-1 gate’s note, is services/m365-integration/src/__tests__/ks1670-the-success-redirect-keeps-a-hostile-connection-id-intact.test.ts (vitest, 6 cells), a behaviour test: it drives the real GET /api/callback over 127.0.0.1 with Microsoft and the database stubbed, plants a hostile connection id by stubbing crypto.randomUUID for one sign-in (and checks that the id really became the connection’s), and parses the Location header the way a browser would. No tier timing or budget in these documents moves.

98.2 What the cells prove, and what they do not

The template text, and the redirect on the wire. The source-text pin (R1, R2) proves the interpolation is wrapped and that the encoded id and tenant appear in order; C1 to C3 prove it finds the line it should and leaves the other redirects alone. The behaviour test proves what a browser receives for five ids, from the ordinary one to ones carrying &, #, %, +, a space, ? and non-ASCII characters: one connectionId parameter equal to the id, the tenant parameter and the host untouched, and no fragment. Sites 2 and 3 of KS-1670 are not touched. A lone-surrogate id would make encodeURIComponent throw a URIError, which the route’s catch turns into an error redirect and saves on the connection as error; real ids are conn_ plus a uuid, so this cannot happen today, and no cell covers it.
