9. Auth surface — connector tokens on the users routes (KS-564, KS-1402)

9a. KS-1402 — GET /api/users/lookup accepts a connector token (Kam ruling 2026-10-02, option (a))
What it pins. Platform S authenticates with an sk_ connector key, so its token is a type: 'connector' token rather than an interactive access token.
Before KS-1402 only POST /api/users/stub accepted one (KS-564, Option A); GET /api/users/lookup still used plain authenticate(), so every Platform-S transfer-custody call 401'd and fell back.
Both routes now go through authenticateAccessOrConnector(). The token type is not the permission. The route's own role/scope gate still runs afterwards, so users:read is the effective gate on /lookup, and a cross-tenant lookup still returns 404 — not 200-empty, so positive existence is not readable from the response shape.
The audit label is route-neutral, deliberately. The connector-accepted log line read users/stub: … unconditionally, so once a second route accepted connector tokens every /lookup call would have written an audit line naming a route it never touched.
It now carries route: req.baseUrl + req.path. req.originalUrl was rejected for this field because it carries the query string: measured on GET /api/users/lookup?email=alice%40example.com, req.originalUrl is /api/users/lookup?email=alice%40example.com while req.baseUrl + req.path is /api/users/lookup — so originalUrl would put the email address in the clear in the audit log, which is the very thing maskEmail() exists to prevent.
