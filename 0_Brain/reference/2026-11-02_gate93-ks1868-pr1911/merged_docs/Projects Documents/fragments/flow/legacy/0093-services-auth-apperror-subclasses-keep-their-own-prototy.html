104. services/auth AppError subclasses keep their own prototype, so the weak-password 422 now carries its feedback in the published array shape (KS-1467, the services/auth half)

What this changes. Behaviour change: the three weak-password 422 answers of services/auth (registration and password reset in routes/auth.ts, lines 204 and 822 at the base, and change-password in routes/users.ts, line 993) now carry error.details as an array with one { code: ‘custom’, path: [<field>], message } per feedback line, path being [‘password’] or, for change-password, [‘newPassword’]. That is the shape the published 422 already promises (ValidationErrorResponse: details is a ZodIssue-compatible array), so the OpenAPI schema is not widened and no client meets a new shape. Round 1 of this change sent { feedback: [...] }, an object; the tier-1 gate (gate 9, finding 1799-1) found that, and Wednesday ruled round 2 (2026-10-28 14:57:54Z): conform to the published contract. Line 173 of routes/auth.ts (a role not permitted on /register) has no details and is unchanged. Cause: the AppError constructor in services/auth/src/middleware/errorHandler.ts ended with Object.setPrototypeOf(this, AppError.prototype), which reset every subclass instance to the base prototype, so err instanceof ValidationError was always false and the handler’s own if (err instanceof ValidationError && err.details) branch (line 296) never ran. The constructor now uses new.target.prototype (one line), and a stale comment above the 503 check in passwordLoginGate.ts is reworded. The feedback is a list of fixed strings built by checkPasswordStrength (only the minimum length is interpolated), so it cannot echo the candidate password; cell N1 proves that through the real helper, class and handler, and the E cells prove it through the three real routes. Wednesday accepted the visible change on 2026-10-28, on that one condition.
