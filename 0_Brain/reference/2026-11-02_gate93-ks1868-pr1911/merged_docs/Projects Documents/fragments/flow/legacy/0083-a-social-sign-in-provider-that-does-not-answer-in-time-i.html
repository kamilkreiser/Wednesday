94. A social sign-in provider that does not answer in time is classified as unavailable, and every provider fetch is bounded (KS-1240)

What this changes. KS-1240: the six social provider adapters in services/auth/src/providers/social/ (GitHub, Google, LinkedIn, Apple, Facebook, Microsoft) made 12 fetches with no timeout, so a provider that never answered, or answered the headers and stalled the body, held the sign-in request open with no bound, on the login callback and on POST /social/link alike.
The six adapters change and one test file is new: services/auth/src/__tests__/ks1240b-social-provider-fetches-are-bounded-and-classified.test.ts (vitest, 44 cells). routes/auth.ts and middleware/errorHandler.ts are unchanged. No tier timing or budget in these documents moves.

94.1 What each entry path answers now

A timeout, or a provider that cannot be reached, is the provider being unavailable. Each adapter carries one 10 s constant (PROVIDER_TIMEOUT_MS) and one small helper. Every fetch has AbortSignal.timeout, which also bounds the body read after it, and exchangeCode turns only a timeout into the existing ServiceUnavailableError (KS-253, 503 SERVICE_UNAVAILABLE) with the text “<Provider> did not answer in time; please try again.” It is thrown from the adapter, so neither route file changes.
POST /social/link has no local try, so the error handler answers it 503; before, the request hung. The login callback wraps every exchange failure in its own BadRequestError, so it still answers 400, now as “OAuth authentication failed: GitHub did not answer in time; please try again.” instead of hanging. Its OAuth state is consumed before the exchange, as before, so a timed-out sign-in needs a fresh one.
A refused or unresolvable provider (fetch’s own TypeError: fetch failed) is classified the same way, with the text “<Provider> could not be reached; please try again.”: 503 on /social/link (was 500) and the classified 400 on the callback. A TypeError that is not a network failure stays unclassified.
The provider’s own error text no longer reaches the client (gate 5, finding 1788-1). Every adapter put await tokenRes.text() into its token-refusal Error, and the callback echoed it (the gate measured a JSON error_description and an upstream HTML page). The Error now carries the status only, “<Provider> token exchange failed (HTTP 400)”, and the provider text is logged server-side, first 200 characters, as routes/auth.ts bounds error_description. A token 4xx or 5xx is still not classified as unavailable (500 on the link route), and a profile call answered 401 still rejects with its adapter’s own error. The cells assert status, code and message, never instanceof ServiceUnavailableError: at this base AppError’s constructor resets every subclass instance to AppError.prototype (KS-1467 in auth), and only instanceof AppError, which the error handler uses, holds.

94.3 What the cells prove, and what they do not

Real adapters, a stub provider. The hang and the stalled body are real network behaviour against a local server; the provider endpoints, their answers and the OAuth state store are stand-ins (the state store is an in-memory map, the ks819 pattern), and the authenticate middleware on /social/link is a pass-through.
Not measured: Node 24; any real provider; any running stack; the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), none of which is claimed as passing; any deploy.
