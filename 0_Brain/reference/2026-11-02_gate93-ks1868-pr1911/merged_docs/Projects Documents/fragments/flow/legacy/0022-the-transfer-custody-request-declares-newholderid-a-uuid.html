31. The transfer-custody request declares newHolderId a uuid, so the published contract stops accepting any string (KS-591)

31.1 What the register says, and what this row narrows

KS-591 is a register: positive_data_acceptance across 64 operations, 734 failures. TransferCustodyRequestSchema declared newHolderId: z.string().optional(), so the published spec advertised a plain string for what is a user id. Schemathesis generates a non-uuid, the contract says it is valid, and the operation is scored as accepting bad data. This row narrows one operation's one field. The register stays open and the ticket does not move to Done.

31.2 The change, and why it is a spec row rather than a handler row

z.string().uuid().optional() in services/originate/src/originate.openapi.ts at TransferCustodyRequestSchema. This registry schema is the published contract — the spec is generated from it, so the declaration and the document cannot drift. optional() is retained deliberately: the narrowing is the format, never the presence, and newHolderEmail is untouched, so the email-resolution path is unaffected. One line of product code.

31.5 Not covered

A spec narrowing, not a handler change. No runtime validation branch moves, so no live sweep is owed for this row — the handler behaves exactly as before and only the published contract is tightened. The 63 other operations on the register are untouched, and newHolderEmail is deliberately left as a plain string because it is resolved server-side. The four platform suites (Schemathesis, Akto, Playwright, performance) are UNMEASURED, not passing — the local stack is not up — and Schemathesis is precisely the instrument that would score this narrowing, so the improvement this row buys is asserted by the contract and not yet observed end to end.
