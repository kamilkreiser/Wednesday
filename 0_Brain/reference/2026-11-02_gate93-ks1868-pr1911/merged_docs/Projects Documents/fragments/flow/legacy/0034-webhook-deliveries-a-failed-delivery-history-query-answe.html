48. webhook deliveries — a failed delivery-history query answers 500, not 200 with an empty list (KS-1345)

48.1 What this row is, and what it is not

GET /api/webhooks/:id/deliveries chained .catch(() => []) onto its history query, so a database failure answered 200 { success: true, deliveries: [] } and read as “this webhook has no deliveries”. The swallow is removed: a rejected query now reaches the route's existing catch and answers the constant 500 body through fail500, logged once with the route named. This is the deliveries route only. The list route (GET /api/webhooks, row 13) is a separate, earlier KS-1345 change. The 400 for an id that fails the format pattern is unchanged, and so is the one .catch(() => []) left in the file, the fire-and-forget dispatchEvent subscription read.

48.2 The one answer that is kept on purpose

An id that passes the format pattern but is not a UUID (e.g. 0) answered 200 [] before, because the swallow hid the ::uuid cast error. It still answers 200 [], and the query is now not run for it, so the cast cannot turn into a 500. The check is the file's own UUID_PATTERN (canonical hyphenated form, case-insensitive), the same pattern the four sibling routes use through rejectInvalidWebhookId. Moving such ids to 404, as those routes do, is a contract decision for another ticket. Read, not tested: a 32-hex id written without hyphens, which Postgres would cast, now also gets 200 [] instead of its rows.
