116. The did:jwk shape pattern also refuses a payload with a plus sign or a slash: adding either to the class now turns a cell red (KS-1830)

What this changes. Test only, zero product bytes. QA gate 18 found that adding +, / or both to the DID_PATTERN character class (anchorSchema.ts line 124) passed all 135 cells of ks1175-identity-anchoring.test.ts: no cell used a payload that contains either character, and they are the two characters of standard base64 that base64url leaves out. The product refused such a payload then and still does; nothing pinned it.
Two hunks, +12 -0 lines in all, in ks1175-identity-anchoring.test.ts: two rows added to SHAPE_REFUSALS (the realistic did:jwk with exactly one + inserted in its payload, and with exactly one /) and one control cell per character. For each of the two did:jwk fields (actorDid, orgDid) that is 4 new cells per character: 2 RED cells that assert the field’s own issues are exactly one invalid_string (the shape pattern), so a widened pattern goes red whether it then accepts the value or lets the private-key guard refuse it for another reason, and 2 control cells that check the row is the realistic did:jwk with exactly one of that character inserted and nothing else, so the row cannot drift into testing something else.
Eight new cells in all (4 RED, 4 controls). “1805-1” in the older cell names is a gate finding id, not a ticket.
