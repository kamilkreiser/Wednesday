110. POST /seed-demo-users keeps going when a user’s insert throws a hostile value: the per-user catch logs through a guarded helper (KS-1802)

What this changes. In routes/adminConfig.ts the loop over the 14 demo users wraps each insert in a try. Its catch counted the failure (failed++) and then logged err?.message. That read touches the thrown value itself, so a revoked Proxy, or an object whose message getter throws, made the log line throw from inside the catch: the loop stopped at the first such user, the other users were never attempted, and the route answered the constant 500 instead of its report.
The log line now reads the message through a new helper readableErrorMessage, a try around err?.message that returns the fixed text “thrown value that could not be described” when the read throws. Product diff: +10 -1 lines in adminConfig.ts (blob dfe0d29865c0); the other catches in the file are not touched.
New test file ks1802-seed-demo-users-survives-a-hostile-throw-in-the-loop-catch.test.ts (+127 lines, 6 cells), driving the real router over a loopback listener with the database mocked and both seed flags set. R1 and R2 make every insert reject with a revoked Proxy and with a throwing message getter and expect the normal report with 14 failed; R3 makes only the first user fail with a hostile value and expects the other 13 to be seeded. C1 to C3 are controls: an ordinary Error on every insert is reported as 14 failed and its message logged, every insert creating a row is 14 created, every insert hitting a conflict is 14 already present.
