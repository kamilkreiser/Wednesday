93. The api-gateway front door answers 503 when an API key cannot be checked, and every hand-built gateway fetch is bounded (KS-1240)

What this changes. KS-1240: the two front-door calls in middleware/auth.ts (key validation at the security service, the connector-token exchange at auth) and nine hand-built forwards (routes/proxy.ts five, routes/admin.ts two, routes/batch.ts one, routes/audit-export.ts one) carried no timeout, so an upstream that never answered, or answered the headers and stalled the body, held the request open with no bound. And the front door could not tell “this key is rejected” from “I could not ask”: a thrown fetch answered 401 Invalid API key, and the security service’s own 503 'Unable to verify key' was answered 401 and negative-cached for 30 s.
Five source files change and two test files are new: services/api-gateway/src/__tests__/ks1240b-front-door-key-exchange-timeout-answers-503-not-401.test.ts (12 cells) and services/api-gateway/src/__tests__/ks1240b-every-hand-built-gateway-fetch-is-bounded.test.ts (28 cells), both vitest. No tier timing or budget in these documents moves.

93.1 What a client sees now

A presented sk_ key. checkApiKey returns valid, rejected or unavailable. Unavailable is no complete answer within 5 s (a hang or a stalled body), an unreadable body, or a 5xx, 408 or 429 from the security service. It answers 503 SERVICE_UNAVAILABLE 'Unable to verify API key, please retry' on required AND optional mounts, is never cached, and is logged once as API_KEY_VALIDATION_UNAVAILABLE with its reason and never the key. Authority: Kam’s rulings on cards secuura-ks888-revoke-validate-on-failed-save (a) and secuura-ks1370-validate-when-the-revoke-check-cannot-read (a), that an unverifiable key is refused with 503.
Rejected keeps every answer it had: 401 Invalid API key and a 30 s negative cache on a required mount, and the KS-1207 fall-through to the Bearer path on an optional mount. A non-2xx with no status that says “could not answer” (any 4xx other than 408 and 429, or no status at all) is still a rejection, as auth.test.ts pins.
Optional mounts answer 503 for an unverifiable key instead of serving the caller as anonymous: the caller asked to be the key’s principal. It is a refusal, never a pass, so KS-1207’s guarantee (a junk key cannot switch off the Bearer check) holds.
The exchange stays fail-closed: within 5 s the request goes on with no Bearer, and a Bearer-only upstream refuses it 401, as before; the log now says “timed out after 5000 ms”. The ticket’s line that a 503 “is consistent with how the connector branch already answers a refused exchange” was checked and is not borne out: no gateway code answers a refused exchange with 503, and auth’s /internal/connector-token answers 502. A gateway 503 there would also refuse the gateway-local handlers that serve sk_ callers from req.user without the Bearer.

93.2 The bounds, and what the forwards now answer

Two values, each a named constant. 5 s for the two front-door calls (KEY_VALIDATE_TIMEOUT_MS, CONNECTOR_EXCHANGE_TIMEOUT_MS): the bound the gateway’s own health probes give the same internal services. 60 s for every hand-built forward (UPSTREAM_FORWARD_TIMEOUT_MS in proxy.ts and admin.ts, BATCH_ITEM_TIMEOUT_MS, AUDIT_LIST_TIMEOUT_MS): the generic proxy’s proxyTimeout for every other route to the same upstreams, so hand-building a route neither tightens nor loosens it. MCP package generation takes 60 s too: the package is built from templates in-process.
The signal on the fetch also bounds the body read that follows it. Measured on Node 26.8.1 with a probe outside the repo: a hang before the headers, and a stall in the middle of json(), text() or arrayBuffer(), each reject with DOMException TimeoutError at the bound; a refused connection is TypeError: fetch failed.
A body cut off by the timeout now reaches each route’s own catch (502, like a connect failure) instead of reading as {} with the upstream’s status; a body that is simply not JSON still reads as {}. A batch item whose body never arrived now FAILS (“Upstream service did not answer in time”); it used to be a success with empty data. generate-package reads the whole package before it writes Content-Type: application/zip and the attachment disposition, which it used to write first, so a failed read sent the 502 as a zip attachment. The arrayBuffer() read itself was already inside the route’s try at the base; the header order was the defect.
