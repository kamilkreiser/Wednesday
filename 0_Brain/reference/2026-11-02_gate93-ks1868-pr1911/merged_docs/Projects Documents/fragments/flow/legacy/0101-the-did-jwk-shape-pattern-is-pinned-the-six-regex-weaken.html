112. The did:jwk shape pattern is pinned: the six regex weakenings that every cell let through now each turn a cell red (KS-1175)

What this changes. Test only, zero product bytes. QA gate 15 found that six weakenings of DID_PATTERN in anchorSchema.ts survived every cell in ks1175-identity-anchoring.test.ts: the m flag (a newline), = in the class (padding), $ dropped (trailing junk), the i flag (case), + turned into * (an empty payload) and \s in the class (whitespace). The product refused each input then and still does; nothing pinned it. (“1805-1” in the cell names is that gate finding’s id, not a ticket.)
One hunk of +32 -0 lines in ks1175-identity-anchoring.test.ts: 18 new cells, for each of the two did:jwk fields. Seven RED cells per field refuse an empty payload, a trailing newline, a newline between two payloads, base64 padding (==), a trailing space, an upper-case method (DID:JWK:) and a space inside the payload. Each asserts that the field’s own issues are exactly one invalid_string, so a weakened pattern goes red whether it then accepts the value or lets the private-key guard refuse it for another reason. Two control cells per field: a leading space is refused, and a did:key and the realistic did:jwk are still accepted, kept verbatim.
The six weakenings are the ones the gate listed; the pins were written for exactly them and are tested against them below.

112.1 What proves it

Green on the real pattern, red under each weakening. The file on the untouched product: 135 of 135 pass, with the 18 new cells included.
Each weakening planted alone (an exact-once replace of the pattern line, restored byte for byte, sha256 read back equal): the m flag turns 4 cells red; = 2; $ dropped 10; the i flag 2; + to * 2; \s 8. All six were killed, every red cell was one of the 14 new RED cells, and no older cell went red. All six at once (the gate’s tamper): 14 of 135 red, exactly the 14 new RED cells.
Whole anchoring unit suite: 35 files / 479 cells at the base, 35 files / 497 with the change (+18 cells). One cell fails in both runs and it is the same one, the emulator round-trip in threadTokenMint.test.ts (already failing at the base, not touched here), so 0 new reds. tsc with the test file in the program (225 files, the file listed): 0 errors, and a planted type error was reported once as TS2322 by file name.
