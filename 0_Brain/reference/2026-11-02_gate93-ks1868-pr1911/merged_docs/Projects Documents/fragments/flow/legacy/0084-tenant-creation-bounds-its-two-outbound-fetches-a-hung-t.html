95. Tenant creation bounds its two outbound fetches: a hung tokenisation or security service ends in the fail-soft path an unreachable one already took (KS-1240 part 4)

What this changes. KS-1240 part 4, services/tenant-provisioning: POST /api/tenants made two outbound fetches with no timeout, the vault key generation to the tokenisation service (requestKeyGeneration in index.ts) and the metering-key mint to the security service (requestMeteringKey in meteringKey.ts). Each now passes AbortSignal.timeout with a named 3 s bound (KEY_GENERATION_FETCH_TIMEOUT_MS, METERING_KEY_FETCH_TIMEOUT_MS). On expiry the fetch (or the body read) rejects into the try/catch each call already sat in, the same path an unreachable service takes.
Only the bounds change. The status and the body of every path are exactly what they were, and so are the writes of an unreachable or a hung service, with one exception: a service that is merely SLOWER than the bound (not hung). Where the unbounded code waited and returned the key (and so did the first 10 s version of this change, for an answer between 3 s and 10 s), the bounded code answers 201 with keyFile (or meteringApiKey) null in the body and stores vault_key_hash as NULL, while the key service still completes its own insert (exercised in the vault-key trace); nothing reads either value. What the route SHOULD answer when key generation cannot complete (today a 201 with keyFile: null and an empty vault_key_hash) is a separate decision and is not made here: it was decided on 2026-10-28 (option b, an explicit key-pending flag) and is built as a separate PR after this one.
Scope. The ticket text names only the api-gateway key-validate fetch; this part was added by the coordinator’s brief, not by the ticket.

95.1 What tenant creation did before the fix, and answers today

Measured at base bd6697e079fc, 2026-10-28 (UTC), Kamil’s MacBook Pro (Mac14,5, Apple M2 Max, 32 GB), shared with other sessions. The real service entry module, with pg replaced by a recorder and the JWT middleware by a pass-through, against real local servers that answer, stall or are shut down. The “DB row” is the parameters the route sends to the recorder, not a row in a database.
A hung tokenisation service, unbounded: the request never answers, and the only write is the tenant INSERT with status provisioning. No tenant_config, no status update, no audit row and no rollback follow (the rollback runs only on a throw), 3 s and 1 s later: a half-created tenant. A hung security service, unbounded: the tenant IS fully written and active (four writes) and the request still never answers, because the mint is the last step.
Bounded, a hung service and an unreachable one end identically: 201, success: true, tenant active, keyFile: null (tokenisation) or meteringApiKey: null (security), vault_key_hash stored as NULL when key generation failed, the same four writes. Only the log line differs (fetch failed against The operation was aborted due to timeout).
A third path nobody logs: a tokenisation service that answers 403 { success: false } ends in the same 201 with keyFile: null and a NULL hash, and writes no log line at all (unchanged by this change).

95.3 What the cells prove, and what they do not

The bound and the unchanged answer, not production timings. The route cells shorten the bound to 150 ms by wrapping AbortSignal.timeout; the cell that pins the length asks for exactly two 3 s bounds. The front door. The only gateway route to this handler, POST /api/platform/tenants (services/api-gateway/src/routes/platform.ts: the deadline is declared at line 132 and the route is registered from line 314, at develop d531abd5f34b), forwards with a default deadline of PLATFORM_UPSTREAM_TIMEOUT_MS, 8000 ms, and answers 504 when it expires (read from the code, not measured through a real gateway). The two bounds run one after the other, so with both services hung the create takes about 6 s plus the route’s own writes. A 10 s bound, the first choice, never fired first: the gateway answered 504 at 8 s while tenant creation finished afterwards and minted a metering key nobody received (tier 1 gate round 1, finding 1782-1). The generic proxy’s own timeout (routes/proxy.ts) is not the one this route uses. One cell runs the create with both services hung at the real bounds: a 201 after 6068 ms, five runs, against the 8000 ms deadline. The 1500 ms allowance for the writes inside the remaining margin is a stated allowance, not a measurement, and the deadline is a default an operator can change with the environment variable. A service that is slower than 3 s but not hung now takes the fail-soft path where the first version waited up to 10 s.
Not covered. A real tokenisation or security service; a real database row; Docker; the 409 a retry would meet after an unbounded hang (read from index.ts lines 206 to 213, not measured); Node 24; the four platform suites (Schemathesis, Akto, Playwright, Performance/k6). The change is not deployed.
Any change to what the route answers (a pending flag, a refusal) would change the published 201 contract (tenant-provisioning.openapi.ts and the OpenAPI yaml) and is held for a ruling.
