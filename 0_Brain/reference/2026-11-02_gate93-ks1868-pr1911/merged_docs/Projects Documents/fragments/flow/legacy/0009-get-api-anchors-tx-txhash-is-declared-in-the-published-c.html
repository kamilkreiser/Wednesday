16. GET /api/anchors/tx/{txHash} is declared in the published contract (KS-723)

What this pins.GET /api/anchors/tx/:txHash is routed by services/anchoring/src/index.ts:1089 and answers { success: true, data: <one anchor> }, but the published OpenAPI contract did not declare it.
An undeclared operation is invisible to every offline check: a change to its response shape broke no test, and the contract suites had no operation to generate against.
It is now registered on the shared registry that anchoring.openapi.ts populates on import, so the generated document carries it.
Scope — this is narrowing, not closing. KS-723 covers the remaining ~157 routed-but-undocumented /api operations; this declares one of them.
Stuart named two /api/anchors operations on the ticket (2026-09-29) as Platform-S hot-path reads.
Only GET /api/anchors/tx/{txHash} is declared here.
The other, GET /api/anchors/{id} (index.ts:827), is deliberately left out: declaring it on this registry would make the gateway answer 405 to two LIVE POST routes that share the path prefix.
It is not rejected and it is not covered — KS-723 stays open for it.

16.1 The cells

One new file, Blockchain/Dev/services/anchoring/src/__tests__/ks723-anchors-tx-lookup-is-declared.test.ts, 5 cells. It renders the document the generator publishes, from the shared registry the anchoring module populates on import — no server, no database, no network. Three cells are the red arms (TX1 the operation exists with bearerAuth and a required txHash path parameter; TX2 the 200 body is the success envelope around one anchor, not an array or a list wrapper; TX3 the 404 is declared). The remaining two are the file's own controls and pass at both ends, which is what makes the three reds discriminating rather than a blanket failure.
