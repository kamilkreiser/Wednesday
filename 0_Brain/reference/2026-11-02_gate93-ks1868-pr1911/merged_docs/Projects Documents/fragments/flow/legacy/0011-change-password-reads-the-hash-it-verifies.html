19. change-password reads the hash it verifies (KS-1005)

What changed.POST /api/users/me/change-password answered 404 for every password account. services/auth/src/routes/users.ts loaded the row with userRepo.getUserById, whose column list (userRepo.ts USER_COLS, commented “All user columns EXCEPT password_hash”) omits password_hash; the next line throws NotFoundError('User') on !user.passwordHash.
So the hash was always absent and the endpoint was wholly non-functional — not wrong at an edge.
It now calls getUserByIdWithPasswordHash, the hash-carrying variant that already existed and was used once, by mfa.ts, never here. One call site changed; the other seven getUserById call sites in the file are untouched.
The defect was worse than “returns 404”. The throw precedes verifyPassword entirely, so at base the route answered 404 whether the current password was right or wrong — it could not tell the two apart.
Cells A and B pin exactly that asymmetry: A requires 200 for a correct password, B requires 400 for a wrong one.
Both were 404 before the change.

19.1 Why the cells mock the database and not the repository

The defect is the repository’s column list, so a cell that stubbed userRepo.getUserById to hand back a passwordHash would have mocked the defect away and passed on broken code. These cells run the real repository, routes, error handler and argon2/bcrypt password service, and mock only ../db. The mock is faithful on the one property that decides the outcome: it returns password_hash only when the SELECT actually named that column, exactly as Postgres would. Cell C pins the mechanism directly — at base zero SELECTs asked for password_hash.
