82. GET /api/anchors/:documentId answers 500, not 404, when its database read fails (KS-1657)

What this changes. KS-1657: getAnchorByDocumentId in originate’s routes/anchors.ts caught every error and returned null, and its only caller, the GET /:documentId handler, reads null as “no anchor on record” and answers 404 with anchored: false. A failed read and a genuine absence were one answer. The catch now logs the same warn line and rethrows, so a fault reaches the route’s own catch and answers its constant 500 INTERNAL_ERROR; zero rows is still the same 404 body. Kam’s ruling, 2026-10-28 07:13 AEDT: “a — Fix it”.
One source file changes: throw err replaces return null in the catch, with a three-line comment naming the ticket and the prior behaviour. The new test is services/originate/src/__tests__/ks1657-an-anchor-read-fault-is-not-a-404.test.ts (8 cells). No tier timing or budget in these documents moves.

82.1 Why 500 and not 503

There is no classifier in originate to reuse. auth classifies infrastructure faults with isInfrastructureDbError (services/auth/src/repositories/dbErrors.ts), which reads pg error codes (classes 08, 53, 57), socket error codes and pg pool messages. originate reads through Prisma (prisma.$queryRaw), whose errors carry other codes and other text, and a search of services/originate/src outside the tests finds no classifier and no service-unavailable error type (the 503 hits are OpenAPI declarations and the load-shedding mount in index.ts). A 503 here would mean writing and proving a new classifier for one route. The route’s existing catch already answers a constant 500, which is inside Kam’s ruling (“500/503”), and the coordinator accepted it: do not import auth’s helper across services for this.
The other shape the ticket names, a discriminated result, was not chosen: it would carry one bit (fault or absence) through a single caller that already has a catch. Letting the error propagate changes one line and leaves null meaning one thing only.

82.3 What the cells prove, and what they do not

The handler, not the database. The cells prove what the route answers when prisma.$queryRaw rejects (an Error or a bare string) and when it returns zero rows or one row, and that the warn line is still written and nothing is written to anchor_store. The rejection is a mock: no real Postgres or Prisma fault, and no Prisma error shape, was produced.
Not measured: how the api-gateway’s /api/anchors proxy relays this 500 (not read), any running stack, and the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), none of which is claimed as passing. The change is not deployed.
