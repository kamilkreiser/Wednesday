118. The NFT certificate list answers only the verified caller’s rows: the query string can no longer name the owner (KS-1836)

What this changes. GET /api/nft/certificates took its owner from the query string (?userId=, default 'user-id'), and a ?walletAddress= selector read any wallet with no owner check. Both mint paths stamp every record 'user-id', so a bare list by any authenticated caller returned every recorded NFT across users and tenants, each with its encryptedKey. A new nftReadGate.ts (+95 lines) holds two pure functions: readerIdentity (the caller’s trimmed userId, or null when it is absent, not a string, blank, or any spelling of the legacy 'user-id') and selectReadableCertificates (only rows whose userId equals the owner, exactly and case-sensitively; each selector can only narrow).
The list handler in nft.routes.ts (+22 -9, plus one import line) reads the owner from req.user, which jwtAuthenticate() sets. A caller with no usable identity gets 403 and no service method runs. Otherwise the service readers run unchanged (the wallet query when a string wallet selector is given, else the user query with the owner id, never the query string’s), and the result goes through the gate. count is the filtered length. An empty selector counts as absent; a selector that is not a string (a repeated parameter) matches nothing and never reaches SQL.
A refusal reads as empty: a selector naming another user’s wallet or id gets the same 200 { certificates: [], count: 0 } a caller with no rows gets, byte for byte, never a 403, so it says nothing about what the wallet holds. One warn line names the caller’s owner id, the selector and the counts; the response names no other owner, and no log carries a key. No spec change: the route already declares 200 and 403 and no query parameters.
Two new test files. ks1836-nft-list-owner-bound.test.ts (+334 lines, 24 cells) mounts the real router on an express app over an ephemeral port, with a test-only middleware standing in for jwtAuthenticate(). The real minting service runs against a fake table that answers its four SQL shapes and throws on any other; its in-memory Map is real (fresh modules per cell); the chain module and the Blockfrost verifier are test doubles. ks1836-nft-read-gate.test.ts (+72 lines, 7 cells) unit-tests the two functions.

118.3 What this does not prove

One route, bound to an owner the records do not yet carry. Known gaps, deliberate: every record written today carries 'user-id', so every real caller lists nothing until the mint paths record the caller; there is no tenant or organisation separation (a record holds no tenant); there is no admin override; GET /api/nft/certificates/:id and GET /api/nft/ipfs/:cid/encrypted are not gated; a listed owner still receives their own rows’ encryptedKey; and connector tokens without a connector id all carry connector:api-key, so they would share one owner once a mint records the caller.
Not run: the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), a running stack, a real Postgres (the user and wallet SQL ran against the fake table only), Node 24, any deploy. The pre-push hook’s own leg count is stated in the pull request.
Not measured: whether any record exists on a box, and what user_id values it holds.
