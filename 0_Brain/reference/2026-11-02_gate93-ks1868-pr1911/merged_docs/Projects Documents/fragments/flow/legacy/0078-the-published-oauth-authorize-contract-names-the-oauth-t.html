89. The published OAuth authorize contract names the OAuth token and the role-or-scope door (KS-1472)

What this changes. KS-1472: the sentence in both /api/oauth/authorize descriptions (GET and POST) read “A token with no scopes satisfies no scope requirement, so a route that requires a scope refuses it (403); a route that requires none accepts any valid token.” It now reads “An OAuth token with no scopes satisfies no scope requirement, so a route that requires a scope refuses it (403), unless the route also admits the caller by role; a route that requires no scope does not refuse it for want of one, though a role check on that route can still refuse it.” The ticket’s three points: (1) a plain login JWT with no scopes passes requireScope on RBAC (the jwt and email branch in middleware/scopes.ts), so only an OAuth token is refused; (2) requireOrgProvisioner (routes/platform.ts) admits SUPER_ROLES by role with no scope; (3) “requires none” read as none of anything, while role, MFA and tenant gates can still refuse.
QA gate round 1 (GO WITH NOTES) on the first published wording, which ended “a route that requires no scope accepts any valid token.”: that clause is false for a route with a role gate. requireSuperAdmin (api-gateway routes/platform.ts, lines 67 to 74) answers 403 on a role outside SUPER_ROLES, and GET /api/platform/tenants runs authenticateToken() then requireSuperAdmin with no requireScope (the file has none). The clause is narrowed to the sentence above: the route does not refuse for want of a scope, and a role check on it can still refuse. Only the role check is named, because it is the one that was read; the MFA and tenant gates the ticket also mentioned were not read and are not claimed. The first published wording, in full: “An OAuth token with no scopes satisfies no scope requirement, so a route that requires a scope refuses it (403), unless the route also admits the caller by role; a route that requires no scope accepts any valid token.”
The wording is edited in services/auth/src/auth.openapi.ts only; docs/openapi/secuura-api.yaml is regenerated, never hand-edited. The ks839 pin STATES_THE_TOKEN and its header moved to the new wording. Point 4 of the ticket (the guard cell forbids one exact wording of the false claim) is left, as the ticket says. Point 5: the ks1210 header said its control checks name too; it reads redirectUris only, so the header sentence was corrected and no toContain('name') check was added, because a bare substring check passes on any text that contains “name” and would claim more than it proves.
