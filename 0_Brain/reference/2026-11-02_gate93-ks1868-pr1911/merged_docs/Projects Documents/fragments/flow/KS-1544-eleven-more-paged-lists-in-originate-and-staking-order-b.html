. Eleven more paged lists in originate and staking order by a unique last key (KS-1544 class)

What this changes. Eleven paged SELECTs gain the table’s primary key as the last ORDER BY column; nothing else in any query changes. originate (src/services/errorTrackingService.ts, the five system_errors reads in getRecentErrors: , id DESC; src/routes/adminConfig.ts, two audit_logs reads: , id DESC, and two rights_holders reads: , id ASC) and staking (src/routes/rewards.ts: svc_reward_claims ORDER BY claimed_at, id and svc_revenue_distributions ORDER BY distributed_at, id). Without a unique last key, Postgres does not promise the same relative order for rows that share the sort value, so a LIMIT/OFFSET window can repeat or skip them between pages. Same class as the platform audit log in tenant-provisioning, which an earlier pull request (#1600, merged) already fixed.
Two new source-text tests, 6 cells each: ks1544-class-originate-paged-lists-order-in-a-total-order.test.ts (RED: every paged read in errorTrackingService.ts, the two audit_logs reads and the two rights_holders reads end in the key) and ks1544-class-staking-rewards-paged-lists-order-in-a-total-order.test.ts (RED: the claims read, the distributions read, and no paged read in rewards.ts is left tied); three controls in each. id is the primary key of all five tables: UUID for system_errors, audit_logs and rights_holders, TEXT for the two staking tables (read in the migrations, not in a database).

.3 What this does not prove

The tests read the sources as text; no query was run against a database. Not touched: services/staking/src/routes/stake.ts (ORDER BY stake_date, the same class, held by another change) and any paged list not in these three files; no census of the rest of the repo was made.
