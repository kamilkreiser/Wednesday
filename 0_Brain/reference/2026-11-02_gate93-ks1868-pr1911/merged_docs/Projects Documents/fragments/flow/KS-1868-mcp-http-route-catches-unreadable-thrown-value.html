. The mcp-server HTTP routes log a constant reason when a thrown value cannot be read, and still answer their constant 500 (KS-1868)

What this changes. In Blockchain/Dev/services/mcp-server/src/http-server.ts, nine route catch blocks read the caught value with const message = err instanceof Error ? err.message : String(err) only to put it in a console.error line: POST /register, POST /register-batch (outer), POST /verify, POST /verify-batch (outer), GET /documents, GET /workflow/:id, GET /connector, GET /policy and POST /generate-package (lines 91, 128, 153, 191, 205, 216, 227, 238 and 292 of the base). That read can itself throw: a revoked Proxy throws on instanceof, and an Error whose message getter throws throws on .message. The route handlers are async under Express 4, so the rejection is not caught and the handler never reaches its res.status(500) line. Each of the nine now logs describeThrown(err), the helper KS-1901 added to this file (it has its own try/catch and falls back to the constant unreadable thrown value), and answers the same constant 500 as before. The change is nine hunks, 1 product file, +9/−18.
What does not change. No status code and no response body changes. For an ordinary Error the log line is the same: the message, unchanged (the new control cells fix that at base and after). Only the log text for a thrown value that is not an Error changes: a thrown string is logged as non-Error string thrown and an object by its field names, never its values (Kam's KS-1346 ruling). The :76 /hash catch is not touched: it echoes the text into its 500 body, which is a different defect class.

.1 What proves it

Red without the change, green with it, the full suite only grows. Red first, by assertion, develop 03977e89a343: only the three new test files applied, product unchanged: 18 passed, 27 failed. The 27 are R1, R2 and R3 of each of the nine routes. 18 fail with AssertionError: expected 200 to be 500 (R1 and R2: the handler rejected, the stub response was left at its default 200) and 9 with AssertionError: expected '[mcp-http] ... failed: S3C...' to contain 'non-Error string thrown' (R3: the thrown string was logged as itself). The 18 that pass are the controls C1 (an ordinary Error logs its message and the answer is the constant 500, without the message) and C2 (the log line keeps its route prefix), so an ordinary Error already gets the after-state at base. With the nine product hunks applied: 45 passed, 0 failed.

Each of the nine hunks was reverted on its own (the log argument read the old way, inline), with the red set written down before the run: exactly that route's R1, R2 and R3 went red, by assertion, 9 of 9 as predicted; the unmutated run was 0 red, and the file was restored to the same sha256 after every run.

.3 What this does not prove
