. The reconciler settles anchor rows that have no transaction hash: it finds their payload on chain or marks them failed, never while this process still drives them, and searches before any give-up (KS-1384 F-b)

What this changes.The gap it closes. A row resting pending with no transaction hash was never looked at by anything: the reconciler selects only rows that name a hash (reconciler.ts), and after a restart nobody is left to drive it. KS-1384 F0 makes more such rows, because an anchor with nothing to spend now waits up to 2 h instead of failing in about 15 s. This entry adds the sweep that settles them (design rev 2 §9 row R6, rev 4 §4.3).
The driving set (services/anchoring/src/drivingSet.ts, new; row R5). The anchor ids this process is still working on: waiting for the wallet lock, holding it, on a retry or wait timer, or inside a batch. processAnchor, processBatchAnchor and scheduleRetry in index.ts hold their ids in it, counted, so a re-POST and a pending wait timer on one id cannot release each other. It lives in memory, so it is empty after a restart, which is exactly when a row has nobody left to drive it.
The sweep (R6). A pending, submitting or submitted row with no hash, not driven here, untouched for 10 minutes, is searched for on chain. If a platform-wallet transaction carries its payload, the row is confirmed with that transaction. If a COMPLETE search finds none, the row is failed: “no transaction found for this event; nothing was submitted”. A search that ran out of time or pages, or could not read a page or a label, decides nothing; the row waits for the next pass. The sweep never builds, signs or submits.
One comparison, on the encoded side. The search keeps a transaction only when its metadata, under the label the row was anchored with (674 single, 675 batch), equals the row’s payload in the exact form the builder writes to chain. This is the same function KS-1384 F0b’s A1 uses (encodedPayloadEquals), so the two cannot drift. Decoding the chain’s form instead can never match a payload with booleans in it.
The shared search (services/anchoring/src/walletLabelScan.ts, new, over a new provider read, fetchAddressTxPage). It walks the wallet’s transactions newest first, from 10 minutes before the row’s creation, and reads only those inside the window. (Round 1 started at the row’s last write; gate 49 showed that missed a member signed before a later wait marker, so R6 and R4 now start at the creation: cells (r4), (l2) and its control, and (r4b) for R4, added after gate 57.) It answers complete, truncated or unanswered, and only complete may decide anything. KS-1384 R2’s own-create lookup will use the same search.
Four guards against sweeping a row that is still alive. (1) A row carrying the submitter’s wait marker is not swept before its t0 + 2 h + 15 min, so a waiter in any process finishes its own horizon first. (2) The sweep does not run until the boot arm’s window has passed since the process’s first pass: the TTL plus its 600-slot margin, about 2 h 10 min, read from the same constants as the arm (the fourth review’s m-3, as ruled after gate 48). Inside that window a transaction signed before the restart may still land, and during a deploy overlap the new process cannot see rows the old one still holds. (3) The driven check runs again after the search. (4) The write expects the row exactly as read: the same status, still no hash, and the same updated_at, so a front-door re-POST landing during the search makes the write match 0 rows (a new expectUpdatedAt in anchorStatusUpdate.ts, compared as an instant, not as text).
Before any give-up (R4). A row with a real hash, past the 24 h window after two answered “not found” passes, is first searched for: a transaction carrying its payload under ANOTHER hash is adopted, and the row is confirmed with it (the restart shape: the row rests on one transaction while an equal one landed). A search that could not decide defers the give-up to the next answered pass; it never forces it.
Not built, on purpose. R7, a failed write for a non-final row carrying a placeholder hash, is PINNED as today’s behaviour (the reconciler never touches such a row) and filed as KS-1870, which needs a census first. R8, re-driving a swept row, is a Kam card and is not built either.

.3 What this does not prove

Stated, not claimed.Blockfrost’s paging of addresses/{address}/transactions on a real wallet, and how long a search takes there: every cell scripts the chain. The search’s bounds (100 per page, 20 pages, 30 s, 10 reads at once) are the design’s choice, not measured.
A real deploy overlap: the boot grace and the marker narrow it; the rule is still no container overlap at recreate and one anchoring process per wallet (the census line).
The four platform suites, a running stack, Node 24 (LTS), any chain or box. Deploy hold: F-b deploys only with F0 and R, after the census, box by box.
