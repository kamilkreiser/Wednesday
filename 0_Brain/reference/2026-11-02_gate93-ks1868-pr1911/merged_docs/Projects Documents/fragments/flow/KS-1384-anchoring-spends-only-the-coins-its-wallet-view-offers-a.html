. Anchoring spends only the coins its wallet view offers, and a write-ahead that did not land now stops the submit (KS-1384 F0a)

What this changes.The wallet view (services/anchoring/src/walletView.ts, new). Per anchoring process it records which of the platform wallet’s coins each transaction spends. A coin a live transaction spends (its inputs and its collateral) is never offered to the next build. After confirmation the chain’s own answer decides what was spent (valid_contract: the inputs when valid, the collateral when not), and that claim lasts 24 h. A transaction past its TTL on an answered tip whose lookup says “not found”, or one the node refused, releases its coins at once; a refusal after a LOST reply does not, because the first submit may still be in a mempool. A stale page that omits a coin never ends a claim. Two passes: pass 1 offers listed, unclaimed coins; pass 2 adds our own unlisted change younger than 10 minutes, and an add-back is dropped after the first refusal of a build that used it.
The builder and the provider (cardano/transaction.ts, cardano/provider.ts). The builder no longer fetches coins: it spends only the candidates it is given, the family outpoint first and once, and returns the inputs, collateral, change output and TTL of the body it signed. A shortage is a typed error raised before signing. New provider reads: every page of the wallet’s UTxOs with an explicit batch size; the live tip, where a slot of 0 or none is not an answer; the spender of an output (consumed_by_tx; null, absent or a failed read are all “unknown”); and a transaction’s label metadata.
Spending through the view (walletSpend.ts, new, wired in cardano/index.ts): two passes, a bounded refetch, TTL settlement only against an answered tip, and a transaction enters the view only after its write-ahead matched.
The write-ahead now stops the submit. anchorSubmission.ts: the single-anchor write-ahead submits only when it matched exactly 1 row. 0 throws WriteAheadDeclined: a newer call owns the row, so nothing is sent, nothing written, no retry, one warn line. null or any other count throws WriteAheadUnavailable before the submit, and the ordinary failed path follows. Before this change a write-ahead that did not land was followed by the submit anyway.
The batch (index.ts): sent, and admitted as one spender over its N rows, only when all N write-ahead rows matched; its confirmation, outside the lock, marks the view. The refusal log line keeps the whole provider reply (status, message, error and body).
A bounded wallet-lock wait (withWalletLockWithin): the same lock, but it rejects with WalletLockTimeout and never runs its callback when the turn has not come in time. Nothing calls it in this change; KS-1384 F0c’s thread-mint does.
Existing tests changed on purpose. ks726-review-f1-f3.test.ts F2: a swallowed write-ahead now stops the submit, so guard 5 never arms (design rev 4 §3.7, cell q3b). ks1385-stored-identity-matches-the-anchored-transaction.integration.test.ts R2 also asserts sent === 1: event 1’s write-ahead matched 0 rows, so its transaction never reached the network; before this it was sent and paid a second fee. Nine updateStatus fakes return the row count, two casts in ks705-submission-idempotency.test.ts are typed to it, and ks1284-attach-point.test.ts passes the builder its candidate coin.

.3 What this does not prove

Stated, not claimed.Anything on a real chain: every cell mocks the provider and never sets a chain key. How Blockfrost fills consumed_by_tx, how often a mint is phase-2-invalid, and how many coins and anchoring processes share the wallet on a box are the read-only census’s, before any deploy.
That one process’s view protects another process on the same wallet: it cannot, and the deploy rule is one anchoring process per wallet.
The four platform suites, a running stack, Node 24 (LTS), and any box: not run here.
