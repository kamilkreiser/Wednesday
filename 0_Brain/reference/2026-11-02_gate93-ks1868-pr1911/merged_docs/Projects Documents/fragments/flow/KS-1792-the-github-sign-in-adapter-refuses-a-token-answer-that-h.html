. The GitHub sign-in adapter refuses a token answer that has no access token, before it calls /user (KS-1792)

What this changes.A sign-in adapter behaviour change. Blockchain/Dev/services/auth/src/providers/social/github.ts, +8/-2. GitHub answers a bad or expired sign-in code with HTTP 200 and an {error, error_description} body, so the adapter’s !ok branch never saw it: it read access_token unchecked and called /user with Bearer undefined, relying on GitHub answering 401 (then Failed to fetch GitHub user profile). It now refuses a token answer whose access_token is not a non-empty string, or that carries an error field, before any profile call, with GitHub token exchange failed (no access token). It logs a warning with the provider’s error string cut to 80 characters. A good token answer and the existing non-2xx refusal are unchanged.
New test ks1792-github-refuses-a-token-answer-without-an-access-token.test.ts, 8 cells, with fetch replaced by a recording stub (no socket): R1 a 200 bad_verification_code error answer, R2 a 200 empty object, R3 a 200 answer whose access_token is not a string, each refused with /user never called; and, added at merge prep (gate 33 F1, F2), R4 a 200 answer whose access_token is an empty string and R5 a 200 answer that carries an error next to a string access_token, each refused with /user never called, and R6 the refusal logs only the error code (the token in the answer is in no logger channel); C1 a good token answer still signs in with the Bearer token; C2 a non-2xx token answer is still the status-only failure. The message a signing-in user sees for a bad code changes from the /user failure text to the token-exchange text: read from the code, not measured end to end.

Gate 33 notes taken as notes and not as changes: F3 (a JSON null body or a non-JSON 200 body is refused before /user, but as a raw TypeError or SyntaxError whose text reaches the client; not a regression, GitHub sends JSON because the request asks for it); F4 (shapes the guard deliberately does not judge: a whitespace-only token and a token_type other than bearer reach /user and fail there; error: null next to a token is refused, which is over-strict and harmless).
