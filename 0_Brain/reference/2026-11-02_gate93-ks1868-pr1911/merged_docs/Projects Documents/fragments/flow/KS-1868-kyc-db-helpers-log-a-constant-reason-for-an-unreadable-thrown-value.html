. Five kyc database helpers log a constant reason when the thrown value cannot be read (KS-1868)

What this changes. In Blockchain/Dev/services/kyc/src/index.ts the catch block of dbSaveVerification, dbGetVerification, dbGetVerificationsByUser, dbGetVerificationStats and dbSaveConsent logged err instanceof Error ? err.message : String(err). For a thrown value that cannot be read (a revoked Proxy, or an Error whose message getter throws) that expression throws inside the catch, so the helper rejected instead of returning its usual fallback. Each catch now reads the value inside its own try and logs the constant unreadable thrown value when it cannot. 35 lines added, 5 removed, one file.
Five new test files in Blockchain/Dev/services/kyc/src/__tests__/, three cells each (15): one control that an ordinary Error still logs its message, and two red cells (a revoked Proxy, an Error with a throwing getter). 10 of the 15 fail at develop, all by assertion. This is tier 1: one caller of dbGetVerificationsByUser is the GDPR erasure cascade (see the next table).

.1 What proves it

Red first, then green, one site at a time. Red first, by assertion: at develop 8126b22bd5aa with only the five test files applied the kyc suite is 73 cells, 63 passed, 10 failed (the 58 existing cells and the 5 controls pass). With the five product hunks it is 73 passed, 0 failed. Before the change the kyc suite is 58 of 58 on a second run; the first run read 57 of 58 with a beforeEach hook timeout in ks849-mock-timer-stale-write.test.ts under machine load, which passes 3 of 3 alone, three times.
One site at a time: with all five hunks applied, reversing ONE hunk turns exactly that site’s test file red (2 of its 3 cells) and the other four stay green, for each of the five sites (5 of 5 killed). Each of the five hunks applied strictly one after the other on the previous result; a copy with one context line changed was refused every time. The product file is byte-equal to develop’s plus the five canonical hunks (sha256 1fe9f599a9d0…).
Types and lint: tsc --noEmit over the service with its tests in the program (the service tsconfig leaves them out): 0 errors, with a planted type error reported once; eslint on the six files: 0 errors, 0 warnings, with a planted file raising two rules. A 4-line hand edit to the tests was needed for this (an unused SITE_ID in three files); it is shown in the pull request.
Callers, read at develop 8126b22bd5aa (not run): see the pull request, section “Caller by caller”. The change turns a rejection into the helper’s normal fallback. Callers without a try go from an unanswered request to an answer.

.3 What this does not prove

The erasure path is read, not run. No new cell calls dbDeleteUserData or DELETE /api/kyc/user/:userId/data, so the change from “the erasure aborts and the bus retries” to “the erasure continues” for a thrown value that cannot be read is taken from the code, not from a test. The thrown values in the cells are written by the test author (a revoked Proxy, a throwing getter); that a real one of this kind occurs was not shown. No real PostgreSQL, no boot of the service, no other site in the file was touched, and no site of the same class outside it. The four platform suites and any deploy were not run.
