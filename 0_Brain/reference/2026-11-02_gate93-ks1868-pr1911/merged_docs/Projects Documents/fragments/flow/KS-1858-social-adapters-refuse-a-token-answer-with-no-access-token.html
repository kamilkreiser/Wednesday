. The Google, Facebook, LinkedIn and Microsoft sign-in adapters refuse a token answer with no access_token (KS-1858)

What this changes. Four sign-in adapters in Blockchain/Dev/services/auth/src/providers/social (google.ts, facebook.ts, linkedin.ts, microsoft-personal.ts) read access_token from the token endpoint's answer without checking it, so a 200 answer that carried none went on to the profile call as Bearer undefined (Facebook: access_token=undefined in the profile URL). The GitHub adapter has refused such an answer since KS-1792. Each adapter now reads the answer as access_token?: unknown; a missing, non-string or empty value is logged (the provider name only, no body) and thrown as <Provider> token exchange failed (no access token) before any profile call. Product bytes: +6/-1 in three adapters, +5/-1 in Google. Unchanged: the !tokenRes.ok branch, the profile call and its mapping, the timeout wrapper and every other error text.
Four new test files, one per adapter, 5 cells each: three red cells (an empty body object, a non-string access_token, an empty-string access_token) and two controls (a good answer still signs in; a non-2xx answer still gives the status-only failure). Four held Spark passes applied with strict git apply --check -p1 (rc 0, and rc 1 on a copy with one line's content corrupted); there is no hand edit. Open question for the gate, not decided here: unlike github.ts, these four guards do not also refuse a 200 answer that carries an error field. Facebook's token travels in the profile URL's query string; that is pre-existing and unchanged.

With the four guards: 20 of 20 pass.
Whole auth suite on a scratch merge with develop d786daa4fc9b (vitest, --maxWorkers=2, load1 at or below 9 at the start): untouched develop 113 files / 1365 cells, 1357 pass, 2 fail, 6 skipped (a second run: 1307 / 2 / 56); with the change 117 files / 1385 cells, 1385 pass, 0 failed, 0 skipped (a first run: 1383 pass, the same 2 failed). The 2 failures and the skipped cells are on develop itself and move between runs: the two ks949-platform-admin-seed-identity seed-site cells hit vitest's 5 s default (5002 ms), and a cold-start hook timeout (10 s) skips every cell of whichever file starts slowest (auth.integration in one run, ks1005-change-password-reads-the-hash-it-verifies in another). Alone with --testTimeout=60000 --hookTimeout=60000: ks949 31 of 31 on develop and 31 of 31 with the change, auth.integration 56 of 56 on develop.
Static: tsc --noEmit -p of the service (production code): 0 errors. The test-file type ratchet (hook leg 16) for auth: 168 files examined, 117 under __tests__, 42 errors, 42 in the baseline, 0 new; no error names a new file; a planted type error was reported once. eslint on the 4 product files and the 4 new tests: 0 errors, 0 warnings; a planted file raised two rules.

.3 What this does not prove

Four guards, not a provider test. The four sign-in error paths were not exercised against a real provider: the tests replace fetch with a recording stub. Whether any real provider answers a 200 with no access_token, or with an error field, is not measured. The error-field clause that github.ts has is not added here (open question for the gate). Apple's id_token read is a different ticket (KS 1617, item 8).
Not run: the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), a running stack, Node 24 or any LTS Node, npm ci on the merged lockfile, any deploy. Two of the four Spark runs (Google, Microsoft) were harness false-fails at the whole-suite step on the ks949 5 s timeout; the suite runs above are this change's own.
