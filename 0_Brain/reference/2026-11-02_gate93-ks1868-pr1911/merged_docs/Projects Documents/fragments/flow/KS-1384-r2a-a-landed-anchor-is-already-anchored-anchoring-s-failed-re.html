. The document anchor retry route never pays again for an anchor that already landed, anchoring answers a failed read with 503, and the route’s 409s are declared (KS-1384 R2a)

What this changes.A landed anchor is “already anchored” (QA gate 58, G58-F2). Before this, the retry route (POST /api/documents/{id}/anchor) read a confirmed anchoring row as “nothing in flight” and posted again; anchoring’s upsert resets a confirmed (document_id, network) row and submits it again, a second fee for a document already on chain. Gate 58 reproduced it after a holder crashed post-submit (Q3a) and for an anchor_failed blob whose row later confirmed (Q3b). Now (services/reanchorInFlight.ts) a confirmed row on the route’s network with the document’s hash (both normalised: sha256: stripped, lower case) answers 409 “This document is already anchored (<anchorId>)” with error.anchorId, and nothing is posted. A missing or unreadable hash or network counts as anchored (fail toward not paying); a readable different hash, or another network, proceeds as before.
Anchoring’s failed read is 503 (G58-F3) (services/anchoring/src/index.ts). GET /api/anchors/document/{documentId} used to answer a database read that threw, or a database that was not available, with the same 404 “No anchors found” an absent document gets, so originate’s retry route read it as “nothing in flight” (gate 58’s Q4c). Now that read answers 503 with fixed text (no database error reaches the caller); originate turns it into its own 503 with nothing posted. The KS 1822 ownership probe keeps its fail-open rule; the by-id route’s document-id fallback is unchanged.
The 409s are declared (originate.openapi.ts and the generated docs/openapi/secuura-api.yaml). postDocumentsByIdAnchor declared no 409; it now declares one 409 naming all four messages (the fourth is R1 round 3’s “may have landed”, merged in), and its 503 declares the Retry-After header (60 when anchoring could not be read, 600 when a submit’s outcome is unknown). With round 3 merged in, a document that records an unknown-outcome submit and has a confirmed row for this content answers R2a’s “already anchored”, not “may have landed”: the definite fact first (Wednesday, 2026-10-31 17:44:28Z; cell (order)).
Who sees a different answer: a retry of a document whose anchor already landed is refused (409) instead of paying again; a caller of GET /api/anchors/document/{documentId} gets 503 instead of 404 while that read fails.

.3 What this does not prove

Stated, not claimed.QA gate 68 (GO WITH NOTES) measured two more. (G68-F1) This rule compares the row’s network, which anchoring writes from its OWN CARDANO_NETWORK, with originate’s: where the two services are configured differently, a landed anchor reads as “another network” and is paid for again. R2b drops that comparison, and the deploy hold requires the two values to be equal on each box. (G68-F3) Anchoring’s upsert never refreshes content_hash, so a confirmed row with a different hash is paid again on every retry, as before R2a (KS 1919). A real anchoring service against a real database fault, real chain state, the four platform suites, a running stack, Node 24 (LTS) and any chain or box: not run here.
The one resolver, the own-create lookup, the loose mint guard, createAttempts and the verify heals are R2b’s. The retry route answers 409 for a landed anchor but does not heal the document’s blob; the resolver does that on read (R2b).
