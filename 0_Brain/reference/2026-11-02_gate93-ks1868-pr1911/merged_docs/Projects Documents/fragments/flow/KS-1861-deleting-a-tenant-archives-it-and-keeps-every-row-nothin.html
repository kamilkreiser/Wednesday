. Deleting a tenant archives it and keeps every row; nothing is erased and no database is dropped (KS-1861)

What this changes. DELETE /api/tenants/:id (services/tenant-provisioning/src/index.ts) is reached through the gateway’s DELETE /api/platform/tenants/:id. Until now it deleted the tenant’s registry rows from the platform database, each in an empty catch, then the tenant row. It then ran DROP DATABASE on a per-tenant database name whatever PROVISION_PER_TENANT_DB said, and answered { success: true, deleted: true }, while the tenant’s users, documents and vault entries stayed in the application database. Kam ruled “Archive, not erase”. So the route now sets the status to archived and keeps every row, and the answer says so: { success: true, deleted: false, archived: true, status: "archived", message }.
No database is dropped and no row is deleted, under either value of PROVISION_PER_TENANT_DB. The status change and its tenant_archived audit row (slug, previous status, erased: false) commit in one transaction. If either fails, both roll back and the answer is the constant 500; a tenant_archive_failed row is then attempted on a best-effort basis (a failure of that write is only logged). The update only matches the status it read, so a concurrent status change answers 409 instead of being overwritten.
Start statuses (Kam, 2026-11-01 10:05:44 AEDT, card secuura-ks1861-archive-from-which-status-1101: “b — As (a), and archived can go back to suspended”): provisioning, active and suspended archive. An already-archived tenant answers 409 “Tenant is already archived”. 404 and the {"confirm": true} requirement are unchanged.
Reversible through the API. The status route (PATCH /api/tenants/:id/status) now also allows archived → suspended, and suspended → active as before. archived → active in one step stays refused with 409 (Kam’s KS 1860 ruling). The admin portal still asks “This cannot be undone” and discards the answer, and its audit-log page colours tenant_deleted but not the new tenant_archived (filed as KS 1912 and KS 1913). The portal is not changed here.
Status reads at start-up stay as built (Kam, 2026-11-01 10:05:24 AEDT, card secuura-ks1860-status-refresh-fails-at-startup-1101: “a — Keep it as built and say so”). Where MULTI_TENANCY_ENABLED is on: if the platform database is down when originate starts, originate serves every tenant, suspended and archived ones included, until a status read succeeds. A tenant suspended after the last good read is served for as long as the database stays down. This is not a regression: before KS 1860 nothing refused a suspended tenant at all.
