. A suspended or archived tenant is refused by originate’s existing check, and tenant status changes follow the documented order (KS-1860)

What this changes. extractTenantContext (packages/shared/src/db/tenant-context.ts) answers 403 “Tenant is suspended” or “Tenant is archived”, but that branch could never run. It reads getTenantStatus, which read the pool-config map, and refreshConfigs filled that map only with active and provisioning tenants. refreshConfigs now records every tenant’s status in a map of its own, and getTenantStatus reads that map, so the 403 fires. The check is mounted in originate only, and only where MULTI_TENANCY_ENABLED is true (the compose default is false). Each originate process re-reads the map every 60 s, so a status change takes effect within one successful refresh. That holds only while the platform database answers. If it is unreachable at start-up, no status is known and every tenant is served until a read succeeds. If it goes down later, the statuses last read stay in force, so a tenant suspended after the last good read is still served (and one reactivated is still refused). This change does not alter that behaviour, and Kam ruled to keep it (2026-11-01 10:05:24 AEDT, card secuura-ks1860-status-refresh-fails-at-startup-1101: “a — Keep it as built and say so”).
Unchanged for a suspended or archived tenant: getPool still falls back to the default pool, as it does for an unknown tenant. So originate’s cross-tenant reads, which call getPool for a document’s home tenant, behave as before: public verification, the admin document lookup and the template clone. Sign-in, the gateway and the other services are not touched. There is no platform-admin exemption: a super-admin acting on a suspended tenant through X-Tenant-Id also gets originate’s 403.
Status moves follow the documented order. PATCH /api/tenants/:id/status is reached through the gateway’s /api/platform/tenants/:id/status, which forwards its answer. It now allows provisioning → active, active → suspended, suspended → active and suspended → archived (KS-1861 later adds archived → suspended, on Kam’s ruling b). Any other move answers 409 CONFLICT “Cannot change tenant status from <current> to <requested>” and changes nothing, with no audit row. That includes archived → active, active → archived and a same-status request. A well-formed id with no tenant answers 404. The check and the write are one conditional UPDATE. The published spec gains the 409.
What the admin portal shows. The client list offers Activate, Suspend and Archive whenever the tenant’s status differs, and it discards the answer before reloading. So a refused move, such as Archive on an active tenant, shows as no change and no message. The portal is not changed here.
