. The social sign-in callback no longer echoes the token in an exchange error (KS-1885)

What this changes.Blockchain/Dev/services/auth/src/routes/auth.ts, +55/-6. The callback’s catch around provider.exchangeCode(code) put the error’s message into its 400 unless it was a SyntaxError (KS 1791). A provider token answer whose access_token holds a newline makes fetch throw a TypeError that quotes the whole Bearer <token> header, so the token reached the client (github, google, linkedin, microsoft_personal) and the error log (the error handler logs every error’s message). A JSON null token answer echoed the runtime’s internal text (all six adapters).
Now only text our own code wrote reaches the client: an AppError (the adapters’ timeout and unreachable texts), or exactly one of the adapters’ own texts by two anchored patterns. Anything else answers 400 BAD_REQUEST OAuth authentication failed: the provider answer could not be read, the KS 1791 text. The status is unchanged. One new warn line names the provider and an identifier-shaped error class, never the message. A thrown value with an empty message now gets the constant too (it answered invalid authorization code); a thrown value whose own property reads throw still answers 500, as before.
POST /api/auth/social/link answers exactly what it did (500 INTERNAL_ERROR, or the AppError’s own 503). Its exchange is now wrapped: our own texts are rethrown, and anything else is logged by provider and class and replaced by a neutral Error, so the error log no longer carries the token.
