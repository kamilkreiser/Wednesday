KS-1384 R2a: a landed anchor is “already anchored”; anchoring’s failed read is 503; the retry route’s 409s declared

What to know.POST /api/documents/{id}/anchor answers 409 “This document is already anchored (<anchorId>)” and posts nothing when anchoring holds a confirmed row on the route’s network with the document’s hash (normalised). An unreadable hash or network counts as anchored; a different hash or another network proceeds.
GET /api/anchors/document/{documentId} answers 503 (fixed text) when its database read fails or the database is down, never the 404 “No anchors found”; originate turns that into its own 503 with nothing posted.
postDocumentsByIdAnchor now declares one 409 naming all four messages (R1 round 3’s merged in), and its 503 declares Retry-After. Deploy hold: R2a deploys only with F0, F-b, R1 and R2b, after the census, box by box, and only where the deploy seat has read CARDANO_NETWORK of originate and of anchoring on that box and found them equal (QA gate 68, G68-F1: where they differ, this rule read every landed anchor as “another network” and paid again; R2b drops the network comparison).
Not measured here.A real anchoring service against a real database fault, the four platform suites, a running stack, Node 24 (LTS), any chain or box.
