Job 04 records a scan as failed when trivy reports neither Results nor ArtifactName — KS-1274

What to know. A trivy that exits 0 and prints a bare {} used to be recorded as a clean image. KS 1136 covered a non-zero exit and unparseable output; it did not cover a parseable empty object. The guard at Blockchain/Testing/jobs/04-container-trivy.sh:115-120 now records scan-failed when stdout carries neither Results nor ArtifactName.
Both keys must be absent. Requiring Results alone — which is what the ticket suggests — fails a genuinely clean image that reports only ArtifactName. The suite pins this with a control cell that stays green in the patched and reverted states alike.
The three suites' clean stub moved from {} to {"Results":[]} in the same commit, because under the new guard {} is the failure case. fail.txt accepts bare and nores alongside empty and partial.
Gotcha when you run this locally. (1) docker and trivy are never run. All three suites put stubs on a private PATH; the trivy stub reads $root/fail.txt. So a green run here says nothing about the real scanner — a live run is owed and the ticket stays open.
(2) The exec bit. This repo sets core.filemode=false, and git apply does not restore the executable bit on disk. 04-container-trivy.sh is 100755 in the tree but lands non-executable after a patch, so the suites cannot invoke it until you chmod 755 it. Because filemode is off, git diff shows no mode change either way — read the mode off the committed tree with ls-tree, never from git status.
