The api-gateway front door answers 503 when an API key cannot be checked; every hand-built gateway fetch is bounded — KS-1240

What to know. A presented sk_ key whose check could not complete (no complete answer from the security service within 5 s, an unreadable body, or a 5xx, 408 or 429, including its own 503 'Unable to verify key') now answers 503 SERVICE_UNAVAILABLE on required and optional mounts and is never cached. It used to answer 401 Invalid API key, and the security service’s 503 was negative-cached for 30 s. A rejected key keeps every answer it had (401 plus 30 s cache; the KS-1207 fall-through on optional mounts).
The connector exchange is bounded at 5 s and stays fail-closed: no Bearer is forwarded and a Bearer-only upstream answers 401, as before. Nine hand-built forwards are bounded at 60 s, the generic proxy’s bound; a body cut off by the timeout is the route’s own 502 instead of the upstream’s status with {}; a batch item whose body never arrived fails instead of succeeding empty; generate-package reads the package before writing the zip headers.
Authority for the 503: Kam’s rulings on cards secuura-ks888-revoke-validate-on-failed-save (a) and secuura-ks1370-validate-when-the-revoke-check-cannot-read (a).
Not measured here. Node 24 (host Node 26.8.1 only, no Docker in this lane); a real security or auth service (the upstreams are stubs); any running stack.
The four platform suites (Schemathesis, Akto, Playwright, Performance/k6) are not claimed as passing. The change is not deployed.
