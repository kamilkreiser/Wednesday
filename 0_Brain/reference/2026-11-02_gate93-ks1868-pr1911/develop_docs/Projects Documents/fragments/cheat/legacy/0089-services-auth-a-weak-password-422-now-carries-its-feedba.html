services/auth: a weak-password 422 now carries its feedback in the published array shape (AppError prototype fix) — KS-1467

What to know. Behaviour change: the registration, password-reset and change-password routes answer a weak password with a 422 that now carries error.details as an array, one { code, path, message } per feedback line, which is the shape the published ValidationErrorResponse already promises (round 1 sent { feedback: [...] }; the gate caught it and round 2 conforms). The cause was the services/auth AppError constructor resetting every subclass to the base prototype, so the error handler’s instanceof ValidationError branch never ran; it now uses new.target.prototype. The route for a role not permitted on /register has no details and is unchanged.
The feedback is fixed strings from checkPasswordStrength and cannot echo the candidate password; cell N1 and the three route E cells prove that and fail if a route is made to echo (nine mutants, three per route, each turns red only its own route’s cells). The packages/shared half is separate. A local model wrote the first patch; it is applied unchanged.
Not measured here. Whether the front end shows the details, a running stack (the routes ran with the repository and database replaced), and a Node 24 LTS run (the host is Node 26.8.1).
The four platform suites (Schemathesis, Akto, Playwright, Performance/k6) are not claimed as passing. The change is not deployed.
