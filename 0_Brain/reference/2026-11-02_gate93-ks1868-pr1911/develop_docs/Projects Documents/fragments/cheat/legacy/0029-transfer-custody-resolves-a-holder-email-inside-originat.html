transfer-custody resolves a holder email inside originate, so S's connector can name a holder by email — KS-1402

What to know. POST /api/documents/:id/transfer-custody with newHolderEmail no longer calls auth's GET /api/users/lookup with the caller's credential. Originate hashes the email (auth's own toLowerCase().trim()) and reads users on the request's db with the tenant bound. Platform S's connector carries no users:read, so it was refused 403 every time; it now resolves.
The guard to watch is the tenant. A connector can now reach resolution, so the bound tenant predicate is what keeps it out of another tenant: a tenant-B-only email is 404, byte-equal to no user at all (cells C2 and C2b). The act's own gate (documents:transfer-custody or an allowed role) is unchanged and runs first.
Answers. Malformed email 400 (same body as before); no user in your tenant 404 RECIPIENT_NOT_FOUND; originate without a lookup key 502 BAD_GATEWAY, labelled. The old 401/403/502 that came from the lookup (KS 739) cannot occur on this route any more.
Gotcha when you run this locally. (1) Originate now needs PII_LOOKUP_HMAC_KEY. Without it every email transfer answers 502, and a unit suite that drives the email path must register a key first: that is the one line ks697 gained.
(2) Run the WHOLE suite (npm test in services/originate): 97 suites / 1096 tests / 0 failed (base 96 / 1093), measured 2026-10-09 on Kamils-Mac-Studio, node v24.7.0. Three per-file runs were green while the whole suite was not: the KS 1061 guard requires every @secuura/shared mock to be () => require('./helpers/sharedModuleMock').makeSharedMock(, matched as text, so a block-bodied factory still fails it.
(3) A tamper that does not compile reds nothing. ts-jest type-checks, so a tamper that leaves a variable unread (TS6133) is a load failure with 0 passed and 0 failed, not a red. Read the executed count before calling a tamper proven.
