The published document operations state the reserved metadata keys, and the real-Postgres file pins the strip before the hash — KS-1537

What to know. Four operations now carry one sentence on the keys a caller cannot choose. POST /api/documents silently STRIPS data.versionedById before hashing. POST /:id/version, /:id/sign-cert and /:id/sign-wallet reserve versionAction, versionedAt, versionedById and parentDocumentId: the server sets them after metadata, so a value you supply is overwritten. The pin is ks1537-the-contract-states-the-reserved-metadata-keys.test.ts; the yaml is regenerated, never hand-edited.
ks1508-a-planted-versionedbyid-is-not-stored.integration.test.ts goes from 6 to 12 cells on a real Postgres, in both tenancy modes: hash and hash2 pin the strip to come BEFORE the content hash and the thread-token hash; the certify cells plant the key in POST /api/certifications/issue as JSON, form-encoded and as a __proto__ payload. The route needs no stubbed collaborators; the old header said it did.
The integration cells need a migrated database and three URLs (TEST_DATABASE_URL, TEST_APP_DATABASE_URL as secuura_app, and TEST_PLATFORM_DATABASE_URL for pool mode). Run the migration runner with the main URL only, so the platform-routed file 003 lands in the one database. N-4 (should the certify response, record and hash input also drop the value) is a decision and is not built.
The erase-connector description no longer says a writer can still hide a derivative “until the server sets versionedById”: it says the server sets it itself, a value supplied on create or on a certify is dropped, and a row stored before that change keeps whatever it was written with. One guard cell in the pin keeps the stale phrases out and the corrected sentence in. The same stale claim is still in a code comment in connectorOrganisationErasure.ts (line 209), reported and not edited here.
