103. /api/oauth/authorize refuses a scope that is not a string with 400 invalid_request, instead of a 500 (KS-1219)

What this changes. Behaviour change: on the authorize route a scope that is present and is not a string now answers 400 invalid_request. That covers an ARRAY (a repeated query parameter ?scope=a&scope=b, or a JSON array in the POST body), which used to answer 500 server_error because parseScopeString calls .split on it; and a JSON null, 0 or false, which parseScopeString treated as an absent scope (the default allow-list, KS-822 F-4) and which now answer 400 too. Only a JSON body can carry those scalars; query-string and form values are strings or arrays. Wednesday accepted the tightening on 2026-10-28. In services/auth/src/routes/oauth.ts, resolveAuthorizeClient returns the existing invalid_request message (description “scope must be a single space- or comma-separated string”) before it calls parseScopeString, so no published message changes. A local model (the Spark, DeepSeek V4 Flash, pass ks_1219_p1) wrote the patch; its checker passed 7 of 7 and the patch is byte-identical to the drafter’s golden. It was applied here strictly and unchanged.
The product file changes +10 / −0 (a three-line comment and a seven-line guard). The new test is services/auth/src/__tests__/ks1219-authorize-refuses-an-array-valued-scope.test.ts (vitest, 9 cells), which drives the real router on a loopback listener with the same mocks as ks804-authorize-get-post-agree-per-rule.test.ts. Its cells cover the array carriers (R1 to R3) and the JSON null, 0 and false edge (R4, three cells, added at the merge prep on the gate’s note), with three controls (C1 to C3). This is an authentication-surface change. No tier timing or budget in these documents moves.

103.2 What the cells prove, and what they do not

The array carriers and the JSON null, 0 and false edge, through the real router with its collaborators mocked. R1 to R3 prove that each array carrier is refused with 400 invalid_request and that approving with an array mints no authorization code; R4 proves the same for a JSON null, 0 and false scope on approve; C1 to C3 prove a single string scope, an absent scope and a denied string scope behave as before. They do not exercise real clients, tokens or a database.
Not covered: the other authorize parameters. A repeated state or code_challenge on GET still answers 500, JSON arrays for them on POST are coerced rather than refused, and scope is still neither deduplicated nor bounded; that is a separate follow-up ticket (KS 1797). Not measured: a running stack, the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), a Node 24 LTS run, and any deploy. None of them is claimed as passing.
