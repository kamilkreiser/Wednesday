21. An unreadable connector allow-list refuses the create with 503 instead of granting everything (KS-1256)

What this fixes. The connector allow-list is read out of platform settings to decide whether a caller may create a restricted document type.
When that read failed, the parse left connectorConfig = {} — and an empty config reads as no restriction.
So every restricted connector became unrestricted precisely when the platform could not tell what the restrictions were.
This is the same fail-open class KS-1233 closed for the TTL trigger, still open on this path.
The read now fails closed: an unreadable allow-list answers 503 SERVICE_UNAVAILABLE and the create is refused until the configuration can be read.

21.2 Two unreadable paths that do NOT share a mechanism, and why a catch cannot close one of them

Driven against real ioredis 5.11.1 and a real TCP RESP server, not a mock. In the unavailable state getNotificationSettings resolves null without throwing — it reads an empty in-memory store (services/redis.ts:671-678). A catch never observes a resolved null, so the availability test has to come before the read rather than inside the catch. That is why the fix is two edits and not one.
Separately, fallbackMode is set on a sustained runtime outage by retryStrategy at services/redis.ts:78, which carries no NODE_ENV guard. Driven under NODE_ENV=production the branch fires identically, so production reached the fail-open state on a runtime blip despite refusing to START without Redis. The production cell exists to pin that.

21.3 Red-first, by assertion

Six cells, all six green at head. At base, 4 of the 6 are RED — the two CONTROL cells are green at base by design, because they pin behaviour this change does not touch (403 on a malformed container, and a readable allow-list still restricting). A control that reddens with the fix would be testing the fix, not guarding it. Measured by Seat E 6th and carried forward unchanged.

21.4 One collateral test, re-pointed deliberately

ks1195 exists to test the no-Redis degrade path: it asserts isRedisAvailable() === false as a precondition, then used to pin that a connector create still answered 201 there. Both promises cannot hold — fail-closed and “201 while Redis is down” are contradictory. Two assertions were re-pointed to [503, 503, 429, 429, 429] and toBe(0), and that cell's title now states the new contract. These are the only assertion changes in this work. The DEGRADED / redis-not-ready assertions are untouched.

21.5 What this costs, and whose decision it was

The cost is stated rather than discovered: while Platform K’s Redis is down, Platform S cannot create documents through a connector — they answer 503. That was put to Kam as secuura-ks1256-redis-outage-stops-connector-creates-1006 and ruled a, “Accept: fail closed (503) during a Redis outage”: “Security first: no restricted document type slips through while the allow-list cannot be read. Cost: Platform-S cannot create documents while K’s Redis is down.”

21.6 Residue, named and NOT fixed here

The other readers of the same settings key were not audited: admin.ts:1119, :1144, :1154, health.ts:52 and verification.ts:1283. Each may carry the same fail-open shape. They are named here so the gap is on the record, not widened into this ticket. The fresh-install gap in 21.1 row 3 stays open by Kam’s ruling b.
