99. Tenant creation says when the tenant’s vault key was not confirmed: a keyPending flag on the 201 and a log line for the not-ok answer (KS-1240, Kam’s option b)

What this changes. Kam ruled decision card secuura-ks1240-key-fail-answer-measured-1028 as option b, an explicit “key pending” flag, after the read-only vault-key trace. POST /api/tenants (published as POST /api/platform/tenants) keeps answering 201 and keeps its writes. The 201 body gains keyPending, appended after every existing field: false when the key service answered success: true, true when it was unreachable, did not answer within the bound, answered a body that is not JSON, or answered not-ok. Only when true the body also carries keyPendingMessage.
The log line. A key service answer that was not success: true used to write no log line at all. It now writes one carrying the error code and message only (capped at 200 characters) with the tenant id and slug; nothing else the key service sent is copied. The existing failure line keeps its text and gains the tenant id and slug.
The success body is otherwise byte-identical, and the metering key keeps its own signal (meteringApiKey: null and its own log line): a failed mint does not set keyPending.
Not in this change. 99.3 What the cells prove, and what they do not

The answer and the contract, not production. The success and failure bodies are compared as raw text against strings recorded from this route before the change, so no existing field can change unnoticed. One cell sends a key service answer that has no success field and carries a key hash: the route must read it as not confirmed, set the flag and store no hash. The contract cells read docs/openapi/secuura-api.yaml and check that the real bodies conform to the published 201 schema and that it declares the flag.
