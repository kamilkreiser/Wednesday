77. countUsers answers a database fault like listUsers, so a faulting count is a 503 and not a raw 500 (KS-1769)

What this fixes. Blockchain/Dev/services/auth/src/repositories/userRepo.ts: countUsersInner had no try/catch, so a database fault in the COUNT answered a raw 500 (INTERNAL_ERROR) on GET /api/users and GET /api/users/admin/list. Both routes call listUsers and then countUsers on one request, and listUsers has answered 503 since KS 1484, so with the list answering and the count faulting the route still came back 500. countUsersInner now carries a spelled-out copy of the list’s catch: the query and the parse are inside the try; an infrastructure fault (isInfrastructureDbError) becomes ServiceUnavailableError (503, SERVICE_UNAVAILABLE); anything else is rethrown as the very same error; the failure is logged as DB countUsers failed with the error and its code. The WHERE builder stays outside the try. A behaviour change on the user-listing path.
Twelve cells are appended to services/auth/src/__tests__/ks1186-userrepo-fromrow-sites-are-awaited.test.ts (23 → 35): four red-first, three controls on the result path (a non-infrastructure fault is the very same error, a clean count returns the number and logs nothing, an empty result counts 0), and five controls that the filters still reach the query as the same SQL and the same bound values.
The two search clauses in those filter controls pin today’s ILIKE text. KS 1168 (the encrypted-column search) rewrites them on purpose and has to update those cells in the same change.

77.3 The route, with no database

Row LISTOK_COUNT_ECONNRESET, over real HTTP. The real router (routes/users.ts) and the real error handler run. db.query answers the list with an empty page and rejects the COUNT with ECONNRESET, and authenticate passes a SYSTEM_ADMIN identity. Before the catch, GET /api/users and GET /api/users/admin/list both answered HTTP 500, INTERNAL_ERROR. After it, both answer HTTP 503, SERVICE_UNAVAILABLE and log DB countUsers failed with the code.
The driver sits outside the repo and edits nothing; the “before” run loads the base userRepo.ts from a copy through the module cache. A first attempt assigned its seams onto the modules and got HTTP 401 on both routes, because esbuild’s getter-only exports ignore assignment; the seams are now installed by replacing the cached module’s exports, with the database seam first.
