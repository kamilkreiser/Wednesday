54. ApiKeyCreateRequest declares the rotate flag that POST /api/security/keys acts on (KS-1434)

What this fixes. The create handler for POST /api/security/keys accepts rotate (z.boolean().optional().default(false) in the create schema in services/security/src/index.ts, added under KS 577). With a connectorId it retires that connector’s other active keys once the new key is minted.
The published request schema, ApiKeyCreateRequest, listed eight properties and not rotate, so an integrator reading the contract, and a spec-driven caller such as Schemathesis, could not see the field or send it.
rotate is now declared on ApiKeyCreateRequest in security.openapi.ts as an optional boolean with default false and a description of the retire effect. docs/openapi/secuura-api.yaml is regenerated by npm run generate-openapi, never hand-edited.

54.1 Scope: the published contract only

What is and is not carried. A declaration and nothing else: index.ts, requestSchemas.ts and every other runtime file are untouched. No service source imports security.openapi.ts; git grep finds two non-test references and both are comments, so the OpenAPI generator and tests are its only importers.
Left open, not decided here: the spec and the runtime schema are still written twice and can drift again. docs/S-K-OWNERSHIP-CONTRACT.md still describes a rotate that leaves the old key untouched; that file is outside this change and is raised as a question.

Document and yaml, not runtime. They show that the document the generator renders, and the committed yaml, declare rotate as an optional boolean with default false whose description names the retire effect, the connectorId it needs, API_KEY_ROTATION_GRACE_SECONDS and priorKeysRevoked.
