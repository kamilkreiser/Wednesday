117. The anchor retry route checks who may re-anchor, and refuses a revoked or deleted document (KS-1814)

What this changes. POST /api/documents/:id/anchor (originate routes/documents.ts, the retry route) spends an anchoring fee and rewrites the document’s status. Before this change it checked only authentication and the caller’s tenant. It now refuses, in this order and every time before the anchoring call: a caller with neither a document-write role nor the documents:write scope (403, before the document is read); a caller who is not a platform admin, the owner or the creating connector (the same 404 an absent document gets); a revoked or deleted document (400). The write now passes preserveTerminalStatuses, as the create path does.
Platform S keeps working: its connector key carries documents:write and is the creating connector of the documents it re-anchors, ownerless ones and /version-minted children included (cells P1, the Platform S cell, and P1b, P2, P4). The S organisation-merge edge is refused, as Kam ruled on 2026-10-20 (card secuura-ks1688-org-merge-edge-which-side-1020, option a). An OWNER-role user re-anchors only its own documents (cells Q4, Q4b, Q5).
Tests: a new cell file ks1814-anchor-route-needs-write-role-and-document-access.test.ts, 28 cells, running the real isAllowedByRoleOrScope and hasScope with a mocked repository and a mocked anchoring service. The ks520 and ks1385 anchor-route fixtures gain an owner, with their assertions unchanged, and the KS-1293 hermetic manifest lists the new file.
