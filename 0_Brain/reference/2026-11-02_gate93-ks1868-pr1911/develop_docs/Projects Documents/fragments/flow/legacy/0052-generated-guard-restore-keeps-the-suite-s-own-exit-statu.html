63. generated_guard_restore keeps the suite's own exit status when a cleanup is chained in front of it (KS-1738)

What this fixes. systemTest/__tests__/support/generated_guard.sh’s generated_guard_restore() captures the suite’s exit status as its FIRST statement (local rc=$?) so a failed restore can re-raise it. That works when the guard IS the EXIT trap. It does not work when a suite chains its own cleanup in front of it: the chained command runs first and overwrites $?.
systemTest/__tests__/bootstrap_login_diagnosis.test.sh did exactly that — trap 'stop_stub; generated_guard_restore' EXIT. stop_stub succeeds, so $? was 0 by the time the guard read it, the guard took its “the suite itself passed” branch, and a suite that exited 3 was reported as 1. LOW severity, and stated as such: a failed restore is still reported and still exits non-zero, and the runner still scores the suite as failed — only the distinction between “the suite failed” and “the restore failed” is lost.
The ticket listed three shapes and chose none. Shape 3 (“leave it”) was ruled out by Wednesday; shapes 1 and 2 together were chosen by the builder and ratified. Shape 1 is the fix (an optional status argument), shape 2 is the constraint written down at the guard’s header and at the chained call site — because the ticket’s own risk statement is that chaining is the natural thing for the next suite to do.

63.1 The shape, and why the ticket's own suggested call-site form was NOT used

Opt-in, so no existing caller changes behaviour. generated_guard_restore now PREFERS a status passed as its first argument over $?. local rc=$? stays the first statement — any command before it, [ included, overwrites $? — and the argument is applied immediately after. With no argument the behaviour is byte-for-byte the old one, which is why the two inline copies and every plain-trap caller are untouched.
The chained call site becomes trap 'rc=$?; stop_stub; generated_guard_restore "$rc"' EXIT: the cleanup still runs FIRST, and the real status is handed in. The ticket’s literal shape-1 suggestion was trap 'generated_guard_restore $?; stop_stub' EXIT, and that was deliberately not used: on a failed restore the guard exits, so putting the guard first would mean stop_stub never runs on exactly the path the guard exists for — it would leak the login-stub listener that KS 1201 was filed about. That reasoning was put to Wednesday and ratified as reasoning; the gate judges whether the code does it.
A non-numeric argument is REFUSED by name and falls back to $?, rather than being used: exit "$rc" on a non-number is a shell error, which would trade a wrong status for no status at all. That branch has its own cell.
