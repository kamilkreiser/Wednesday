87. The ks1009 wallet-status cells read the response headers and the 500 body (KS-1588)

What this changes. KS-1588, test-only: ks1009-wallet-status-reveals-only-existence.test.ts goes from 8 to 13 cells. Cell 7 pins that the registered-address answer carries only the Express default header names; cell 8 pins that no header VALUE carries the seeded id, role or timestamp; cell 9 pins that a database error answers exactly the generic INTERNAL_ERROR body, with none of the error text, the address or the seeded values. C4 and C5 are controls: C4 shows the header reader sees real headers (content-type, and the measured content-length of 15), C5 shows cell 9 really entered the error path (the lookup threw once).
Why: the body-only cells 1 and 2 left two surfaces unread, and two of the KS-1009 gate’s mutants lived there and survived. N3 puts the user id in an X-User-Id response header with the body untouched; N8 makes the error path echo a message or the requested address into the 500 body. Neither exists in the route today; the cells make it notice if one appears.
The route (services/auth/src/routes/wallet.ts, the /status/:walletAddress handler) and every product file are untouched: the route’s sha256 (17cd98c3cad1) is identical before and after. The file’s stub gained one switch (failWith) that only cell 9 and C5 arm; cells 1-6 and C1-C3 run unchanged.

87.1 The mutants, and what kills them

Four mutants, each a COPY of the route with one change. N3 (the gate’s) sets X-User-Id to the id; N3b (added here) sets ETag to the id, so a header whose NAME is on the default list still carries it; N8m (the gate’s, message form) makes the catch answer a 500 whose message is the thrown error’s text; N8p (the gate’s, param form) makes it answer a 500 naming the requested address. Each anchor occurs exactly once in the route, each copy parses (TypeScript transpileModule, 0 diagnostics) before it runs, and each differs from the route by the lines shown in its diff only.
Against the BASE cell file (8 cells) all four SURVIVE: 8 / 8 each. Against the new file: N3 fails cells 7 and 8 (11 / 13); N3b fails cell 8 only (12 / 13, so cell 8 is not redundant with cell 7); N8m and N8p each fail cell 9 only (12 / 13). Control: a byte copy of the real route through the same harness reads 8 / 8 (base) and 13 / 13 (new), so the harness itself changes nothing.
Harness: a throwaway vitest config (not committed) whose alias sends the specifier ../routes/wallet to the route copy, run through the npm workspace so the working directory is the service. The repository carries no seam for this: the cell file imports the real route.
