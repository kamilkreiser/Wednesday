35. Job 04 fails a scan when trivy reports neither Results nor ArtifactName (KS-1274)

35.1 What this row is, and what it is not

KS 1136 already made job 04 treat a non-zero trivy exit, or output jq could not read, as a FAILED scan. What it did not catch is a trivy that exits 0 and prints a well-formed but empty object. A bare {} parses cleanly, carries no findings, and so was recorded as a clean image — the one shape where "no vulnerabilities" and "no scan happened" are indistinguishable from the artefact. This row adds the missing guard at Blockchain/Testing/jobs/04-container-trivy.sh:115-120: the scan is recorded scan-failed when stdout has neither Results nor ArtifactName.

35.2 The ticket's own suggested fix is wrong as written

The ticket proposes failing on a missing Results key. That over-fires. A genuinely clean image can report ArtifactName with no Results array at all, and failing it would turn every clean scan into an error. The guard therefore requires both keys to be absent, and the suite pins that distinction with a control cell — CONTROL KS-1274 a clean report with ArtifactName and no Results stays clean: rc 0, no error — which passes in the patched state and in the reverted state, so it cannot be mistaken for the cell under test.

35.3 Why the three suites' clean stub had to move with the guard

All three trivy suites stubbed a clean image as {}. Under the new guard {} is precisely the failure case, so left alone every clean-path cell in all three suites would have started failing for the right reason in the wrong test. The stub becomes {"Results":[]} in the same commit — a real clean report rather than an empty one. The fail.txt vocabulary gains bare and nores so the stub can produce each shape deliberately.
