11. RFC 3161 Timestamp Token Verification (KS-1404)

What changed.services/timestamping accepted an unsigned timestamp token as valid.
The old verifyRealToken walked the ASN.1 tree and returned valid: true whenever any OCTET STRING equalled the expected document digest — no signature check, no certificate chain, no TSTInfo parse, no algorithm-OID check.
A second path accepted a JSON {"hash":"…"} token outright.
Both are closed.

11.1 The verification chain, in order

KS-1404 ITEM 2 (Seat D 5th): the verifier binds the signer certificate via signingCertificate(V2) and builds the chain from the token's own certificates to a pinned root.
The signer is selected by an exact SignerIdentifier match — issuer+serial or subjectKeyIdentifier — and the previous ?? certs[0] fallback is gone, so a token whose SignerInfo names nothing it carries is refused rather than checked against whichever certificate happened to be first.
The token's other certificates are passed to the chain engine as untrusted intermediates; trustedCerts remains the configured anchors alone, so carrying an intermediate can never create trust. rsaEncryption (digest taken from digestAlgorithm) and RSASSA-PSS (parameters parsed, never defaulted) are accepted, because those are the algorithms the pinned providers measurably use.
A defect of this PR, found and fixed inside it, and the cell that caught it. The first version of the chain fix passed certs: [signer, ...intermediates]. pkijs treats the LAST element of certs as the end-entity — its own documented example is certs: [rootCa, intermediateCa, leafCert] — so an intermediate was validated as the leaf, and a token whose signer chained to nothing was ACCEPTED whenever some certificate it carried chained to an anchor.
The order is now [...intermediates, signer]. CHAIN-3 is the only cell that fails on the reversed order, and it stays in the suite for that reason.
Strict DERdefinite, minimal lengths, nothing trailing.
BER indefinite-length encoding is refused: a genuine token re-wrapped as 30 80 … 00 00 was accepted before this change.
ContentInfo is id-signedData; SignedData's eContentType is id-ct-TSTInfo.
TSTInfo is parsed, and the message imprint is read from messageImprint.hashedMessage — never searched for in the tree.
Exactly one SignerInfo, whose signed attributes carry contentType = id-ct-TSTInfo and messageDigest = digest(eContent).
The signature over the signed attributes re-encoded as SET OF, against the signer certificate's public key.
The signer certificate carries EKU id-kp-timeStamping, is valid at genTime, and chains to a configured trust anchor.

11.2 Fail-closed, and what that means operationally

Trust anchors come from TSA_TRUST_ANCHORS_PEM (PEM text, or a path to a bundle), committed as config. Unset or empty means every real DER token verifies false with reason no trust anchor configured. Stored tokens continue to verify through the database-row branch (same hash and byte-identical proof), which this change does not touch. Compose and per-environment wiring landed in KS-1404's second half and is described in 11.4; this sentence previously read “Compose and per-environment wiring is a separate step, so which environments have an anchor in effect is not covered here”, which was true of #1376 and is now false.

11.4 Compose and per-environment wiring (KS-1404, Seat D 8th)

#1376 closed the forgeable paths in the verifier and committed the roots, but nothing delivered an anchor to a running service, so every real DER token was refused on every box with no trust anchor configured — regardless of what the TSA did.
Two changes close that, and one measurement decides their shape.
