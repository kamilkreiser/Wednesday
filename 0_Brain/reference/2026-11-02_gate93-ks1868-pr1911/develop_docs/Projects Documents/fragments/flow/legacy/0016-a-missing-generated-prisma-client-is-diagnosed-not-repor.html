24. A missing GENERATED Prisma client is diagnosed, not reported as a module error (KS-1305)

What this fixes. A fresh worktree installs @prisma/client but never generates it: npm ci runs with --ignore-scripts, so prisma generate does not run.
The bare require('@prisma/client') inside getPrismaClient() then throws Cannot find module '.prisma/client/default' — a module-resolution error that reads like a product defect in the originate service, and which cost real time to diagnose more than once.
The load now names the cause and the command that fixes it, and every other load error is rethrown untouched.

24.1 The mechanism, and what is deliberately NOT changed

The change is a pure insertion of 19 lines (numstat 19 0) immediately before the existing require. It loads @prisma/client once inside a try; on success the original require reads the module cache, so the happy path is byte-for-byte the same behaviour. db.ts is the tenant-isolation module — it holds withTenant, the GUC wrapper, getGucPrisma and createPoolProxy — and no GUC, tenant or RLS line is touched. The six KS 458 tenant-GUC cells are green at the head. The new message carries no environment or credential data; cause carries the resolver's error, which holds module paths only.

24.2 The guard is a three-term conjunction, and each term has its own red arm

The rewrite fires only when err?.code === 'MODULE_NOT_FOUND' and the message contains .prisma/client; anything else is throw err — the same object, not a copy. A guard with three terms needs three arms, or some term is being asserted by prose rather than by a cell.

No cell presented an error whose message matched while its code did not, so deleting the code test changed no verdict. C3 supplies exactly that error and requires the same object back.
Each arm was run with tsc rc 0 first: an arm that does not compile reports Tests: 0 total, which is a load failure, not an inert tamper, and proves nothing about the guard.
