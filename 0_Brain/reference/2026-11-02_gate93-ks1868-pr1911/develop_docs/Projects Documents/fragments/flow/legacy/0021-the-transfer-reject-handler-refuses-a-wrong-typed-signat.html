30. The transfer reject handler refuses a wrong-typed signature instead of running the reject (KS-1435)

30.1 What was wrong, and why a 200 was the worst possible answer

The published TransferRejectRequest declares signature as a string, but rejectTransferSchema in services/transfer/src/index.ts did not declare it at all. Zod strips keys a schema does not name, so a signature of the wrong type was not refused — it was silently discarded, the schema then validated, and the reject ran with 200. The caller gets a success for a request the published contract says is invalid, and the rejection is recorded without the signature it believed it had sent. A stripped field is worse than a rejected one precisely because nothing surfaces.

30.2 The fix is one declaration, and optional() is the load-bearing half

signature: z.string().optional(), added to rejectTransferSchema. Typed, so a non-string is now a validation error and the handler answers 400. optional() keeps the field not required, which is what the contract says and what every existing caller relies on: making it mandatory would have reddened the pre-existing reject cells that send no signature at all. The narrowing is the type, never the presence.

30.3 Red-first, and the red is an assertion rather than a load failure

With the test hunk applied alone and the product file untouched at the base, the suite gives rc 1, 2 failed | 77 passed (79). Both failures read AssertionError: expected 200 to be 400 — the defect reproduced by its own symptom, not a module that would not import. That distinction is the point of running the test hunk first: a compile-breaking tamper reds with 0 passed and 0 failed, which is a load failure and proves nothing about the guard. 30.5 An idempotence control that does NOT fire here, and why it is recorded rather than claimed

Re-applying the test section after it is already applied succeeds, rc 0, on the working tree and through apply --cached against a temp index at the base. git apply --check -v says Hunk #1 succeeded at 938 (offset -39 lines): the hunk's only context is two closing-brace lines, which recur throughout a test file, so git apply cannot tell the patch from a fresh insertion elsewhere. So "applied twice refuses" is not a usable idempotence guard for this payload, and it is not offered as one. What is asserted instead is content: the ordered-join sha, the two applied blobs, and the write-tree result 84a98ca82ee0bce4 against a different-base control. An apply's exit status is not evidence that the right bytes landed.

30.6 Not covered, and the live sweep

This is a narrowing of the KS-1435 defect on one operation, and the ticket does not move to Done. Only POST /api/transfers/{id}/reject is touched; no other operation's schema was audited for the same stripped-field class, and the published spec was not regenerated because this row changes no spec file. The cells drive the handler in process — no gateway, no live stack — so the route-level behaviour behind nginx is unmeasured, and the four platform suites (Schemathesis, Akto, Playwright, performance) are UNMEASURED, not passing, because the local stack is not up. This moves runtime request validation on a transfer operation, so a live sweep is owed.
