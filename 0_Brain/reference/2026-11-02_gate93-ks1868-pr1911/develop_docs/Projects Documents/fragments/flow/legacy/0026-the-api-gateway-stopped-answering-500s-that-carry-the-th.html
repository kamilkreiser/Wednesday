36. The api-gateway stopped answering 500s that carry the thrown error's own text (KS-1410)

36.1 What this row is, and what it is not

Ten catch blocks across three api-gateway routers answered res.status(500).json({ ... message: err.message || 'Internal server error' }) with no NODE_ENV guard, so whatever the thrown error said — a driver message, a constraint name, a path — reached the client in every environment, production included. Each router now has a local fail500 helper, the shape originate already uses (KS 1334, KS 730): log the thrown text server-side with the route named, answer a constant INTERNAL_ERROR body. Sites: six in routes/notifications.ts, three in routes/batch.ts, one in routes/audit-export.ts. This is 10 of the ticket's 28 sites; the other 18 stay OPEN, including transfer/delegations.ts.

36.2 Red-first, on the real routers

Two new suites dispatch the real routers through a fake req/res pair, with the router-wide authenticateToken replaced by a pass-through, so no server and no network are involved. At the base the same 27 cells read 21 failed | 6 passed, rc 1 — the six survivors are the 200-path controls, which is what shows the suites loaded and the cells executed rather than failing to import. With the fix: 27 passed, rc 0. The touched service's whole unit suite reads 845 passed, rc 0.

36.3 What this row does NOT prove

Every cell above ran offline against the router objects. No gateway process served a request, so the runtime 500 path is unmeasured: a live run is owed and the ticket does not move to Done. The four platform suites (Schemathesis, Akto, Playwright, Performance/k6) did not run — no local stack — and nothing here claims they passed.
