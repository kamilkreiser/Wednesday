8. Local Stack Slots — Running Four Configurations at Once (KS-666)

8a. A LOCAL run must name its slot (KS-1016, 2026-09-11)
Every harness — Schemathesis, k6, Playwright, Akto and the shared provisioning step — refuses to start against a local target (localhost, 127.0.0.1, [::1], host.docker.internal) when neither SECUURA_STACK_SLOT nor the platform-s alias STACK_SLOT is set, and prints the command to run instead: 
No stack slot named. Every LOCAL system-test run must say which Docker stack it targets
(target: http://localhost:6882/api). Name the slot and run again, for example:
  SECUURA_STACK_SLOT=<n> python3 scripts/run.py pr
  or: systemTest/run-in-slot.sh <n> python3 scripts/run.py pr
Remote targets need no slot; CI (CI=true) is exempt.
Local only. A remote target carries no slot and is left alone; CI is exempt because its isolated per-suite stacks are local by construction and deliberately unslotted (CI=true).
Before this rule an unset slot meant slot 1 silently — another ticket's stack on a shared machine.
Proven on slot 2: no slot → exit 2, 0 docker calls, nothing provisioned; STACK_SLOT=2 → 1,759 requests to the slot-2 gateway (6882 + 100·(2−1)).

Four slots per platform, and the numbering is shared with platform-s (PS-622). Every published port is the historic one plus 100 × (N − 1), so platform-s slot N and platform-k slot N pair up with no configuration: platform-k slot N's gateway lands on 6882 + 100 × (N − 1). platform-s exports STACK_SLOT; platform-k reads SECUURA_STACK_SLOT and falls back to it, so a single export in a worktree drives both platforms.
Four is a deliberate ceiling — the two platforms first collide at platform-s slot 9, where its PMA proxy (8081) meets platform-k tokenomics (8881).
⚠ The same four ports mean different things locally and in CI. Section 5 (historical, Actions retired 2026-08-27) gave each suite — schemathesis, playwright, performance, akto — its own CI-only port block because each CI job booted its own single-tenant stack on an ephemeral runner.
Locally the ports are per stack slot (slot-1 base + 100·(N−1)), and every suite targets whichever slot it was pointed at.
Reading a local port as a CI suite (or the reverse) will attribute a result to the wrong thing.
Every harness follows the slot, and every result names it. Source systemTest/slot-target.sh and Schemathesis (SECUURA_BASE_URL), Playwright (GATEWAY_URL), Akto (SECUURA_API_URL, plus its own side-stack, mongo volume and dashboard port) and the performance runner (PERF_BASE_URL) all aim at the same stack.
Akto and the performance runner used to default to localhost:6882 on their own, so a run silently tested slot 1 whichever slot was meant; since KS-1386 an unslotted local run is refused instead — there is no default URL. Playwright is the exception since KS-682: config/stackSlot.ts reads SECUURA_STACK_SLOT itself, derives the gateway, refuses a malformed or out-of-range slot and a label naming another slot, writes results/playwright-report-<ticket>-<ts>-slot<N> behind a results/latest-slot<N> pointer, and serves the report on 9324 + 100·(N−1).
Pinned by the unit suite in systemTest/playwright/tests-unit/ (292 cases on the Mac, 2026-09-10; 389 passing in 6.5 s, Mac, 2026-10-06) — including a boundary suite: an explicit slot outside 1–4 derives no port, a suffix that spells the slot any way but the wrapper's (-slot01) is refused, and a pinned report port must be decimal digits; KS-1056 tracks the other three.
A fresh local stack needs its bootstrap admin, or every harness degrades. Actor provisioning (fixtures/provision-actors.ts) grants roles as admin@secuura.com; that account is seeded only when the auth service receives ADMIN_USER_PASSWORD at build time. docker-compose.yml forwards it since 2026-09-10 (KS-682, from KS-971) — before that the templated value never reached the container, the account was never seeded, and provisioning collapsed every actor to OWNER and refused the manifest (KS-969, KS-972). check-stack-safety.sh now holds the forward as an invariant.
Since 2026-09-10 Playwright's global-setup also passes its slot-derived gateway to provisioning (--base-url): an unsourced SECUURA_STACK_SLOT=N run provisions on slot N rather than on slot 1, which it did before — found on the slot-2 rotation, invisible on slot 1.
A superseded manifest keeps its slot segment (actors-slot<N>.superseded-<ts>.json) — found on the slot-4 rotation.
Schemathesis resolves its own slot (KS-1016). It no longer depends on that export: src/slot.py reads SECUURA_STACK_SLOT (or platform-s's STACK_SLOT) and derives the gateway by the same historic + 100 × (N − 1) rule, so SECUURA_STACK_SLOT=<n> alone targets :6882 + 100·(n−1).
It is one resolver for the runner, the hooks and the persona logins.
Those three used to answer differently — constants.py preferred API_BASE_URL, cli.py preferred SECUURA_BASE_URL, and config/settings.py and config/fixtures.py ignored API_BASE_URL entirely — so a shell carrying only one of the pair drove the runner to one slot and every login to another, within a single run, with nothing reporting it.
The checked-in [tool.schemathesis] base-url in pyproject.toml is gone for the same reason: a file in git cannot know which slot a run is aimed at, and a direct st run consulted nothing else.
The resolver's edges are pinned in tests/unit/test_slot_resolver_edges.py: padding around the slot, a trailing slash or a missing /api on either base-URL variable, a blank-but-present SECUURA_BASE_URL, and — found by probing after the four-slot live series — a whitespace SECUURA_STACK_SLOT that used to mask a valid STACK_SLOT and default the run to slot 1.
Four further modules close the branches around the fix: test_stack_postgres_fixture.py (the fixture the migrated call site runs through: skip, cross-slot refusal, the guard actually called), test_compose_project_resolution.py (which compose project a recreate is aimed at: slot-prefixed probe order, blank label, fallback, explicit override), test_slot_rule_executes_like_the_shell.py (sources stack_env.sh per slot and compares what it exports, so the pin is on behaviour rather than text), test_observability_best_effort.py (a refused Pushgateway or Grafana degrades to False, never to a red run); and the no-hardcoded-slot guard now walks src/, scripts/ and config/ as well as tests/.
The resolver refuses what stack_env.sh refuses — 0, 01, abc, 5 — and test_slot_rule_executes_like_the_shell.py sources the shell per slot to prove both sides agree on behaviour, not text.
Proven by rotation, one slot at a time (KS-1016, 2026-09-10/11). Slots 4 → 3 → 2 → 1, each built from an empty host with every other slot torn down, launched with no slot-targeting variable set and every docker call audited: every request to the slot's own gateway, zero to any other, zero docker calls, artifacts and latest-slotN carrying the slot.
On 2026-09-11, with develop forwarding ADMIN_USER_PASSWORD, the first valid sweeps ran (0 of 316 operations errored) and the four harnesses ran in series on slot 4 — Schemathesis pr, k6 smoke, Playwright ci:e2e, Akto pre-merge — with slots 1–3 empty throughout. Rule from that series: export BOOTSTRAP_ADMIN_PASSWORD on every suite run, Schemathesis included. The first provisioning on a fresh stack creates the generated actors; without the variable they are created as OWNER and every later harness — k6, Playwright, Akto — inherits them (DEGRADED, and Playwright 400s at auth-setup) until the slot's database is reset. Since KS-1016 provisioning refuses instead (assertBootstrapAvailable in fixtures/provision-actors.ts, unit-tested in performance/tests/unit/fixtures/): an unavailable bootstrap admin throws before the first registration, so nothing is created and the next run with the variable set provisions correctly.
And every slot reader — the shared writer, Playwright, k6, Akto, Schemathesis's manifest reader and src/slot.py — honours platform-s's STACK_SLOT alias in stack_env.sh:37's order (SECUURA_STACK_SLOT wins, blank falls through, a malformed alias is refused), pinned per harness and by __tests__/manifest_readers_agree.test.sh.
DEGRADED reports what it did to the manifest, strict arm included (KS-981, 2026-09-29). When provisioning fails, the pre-suite moves any manifest on disk aside so no harness reads stale actors — with or without SYSTEMTEST_REQUIRE_PROVISIONED.
The strict banner used to print only FATAL, so a manifest that could not be moved, and is still on disk for the next run on that slot, went unreported.
Both arms now print moved-to / none-on-disk / could-not-move, the last naming the file consumers read (actors-slotN.json, not the pre-KS-971 actors.json).

A failed login now says which cause, and a refused connection names its port (KS-1167, 2026-09-14). The shared pre-suite login dropped the HTTP status, so bootstrap admin: UNAVAILABLE explained every non-200 as “check the password” — a 429 from the per-IP login limiter included, on the first step every harness runs. fixtures/login-outcome.ts classifies the attempt (unreachable > rate-limited > rejected > unexpected) and each branch names a different next step; the fetch in fixtures/provision.ts was unguarded, so a refused connection reached the DEGRADED banner as the bare fetch failed with the ECONNREFUSED <host>:<port> lost in an empty-message AggregateError; fixtures/describe-error.ts now renders it.
Playwright's auth-setup diagnoses its own login the same way (limiter / EMPTY password from a withheld manifest / rejected / unhealthy) and its global-setup refuses on a 429 ping rather than proceeding into provisioning inside a cooldown.
Proven red→green against a stub gateway answering one fixed status and a port proven closed (__tests__/bootstrap_login_diagnosis.test.sh: 10 of 16 cells red on the previous fixtures), with no stack.
The API Explorer resolves its stack slot too (KS-1386, 2026-09-29). It was the last systemTest package fixed to slot 1: an explorer generated while working on slot N offered slot 1's gateway as its Local server and printed slot 1's health-check curls, and a server chosen on one slot's page was reused by another's (every explorer opened from disk shares one browser-storage origin).
Generation now takes SECUURA_STACK_SLOT (or STACK_SLOT) and refuses a generation that names neither — under CI too, since it has no URL of its own — and the page ignores a stored server it does not offer.
Pinned by per-slot unit tests derived from slot 1, a parity test against fixtures/slot.ts, and a guard that keeps slot 1's port out of every other file under api-explorer/src/.
Nothing defaults to slot 1 any more, in any harness (KS-1386, 2026-09-29). Five slot resolvers turned an unnamed slot into slot 1, so an unslotted run could provision, log in, scan or stop containers on slot 1 while the rest of it was aimed elsewhere — Schemathesis's setup minted an admin API key there, Akto checked its scan target but not its own dashboard, and prove-slot-isolation.sh defaulted its victim slot to 3.
Every stack-touching entry point now refuses a local run that names no slot; CI and remote targets stay exempt from naming one, but with no slot and no URL every harness refuses; an exempt run is labelled unslotted, never slot1.
No slot 2–4 value is typed anywhere: tests derive them from slot 1, and __tests__/no_hardcoded_slot_literals.test.sh scans every harness. One bounded exemption (KS-1450): the Schemathesis baseline's $generated.from_runs run ids record which sweep produced a row and cannot carry an inline marker, so a lone string element of that exact shape is exempt in that one file — and a guard cell asserts every exempted line really is a from_runs member, so the exemption cannot widen silently.
Same branch: the Akto offline gate no longer spawns docker, no script prints part of the API token, api-explorer's golden snapshot is tracked, the Schemathesis offline suites fail any test that writes into the real output/reports/, and the Akto and Performance no-slot refusals name the npm script that was run. slot-target.sh (KS-1389) and observability/ (KS-1388) are tracked separately.
The slot gate is driven as a process, and the offline unit suites are slot-independent (KS-1167). Playwright and k6 proved the KS-1016 guard was called by reading the runner as text; both now spawn the real entry point with the slot family stripped and read the exit code — and npm run report (Playwright), which resolved slot 1 silently, consults the rule (SECUURA_STACK_SLOT=1 npm run report).

The suites' verdicts depended on which worktree ran them — files cleared the slot family only in afterEach, never the STACK_SLOT alias, and k6's runner modules freeze their slot at import.
Both now strip the slot family before every file (Playwright: clear-before-each plus a childEnv() door for spawns; Performance: a vitest setupFiles entry), and each carries a matrix that re-runs the suite under no slot and slots 1–4 — both variables and the wrapper's suffix shape — demanding identical counts.

⚠ A cross-slot read is refused, not merely improbable (KS-1016). The anchoring DB sweeps and the compose controller both compare the container's slot with the target gateway's slot and stop if they differ, naming both sides.
Before this, test_anchor_read_honesty ran docker exec secuura-postgres with the name hardcoded — slot 1's container and only slot 1's — so a slot-3 run created a document on slot 3 and then counted contradictory rows in slot 1's anchor_store.
Nothing refused the connection, because every slot ships the same Postgres password (KS-731), so the answer came back and read as authoritative.
The compose path had no guard at all and is the more dangerous of the two: it stops and recreates containers, so an unsourced shell would have taken another ticket's stack down while asserting against this one.
An unidentifiable slot on either side — the isolated CI stack, a demo target — is allowed through; only two known, differing slots are refused.
Run metrics are grouped per slot (KS-1016). The Pushgateway key is /job/integration/environment/<env>/slot/<N>.
There is a single shared secuura-obs-pushgateway on host :9099, so the URL cannot be per-slot; and a push to an existing key replaces that group.
Two concurrent slots therefore overwrote each other's run summary, both reported success, and the surviving series described whichever slot pushed last.
Slot isolation covered the stack under test but not the record of what was tested.
Result isolation is a MUST, with no exception. Folders and files both carry the Linear ticket and the slot — results-ks-666-slot<n>.json, output/reports-slot<n>/pr-ks-666-<ts>, test-fast-ks-666-<ts>-slot<n>.
Slot 1 is labelled too: an unlabelled results-ks-666.json was the one set nobody could relate back to a slot or port.
Three of the four harnesses name runs by the second, so two slots finishing together resolved to a single path — measured on this Mac 2026-08-20, where concurrent Playwright runs on slots 1 and 3 shared the start time 10:55:12.567Z, and Schemathesis and Akto both produced identical timestamps.
The latest pointer is slot-scoped for the same reason.
⚠ Within a slot, suites run in SERIES. Slots run in parallel with each other; suites within one slot do not.
The reason is the platform's per-IP login rate limiter, not resource contention — every harness authenticates through the same gateway as the same personas, and from the stack's point of view every local suite shares one IP. All four harnesses are affected — Akto, Schemathesis, Playwright and the performance suite alike.
Any can trip the limiter and any can be starved by another; Schemathesis is simply where it was first seen, because its report names the cause, while the others surface it as login failures, empty result sets or timeouts that read as product bugs. Once rate limiting appears, wait 15 minutes before starting any further tests — the window has to drain, and restarting inside it both wastes the run and pushes the window out.
Measured 2026-08-20 running Playwright, Schemathesis and k6 together against slot 1: Schemathesis logged 300 engine errors across 289 operations, every one login for persona=super_admin is rate-limited.
That failure lies twice, which is why it is worth naming here. The report was headed PASSED — the operations were never exercised, so nothing could fail — and the errors are filed as engine errors, reading as a Schemathesis fault rather than the platform's limiter doing its job. Use systemTest/run-in-slot.sh <slot> <command>, which holds an exclusive per-slot lock. LOCAL_LOGIN_LIMITER_DISABLED=true (KS-191) suppresses the limiter, but only if the stack was started with it, and it changes the system under test.
Measured on this Mac, 2026-08-20. Four platform-k stacks (33 containers each, 132 total) plus a platform-s stack ran together in 7.2 GiB of a 31.3 GiB Docker Desktop allocation (recorded as 6 CPU then; docker info reports 8 CPU / 31.3 GiB on 2026-10-06), with all 31 bound ports attributable to a platform and slot and no collision. Memory is not the constraint; CPU is — load averaged ~23 with four stacks idle, so four concurrent suites is a different question and has not been measured.

Slot isolation used to be opt-in, and forgetting was silent (KS-687). Every slot-carrying value the Akto harness used arrived from slot-target.sh; the package itself read SECUURA_STACK_SLOT in one place, to word an error.
Correctness was a property of the operator.
It is now a property of the code: validate() refuses a run whose pieces name different slots, an unusable slot request (5, abc, 3.5 — never defaulted to slot 1, matching stack_env.sh), and an artefact suffix that is a path; pre-flight derives its probe from the same function the scan uses, so it cannot vouch for a neighbour (the first live slot-4 run passed pre-flight on host.docker.internal:<slot-4 gateway> while the scan went to localhost:<slot-4 gateway> inside the container (6882 + 100·(4−1)) — 8,816 connectivity skips under a PASS in 25 s); and after every scan the persisted artefact is walked and any local URL on another slot's port fails the run.
Proven live on all four slots on 2026-09-10 — 8,902–8,933 executed, 0 vulnerable, 2,619–2,635 references to the slot's own gateway, zero to any other — and again on slot 4 from the develop-merged tree on 2026-09-11 (9,105 / 9,138 executed, zero foreign); the leak check names the foreign hosts the moment the same artefact is claimed for a different slot.
