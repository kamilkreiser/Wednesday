27. The tenant-isolation job's stderr goes to its own file, so a legitimate run's artefact stays parseable (KS-1436)

What this fixes. Blockchain/Testing/jobs/06-tenant-isolation.sh:71 ran its runner as > "$OUT" 2>&1, folding stderr into the same file as the JSON result.
The runner writes its result to stdout (tests/tenant-isolation/runner.ts:262) and its diagnostics to stderr (runner.ts:74, console.error("login failed for …")), so any stderr line corrupted the artefact.
This is reached on a routine run, not an error path: runner.ts:150-151 is a deliberate two-principal fallback (verifier@ || holder@), and whenever the first login cannot succeed the console.error line is emitted and the fallback proceeds as designed.
The job still exited 0, while :74 and :75 read the artefact through jq … 2>/dev/null || echo "?" — so the parse failure was swallowed and the job printed tested=? cross-tenant_findings=?.

27.1 Why it had to land before the aggregator change

Before KS 1136's change an unreadable artefact was reported as a clean scan, so a genuine cross-tenant finding on a fallback run read as no findings. After KS 1136 lands the aggregator reports the artefact as unreadable instead, which turns every routine verifier@-fallback run red with a false cause. That is why this one-line fix is the merge condition for that pull request and lands first. KS 1382 is a different line in the same file (:31, TARGET_BASE defaulting to slot 1's gateway) and is not addressed here.

27.2 The change, and what is deliberately NOT changed

One product line: 2>&1 becomes 2> "$OUT.stderr". The stderr content is kept, not discarded — it is the diagnostic that explains a fallback, and a 2>/dev/null variant is driven as its own red arm below. The file's Writes: header line (:23) is unchanged: the new sidecar is a diagnostic, not a declared artefact. The jq … || echo "?" swallow at :74-:75 is left in place; this ticket fixes the cause, not that symptom.
