78. Five originate log-line describers can no longer take a request down: the fail500 helpers of four route files and the per-tenant catch of migrate-tenant-data (KS-1772)

What this changes. KS-1772 names five places in services/originate where a log line was built from a thrown value with no try of its own, the shape PR 1754 fixed in api-gateway (KS-1524 (a)). The five are the fail500 helper of routes/systemErrors.ts, routes/gdpr.ts, routes/webhooks.ts and routes/adminConfig.ts, and the per-tenant catch of POST /api/admin/migrate-tenant-data in adminConfig.ts.
A behaviour change on request paths. A thrown value whose description throws (a message getter that throws, a Proxy whose getPrototypeOf or ownKeys trap throws, a revoked Proxy), or a logger that throws, made the describer throw from inside its own catch. In the four fail500 helpers that rejected the async handler, Express 4 never sees a rejected promise, and the request got no response. In the per-tenant catch it escaped into the route’s outer catch: the loop stopped at that tenant, later tenants were never tried, and the route answered 500 where its contract is a 200 whose results carries the failing tenant’s code.
Each site now describes the value in its own try (fallback line thrown value that could not be described) and logs in another, so the constant 500, or the tenant’s row and the next tenant, is always produced. For every value that could be described before, the log line is unchanged. The guards are written inline at each site and not as a shared helper: the per-tenant row TENANT_COPY_FAILED, its bare-string shape and a shared describer are KS-1462 item 2, and are not touched.

Per site there are four D1 cells (one per throwing shape), one L1 cell (a logger that throws on a value that describes fine) and one C1 control (a describable Error is logged by its message, so the stub is live and a green D1 or L1 is not vacuous).

78.3 What the cells prove, and what they do not

The route’s answer, not the process. The cells prove that each route answers (and the per-tenant catch goes on to the next tenant) for the four throwing shapes and for a throwing logger, over a loopback listener with the service calls mocked. They do not say what an unhandled rejection does to a running service: that is the process’s unhandledRejection posture, a separate ticket (KS-1427).
The catch around each logger.error is deliberately empty, with its reason written beside it: if the logger itself fails there is no other channel to report it on, and the caller must still get its answer. This is a named exception, not a silenced error.
Not measured: any of this through a running gateway or on a deployed box, a run on Node 24, and the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), which are not claimed as passing. Two existing ESLint warnings in adminConfig.ts (prefer-const on copied, and an unused e) are present at base and are not touched.
