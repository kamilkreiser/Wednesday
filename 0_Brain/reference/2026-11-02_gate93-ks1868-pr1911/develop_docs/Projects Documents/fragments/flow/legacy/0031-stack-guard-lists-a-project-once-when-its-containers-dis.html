42. stack_guard lists a project ONCE when its containers disagree about the owner (KS-1355)

42.1 What this row is, and what it is not

stack_guard.sh groups foreign stacks by (project, owner). A project whose containers carry different owner labels therefore produced one line per distinct owner, so a single foreign stack could be reported twice and the operator could not tell one project from two. This row makes a project print ONE line. Where some containers carry a real owner and others carry owner=unknown, the line names the real owner and appends the unknown count. NARROWING: this is KS-1355 spot 1 only and the ticket does NOT close — the stack tooling's other non-slot-derived spots are untouched.

42.2 The behaviour change, named explicitly

A reader upgrading past this commit sees different output for one input. A project with two DIFFERENT real owners now prints one line — the first (project, owner) tuple in docker ps order — where the tip printed both. That is a deliberate consequence of "one line per project", not an oversight: the second real owner is no longer shown. The (+N container(s) with owner unknown) wording is this change's own choice; the ticket asks only that an unknown count be appended.

42.3 Red-first, product reverted under the new suite

The red is a real product red, not a tamper: keep the new suite, revert stack_guard.sh to the base. 25 passed, 2 failed, rc 1, failing exactly the two new cells — a stack with an owner=unknown container is listed ONCE (want "1", got "2") and ...under its real owner, with the owner=unknown count (want "1", got "0"). The suite's own KS-1355 CONTROL cell (an all-unknown stack is still listed once) passes at the base too, so the suite is not failing wholesale. With the product change: 27 passed, 0 failed, rc 0. 42.4 The exec-bit trap this row walked into

Both files are 100755 in the tree and must stay so. This repo sets core.filemode=false, so git apply left both files 644 on disk while git recorded no mode change at all. The committed tree therefore keeps 100755 — that is the load-bearing fact — but a direct ./stack_guard.sh would have failed. Restored by reading the mode from the index for the two named paths only; never checkout-index -a -f.
