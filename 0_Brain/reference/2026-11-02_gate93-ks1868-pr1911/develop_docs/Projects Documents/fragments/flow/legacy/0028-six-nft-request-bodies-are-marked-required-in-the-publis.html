38. Six nft request bodies are marked required in the published contract, and the contract is REGENERATED, never hand-patched (KS-1449)

38.1 What this row is, and what it is not

Six operations declared a requestBody without required: true, so a spec-driven caller (Schemathesis) sent no body at all and counted the request valid; each handler's zod safeParse then answered 400 and the run failed positive_data_acceptance. This row marks all six required in services/nft-certificate/src/nft-certificate.openapi.ts: POST /api/nft/mint, POST /api/nft/ipfs/upload, PUT /api/nft/admin/platform-fee, POST /api/nft/ipfs/pin, POST /api/nft/ipfs/unpin and POST /api/nft/metadata/estimate-size. It is the spec half only: the runtime half — each handler's own 400 on an absent body — is READ from the source, never driven, because this host has no running stack. The ticket does not move to Done.

Two new suites render the document the generator publishes, from the shared registry the nft-certificate module populates on import — no server, no database, no network. With the product hunks applied it reads 60 passed (60), tsc rc 0. Red before, green after, on this worktree, with the numbers quoted.

38.3 The published contract is GENERATED — and the Spark YAML companions MISLAND

Blockchain/Dev/docs/openapi/secuura-api.yaml is written by Blockchain/Dev/scripts/generate-openapi.ts. Each Spark pass also ships an openapi-yaml.companion.diff, and those diffs are a trap. They are cut against spec blob 52310cab1; develop carries 146bae7edb87, +87 lines on. Their hunk context is generic (security / requestBody: / content: / application/json:), so git apply places them by offset search on the nearest matching operation. Measured at this base: all twelve apply rc 0 and five land required: true on the WRONG operation — among them this row's own nft-ipfs-pin-unpin-size, which alone flips POST /api/nft/ipfs/upload instead of POST /api/nft/ipfs/unpin.
So the YAML here is produced by npm run generate-openapi and proved structurally: parse base and head, compare every paths[p][m].requestBody.required. Result: exactly the six declared operations flipped, 0 flipped off, 0 operations added or removed, 145 request-bodied operations before and after, and the whole 40,021-line document differs by 6 added lines, 0 removed, every one a required: line. npm run check:openapi is rc 1 with the product change and the old YAML, and rc 0 after regenerating.

38.4 A control that does NOT discriminate here, named so nobody reuses it

The intended firing control is: build the YAML from the real companions and watch the structural reader refuse it. For this row it does not fire. Applied as a pair, the two companions' displaced hunks cancel: the result is byte-identical to the generated file (cmp rc 0) and check:openapi reads rc 0, because the operation one companion mislands onto — ipfs/upload — is itself in this row's op set. The control fires only on the mislanding companion applied alone against its own three intended operations: the reader then exits 2 naming unexpected ['post /api/nft/ipfs/upload'] and missing ['post /api/nft/ipfs/unpin'], and check:openapi reads rc 1. The lesson is that the companion route was right here by luck, and nothing in that route tells a reader which case they are in.
