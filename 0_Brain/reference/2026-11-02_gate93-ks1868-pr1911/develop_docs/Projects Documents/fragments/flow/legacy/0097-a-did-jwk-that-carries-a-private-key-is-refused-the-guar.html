108. A did:jwk that carries a private key is refused: the guard on actorDid and orgDid (KS-1175)

What this changes. Kam’s ruling of 2026-10-29 19:51:25 AEDT on the card secuura-ks1175-private-jwk-guard-1029, option a, “Add a narrow guard before deploying”: “decode the did:jwk value only to refuse private-key members (d, p, q, dp, dq, qi, k), with a 400 and a clear message. Nothing else about the JWK is checked.” A did:jwk is a public key by construction, and what is anchored is public and permanent, so a JWK that carries private-key material (RFC 7518 and RFC 8037: d for EC, OKP and RSA; p, q, dp, dq, qi for RSA; k for oct) must never reach the chain. The shape pattern from the previous entry cannot see inside the payload, so the validator now decodes a did:jwk far enough to read its member NAMES and refuses it with a 400 (zod issue code custom, message starting Invalid DID, naming the members found and carrying no value) when any of the seven is a top-level member.
The one design choice the ruling implies, and the strictness behind it. A payload that is not unpadded base64url of a JSON object is refused too (an undecodable did:jwk is not a public key; Wednesday’s reading of the ruling). The alphabet is checked BEFORE the decode, because Node’s base64url decoder silently skips any other character, and the DID pattern admits ., : and %: a lenient decode could read a different JWK from the one a strict resolver sees. The guard steps aside for a value the shape checks already refuse (over the cap, outside the alphabet), so a bad value is refused once, for its own reason, and it applies to the did:jwk: prefix only: did:key and did:web carry no decodable JWK and are unchanged. Nothing else is read: no kty, no curve, no key use, no key length.
Changed: anchorSchema.ts (+52 / −2: the exported DID_JWK_PRIVATE_MEMBERS, didJwkRefusal, a superRefine on didField, and the posture sentence, which used to say K never decodes the JWK); anchoring.openapi.ts (both DID descriptions carry the rule, built from DID_JWK_PRIVATE_MEMBERS so the text cannot drift); docs/openapi/secuura-api.yaml (generated, +5 / −2: the two description strings); docs/VOCABULARY.md; ks1175-identity-anchoring.test.ts (+168 / −35). Read and left: didField is module-local and only ever .optional()-ed into identitySchema, so the repo rule that base string schemas stay chainable (.regex(), not .refine()) is not engaged; z.infer still reads string. anchorReadback.ts imports only IDENTITY_FIELDS, so reading back an anchor validates nothing. The route answers a refusal as 400 Validation failed with zod’s issues, which carry no input value.
This supersedes two sentences of section 106 (the previous entry for this ticket). That entry says K “never decodes the JWK” and that the pattern admits “not only valid base64url JSON”. Since this change K decodes a did:jwk to read its member names, and a did:jwk whose payload is not base64url JSON is refused. The pattern itself is unchanged. A deployed did:jwk was never reachable before this guard: the widening of section 106 is merged and not deployed.

108.3 What this does not prove

A validator guard, not a deployed or live-tested one. Not run: the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), any stack or database (the ks1385 integration files need one), Docker, a Node 24 LTS run, and any anchor of a did:jwk on any network or box. Not deployed. The spec pattern still describes a did:jwk that the runtime now refuses (a pattern cannot express “decodes to a JSON object without a private member”): a Schemathesis positive case generated from the pattern could meet a 400 on these two fields, and POST /api/anchors has no per-operation override in schemathesis.toml, so the default positive-case statuses (no 400) apply to it. That is unmeasured here, and widening an expected-status list is masking by that file’s own rule, so it is for the owner of the suite to decide.
Limits, stated and pinned, not endorsed. Names are matched exactly and only at the top level, so a differently-cased D and a nested d are not refused; a consumer that reads JWK members case-insensitively would see the first as the member d. The RSA member oth (other primes) is not in Kam’s list; a JWK that carries it also carries d and is refused on that. Whether Platform S can ever put a private member in a did:jwk it sends is unmeasured, as is how many private-key shapes real wallets emit.
A private key that reaches this guard has already travelled from Platform S through the gateway and originate. Whether any of them logs a request body on a 400 is not measured here; the anchoring service itself returns no input value.
