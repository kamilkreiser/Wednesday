20. Clearing MFA NULLs the TOTP seed and the hashed backup codes, at all three sites (KS-938)

What this fixes. “MFA disabled” left the TOTP seed and the hashed backup codes in the row.
The flag flipped, the call answered 200 “MFA disabled successfully”, and the credential material survived — so a seed could be re-armed by POST /api/users/me/mfa/verify, which re-arms on the existing user.mfaSecret without minting a new one.
The case that matters is the user who disabled MFA because the authenticator was compromised.

20.1 The mechanism, and the one thing deliberately NOT changed

userRepo.updateUser builds its SET list with if (tsField in updates && updates[tsField] !== undefined). mfa_secret and mfa_backup_codes are in fieldMap, so the map was never the problem — the value guard was. All three clearing sites passed undefined, so a partial UPDATE landed naming only the fields that survived. The undefined skip is NOT changed: every other caller relies on it to mean “leave this column alone”. null passes the guard and writes SQL NULL, and the encryption branch guards on typeof val === 'string', so a null can never enter it. The codebase already knew the rule — wallet.ts carries “null, NOT undefined” for walletAddress (KS 720).

20.2 Three sites, and why the fix is per-site rather than one shared edit

Addressed by symbol, with blobs, because the line numbers move: at this change's base routes/mfa.ts is blob 87d3ee1079fe and routes/users.ts is blob ea9f8da97a04. mfa.ts setup-verify revert (updateUser) and mfa.ts POST /mfa/disable (updateUserOrThrow) each passed undefined for both columns. users.ts POST /me/mfa/disable did not pass mfaBackupCodes at all, so that site needed the key added, not merely re-valued — which is why no single shared edit could have fixed all three.

20.3 Red-first, by assertion

The cells drive the real route handlers over real loopback HTTP with the real userRepo and the real updateUser, stubbing only ../db so the emitted statement can be captured, and they assert the SQL — not the source text, which would still pass if the fix were commented out.
At the base the three site cells fail and the two controls pass (3 failed | 2 passed (5)); at the head 5 passed (5).
Both numbers are non-zero, so the red is a real red and not a load failure.
The base failure quotes the defect verbatim: UPDATE users SET mfa_enabled = $1, verification_level = $2, updated_at = NOW() WHERE id = $3.
The load-bearing control drives the same real updateUser with undefined and requires the two columns to be absent — a cell that cannot tell the fix from its own fallback is not a regression test.

20.4 Residue, named and NOT fixed here

users.ts POST /me/mfa/disable verifies the TOTP only if (user.mfaSecret && ...), so an account with no stored seed disables MFA with no proof of possession at all. That is a separate defect in the same handler and is left for its own ticket rather than widened into this one.
