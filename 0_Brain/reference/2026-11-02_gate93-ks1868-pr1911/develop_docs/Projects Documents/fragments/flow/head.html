🛡️ Post-run gates — judging the RUN, not its assertions (KS-517 · KS-684)

Gates run after a Schemathesis sweep and feed the exit code alongside the check results (run validity, NDJSON completeness, report reconciliation, triaged baseline, plus the authenticated-coverage gate). They exist because every assertion-based gate shares one blind spot: a check that never ran cannot fail, so a run that tested nothing scores clean everywhere. Each of these answers “did this run have the standing to say anything?” rather than “what did it say?”

Outcome taxonomy — five categories, shared across all three surfaces
The taxonomy is closed and shared: a category exists in the console, in results.json and in the HTML report, with the same label and the same count, or it is a design error. results.json is the source of truth; the other two are renderings of it. Each run also writes Schemathesis's native HTML report at <run>/schemathesis-native-html/index.html (linked from the harness report; KS-1615).
PASS — exercised, no violation
FAIL — exercised, violated a check
UNVERIFIED — should have run, did not; gates the run (KS-478)
OUT OF SCOPE — excluded by mode, not by accident (KS-519)
SKIPPED — a precondition was never met (KS-684)
SKIPPED is new in KS-684. Previously the banner rendered a strict PASSED/FAILED binary, so API_TOKEN not found turned four healthy suites — GDPR IDOR (KS-258), live integration (KS-416), anchoring integrity (KS-489-D) and state-machine preconditions (KS-478) — into FAILED on the 2026-08-24 run, sending readers after defects that did not exist.
An unmet precondition is not a test result.
A SKIPPED suite now contributes neither a pass nor a failure to OVERALL, and each row carries its reason — the two skip causes (“no credentials configured” vs “the platform did not answer”) stay distinguishable because they need different remedies.
Counting a skip as a pass would be the opposite and worse error.
