What this changes.The row-count builder. services/anchoring/src/anchorStatusUpdate.ts: the status UPDATE builder gains expectStatus (one value, or a list read as status = ANY(...)) and expectTransactionHash (null means IS NULL, never = NULL). The body of dbUpdateAnchorStatus moves into an exported runAnchorStatusUpdate, which resolves to the matched row count, or to null when the write did not run or its result is unknown. The reconciler (below) reads the count; the submitter still ignores it (KS-1384 F0 is the first there).
One Date per request. POST /api/anchors takes one Date and uses it for the payload’s anchored timestamp and the row’s created_at. The 202 gains payloadTimestamp: the timestamp inside the payload the row holds after the upsert, read in the upsert’s own RETURNING, so a repeat request whose KS-1385 overwrite was declined reports the kept payload’s time. GET /api/anchors/:id gains the same field from the stored payload (null when it carries none). The published spec adds the field to the 202 schema (additive).
originate stops writing anchor_store. saveAnchorToDb in services/originate/src/routes/anchors.ts is removed with its two calls. It wrote the anchoring service’s anchor id into transaction_hash, a confirmed_at of now, and updated_at = NOW() over the row anchoring owns. The non-production “anchoring unreachable” 202 no longer says the request was persisted locally.
The reconciler’s give-up (KS-1808, KS-1810). services/anchoring/src/reconciler.ts: the 24 h window runs from the row’s last write (updated_at), not created_at, so a re-armed old row is no longer failed at its first pass. A row is failed only after TWO consecutive passes past the window in which the chain ANSWERED “not found” (the polled count of waitForConfirmation); a pass the provider could not answer never fails a row and starts the count again, as does a thrown check or a new hash on the row. The count is in memory, keyed by anchor id and hash, so a restart can only delay a failed write.
Guarded reconciler writes. Each confirmed or failed write expects the status set the pass selected (pending, submitted, submitting) and the hash it read, and only a write that matched its row (1) is counted; 0 (the row moved: a re-anchor or a final status) and null (the write did not run) are logged and left.
Comments and two pins. The reconciler header now states the new rule; its MIN_AGE comment (KS-1816) is kept, because it is still true; its catch comment says a provider outage is decided by the “could not ask” branch. ks1816-reconciler-comments-match-the-code.test.ts is rewritten in the same commit: R1 pins the new header sentence, C2 pins the updated_at give-up line; R2, C1 and C3 are unchanged. .3 What this does not prove

Stated, not claimed.That the old two-new Date() shape ever produced different instants on a box: it differs only when the two calls straddle a millisecond, which a real-route cell cannot force. Cell (wu) pins the deterministic half and cell (w)’s mutant passes a distinct instant.
How a real provider behaves in an outage: the cells feed polled and errored counts; that the production check reports polled: 0 when every attempt threw is read from cardano/confirmation.ts, not measured against Blockfrost.
That two answered passes are enough on a congested chain: the count is the design’s choice, and a restart resets it (it can only delay a failed write).
