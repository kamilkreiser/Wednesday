. The security service's rotate and revoke-on-rotate catches log a constant reason when the thrown value cannot be read (KS-1868)

What this changes. In Blockchain/Dev/services/security/src/index.ts two catches read the thrown value unguarded (err instanceof Error ? err.message : String(err)) inside their log call: revokePriorConnectorKeys (the retire statement, line 293 at the base) and the rotate transaction of saveKeyAndRetirePriors (the savepoint catch, line 400). A thrown value that cannot be read (a revoked Proxy throws on instanceof; an Error whose message getter throws) made that read throw out of the catch. Each read now sits in its own try with the fallback unreadable thrown value; the line is logged and the function returns null, as it does for an ordinary error (KS-577's contract). 1 product file, +14/-2; two new test files, 3 cells each.
TIER 1: a behaviour change for an unreadable value in the rotate transaction. Base: the throw escaped the transaction callback after ROLLBACK TO SAVEPOINT, transaction() issued a full ROLLBACK, the function rejected, and the register-connector route (index.ts lines 1393 to 1407) answers 500 or 503 "the API key could not be saved, so no key was issued" with nothing persisted. Head: the new key is committed and returned, the prior keys stay live, and the route answers 201 with priorKeysRevoked: null. An ordinary Error at the base already ends that way (measured below), so the change adds no new outcome: it makes an unreadable value behave like every other retire failure. The route's answers are read from the source, not run.
