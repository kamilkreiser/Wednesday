. nft-certificate DB catches log and carry on when the thrown value is unreadable (KS-1868, minting)

What this changes. Four catches in Blockchain/Dev/services/nft-certificate/src/services/minting.service.ts (+28/-4, +7/-1 each): dbSaveNFTCertificate (line 90 at the base), loadFromDb (129), getNFTCertificate (504) and getUserNFTCertificates (584). Each logs a failed database call and carries on; none rethrows. Each read the thrown value with err instanceof Error ? err.message : String(err) and no guard, which throws for a revoked Proxy (instanceof throws) or for an Error whose message getter throws; the log line was then never written and the function rejected with that new error. Each read is now in an inner try with the fallback 'unreadable thrown value', so an unreadable value is handled like an ordinary error. For an ordinary Error nothing changes: the log text, the level and the return value.
What changes for an unreadable value, function by function (callers read at the base with git grep, not exercised). dbSaveNFTCertificate is awaited inside mintNFT's try (lines 234, 290 and 350, and through updateStatus at 243, 250 and 315; the try spans 219-362 and its catch at 363 calls classifyMintError), so the new error used to propagate into that catch. The call at line 350 runs after the mint has succeeded: an unreadable save error there turned a successful mint into success: false with MINT_FAILED (HTTP 400) and a FAILED record. It is now logged, like any ordinary save error, and the mint reports success. Line 376 sits in that catch. Line 426 (recordClientMint) has no catch of its own; its route, POST /record, wraps it and answered 500, and now answers as it does for an ordinary save error. loadFromDb is called once, from server.ts:42 inside a try. getNFTCertificate now falls through to return null, so GET /certificates/:id answers 404 where an unreadable value gave 500; getUserNFTCertificates returns the in-memory certificates.
