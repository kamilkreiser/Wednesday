. The gateway refuses a document create from a caller with no write role or scope before the approval workflow writes anything (KS-1871)

What this changes. The gateway handles POST /api/documents itself (services/api-gateway/src/routes/verification.ts). For a document type that requires approval, it called createWorkflowInstanceIfRequired, which stores a workflow instance and the submitted body as a pending document, and answered 201 pending_approval for any authenticated caller. The same caller on a non-gated type reached originate and got its 403. Before the workflow gate, the gateway now applies originate’s own create rule: a document-write role (ISSUER_ADMIN, ORG_ADMIN, SYSTEM_ADMIN or SUPER_ADMIN, ASCII case fold) OR the documents:write scope. A caller with neither gets originate’s exact 403 FORBIDDEN, “Forbidden: your role does not permit document creation”.
OWNER keeps its 201. Every OWNER login token carries documents:write (KS-151, the auth service’s getDefaultScopesForRole), and originate admits it through the scope arm. So the ticket’s “OWNER must get 403” holds only for an OWNER token without that scope, such as an OAuth mint. Refused now: VERIFIER, HOLDER, USER, ISSUER, ADMIN, no role, and a connector key whose only scope is the legacy register.
Where the gateway is stricter than originate. An array-valued role and a Unicode case-fold (a dotless i) are refused; originate’s String(role).toUpperCase() admits both (the KS-1591 class). No real token carries either. The role list is a gateway copy of originate’s DOCUMENT_WRITE_ROLES, and a drift cell fails if the two differ.
A connector set to bypass the workflow also bypasses this check (QA gate 56, F1): with workflowPolicy: 'bypass' it writes no workflow and is forwarded to originate, whose own create rule then decides (the gate measured the forward and read originate’s refusal from the code; no real originate was run).
