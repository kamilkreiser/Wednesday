. The SQL-injection guard reads multi-line templates, filters by file path only, fails when its scan fails, and carries a reasoned allow list (KS-1867, KS-1865)

What this changes. Blockchain/Dev/scripts/check-no-sql-injection.sh (pen-test M6, run by pre-push leg 15 through run-code-guards.sh) matched one line at a time, so the three interpolated *RawUnsafe templates in the tree, which open the call on one line and interpolate on a later one, were reported 0 of 3. It is now two stages: grep -rl lists the files that name $queryRawUnsafe or $executeRawUnsafe (.ts .tsx .js .jsx .mjs .cjs .mts .cts, node_modules excluded), and awk reads each one whole, finds the call (a generic such as $queryRawUnsafe<T[]>( allowed), steps over whitespace and newlines to the first argument, and reports it when that is a template literal holding an unescaped ${ before its closing backtick. A ${ in a later argument is a parameter value and is not reported.
The path filter (KS-1865) looks at the file path only and matches whole segments: a node_modules directory at any depth, a dist directory directly under services/<x>/ or packages/<x>/ (tsc's output), and the one exempt file services/originate/src/db.ts. The old grep -v matched anywhere in the hit line, so a path or a code line that merely contained node_modules or /dist/, a service named not-originate, or a db.ts line with a backslash before $queryRaw read as clean. The scan can fail: grep's exit status 1 is no match, 2 or more is a failure; anything grep wrote to stderr is a failure; the two roots are checked by name (BSD grep exits 1 and says nothing for a missing path once --include is given, measured 2026-11-02); a failing awk is a failure. Exit codes are 0 clean, 1 a violation or a stale allow-list entry, 2 the scan failed. The OK line says how many files it read.
The allow list (scripts/check-no-sql-injection.allow, Wednesday's ruling 2026-11-02): one tab-separated entry per site: path, opener line (trimmed), the ${...} expressions of its first template, reason. A site is allowed only when all three keys match, so changing what is interpolated stops the match; an entry covers one site; an entry that matches nothing fails the guard; a malformed line exits 2. Every run prints ALLOWED (n) and ALLOWED-OPEN (n). A reason starting OPEN: marks a site that is not cleared and is counted apart. Three entries: originate/src/routes/webhooks.ts:310 and signatories.ts:346 (traced: the interpolated text is fixed column fragments and counters, every value is a bound parameter), and packages/shared/src/db/optimization.ts:105 as OPEN against KS 1929 (two caller-supplied identifiers, unvalidated, 0 in-repo callers, external callers unmeasured because the package is publishable).

.3 What this does not prove

It finds a pattern, not a flow; one site is open. The guard reads the first argument of a *RawUnsafe call when it is a template literal. A query built into a variable first, or by string concatenation, is not read (the header says "string-concatenated" but only the template form was ever checked). An expression that holds a nested template literal is cut at the nested backtick (the entry's expression field is then shorter, which is stable). The reason on an allow-list entry is a human claim; the guard checks that the site has not changed, not that the claim is true. The optimization.ts entry is OPEN, not cleared: KS 1929 fixes it in a second change and removes the entry there.
Not run: the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), a booted stack, the pre-push hook beyond leg 15's entry point, Node, any deploy. Nothing deploys from this change.
