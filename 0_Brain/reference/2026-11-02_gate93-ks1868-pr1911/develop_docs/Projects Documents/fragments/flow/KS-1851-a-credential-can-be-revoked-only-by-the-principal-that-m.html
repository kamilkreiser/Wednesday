. A credential can be revoked only by the principal that may read it, and a refused revoke reads exactly like an unknown id (KS-1851)

What this changes. POST /api/credentials/:id/revoke in vc-issuer checked neither the caller’s role nor who created the credential, so any signed-in caller who knew an id could revoke it. KS 1116 had bound the reads only.
The revoke is now bound exactly as the read is. The route loads the row’s owner with getRecordById and applies mayRead (ownership.ts) before credentialRepo.revoke runs:
  • The caller must be the creating principal: the same userId and the same tenant.
  • For a row with no recorded owner, the KS 1116 ruling applies: a tenant administrator of the row’s own tenant, nobody when that tenant is unknown. Superseded for credentials by KS 1906: a platform administrator of the row’s own tenant.
  • A caller who may not revoke gets the same 404 “Credential not found” as an unknown id, nothing is written, and the reason is not logged. The shared error handler still writes one error-level line for the refusal, the same line an unknown id gets, and it never contains the reason.
  • No platform or tenant-administrator bypass is added; who may revoke another principal’s credential is an open question for the product owner.
One new test file (ks1851-credential-revoke-bound-to-the-creator.test.ts, 29 cells, on the KS 1116 harness, which it extends and does not edit). The spec already declares the 404. The status-list revoke (POST /api/status/:id/revoke) is a different route and is not touched.

.3 What this does not prove

Unit level only. No request was made to a running stack or a real database. vc_credentials_store has no row-level security, so this route check is the only control on the revoke UPDATE. How guessable a credential id is, and whether the verify routes act on a revoked flag (KS 1352, KS 1375), are not assessed here.
Not run: the four platform suites (Schemathesis, Akto, Playwright, Performance/k6), Node 24, any deploy.
