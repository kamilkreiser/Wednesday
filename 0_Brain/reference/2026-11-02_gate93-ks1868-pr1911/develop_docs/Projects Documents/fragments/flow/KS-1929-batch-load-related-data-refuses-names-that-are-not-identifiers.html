. batchLoadRelatedData refuses a model or related field that is not a plain SQL identifier (KS-1929, shared)

What this changes. batchLoadRelatedData in Blockchain/Dev/packages/shared/src/db/optimization.ts runs SELECT * FROM ${model} WHERE ${relatedField} = ANY($1) through $queryRawUnsafe, which binds values, not identifiers, so the two names were written into the SQL text unchecked. The function is exported (export * from './db/optimization' and the package subpath ./db/optimization) from a publishable package, so a caller that passes request-derived text would inject SQL. Both names must now be plain SQL identifiers: a string, at most 63 characters (Postgres's identifier limit), matching ^[A-Za-z_][A-Za-z0-9_]*$ anchored at both ends. Anything else throws the constant Invalid SQL identifier before any query goes out; the refused value is never in the error. parentIds stays a bound parameter. For valid input the SQL text and the result are byte-for-byte what they were. The export is not removed: consumers that cannot be seen could break. The SQL-injection guard's entry for this site changes from OPEN to a reasoned entry that cites the validator.
One new vitest file, packages/shared/src/__tests__/ks1929-batch-load-related-data-identifiers.test.ts, 45 cells, with a mocked client that records what reaches $queryRawUnsafe: valid names (V: the exact SQL text, the grouping, upper and lower case, a leading underscore, exactly 63 characters), the bound ids (B: a hostile id arrives as the second argument and is not in the SQL text), and refusals (R) for both parameters: a double quote, an injected statement behind a valid head, a line comment, a block comment, a space, a dot, a single quote, a hyphen, a leading digit, an empty string, a fullwidth lookalike letter, a non-ASCII letter, a trailing and a leading newline, a valid tail behind injected text, 64 characters; five non-string shapes (a number, null, undefined, an array and an object that read as a valid name); the error text is the constant.

.3 What this does not prove

It closes the identifier hole, not the function's other exposure. The helper still builds SQL text by interpolation (now from validated names only). A schema-qualified name such as public.documents is refused; nothing in the repository passes one. getOptimizedCount in the same file indexes the client with a caller-supplied name (prisma[model].count): a different shape, no SQL text, not changed. Not run: a booted service, a real database, the four platform suites, Node 24 or any LTS Node, any deploy.
