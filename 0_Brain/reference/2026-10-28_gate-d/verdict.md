## Findings

MAJOR: none.

MINOR
- **M1 (#1773): the stated side effect misses HEAD.** The commit, the .ts comment (api-gateway.openapi.ts, block above the registration) and R1's title say a non-GET "was the fall-through 404" and is now 405. For POST/PUT/PATCH/DELETE that is true (measured). For **HEAD it is not**: at base, Express routes HEAD to the GET handler, so `HEAD /api/platform/document-lookup` answered 400 (no params) or 503 (?hash, DB unset); after publishing it answers **405 Allow: GET**, because `buildSpecMethodMap` (specRouteMap.ts:41-44) only admits methods the spec declares and the spec declares only `get`. A client or uptime monitor that HEADs this public path would change from a handler answer to 405. This is the gateway's existing behaviour for every GET-only published path (not created by #1773) and is arguably inside "non-GET methods answer 405", which Wednesday accepted; it is MINOR because the "were 404" wording is wrong for HEAD and nobody has ruled on HEAD specifically. Fix options for Wednesday: accept as-is and correct the wording in docs section 83 at merge time; or rule that HEAD should be admitted gateway-wide (a separate ticket, not this PR).

LOW: none.
