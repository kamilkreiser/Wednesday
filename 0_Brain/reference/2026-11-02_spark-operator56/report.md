- Reachability (read at the tip, then measured by the red/green cells): `dbSaveApiKey` (:453) catches first and reads `err?.message` (:471) before rethrowing the raw value (:479). So a revoked Proxy (or an Error whose MESSAGE getter throws) is turned into an ordinary TypeError/Error by that read and the route catch sees an ordinary Error: that is cell C3 (revoked Proxy), GREEN at the tip, so it is NOT a red cell. - Today vs after: the route sets `apiKey.isActive = false` in memory BEFORE the try (:1568), then persists through `dbSaveApiKey(..., {rethrow:true})`. Today, with an unreadable `code`, the `.code` read throws INSIDE the catch of an async Express 4 handler: no KS-888 log line, no answer sent (the request times out; unhandled rejection). After: KS-888 line logged (infra false, no code), 500 INTERNAL_ERROR "The API key revoke could not be saved, so it may not survive a restart". An ordinary non-infra Error already gets exactly the after state (cell C1 asserts the same expectations, GREEN at the tip, checker.out "3 passed BEFORE the product sections").

## O56-P2 services/security/src/index.ts, PUT /api/keys/admin-scopes/:userId, route catch (:1767-1789; changed lines :1768 and :1773)
- hold_ready verbatim: `golden: BYTE-IDENTICAL; touched=2 product_plus=11 product_minus=2 red=2/5 green=5/5 suite=378->383 strict=True`. Model 83.1 s, 42970+2402 tok.
- THE FIX IS NOT THE SAME SHAPE AS O54-P1, and why: the catch tests `error instanceof z.ZodError` (:1768) BEFORE `isInfrastructureDbError(error)` (:1773). `instanceof` on a revoked Proxy throws a TypeError (it reads the prototype), so guarding only the :1773 read would leave a revoked Proxy still crashing the catch. The hunk reads both classifications (`isZod`, `infra`, both starting false) inside one inner try; on failure it calls `next(new Error('unreadable thrown value'))`. I chose that over a bare `next(error)` because the shared errorHandler (packages/shared/src/errors/index.ts:230) starts with `err.message` unguarded: `next(<unreadable>)` would throw inside the error handler and end in Express's default plain-text 500, which an ordinary Error does NOT produce. Handing it an ordinary Error gives the ordinary JSON 500. (errorHandler's own unguarded read is a further KS-1868 site, read from source, not run, not touched.)
- Today vs after: the transaction rolls back on any rejection (nothing written). Today, an unreadable rejection throws inside the catch of an async Express 4 handler: no answer sent (request times out). After: 500 INTERNAL_ERROR through the error handler. An ordinary non-infra Error already gets that (C1, GREEN at the tip). The infrastructure branch is unchanged (C3: Error with code ECONNREFUSED, 503 SERVICE_UNAVAILABLE, infrastructure log line, GREEN at the tip and after). A readable value takes exactly today's paths, in today's order (Zod -> 400 first, then infra 503, then next).
- Revoke/persistence outcome: none. This route is a pure scope write (the code's own docblock says so); no key is created or revoked; nothing is persisted on a rejection in either state. Nothing here changes whether a key ends up revoked.
- Callers: the route itself (`app.put('/api/keys/admin-scopes/:userId', requireAdminScopeWriter, ...)`, :1631), behind `platformRoleGate`; platform operators over HTTP.
- BEHAVIOUR CHANGE text for the PR: "When the admin-scope transaction rejects with a value that cannot be read, PUT /api/keys/admin-scopes/:userId today throws inside its catch (unhandled rejection in an async Express 4 handler: no answer sent); after, it answers 500 INTERNAL_ERROR through the error handler, the same as any ordinary non-infrastructure Error.
