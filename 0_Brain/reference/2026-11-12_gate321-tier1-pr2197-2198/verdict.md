## Q1. Is each change what KS-1868 asks? Design choices left open
- The ticket proposes ONE shared helper, `safeReason(e)`, that "read[s] `e instanceof Error ? e.message : e` and coerce[s] it with `String()` inside one `try`, and return[s] the constant `unreadable thrown value`", and says the structural change is "not done by this ticket". Both PRs choose per-site inline guards instead of the helper (the lane's established shape: PRs 1931, 1949, 1978 etc. did the same). That is a design choice the ticket leaves open; the fallback constant is the ticket's own.
- **2197** matches the helper's semantics exactly: `String(err instanceof Error ? err.message : err)` inside the try. It is now the fifth identical copy in issuerCerts.ts (list and revoke had it already).
- **2198** does NOT: it reads `err instanceof Error ? err.message : String(err)` inside the try, so the read is guarded but the coercion of an Error's `message` is not; the coercion happens later, OUTSIDE the try, in the template literal (and in the `/.../.test(msg)` of verifyKeyMatchesCert's first catch). That departs from the ticket's "coerce inside one try" and from 2197. See G321-2198-1.
- Route-visible behaviour (2198): an unreadable crypto failure now gets the same code and status an ordinary Error from that call gets, with the fallback text in the body. That is the consequence the body names; it is consistent, not new, as a class (Q2).
