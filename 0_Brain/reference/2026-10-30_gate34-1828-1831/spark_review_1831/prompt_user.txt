===== TICKET =====
KS-1836 — nft-certificate GET /api/nft/certificates takes userId from the query string, so any authenticated caller lists every recorded NFT [In Progress]

**BLUF:** Inferred from the code, not reproduced. `GET /api/nft/certificates` reads `userId` from the query string and defaults it to `'user-id'`, and `mintNFT` and `/record` store every NFT with `userId: 'user-id'`. So a bare `GET /api/nft/certificates` by any authenticated caller lists every recorded NFT across users and tenants, while `?userId=<a real id>` lists none. A `?walletAddress=<any wallet>` selector on the same route has no owner check either. Priority 2 (security), as ruled by Wednesday.

## What I read (develop d7ddfa1f6433)

* `Blockchain/Dev/services/nft-certificate/src/routes/nft.routes.ts:224-235`: `const userId = req.query.userId as string || 'user-id';` under the comment "In production, get userId from auth context". If `walletAddress` is in the query the route calls `getWalletNFTCertificates(walletAddress)`; otherwise it calls `getUserNFTCertificates(userId)`.
* `Blockchain/Dev/services/nft-certificate/src/services/minting.service.ts:224` (`mintNFT`) and `:410` (the `/record` path) store `userId: 'user-id'`, with the comments "Would come from auth context".
* `minting.service.ts:514-522`: `getUserNFTCertificates` keeps in-memory records whose `userId` equals its argument; `:550` is `SELECT * FROM svc_nft_certificates WHERE user_id = $1 ORDER BY created_at DESC`.
* `minting.service.ts:594-602`: `getWalletNFTCertificates` keeps in-memory records whose `walletAddress` equals its argument and compares nothing to the caller. This is a second selector on the same route and part of this finding, not a separate one.
* `Blockchain/Dev/services/nft-certificate/src/app.ts:45-47`: `/api` requires a JWT except the two verify operations. The caller is therefore authenticated, but nothing compares the caller to a record's owner or tenant.
