## Q1. GDPR erasure (in full)
**Code (head line numbers; base = head - 30 after the hunks).** `dbDeleteUserData` (`index.ts:362-397`) runs, in order: (1) `dbGetVerificationsByUser(userId)` (`:380`), then collects legacy `frontImageId`/`backImageId` from each decrypted `documents`; (2) only if any were found, `DELETE FROM svc_kyc_images WHERE id = ANY($1)`; (3) `DELETE FROM svc_kyc_images WHERE user_id = $1`; (4) `DELETE FROM svc_kyc_consents WHERE user_id = $1`; (5) `DELETE FROM svc_kyc_verifications WHERE user_id = $1`; (6) `subjectDeks.evict(userId)`; it returns the rowCount of (5). Statements (2) to (5) are unguarded `query` calls, so any rejection there escapes. Its own comment (`:372-373`) says "failures THROW so the event bus retries". `dbGetVerificationsByUser` contradicts that for every ordinary read error and has done so since before this PR (KS-1931).
Callers: `DELETE /api/kyc/user/:userId/data` (`:1206`, no try) and `startUserErasedSubscriber(log, dbDeleteUserData)` (`:1304`) → `userErasedSubscriber.ts:36`, try/catch that logs `err?.message` and rethrows. The bus (`packages/shared/src/events/index.ts:177-210`) calls the handler up to 3 times back to back, with no delay, then writes the event to `secuura:dead-letter` and acks it.

**Probe** (scripts/probe.test.ts, run by scripts/probe.sh; copied into the clone, then moved out to logs/_quarantine; NOT part of the PR). The KS-1845 harness the PR's own cells use (real app on a real listener, db/subjectDeks/logger stubbed), plus the REAL `userErasedSubscriber.ts` with only `initEventBus`/`getEventBus` stubbed so its handler is captured (positive control `handler_captured: true` at both). The SELECT by user_id returns one verification whose documents name `img-front-legacy` and `img-back-legacy`. Results, 15 of 15 cells ran at each (logs/probe_base_vitest.log, logs/probe_head_vitest.log):

**What is left behind.**
- (a) Ordinary error on the SELECT (base = head): the legacy image rows reachable only via the documents blob (here `img-front-legacy`, `img-back-legacy`). Everything with `user_id` set, all consents, all verifications and the cached DEK are gone. The caller is told the erasure succeeded; the event is acked and never retried.
- (b) Unreadable value on the SELECT: at base, NOTHING is deleted. The subscriber fails, the bus re-runs it immediately twice more, and if the fault persists it is dead-lettered, again with nothing deleted. If the fault was transient, a re-run completes the FULL erasure, legacy images included. The route crashes the service (G85-F2). At head: exactly (a).

**Is any outcome worse than an ordinary error at base? No.** In every case the head behaviour for an unreadable value equals the base behaviour for an ordinary Error: the same statements, the same rows left, the same answers, the same ack/retry. The only comparison where head looks worse is against base-unreadable on a TRANSIENT SELECT fault: base fails closed and its re-run can erase the legacy images, while head erases partially and acks. That is precisely the KS-1931 behaviour, which an ordinary error already has. Against a PERSISTENT fault, base deletes nothing (dead-letter) while head deletes everything except the legacy images, which is arguably better for the data subject. The one new degradation is G85-F1 (a lost log line in a double fault; the dead-letter still records the DSR). **Recommendation on Q1: GO WITH NOTES.** KS-1931 should also cover G85-F1/F3 (the subscriber's unguarded `err?.message`, and the DELETE route with no try), and it should decide whether `dbDeleteUserData` must fail closed when the SELECT fails (for example, use a SELECT that throws instead of the swallowing helper).
Limits: stand-in `query`; no PostgreSQL, Redis, real bus loop, Node 24, or production data. The unreadable value is a defensive hypothetical: pg does not reject with a revoked Proxy.
