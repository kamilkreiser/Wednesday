## CAUSE — what was wrong, in one paragraph

`.slice(0, 200)` counts **UTF-16 code units**. The input AM1 found (`'A'*199` + U+1F600 + `'zz'`) puts the
emoji's two code units across index 199/200, so the cut kept the **high surrogate alone**.
`encodeURIComponent` throws `URIError: URI malformed` on a lone surrogate; the call sits in an `async`
Express 4 handler on an **unauthenticated** route; m365 registers **no** `process.on` handler; so the
rejection was unhandled and the process ended. develop did not have it — the previous commit introduced it.

I reproduced the throw in my own run before fixing anything: the red-first suite logged
`URIError: URI malformed` at **`src/index.ts:465:121`**, which is the redirect line itself.

## THE FIX — two defences, and which cell proves which

1. **`capCodePoints(value, 200)`** — `Array.from(String(value)).slice(0, 200).join('')`. Caps by **code
   point**, so a cut cannot land inside a pair. This removes the *source* of the throw.
2. **`encodeReflectedText(value)`** — `encodeURIComponent` in a `try`, falling back to the same encode
   after replacing **lone surrogates only** (`/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/g`
   -> U+FFFD). A valid pair survives it; I checked the naive alternative (`/[\uD800-\uDFFF]/g`) and it
   **mangles valid pairs**, so the precise form is deliberate, not incidental.

**Defence 2 is unreachable over HTTP once defence 1 is right**, and that is on purpose — it is there so a
later caller on this route cannot turn a malformed string back into a dead process. Measured: the guard
is a byte-for-byte no-op versus `encodeURIComponent` on every code-point-capped alphabet I tried
(ascii, U+00E9, U+0800, U+FFFD, astral, `%`, `&`, `#`, space). **So no request-level cell can prove it**
— E7 calls it directly, and the mail says so rather than implying a request exercises it.

Both helpers are **exported** from `index.ts` for exactly that reason.

## THE BOUND IS LOOSER THAN AM1'S, AND THAT IS MINE TO DECLARE

AM1 measured **1,859** chars worst-case Location for a 200-**code-unit** cap. My cap counts **code
points**, and an astral code point is 2 code units, so 200 of them encode to 2,400 chars:

```
ascii          200 cp -> Location  259
BMP U+0800     200 cp -> Location 1859
astral U+1F600 200 cp -> Location 2459   <- the new worst case
'%'            200 cp -> Location  659
```

So I **loosened** the bound from 1,859 to **2,459** while fixing the crash. Still bounded, still
deterministic, against develop's unbounded reflection (AM1 measured 9,059 on the same input, limited
only by Node's 16 KB header limit otherwise). **If the gate wants the tighter bound**, the alternative
is to keep the 200-code-unit cut and drop a trailing lone high surrogate instead — surrogate-safe with
the 1,859 figure preserved. I chose code points because "200" then means what a reader thinks it means,
and a cap that counts an emoji as two characters is the next bug. E8 pins whichever is chosen. Say the
word and it is a one-line change, but I did not want to present the looser bound silently.
