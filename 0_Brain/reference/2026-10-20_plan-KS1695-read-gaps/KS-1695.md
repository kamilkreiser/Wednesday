# KS-1695 Security: same-tenant read gaps on certifications and owner-less documents — GET /api/certifications/:id has NO ownership check at all, and an empty owner skips the documents.ts:1124 cloak (both pre-existing, measured by gate BX1) | priority 2 | state Backlog | updated 2026-10-20T01:19:54.807Z
## BLUF

**Two pre-existing read gaps in** `services/originate`**, both measured on real Postgres 15 as** `secuura_app` **(NOSUPERUSER, NOBYPASSRLS) by gate BX1 while gating PR #1659.** Facts only — **no fix is proposed here**, because the remedy is a design on an auth read path and is ruled before it is built.

1. `GET /api/certifications/:id` **has no owner, holder or org check at all.** A **human-issued** certification that the documents GET *does* cloak is served **200 to every same-tenant user of any organisation**.
2. **An empty owner skips the documents cloak.** `documentRepo.ts:176` derives `''` from `owner_user_id` NULL + `issuer_user_id` NULL, and `documents.ts:1124`'s conjunction is false on `''`, so the 404 cloak never runs. Affects **bare-connector documents** (on `develop` today) and, since `3cc46ae41fed`, **holder-less connector certifications**.

Neither was introduced by PR #1659. KS-1659's fold added a new **row type** to gap 2's existing class, not a new audience, and the gate's control proves it.

## ⚠ This falsifies KS-621's central premise for one row class

KS-621 is the tracking ticket for "document reads are scoped by tenant and owner, never by organization", and it states: *"**Nothing is leaking.** Cross-org document reads are denied today, and that was proved with a control... What actually denies the read is a **per-owner 404-cloak**."* **That cloak does not run when the owner is empty.** For owner-less rows the emergent cross-org protection KS-621 describes is therefore **absent, not merely unenforced**. A comment has been left on KS-621 pointing here.

## Measured audiences (gate BX1)

**a** = same-tenant `ISSUER_ADMIN`, same organisation · **a2** = same-tenant `ISSUER_ADMIN`, **another** organisation · **b** = another tenant · **c** = the issuing connector.

| row | tree | endpoint | a | a2 | b | c |
| -- | -- | -- | -- | -- | -- | -- |
| connector certification, no holder | landing | `GET /api/documents/:id` | **200** | **200** | 404 | **200** |
| **bare-connector** `POST /api/documents` (owner NULL, issuer NULL) | **develop AND landing** | `GET /api/documents/:id` | **200** | **200** | 404 | **200** |
| human-issued certification, no holder (owner = issuer = a UUID) | both | `GET /api/documents/:id` | 404 | 404 | 404 | 404 |
| **human-issued certification** | **develop AND landing** | `GET /api/certifications/:id` | **200** | **200** | 404 | — |
| connector certification, no holder | landing | `GET /api/certifications/:id` | **200** | **200** | 404 | **200** |

The owner-less 200 body carries `"owner":{"id":""}` plus title, data and contentHash. The human-certification row being 404 on the documents path is the **positive control**: the cloak works when the owner is non-empty, so these 200s are not "everything is readable".

**Audience for the owner-less class: the whole tenant, every organisation, all roles.** ⚠ **Kam's KS-1116 ruling — owner-less rows readable by the row tenant's administrators (**`ORG_ADMIN` **/** `SYSTEM_ADMIN` **with a tenant on the token) — is NARROWER than what ships today for both row types.**

**List endpoints are not affected:** `documents.ts:321` filters on `d.owner?.id === userId` and the certifications list filters on holder or issuer id. Only **c** saw the new id in a list.

## Where

* **Gap 1:** `services/originate/src/routes/certifications.ts:956-1010` — calls `getCertification(id, tenantId)` and returns issuer, holder, data and blockchain with no access predicate.
* **Gap 2:** `services/originate/src/repositories/documentRepo.ts:176` → `id: row.owner_user_id || row.issuer_user_id || ''`; `services/originate/src/routes/documents.ts:1124` → `if (userId && document.owner?.id && document.owner.id !== userId && !isAdmin && !isRecipient)`.

## The remedy shapes BX1 costed — options, NOT a decision

1. **Fail the cloak closed at** `documents.ts:1124` (drop the `document.owner?.id &&` conjunct). One line, covers both row types. **Cost, measured: it strands the issuing connector.** A bare connector create writes **no** `create` **row in** `action_provenance` (0 rows against 12 documents), so `wasCreatedByConnector` never admits it, and per the KS-480 §6 comment at `:1126` Platform S drives the whole lifecycle through that id. Needs a companion — record a create row, or admit a connector whose organisation matches the row's. **Does nothing for gap 1.**
2. **Cloak an empty owner to admins plus the creating connector** — the KS-1116 ruling shape. Same edit plus a tenant-admin admit; same provenance dependency; does not cover gap 1.
3. **Set the owner at write time** from the connector's organisation or a tenant administrator. Reads unchanged, but it changes custody semantics (`anchorOverwriteGuard`), needs a write-path lookup, and does nothing for existing bare-connector rows.
4. **Refuse a holder-less connector certification** (400 `HOLDER_REQUIRED`). Smallest blast radius; returns to develop's "no row" with an honest error instead of 22P02-as-payload. A **client-visible contract change for Platform S**, and the bare-document class stays as it is.
5. **For gap 1: give** `GET /api/certifications/:id` **the same predicate** as `documents.ts:1124`. **Without it, options 1 and 2 do not close certification reads.**

**Plan against Kam's KS-1116 ruling**, which is the nearest precedent: a remedy matching that audience inherits his authority; a different audience is a new decision for him.

## Not measured

No gateway and no real JWT layer — BX1 mounted the routers directly with the repo's probe-user auth mock, so **any scope gating at api-gateway is unmeasured** and could narrow these audiences in production. Also not run: `MULTI_TENANCY_ENABLED=true`, a `system_admin` or recipient reader, an `onBehalfOf` connector certification, the derived lineage row. The remedies were not built.
