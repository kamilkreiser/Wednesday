##### KS-629 kyc `livenessVideo` is accepted by spec and runtime, then silently discarded — no code path reads it In Progress 2026-11-03T22:55:09.475Z
## BLUF

`livenessVideo` is accepted by both the OpenAPI spec and the runtime Zod schema on `POST /api/kyc/{id}/selfie`, and **no code path anywhere reads, stores or processes it.** A caller who uploads liveness evidence gets `success: true` and the bytes are discarded.

## Recommendation

Decide which half is right, then make the other match — do not align one to the other by reflex. Either implement storage + liveness processing, or remove the field from the schema and the spec. Documenting it as inert (done in KS-487 B-4) is a stopgap, not the fix.

## Detail

* Declared: `services/kyc/src/index.ts` `submitSelfieSchema` (`livenessVideo: z.string().optional()`) and `services/kyc/src/kyc.openapi.ts` `KycSelfieUploadRequestSchema`.
* Repo-wide grep for `livenessVideo` returns **only those two declarations plus a comment** — no reader, no writer, no persistence.
* Meanwhile the handler sets `livenessCompleted: true` and `livenessScore: 0.95` in mock mode regardless of what was sent (and regardless of whether `livenessVideo` was sent at all).

This is the KS-624/625/KS-488-C-2 family: a contract that advertises a capability the runtime does not have. Found while fixing KS-487 B-4 (magic-byte verification on the sibling image fields).

Filed from session 30. Not fixed in the B-4 PR — that PR's scope is image content verification, and silently deleting or implementing a published field is a contract change that deserves its own decision.
