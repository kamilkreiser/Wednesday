## Findings

1. **Minor: the list has no total order, so the caller's own pages repeat or skip rows.** `ORDER BY created_at DESC LIMIT/OFFSET` with ties (bulk inserts share `NOW()` in one transaction) or NULL `created_at` (the column is nullable in all three schema sources) is unstable across pages. On PG 17.5 this gave duplicates or skips in 24 of 180 walks, and 0 once `, id DESC` was appended. No foreign row was ever served and `total` is right, so this is not a confidentiality defect. But the PR's own claim is "`total` and the page are the caller's own ... page boundaries right", and by-hash got a tiebreak that the list did not. The ordering predates the PR. Fix shape: `ORDER BY created_at DESC, id DESC` in `selectList`. Regression cell: two of the caller's rows with an identical `created_at`, paged at limit 1, must yield both ids exactly once. That needs a real PG or a model that honours ORDER BY. **Evidence: MEASURED AT RUNTIME (PG 17.5, G-PG3/G-PG8).**
2. **Note: the backstop protects rows, not `total`.** If the SQL predicate ever admits more than `mayRead` (my tenant-clause-dropped mutant, on real PG), the page is cleaned but **COUNT reports the foreign rows: over-claimed for 60/60 callers. That is an existence and count oracle.** The builder's comment says this ("`total` ... would then over-claim"), and the S1 text pin is the only guard. It is adequate today because S1 kills that mutant (my P2), but any edit to the predicate must be re-measured on a real PostgreSQL, because the suite's model cannot see it. A cheap extra guard is a cell asserting `credentials.length === min(limit, total - offset)` on a full single page: it would turn a drift into a red on the model path too. **Evidence: MEASURED AT RUNTIME (mutant on PG 17.5).**
3. **Note: a caller can force the memory path with malformed `limit` / `offset`** (NaN or negative make Postgres error, and the list is served from the process-local memory copy). It is still bound (measured). But it switches data source on caller input: in a multi-replica deployment memory is replica-local, and the response carries `limit: null` / negative values. This predates the PR. Fix shape: validate both parameters (integer, `limit` 1..N, `offset` >= 0) and answer 400. **Evidence: MEASURED AT RUNTIME (repo level, G-PG5).**
4. **Note: migration 054 must be applied before ANY vc-issuer from #1648 on, and this PR does not change that.** With 054 absent, authorization fails closed (measured), but writes are silently memory-only and lost at restart, and list/by-hash now show only what was issued since boot. Before merge-to-deploy, confirm per environment that 054 is in the migration ledger. I could not reach any environment. **Evidence: MEASURED AT RUNTIME (PG 17.5, schema 001 only); environment state READ ONLY / not checked.**
5. **Note: the by-hash memory fallback is not "the newest".** On DB throw or DB unavailable, `getReadableByHash` returns the first readable match in Map insertion order. `loadFromDb` inserts newest-first and later `store()` calls append, so after any issue in-process the "first" is no longer the newest. Only the caller's own rows are in play, so this is not a leak. It is a divergence from the DB path's contract. **Evidence: READ ONLY.**
6. **Note: stale comment and no index.** Migration 054 says "No index: nothing in this change filters on the new columns". The list now filters (and COUNTs) on them on every request. This is a full scan, as the unbound list already was, so it is a performance note, not a regression. **Evidence: READ ONLY.**
7. **Note: connector principals without a `connectorId` share one owner identity.** Every such API key mints `userId: connector:api-key`, so within one tenant they read each other's credentials. This is the KS-1116 rule applied as written and is the same on `/:id`. I raise it only because list now makes it visible in bulk. **Evidence: READ ONLY.**
