## Findings

**Major**

1. **The auth baseline is machine-specific; the push gate fails everywhere but one worktree.** `scripts/typecheck-tests/baseline-auth.txt:10` is `src/__tests__/ks1006-mfa-disable-refuses-when-no-secret-is-stored.test.ts TS1192 67406236 1`. The tsc text is `Module '"<ABSOLUTE PATH>/Blockchain/Dev/services/auth/src/repositories/userRepo"' has no default export.`, and `check.cjs:79-80` hashes the whole message (`fingerprint`, used at `:86`). I brute-forced the fingerprint over the 567 candidate paths of the project: it matches `/Volumes/DevMASTER/!CODING/Secuura/Blockchain/worktrees/s-v3-l05g` and nothing else (`MATCH ...worktrees/s-v3-l05g`). Run from any other path (my `head`, `merged` trees, same commit) the result is `42 errors: 41 in the baseline, 1 new; 1 stale`, rc 1, the NEW line printing my path and the STALE line `TS1192 67406236: baseline 1, now 0`. `--update` there is a dead end (`refuses to admit 1 new entry`, rc 1, file sha unchanged), so the documented repair path does not work. Effect: leg 16 (`test-types-ratchet.sh`), the KS-1000 `REAL` cell (`ks1000...test.ts:144-150`, fails 18/19 at any other path) and `npm run check:test-types` go red for every seat, the main checkout and any CI that is not that worktree; develop at the same path passes. The api-gateway baseline is unaffected (regenerating both baselines at two paths with `--init`: gateway identical except the floor 113 vs 114; auth differs in exactly this one line). The test suite cannot catch it because the fixtures never emit a path-bearing message. Fix direction (not mine to apply): normalise the service/repo root out of the message before hashing (replace the absolute `serviceDir` prefix with a token), add a cell with an import of a missing default export from a sibling file, and `--rekey`/regenerate the entry. Any future TS1192/TS2307/TS2305-style baseline entry has the same trap.

**Minor**

2. **Fingerprint stability across paths is untested; position-free identity is pinned only by the REAL cell.** Mutant G2 (position in the hash) is killed only by the `REAL` cell, which depends on the committed file; no synthetic cell moves a line.
3. **`@ts-ignore` / `@ts-expect-error` are an open bypass** (probe: planted `TS2322` under `// @ts-ignore` in a non-baselined file, rc 0). Stated by the builder as a known limit but not written in `check.cjs`, CLAUDE.md or the test (zero hits); only the PR body, which I did not read. Today there are none in the two services' tests.
4. **A baseline with no `examined-test-files` line silently has no floor** (`check.cjs:204` `base.floor !== null`): deleting the line, then deleting a test file, gave rc 0. Likewise a second `examined-test-files 0` line wins (`check.cjs:118`, last wins) and a duplicate entry key overwrites rather than being rejected (`:117`). All are visible baseline edits, but a converted baseline lacking a floor should be exit 2, and duplicates should fail.
5. **A CRLF comment line makes the baseline unreadable (rc 2)**: `check.cjs:114` `raw.replace(/#.*$/, '')` does not strip a comment ending in `\r` (`.` does not match CR), so the header line reads as garbage. Entry lines with CRLF are fine. Fails closed; would bite a Windows/autocrlf checkout. No `.gitattributes` in the tree pins eol.
6. **`--init`/`--update`/`--rekey` will write a baseline the reader then rejects** for a path with a space or a `#` (probe: `--init` rc 0 "wrote", next check rc 2 at the entry line). Fail-closed and documented in the header (`check.cjs:39`) but the writer should refuse instead of reporting success. None exist in the repo.
7. **Four guards have no killing cell** (mutants survived 19/19): the `/m` flag on the `@ts-nocheck` regex (`:100`; the test puts the comment on line 1; a header-comment-first file is the common real shape and my probe shows it works today), and the unbaselinable refusal in `--init` (`:154`), `--rekey` (`:162`), `--update` (`:197`). Low impact (a subsequent plain check still fails on the same item) but the 19-cell claim of "every guard killed" is not true for these.

**Note**

8. `test-types-ratchet.sh:66-74` still says exit 1 means "a NEW test-file type error, or a baseline entry that no longer reproduces" and "Fix the type error"; it now also means a swap, a `@ts-nocheck`, a dropped diagnostic or a fallen floor, and exit 2 also means a count-only/unparseable baseline. The checker's own output names the cause, so it is wording only.
9. The `@ts-nocheck` matcher (`:100`) is broader than tsc: `/* @ts-nocheck */`, a block-comment line, a line after the first statement and a line inside a template literal are flagged although tsc does not honour them (probe, `tsc suppresses the error=false` for those). Fails safe (refuses something harmless); the header comment's "comment forms tsc honours at the start of a line" is not what the regex does.
10. The floor protects only down to its last recorded value (builder's stated limit); a baseline recorded at floor N, with a tsconfig narrowing that keeps N or more, is not caught. Confirmed by construction, not separately run.
11. Test files outside `__tests__` are invisible to both the floor and the nocheck guard (`:95`); none exist today (find, rc blank).
12. develop moved one commit (88c348375) after the builder's base; it touches a new api-gateway test and `verification.ts`. Merge is clean and the gateway ratchet passes on the merged tree (floor 113 -> 114 examined, no baseline change needed). If the builder re-keys, it must re-run on a path-independent normalisation, not at its own worktree.
