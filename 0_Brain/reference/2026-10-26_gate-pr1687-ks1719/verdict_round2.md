## Findings
1. **Minor — item 1 is bounded to the account, not to "what the suite created".** `proposerId == admin_client's user` is every proposal that account ever made, including a human's using the shared `admin@secuura.com`, and including that account's own `queued` ones. Oldest 3, active/queued only. For a disposable slot this is exactly right; on a shared box where people propose as `admin@secuura.com`, it can still cancel theirs. The README slot rule (local runs must name a slot) is the remaining bound. Acceptable; say it that way.
2. **Minor — the per-row and fail-closed layers are tested; the server-side filter is not.** Plant D passed: nothing asserts the helper actually sends `proposerId`. Effect if it were dropped is not unsafe (the per-row check still holds) but the list would then also carry other proposers' rows, and with a long list the oldest-own could fall outside what the route returns (the route has no limit in this code, so unlikely). Cheap to add one assertion on the request params.
3. **Note — the "sweep persona == admin_client user" assumption is still unmeasured.** The code agrees (both resolve to `admin@secuura.com` by default), but I did not observe a sweep's proposals carry that user's id. If the sweep ran as a generated actor under `run-in-slot.sh`, the helper would free 0 on that slot. The comment's last paragraph discloses the TEST_ADMIN_EMAIL case but not that one.
4. **Note — mypy count not reproduced** (environmental abort); unit +21 delta confirmed.
