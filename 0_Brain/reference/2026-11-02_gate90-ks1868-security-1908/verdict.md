**My judgement:** moving this failure mode from fail-closed onto the existing fail-open path is acceptable as a KS-1868 raise. It happened because the log call itself crashed, and the code's own contract (index.ts:346-348 at head, and the route comment at :1401-1403) says a failed retire leaves the mint standing and reports `null`. Keeping fail-closed only for this unreachable value (mutant M3, "rethrow only when unreadable") would keep an accident and leave the reachable ordinary-error path fail-open. **Q1 is not a design decision about this PR.** It does sit beside one that is real and pre-existing (KS-1152 R-880-1, plus G90-F1 below), and that question is worth a card for Kam on its own.

## FINDINGS
- **G90-F1 (INFO for this PR; the real design question; pre-existing, belongs with KS-1152 R-880-1; read from source, not run)** The only production caller of the rotate path is the gateway's `register-connector` route (`api-gateway/src/routes/platform.ts:884-919`), and it **drops `priorKeysRevoked`**. When the value is `null` it only writes a `console.error`, then answers the operator 200/201 with `rotated: true` (platform.ts:919). So after ANY retire failure (an ordinary error at base, or now an unreadable one too), an operator re-keying a lost or compromised credential is told `rotated: true` while the old key still validates. This PR adds no new outcome here; it adds one more input that reaches it. This is the card for Kam: should a rotate whose retire fails (a) fail closed (roll back and refuse), (b) stay fail-open but carry `priorKeysRevoked` / `rotated: false` up to the operator, or (c) stay as it is? It is not a merge block for 1908.

**Who can make that UPDATE reject with an unreadable value?** Nobody who acts on the system. The rejection value is whatever node-postgres's `client.query` rejects with. For a server error that is a `DatabaseError` (an `Error` subclass whose `message` is a plain data property); for a lost socket or pool trouble it is an ordinary `Error`. The statement's parameters (`retirePriorStatement`, :215-230) are all built by the server: a zod-validated string `connectorId` (from the gateway, `platform-s:${externalRef}`), the tenant uuid, the server-generated key id and `String(grace)`. No caller supplies an object that pg would call into. The caller is a platform role in any case (rotation is platform-only, :1361-1369). An unreadable rejection needs a defect in pg itself, a wrapper or monkeypatch around the client, or a test double. It is defence-in-depth, like every other KS-1868 site. The thrown values in both the PR's cells and this probe are synthetic.

**Judgement.**
- The base behaviour for this value was fail-closed only by accident: the `log(...)` argument `err instanceof Error ? err.message : String(err)` threw a fresh TypeError out of the savepoint catch. That TypeError, not any design, made `transaction()` roll back. The designed contract for a failed retire is in the function docblock (:346-348: "null if the retire FAILED (KS-577's contract: the new key still stands and the failure is reported)") and in the route comment (:1401-1403). Head brings the unreadable value into line with that contract.
- A rotate path for a security credential could fairly be made fail-closed, but then it should be fail-closed for the REACHABLE failure (an ordinary retire error: a lock or statement timeout, an RLS misconfiguration, a dropped connection between INSERT and UPDATE). Keeping fail-closed only for the unreachable unreadable value (M3) protects against nothing that happens and leaves the real path fail-open.
- At :293 head is strictly better (G90-F6): base dropped the new key after it had already retired the prior one in memory.
- **Recommendation: GO WITH NOTES, no fix-before-merge.** Wednesday's card for Kam should be about R-880-1 together with G90-F1: whether a rotate with a failed retire should be refused, or should at least reach the operator as `rotated: false` / `priorKeysRevoked: null` instead of being swallowed by the gateway. Whatever Kam rules there applies to ordinary and unreadable values alike, and this PR makes that ruling simpler to implement, because both now arrive at the same `return null`.
- Limits: a stand-in pg (rows here are a model, not PostgreSQL), no real boot, no gateway hop run (the gateway behaviour is read from platform.ts), Node 26.8.1 rather than 24.
