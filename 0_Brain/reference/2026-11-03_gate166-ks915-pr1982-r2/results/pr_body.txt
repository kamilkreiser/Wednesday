Behaviour change first:** a developer can now get working local platform-k credentials from one command, `Blockchain/Dev/scripts/restore-local-secrets.sh`, generated on their own machine, instead of asking someone to send a password. **Nothing in any deployed environment changes:** no product code, seeder, compose file, env template or `bootstrap-env.sh` line is edited, and nothing deploys from this PR.

**Gate questions:** (1) can any path print or commit a generated value? (2) does a second run ever change a working set? ## Why

`Blockchain/Dev/env.example` (the canonical template) ships `ADMIN_USER_PASSWORD=` and `ALLOW_DEFAULT_SEED_PASSWORDS=` empty, and `bootstrap-env.sh` fills only the infrastructure keys. The auth seeder (`seedDemoUsers`, `services/auth/src/repositories/userRepo.ts`) skips everything unless `ALLOW_DEFAULT_SEED_PASSWORDS === 'true'` (L1332) and seeds the platform admin only from `requiredSeedPw('ADMIN_USER_PASSWORD')` (L1407). So a clone that follows the docs seeds no users, and the admin password systemTest asks for (`BOOTSTRAP_ADMIN_PASSWORD`, systemTest/README.md L84) exists nowhere. The ticket's own words: "A clean stack has no supported way to obtain its first privileged account." This PR is the "one-shot bootstrap command" the ticket names, scoped to a developer's local stack.

The name matches platform-s's script so a developer finds it. The mechanism is deliberately different: platform-s's `restore-local-secrets.sh` copies files from a store the developer already holds (a transfer); this one generates the values locally, so nobody sends anybody a password.

## What the script does, in order

1. **Refuses first, writing nothing (exit 3):** when `.env` or `.env.local` is a symbolic link; when `DATABASE_URL` names a host other than `localhost`, `127.0.0.1`, `::1` or the compose service `postgres`, names more than one host (a comma, or anything after `]` but a port), carries a `host` or `hostaddr` query parameter or a percent-encoded parameter name, or cannot be read as a URL; when `NODE_ENV` is `production` in any case. Both keys are read **the way their consumers read them**: the shell, and every line of `Blockchain/Dev/.env` (or of the template a fresh `.env` is copied from) that dotenv 16 or `docker compose` would read as that key, in any spelling (`export KEY=`, leading spaces, `KEY = v`, `KEY: v`, quotes, an inline `# comment`), each read three ways (as the consumer would, cut at any `#`, and whole); **one reading that is not local is enough to refuse**. `ALLOW_DEFAULT_SEED_PASSWORDS=true` turns on the published demo accounts, which must never happen on a shared box. The message names the variable and where it was read, never the value.
2. Runs `bootstrap-env.sh` unchanged.
3. Fills **only when blank in every spelling**: `ADMIN_USER_PASSWORD` (`openssl rand -hex 24`) and `ALLOW_DEFAULT_SEED_PASSWORDS=true`. A set value, in any spelling, is kept; `--rotate` replaces `ADMIN_USER_PASSWORD` (every spelling becomes one `KEY=value` line), and nothing else replaces anything. `ALLOW_DEFAULT_SEED_PASSWORDS` that is `true` in another case (`TRUE`) is rewritten to `true` and the output says so, because the seeder compares exactly; any other explicit value is kept. The value reaches `awk` through its environment, not its argument list; the file is replaced by one rename from a `mktemp` copy named `.env-ks915.XXXXXX`, which the root `.gitignore` (`.env-*`) covers, so a copy left by a SIGKILL cannot be committed.
4. Sets `.env` and `.env.local` to mode 0600 (a complete `.env` left at 0644 is brought back without a rewrite).

It prints names, paths and lengths only. Compose already forwards both names from `.env` to auth (`docker-compose.yml` L791 and L821), so `docker compose up -d` recreates auth and its seeder (which re-hashes an existing row on every boot) picks the values up.

**Out of scope, on purpose:** `DEMO_SECUURA_PASSWORD` (auth's only `env_file` is `.env.local`, so a value in `.env` never reaches it) and the published `*123` demo defaults, both `KS-668`'s question.
