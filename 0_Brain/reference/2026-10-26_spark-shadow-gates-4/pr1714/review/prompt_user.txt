===== TICKET =====
KS-1729 — vc-issuer unit suite: the first run after `npm ci` skips 110 cells - three files cold-import the routers inside their first beforeAll and lapse the 10 s hook (import 87.5 s cold vs ~5 s warm) [In Progress]

## BLUF

**The first** `vitest run` **of** `services/vc-issuer` **after an** `npm ci` **exits rc 1 with 0 failed and 110 cells SKIPPED.** Three files cold-import the routers inside their first `beforeAll`, and that import lapses vitest's 10 s hook timeout. A second run passes all 412. **The trigger is the cold first run, not the machine's load:** the 87.5 s run started at load1 5.58, while a warm run at load1 12.77 passed.

## Where

The three affected `describe`s. Each one's first `beforeAll` calls `freshModules()`, which does `vi.resetModules()` and then `await import('../routes/…')`:

* `services/vc-issuer/src/__tests__/ks1020-presentation-lookup-exact-or-404.test.ts` — describe `:129`, `beforeAll` `:137` (`freshModules` `:69`). **14 cells skipped.**
* `…/ks1116-presentation-and-credential-reads-bound-to-the-creator.test.ts` — describe `:254`, `beforeAll` `:259` (`freshModules` `:162`). **40 cells skipped.**
* `…/ks1683-credential-list-and-by-hash-bound-to-the-creator.test.ts` — describe `:196`, `beforeAll` `:208` (`freshModules` `:111`). **56 cells skipped.** This file is new on PR #1691 and has the same shape.

Line numbers are at PR #1691's head `8cc4ec4c2190`. ks1020 and ks1116 are identical on develop `28dac5c12ba5`.

## Measured

Node v26.8.1, macOS, one clone (`deploy-clones/seatK1-…`). `Duration`'s `import` figure is vitest's own aggregate.

| run | condition | load1 | `import` | result |
| -- | -- | -- | -- | -- |
| A | **first run after** `npm ci`, develop `1ae6f17d19a8`, before any edit | not recorded | not recorded (JSON reporter only) | **rc 1 — 54 skipped** (ks1020 14 + ks1116 40), 0 failed, no message captured |
| B | develop `1ae6f17d19a8`, warm, ×6 (3 of them with `node_modules/.vite` quarantined) | — | — | 300 / 300 every time |
| C | **first run after a second** `npm ci`, head `8cc4ec4c2190` | **5.58** | **87.47 s** | **rc 1 — 110 skipped** (14 + 40 + 56), 0 failed, three `Error: Hook timed out in 10000ms.` |
| D | the same head, the next two runs | 12.77 | **6.16 s / 4.86 s** | 412 / 412, twice |
| E | the same head, Docker Desktop VM wedged at \~800-900 % CPU | 54-97 | 764.91 s | 199 passed / 2 failed / 211 skipped |

So it happened on both first runs after an `npm ci` (A, C) and on none of the 8 warm runs (B, D). The cold run is \~15-18× the warm `import` cost, and it failed at a lower load than a warm run that passed. **Not separated:** whether the cold cost is the OS page cache or the on-access antivirus scanning freshly written `node_modules` files.

## A second effect under load (run E): a lapsed hook keeps running

A `beforeAll` that times out is not cancelled; its promise runs on. In run E, two cells in **later** `describe`s of the same files failed on assertions:

* ks1116 *"presentations, memory fallback: the query THROWS…"* — `expected 3 to be 1` (an INSERT count).
* ks1683 *T1* — Bob's list returned 3 rows where 1 was expected.

Both numbers are consistent with the lapsed hook's `POST /`s landing in the next `describe`'s module instance. If the late hook is still inside `freshModules()` when the next `describe` calls it, both resolve the same module after `vi.resetModules()`. In ks1683 T1, the lapsed hook issues two Bob credentials, which with T1's own makes 3, all Bob's. **That mechanism is inferred from the arithmetic, not traced.**

## Why it matters

* Every fresh clone or worktree runs this suite cold first, so a first run reads rc 1. A reader or a gate has to notice the word *skipped* to tell "never booted" from a regression. That is KS-1602's trap.
* The lapsed-hook effect turns a timeout into assertion failures in cells that did nothing wrong.

## Fix shapes (none chosen here)

* Do the cold import once at **module scope** before the first `describe`, so the expensive load happens at collection, outside any hook.
* A per-file `hookTimeout`, with the reason written next to it (KS-1602's suggested convention).
* Make `freshModules()` refuse to hand out a module instance while an earlier one is still being set up, so a late hook cannot write into the next `describe`.
