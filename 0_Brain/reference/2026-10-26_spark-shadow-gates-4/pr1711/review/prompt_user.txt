===== TICKET =====
KS-1735 — generated_guard.sh: a failed restore copy is unchecked and the stash is then deleted, so the only copy is lost without a word [In Progress]

## BLUF

`systemTest/__tests__/support/generated_guard.sh` is the shared copy of the `generated/` snapshot-and-restore guard, and its `generated_guard_restore()` has the two defects the two inline copies already had fixed. **The restore copy is unchecked, and the stash is then deleted, so a failed restore loses the only copy and says nothing.** Found while working KS-1714. **Read from source at develop** `28e2d27de337`**; not run.**

## Where (develop `28e2d27de337`)

* `:40` `cp -R "$GENERATED_GUARD_STASH/." "$GENERATED_GUARD_GEN/" 2>/dev/null` has no check and prints nothing on failure.
* `:42` `rm -rf "$GENERATED_GUARD_TMP"` runs straight after. The stash is `$GENERATED_GUARD_TMP/stash`, so it goes with it.
* Net effect if the copy at `:40` fails: `generated/` is left empty (or partial), no message, the only copy deleted, and the suite exits with its own status.
* The snapshot-failed branch (`:28-34`) prints its message and then `rm -rf "$GENERATED_GUARD_TMP"` at `:33`, which deletes the partial stash too. That branch is a different situation (a guard that could not save does not restore), but the partial copy is thrown away.
* One suite sources it: `systemTest/__tests__/bootstrap_login_diagnosis.test.sh` (`:46`). `systemTest/CLAUDE.md:1475` points the next suite that drives the DEGRADED path at it.

## Why it matters

The two inline copies, `pre_suite.test.sh` and `quarantine_call_sites.test.sh`, were hardened for exactly these two things under KS 1027 (item 1: the restore copy was unchecked; item 2: the refusal path deleted the partial stash). This file was written under KS 1167 as "the same guard for suites written after them" and carries the KS 992 snapshot check only. KS-1714 then made the inline copies exit non-zero after a failed restore; this file still has no failed-restore branch at all.

## It is the third copy

Both inline suites carry a note recording why the guard is duplicated rather than shared: a sourced helper makes the guard depend on a file that could itself be missing or unreadable, and "if a THIRD site ever appears, that is the trigger to revisit". This file is that third site.

## Two options, not chosen here

**A. Fix in place.** Check the restore copy; on failure print the message and keep the stash (`KS 1027` items 1 and 2 as the inline copies have them); exit non-zero, as KS-1714 does for the two inline copies. Smallest change; keeps three copies to keep in step.

**B. Extract one shared helper** and source it from all three. Removes the drift, at the cost the inline suites' note names: the guard then depends on a sourced file.

Either way the cell is the instrument from the KS-1714 PR: a fake `cp` first on `PATH` that fails only when the destination ends in `/generated/` (control: it copies to any other destination), a sentinel file in `generated/`, then read the suite's exit code and whether the stash survives. **Expected from the source, unmeasured:** exit status is the suite's own, `generated/` empty, no stash.
