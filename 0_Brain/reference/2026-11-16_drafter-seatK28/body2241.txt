## Summary

Seat Q 1st measured that a second signed-in user, in the same tenant and in another tenant, could read someone else's transfer and delegation by id and list every transfer. The same was open on three sibling reads. This PR closes all six transfer-service read paths with one rule.

**The rule.** A caller may read a transfer or a delegation when either holds:
- they are a person named on it, compared with `sameId` (an ASCII-only case fold). For a transfer that is `currentOwnerId`, `newOwnerId`, `initiatedBy` or `executorId`, the same `PARTY_FIELDS` as the KS-2038 write rule. For a delegation it is `delegatorId` or `delegateId`.
- they are a person whose role is a platform role, `SYSTEM_ADMIN` or `SUPER_ADMIN` (the shared `isPlatformRole`).

Everyone else gets exactly what an unknown id gets, so a refusal never confirms that an object exists. That includes every company-level role, every API key whatever id or role it carries, and a token with no user id.

**Where it lives.** Three pure functions sit beside the write rule in `services/transfer/src/services/transferAccess.ts`: `mayReadTransfer`, `mayReadDelegation` and `isPlatformReader`. `decideTransferAccess` and the four KS-2038 write doors are untouched.

| Door | Before | Now |
|---|---|---|
| `GET /api/transfers/:id` | any signed-in caller | rule; else the route's own 404 bytes |
| `GET /api/transfers/:id/history` | any signed-in caller | rule; else the same 404 bytes |
| `GET /api/transfers/document/:documentId` (door 4) | every transfer of the document | only those the caller may read; with none, byte-equal to an unknown document's answer |
| `GET /api/delegations/:id` | any caller, with the whole ancestor chain | rule, checked BEFORE `buildDelegationChain`; else the delegation 404 bytes |
| `GET /api/delegations/document/:documentId` (door 3) | every delegation of the document | only those the caller may read (filtered, not all-or-nothing) |
| `GET /api/transfers` (AC5) | every transfer (no `ownerId`), or any client-named owner's | platform reader: unchanged. Anyone else: only what they may read. An `ownerId` that is not the caller's own: an empty page. `total`, `limit` and `offset` count the filtered set |

The party rule is Kam's card `secuura-ks2038-who-may-approve-transfers-1106` = a. Keys are never a party: card `secuura-ks2038-connector-principals-on-transfer-doors-1106` = a.

### What this admits
- Every party of a transfer: owner, recipient, initiator, executor. An initiator who is neither owner nor recipient now also sees the transfer in their own list. Before, `?ownerId=` matched only the two owner columns.
- The delegator and the delegate of a delegation. A party's answer still carries the ancestor chain, which names the delegators and delegates above it, the authority they already hold through.
- `SYSTEM_ADMIN` and `SUPER_ADMIN`, in either case, on every read and the full list.

### What this REFUSES that was open before
- **Every same-tenant non-party**, a company's own administrators included: `ORG_ADMIN`, `ISSUER_ADMIN`, `ADMIN`, `OWNER`, `USER`. This is stricter than today, which Seat Q 1st measured as 200 for a same-tenant `OWNER`. The caller search found no consumer that needs the read: in-repo frontends, gateway, SDK and e2e, at live develop, 373 lines in 34 files. External SDK consumers were not measured.
- Every caller of another tenant.
- Every API key, including one that carries a party's user id or `SYSTEM_ADMIN`, and every token with no user id.
- A client-named `ownerId` on the list.
- Three existing KS-2081 cells changed by design, plus one helper:
  - `control P7 a key can still read all four GET doors` became `RED P7 a key reads nothing at the four GET doors (KS-1703)`, as its own comment said it would.
  - The two `RED R5` cells and `control R5` read the list total and the document count as `STRANGER`; they now read as `OWNER`, a party to every row that file opens. Their assertions are unchanged, and the control still proves the instrument can see a write.
  - The file's `statusOf` helper, used by 8 cells, read by id as `STRANGER`; it now reads as `OWNER`. The brief named the three cells only.

### The administrator asymmetry (D4)
The write rule admits no administrator: `transferAccess.ts`, "No role is read". Delegation revoke admits only the delegator and the delegate. This read rule admits platform administrators. The asymmetry is deliberate, per ruling W2.

### For the board seat (not filed by this PR)

  - The read routes' spec text carries no owner-scope sentence (the write doors' "a caller the transfer does not name gets the same 404" sentence).

- `systemTest/schemathesis/tests/test_get_by_id_object_authorization.py`: the module docstring's "Which markers mean what" paragraph still calls transfers and delegations confirmed defects. Only the marker lines were licensed, so that paragraph is Peter's to update.

### Known limits
- `executorId` has no column. After a restart an executor is no party and reads 404, as on the KS-2038 write doors (fails closed).
- The list reads its rows and filters in the service: no SQL change, no index, no migration. For a non-administrator, `?ownerId=<own>` now reads the full set, as the no-`ownerId` list already did, instead of the owner-column query. That is one scan of `svc_transfers` per call, the cost today's unfiltered list already paid.
