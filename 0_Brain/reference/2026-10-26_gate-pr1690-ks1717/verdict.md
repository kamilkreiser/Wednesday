## Findings

1. **Minor — no deploy path can set the secret, so Azure stays fail-closed with no route out (READ ONLY).** Neither `deployment/azure/deploy.sh` (l.719-760) nor `.github/workflows/deploy-demo.yml` (l.410-422) passes `emitterSigningSecret`, and no parameters file names it. After merge and deploy, every K create and lifecycle on Azure writes the second `anchor` provenance row that KS-566 removed. This is Kam's ruled fail-closed cost, but the docs' "set it on both before deploying" has no mechanism behind it. The env list is declarative, so a value an operator adds by hand to the Container Apps would likely be **dropped by the next template deploy**, silently bringing the duplicates back. The vouch secret has the same gap, so this is a pre-existing pattern rather than a new one. Fix-shape: read the secret from Key Vault in `deploy.sh` and the workflow and pass the param, or file a ticket that names this gap before the images ship. Check: a parameters-file or deploy-script grep that fails when a `@secure()` param that gates a fail-closed guard is never passed.
2. **Minor — the HMAC does not cover the caller, so the residual is wider than "byte-identical replay" (MEASURED AT RUNTIME, harness without DB).** The signing string is label, method, path, timestamp, marker and body hash. `Authorization` is not in it. G2: a signed hop captured from connector A, replayed within the window under connector B's bearer (another org), skipped B's provenance row. On a real DB the tenant-bound ownership guard should refuse a cross-tenant document (READ ONLY). A second connector in the **same** tenant is not stopped. The precondition is unchanged: someone must capture originate's plaintext hop on the compose or ACA network, and such a person can usually capture bearers too. So this is a widening of *who* can use a capture, not of *when*. Fix-shape: include `sha256(Authorization)` (originate forwards the bearer it signs with) in the signing string. Regression test: G2 inverted (a hop replayed under another bearer must record its row).
3. **Note — the real window is just under 61 s, and skew stretches replay life to about 2× (MEASURED).** Both sides floor to whole seconds and the check is inclusive at 60, so a hop signed at T.000 s still verifies at T+60.999 s (G10). A signer up to 60 s ahead of the verifier is accepted, which gives a captured hop a replay life of up to about 121 s of verifier time. That is bounded. No other header form, timestamp unit, duplicate or array header, or body variant widens it (G3, G5, G6, G8, G9, G11). The docs and PR text say "±60 s" and "inside 60 s". "Up to 61 s, longer under clock skew" would be exact.
4. **Note — anchoring's app-level cells do not hold the 32-character floor (MEASURED).** Mutant M4 (floor removed in the shared build anchoring loads) left all 8 of the builder's anchoring cells green. Only my planted G12 (anchoring keyed with a 31-char secret, hop MAC-ed correctly with it, row must still record) went red. The shared S5 cells pin the floor at unit level against `src`, so the property is covered in one place, not where it matters at runtime. Suggest the owner add a G12-shaped cell to `ks1717-the-emitter-marker-is-honoured-only-when-signed.test.ts`.
5. **Note — every JSON body is retained twice for the life of its request (READ ONLY).** `captureRawBody` stores the raw buffer (up to the 100 kB default limit) for every JSON request, marked or not. It is freed with the request (WeakMap), so there is no leak, but in-flight body memory doubles. Optional fix-shape: capture only when `req.headers['x-emitter-internal']` is present (the `verify` hook can see the headers).
6. **Note — no end-to-end originate → anchoring run. Not required for GO in my judgement, but needed as a post-deploy smoke (judgement).** O1 and O2 verify the real setters against the bytes a recorder received, and R2 sends a `signEmitterHop` output through anchoring's real `express.json`. Together they close the signer-to-verifier contract on Node fetch → express. What only a real stack shows: compose interpolation reaching both containers, and the ACA/Dapr ingress not rewriting the path or body (a rewrite fails safe, into duplicate rows). After the secret is set, check that both boot lines read `[emitter-guard] ACTIVE` and that one create writes exactly one provenance row.
7. **Note — two pre-existing reds reproduced exactly as the builder reported:** anchoring `threadTokenMint` and shared `wallet-signature` (KS-1727). Both are outside the diff.
