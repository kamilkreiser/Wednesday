## What this does

Kam ruled on two cards, quoted verbatim:

- `secuura-ks2103-answered-chain-reply-shape-1110` = a: "Strict - only a 404 (null) or an object carrying a block hash counts as an answer; anything else counts as unreachable".
- `secuura-anchoring-second-fee-on-empty-reply-1107` = a (2026-11-08T20:31:42): "Two tickets by a board seat, High for the empty reply and Medium to measure the mint on an image. A build seat fixes the empty reply next, tier 1 gate. Anchoring's deploy stays held for your word."

`getTransaction` (`services/anchoring/src/cardano/provider.ts`) used to return whatever the Blockfrost client's `txs` resolved. QA gate 248 (finding F1) measured the real blockfrost-js 6.1.1 resolving `''` for an empty 200 and for a 204, `null` for a body of `null`, and `{}` for `{}`. On the production schedule the poller then read `''` and `null` as "not found": `polled` 30 and ABSENT, which lets guard 3 schedule the ordinary retry, a **second fee-paying Cardano transaction**. It read `{}` as confirmed, with no block hash.

`getTransaction` now behaves like this:

- **An object carrying a block hash** (a non-empty string `block`) is returned as it came.
- **A 404** returns `null`, as before.
- **No client** returns `undefined`, as before (KS-1171 8k's tri-state is untouched).
- **Everything else throws**: an empty body, `null` from a 200, `undefined` from a client, `{}`, an array, a string, a number, or an object whose `block` is missing, empty or not a string. The message names the shape class, never the body or the hash.

No form is required of the hash: the ruling says *carrying*, not validating. A `valid_contract: false` reply still carries `block`, so KS-1384 F0 M-1 is unchanged.

**Why a throw.** All three readers of `getTransaction` already treat a throw as "the chain did not answer":

1. `waitForConfirmation` counts it in `errored`, never in `polled` or `lastAnswered*`. So `definitelyAbsent` cannot fire on it, and `{}` cannot reach `confirmed: true`.
2. `settleExpiredSpenders` (`walletSpend.ts`, via the `lookup` closure in `cardano/index.ts`) settles nothing. Before, it marked a spender DEAD on `''` or `null` and CONFIRMED on `{}`.
3. The family read in `anchorSubmission.ts` (`try { info = await chain.txInfo(spender); } catch { return 'rest'; }`) rests the row.

`confirmation.ts` changes in **comments only**: the two comments that define an answer now say that a 2xx without a block hash is a throw. A grep of the diff for non-comment changed lines prints nothing.

**What this admits (a real reply now refused?).** By read, none. The client's own declared type for a found transaction, `tx_content` in `@blockfrost/openapi` 0.1.86, makes `block: string` required, and a transaction that is not yet in a block is a 404. This was not measured against the real Blockfrost service: no network call was made.

**Partition extension, ruled by Wednesday (ANSWER 12:16Z).** One more file, for exactly two fixture lines: `services/anchoring/src/__tests__/ks671-chain-health.test.ts` at :277 and :290, each changed from `{ block_height: 1 }` to `{ block: 'b'.repeat(64), block_height: 1 }` with a `// KS-2103:` comment. Those two staleness cells fake one successful chain call to set health to 'ok'. Under card 1110 their reply is not an answer, so the cells errored before reaching their assertions. The fixture moves; the rule does not. No assertion changed.

**Named, not changed:**

- KS-1171 8k cell **8k-9** ("a configured client whose txs resolves undefined reads as no client and rests") stays green by name, since its assertions are 30 `txs` calls, 0 retries and no failed write. That reply now counts as `errored` (a throw) rather than `noClient`, so the cell's title describes the old mechanism. Its file is not edited here.
- **Chain health** (`/health`) still reads an empty 2xx as reachable: the instrumented client records the resolved `txs` call before `getTransaction` judges its shape. It is left as it was and is a candidate filing for the board seat.
