How a step ends up with NO workflow: its step id appears in no row of `svc_approval_workflows` (all rows are read, active or not). The four default workflows seed stable step ids (`step-1`..`step-3`, in all four, so `findWorkflowByStepId` finds the first workflow that has the id, an old quirk); `dbUpsertWorkflow` can overwrite a workflow's `steps`; there is no delete path in the service, no workflow DELETE route. So a no-workflow step needs a direct DB edit, a custom workflow whose steps were later changed, or a lookup that failed. Existing fixtures: no test fixture builds one (ks1868 and ks1881 stub the DB, none seeds a step without a workflow); no seed data inserts step instances.

After the PR the step stays pending, stays approvable (`processApproval` with no workflow skips the requirement checks and works), and `processEscalations` never touches it.
