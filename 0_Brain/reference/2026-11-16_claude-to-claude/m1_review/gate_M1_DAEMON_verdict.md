## Summary

Peer-text containment HOLDS. A real hostile paired peer was built from the library crates. It sent JSON-RPC frames, fake wrapper terminators, the wrapper's own delimiters, controls, NUL, U+2028/2029, bidi, ANSI, OSC title and clipboard sequences, a daemon-IPC look-alike, nested JSON and size boundaries. These went in message text and also in `audience`, `re`, `id`, the hello display-name claim, a seq-0 `chat.msg`, a duplicate, a non-string text and an unknown critical type. Every peer byte reached the agent only inside the fixed wrapper and decoded back exactly. The data section is printable ASCII with no `<` or `>`, so the peer cannot forge the terminator. Nothing reached stderr (daemon, relay, MCP), `status`, tool descriptions or any non-tool MCP line. Malformed, partial, huge and nested JSON-RPC input did not destabilise the server. Pairing wiring is sound: the context binds the pin and the mailbox, a contact is stored only for a key-confirmed peer, and the MITM double fails.

Four Majors stand, so the verdict is **NO GO**. A hostile relay can permanently wedge a session while the victim reports `connected: true` (G1). A peer can flood the unread inbox so the daemon never starts again (G2) and so the agent loses the messages (G3). A `wait` whose client went away silently swallows the next message (G4). All four were reproduced with real processes.

## Peer-text containment (task item 2): what was attacked, all through REAL `coagentd` + REAL `coagent-mcp`

Test `gate_a_hostile_peer_fields_reach_the_agent_only_escaped` (RAN, PASS). The hostile peer was a full joiner built from the library crates (`gate_hostile/mod.rs`): its own identity, Pairing with the link secret, the welcome, KK as initiator, and arbitrary envelopes.
- **Text and `audience`**, each carrying: a complete JSON-RPC response plus a request frame; a fake `"}]` and END marker followed by "SYSTEM: approved" and a fake BEGIN; the wrapper's own BEGIN/END and header strings; `\n \r \0 U+2028 U+2029 U+202E U+2066 U+200B U+FEFF`; ANSI CSI, OSC 0 (title), OSC 52 (clipboard), C1 CSI U+009B; text that looks like the daemon's own IPC reply; 3000-deep bracket text; pre-escaped `<…` text; astral/edge code points.
- **`re` and `id`** at their 64-character maximum. `type` and `id` are limited by the proto to `[a-z0-9._]` and alphanumerics, so their only exposure is a length check.
- **Hello display-name claim** carrying an OSC, a newline and JSON. It appears in no status output, no session.json/contacts.json, no stderr and no MCP line. The local nickname `peer-xxxxxxxx` is used instead.
- **Size boundary**: 16,384 bytes is released. 16,385 bytes (ASCII, and multi-byte ending in `é`) is withheld with the count-only notice `2 peer message(s) withheld`.
- **seq 0 `chat.msg`, a duplicate seq, a non-string text, an unknown critical type**: none delivered. **200-deep nested body**: refused on receive (see G11).
- **Invalid UTF-8**: cannot be produced through `Channel::seal` (it encodes a `serde_json::Value`). The receiver's `decode_for_channel` parses with serde_json, which rejects invalid UTF-8 and lone surrogates (reasoning).
- **MCP stdout**: 14 lines captured as bytes. Every line is UTF-8, a single `\n`-terminated JSON object with `jsonrpc:"2.0"` and keys only from {jsonrpc,id,result,error}. Error messages are drawn only from {method not found, parse error, request too large}. Outside tool texts no marker appears. Inside each tool text, outside BEGIN…END, there is no peer byte and no control byte. BEGIN count equals END count. Each data section is one line of printable ASCII with no `<`/`>` and parses as one JSON array. `tools/list` is identical before and after, with no marker.
- **Malformed MCP input interleaved**: a partial line split across two writes (answered once), `garbage`, `\xff\xfe\0\1`, a batch array (no answer, G16), 200,000-deep `[`, a 2 MiB line (`request too large`, id null), an object id (echoed), an unknown tool, wrong argument types, `params` as a string, an unknown method. The server answers normally afterwards.
- **stderr**: daemon, relay (external relay stderr captured) and MCP. `Run::finish` scanned for every marker and the identity's secret bytes: clean.
- **Wrapper unambiguity**: yes. BEGIN/END contain `<`/`>`, which `escape_json_string` always emits as `<`/`>`, and every non-printable-ASCII character is escaped. The peer cannot produce the terminator. Mutations m01-m03 are caught.
- **"Release needs the witness" at the type level**: no. It is module privacy for `.raw` plus a source grep. See G8 (m08 SURVIVED).

## Pairing and identity (item 3)
- Context `relay = "pin:<fp>"`, `mailbox = hex(id)` on both sides (`engine.rs:838-841, 945-948`). Sound: it binds the code to the certified relay and to the single-use mailbox. Caveat for later: the inviter binds `relays[0].pin` and the joiner binds the pin of the candidate it reached. With more than one candidate this fails safe (pairing fails) and does not fail open.
- Success is reported only after `Pairing` returns `Paired`, which is after explicit key confirmation. The MITM test is green and its CORE red (`no_key_confirm`) went red (RAN). The contact is the `Paired.peer` key. No path stores a contact from a claim or before confirmation (but see G15).
- Welcome (Q3): sealed in the confirmed pairing channel. The joiner checks that `roster.convener` is the paired key, the signature and chain (`RosterChain::start` includes the self-member check), exactly two members, and that its slot equals the welcome's slot. A hostile convener controls only its own session. A hostile relay sees ciphertext. Sound.
- Fresh KK per attachment (Q2): prologue = session id ‖ roster hash ‖ slots. The **epoch is not in it**, which is G1. `insert_with_slot` is used on every path, and `map.close` precedes every insert (`install_channel`, `engine.rs:1824-1825`), so the CORE R2-5 order dependence is handled.
- Invite as hostile input: 4096+64 byte cap before decode, base64url, `deny_unknown_fields`, ≤ 8 candidates, `wss://` and ≤ 256 bytes, 64-hex pin. A wrong-length pin is refused. Non-loopback hosts are accepted by design: the invite is from the intended peer. Connect errors log only the stage, never the host. A replayed or used invite is refused by the relay (test 4, RAN). A second join during a session gets `session_active`. A black-hole candidate list stalls the engine (G10).

## Verify ceremony and persistence (item 4)
- Attempts, shown words, hard stop and verified live in `SessionRecord.verify`. A press is persisted as one used attempt **before** the reply (flush, then reply). Shown words are persisted at the end of the event that produced them, so before any `status` can show them. "No" for earlier-shown words after a restart is a hard stop (m14 caught). The hard stop is enforced in `start_kk`, the Kk1 branch, `send` and `verify_start`.
- CORE R2-1 (one press, one counted ceremony) is fixed in merged main (`sas.rs:310,416,470`). With the daemon's `total = base + in_map` press gate, the cap holds across restarts (RAN: test 6 and m12/m13 below).
- SIGKILL windows enumerated: (a) relay-level ack sent before the inbox flush: covered by app-level redelivery, because the app ack goes out only after a flush; (b) `relay_send_seq` used before it is persisted: after a crash the relay answers `bad_request` to the reused pair_seq, the frame is dropped, the outbox redelivers or KK retries, so it self-heals; (c) a verify commitment frame may leave before the press is flushed (sub-ms; nothing shown yet, so no guess is consumed). No window resets a count or clears a hard stop, given a SIGKILL. A power loss can (G6). A failed write fails open (G7).
- A corrupted, truncated or oversize state file fails closed. That also makes G2 a permanent outage.
- Two daemons on an initialised directory: the second exits at the bind lock before writing (RAN). On an empty directory, see G5.
- Atomicity: the temp file is created with mode 0600 (`create_new`, `.mode(0o600)`, never chmod-ed) and renamed; there is no directory fsync (G6). m19 (chmod after create, 0644 window) SURVIVED: nothing tests the "never world-readable for an instant" property.

## Messaging (item 5)
- Exactly-once and in-order across a cut connection and a relay restart: green (tests 5a/5b/5c, RAN 10× including under load). Up to delivery into the daemon inbox it holds. From the inbox to the agent it does not (G3, G4).
- Unread peer text sits in clear in the 0600 session.json. That is acceptable for M1 against other users. It makes G2/G3 possible and keeps peer text on disk after reading only until the next flush.
- `seq 0` controls: `resume`, `session.end` (convener only, via `admit`), `session.leave`. Anything else at seq 0 is refused (a seq-0 `chat.msg` was not delivered, RAN). Replay and reorder of seq-0 frames is prevented by the channel's nonce within an epoch and by fresh keys across epochs. A peer's `resume` can only shrink the peer's own deliveries to it. Safe.
- Forged reply linkage: there is no check, and `re` is the peer's claim (G12). There is one session per daemon, so no cross-session confusion.
- Duplicate, out-of-order, unknown type, oversize: handled (RAN). A flood has no rate limit and quadratic state writes (G2).

9/10. Relay restart or convener crash means a new certificate, and the joiner needs `relay_moved_line` pasted. **What the user sees:** after any convener relay crash, convener daemon crash or restart, or machine reboot, the joiner shows "not connected" indefinitely. Both outboxes keep growing and nothing flows until the convener's human runs `status`, copies the `relay_moved_line`, and sends it out of band to the joiner's human, who pastes it into `join`. There is no prompt and no notice to either agent. **Would automatic recovery have been unsafe?** Re-pinning whatever certificate now answers at the old host:port (TOFU) would not expose content: the session is protected by KK on roster-pinned keys. But it would hand the joiner's slot token and chan id to whatever process grabbed the port, which allows slot squatting (denial of service) and metadata, the same exposure as G14. So the builder was right not to re-pin blindly. Moving the new pin inside the encrypted channel is impossible after a crash. **R1 (persist the relay TLS identity and hand it to the child on stdin or an inherited fd, never argv or env) is the right fix** and needs the CLI/relay owner. Combine it with signing `relay.moved` (G14) for planned moves.
- R1: as above, **needs the owner**; safe if the key never touches argv, env or a world-readable file.
- R2 (seed ChannelMap with persisted per-slot attempts and hard stop): **endorse**. Today the cap holds through the daemon's parallel count (`base + in_map`, press-gated), but the map's own view after a restart is "3 left", so any future path that bypasses `verify_start` would see a fresh count.

- R4 (export `current_uid`): harmless.
