**M-1 (Major; R5, D-S1, brief §4 "a peer that can cause … a seal"). The own-SEAT trigger is driven by peers' recording requests.** `admit` and `due` measure `OwnSeatAt` as `m.seat_usage(own_slot)` against `limits().own_reserved()` (`host.rs:1218-1227`). In the audit crate the own seat's usage IS the free part plus every member's REQUESTED ALLOWANCE (plus, in N1's state, an earlier member's events in this slot): `session.rs:841-852` (`seat_usage` adds `own_usage()` for the own slot) and design 07 (own seat 5,068,886 = free part 2,534,443 + 7 × 362,063). R5 says "Nothing that carries … a requested allowance … can produce one"; design 10 §2.1 says the policy "may never be driven by … a requested allowance". Probe `qa_triggers.rs` `qa_t1` (release): V with `own_seat_at` on; member 2 alone sends recording requests (`Causer::Member`), V does nothing:
  - default limits, `own_seat_at=1%`: `684 requests by member 2 accepted (first due after Some(97)); free part (0, 0) -> (0, 0) (unchanged: true); own seat used (361044, 684) of (5068886, 28604); … due() = Some(OwnSeatAt(Percent(1))); seal(OwnSeatAt) -> SEALED segment 1 files ["seg-00000000000000000000-0000.bundle"]`; `2%`: due after 193 requests, SEALED.
  - limits 8 × 40,000 / 8 × 400, `own_seat_at=5%`: `4 requests … due() = Some(OwnSeatAt(Percent(5))); seal(OwnSeatAt) -> SEALED segment 1`.
  One member can push the own seat to ≈ 7.1 %; all seven members together to ≈ 50 % (REASONED from the split above). So with the own-seat trigger set at or below about half, peers alone make the owner's machine file a segment; above it, they bring the seal forward. The builder's tests miss it: `triggers.rs:86` fills a peer's SEAT (not requests) with the threshold at 90 %, and the property draws the trigger as the owner's act, never asking whether a peer made it due. **Mitigation: off by default** (the COORDINATOR'S DEFAULT is the owner's command only), so with default settings no peer can cause a seal (§5). **Wrong claims** that follow from it: docs §6 and §9, `settings.rs:3-9`, the D-S1 BUILT line in BACKLOG. Fix (small): measure the own-seat trigger without the requested allowances (the free part and the own checkpoints it pays for, i.e. what V alone causes), or drop `OwnSeatAt` until the owner rules DQ-S1; then a guard test with member requests and a red row.

**M-2 (Major; brief §4 "leaves a folder that will not open"; DQ-H4). A release whose `current` save fails once, then a restart: the folder is refused.** `release` (`host.rs:1131-1139`) on success does `let _ = self.save_current(); let _ = self.anchors.remove(PENDING);`: the pending (post-release) anchor is removed EVEN WHEN the save of `current` failed. The seal path guards this (`host.rs:1393-1395`: remove pending only if the save succeeded); the release path does not. Probe `src_tests_qa.rs` `qa_q1`: peer 3's three events stored, peer 3 removed; release with ONE injected failure at the creation of `anchors/current`'s temporary file (a full disk, an I/O error); then a restart (a crash or a clean shutdown): `answer Released; status anchor_saved=false; pending on disk after the call: false; RESTART (default settings) -> REFUSED Anchor { pending: None, current: Some(Missing { part: PeerEvent(3), author: KeyId(31cf…), n: 3 }) }; with allow_unanchored -> Unanchored, own seq 3`. Nothing is lost (the unanchored open has every record), but the default open refuses and the owner must switch loss detection off to get in. If the process makes another change first, the save is retried and all is well (`qa_q1b`: `OPENED Current own seq 4`). Fix (one line): in `release`, `if self.save_current().is_ok() { let _ = self.anchors.remove(PENDING); }`, as the seal does; add the fault-then-restart case as a test.

**M-3 (Major; R3, brief §4 "limits after a restart that differ without the host saying so"). After an in-call re-open the limits can be the DEFAULTS, silently.** Two causes: (a) `set_limits` stores the offer in `self.cfg.limits` even when the member REFUSED it (`host.rs:1460-1470`: `write_limits(..)?; self.cfg.limits = limits; r.map(..)`); (b) `reopen` (the P-4, P-7 and release-error path, `host.rs:926-952`) re-offers `cfg.limits` and DISCARDS the `LimitsReport`; the caller's answer (`Recorded`, `Reopened`, `SealCommitFailed`) says nothing about limits, and `anchors/limits` is overwritten with the new value. Probe `qa_q8`: limits 3,200,000 / 16,000 in force; member requests fill an allowance (a checkpoint owed); `set_limits(16,000 / 32)` → `Err(Audit(LogFull))`, in force unchanged; then a local record whose store directory sync fails once (P-4): `record … -> Ok(Recorded(21)); in force AFTER the in-call re-open StoreLimits { bytes: 40779920, records: 228832 } (status says the same); changed silently: true; a later restart reports before Some(StoreLimits { bytes: 40779920, records: 228832 })` (the record of what was in force before is overwritten). So the owner's lower limits rise to the defaults with no answer saying so, which is exactly what the two BACKLOG entries this build closes were about. Even without (a), N1's state with a checkpoint owed makes the re-offer of the limits in force refused (the AUDIT-FIX2 exception), with the same silent result (REASONED from `docs/AUDIT.md` §1A, not run). Fix: keep `cfg.limits` only on acceptance (or keep the limits IN FORCE and re-offer those), and make an in-call re-open carry its `LimitsReport` in the answer (or refuse to continue when `differs()`); a test with a refused offer and a P-4 re-open.

**m-1 (Minor; loss detection).
