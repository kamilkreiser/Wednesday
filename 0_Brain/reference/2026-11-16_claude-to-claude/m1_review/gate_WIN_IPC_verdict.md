No `unwrap`/`expect`/slice index outside tests; `Groups[0]` indexes a one-element array after the count check; `rejected += 1` cannot overflow in practice (u64). No panic path found.

**5.5 The accept loop.** The next instance is created at :500, BEFORE the decision at :502-505, so it exists on the admit path AND the reject path (the existing rule holds on every path). Memory: nothing is kept per rejection. The counter is the real one (:482-484), never reset, so it cannot read 0 after a rejection. Spinning and starvation: tokio's `NamedPipeServer::connect` (vendored tokio-1.54.1 `src/net/windows/named_pipe.rs:196-205`) returns at once, without waiting on the reactor, whenever the underlying call does not say "would block" (an instance a client has already opened; mio side from memory, UNVERIFIED); so while a rejected client re-opens the pipe as fast as it can, the loop turns (create, lookup, reject, connect) without an `.await` that yields, and holds the one free instance; an honest client meanwhile gets `ERROR_PIPE_BUSY` and gives up after 40 × 50 ms (`TimedOut`; the hook then blocks: fails closed). Only a process that passes our DACL (inside our logon session) can do this. Finding m-3.

**5.6 The comparison.** `check_peer_sid` (`sid.rs:13-19`): both non-empty and `eq_ignore_ascii_case`. A SID string is `S-`, then numbers (Microsoft, https://learn.microsoft.com/en-us/windows/win32/secauthz/sid-components: "S-R-I-S…"; whether the identifier authority may be printed in hex: SILENT; from memory a large authority prints as `0x` + hex digits). ASCII folding can only merge `S`/`s`, `x`/`X` and hex letters, which name the same value, and `ConvertSidToStringSidW` gives one text per SID: **two different accounts' identifiers cannot compare equal.** Non-ASCII is not folded (my probe `S-1-É` vs `S-1-é`: refused). Elevated token of the same account: Microsoft's UAC page (https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works): the standard token "Contains the same user-specific information as the administrator access token, but the administrative Windows privileges and SIDs are removed", so the user SID is the same and a successful lookup admits; whether a non-elevated daemon may open an elevated client's process and token, and whether both tokens carry the same logon SID (which decides whether the DACL even lets it open the pipe): SILENT, UNVERIFIED (README item 11 records it; refusal fails closed). Restricted token of the same account: Microsoft (https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens): "Access is granted only if both access checks allow the requested access rights", so it opens our pipe only if its restricting SIDs include our logon SID; if it does, `TokenUser` still names our user (the code ignores the `Attributes`, such as deny-only) and it is admitted as our user: same account, not another identity (Note N-6).
**The process-id reuse window on the listener side** (REASONED, not measured): from the client's open completing to `OpenProcess` returning in `accept`: the task's wake-up, one `CreateNamedPipeW` (the next instance, created first at :500) and two calls; usually well under a few milliseconds, unbounded under load. Using it needs a caller that opened our pipe (so passed the logon-session DACL), kept the connection alive in another process, exited, and had its id given to one of our user's processes inside that window. Since only callers inside our logon session can open the pipe at all, **the DACL closes this in practice on the listener side**, as the builder's note says. It does NOT on the client side: finding M-1.

**5.7 Squatting** (the name is predictable from the folder path):
- Another account creates the name FIRST: our first instance fails with ERROR_ACCESS_DENIED (Microsoft, quoted above), `is_name_taken` -> `PipeNameInUse` -> the daemon refuses to start. **No order of events makes our daemon serve on a pipe whose first instance another account created**: the first-instance flag fails whenever any instance of the name exists, and while ours exists another account cannot add one (FILE_CREATE_PIPE_INSTANCE, our DACL). (Side note: `is_name_taken` reads ANY `PermissionDenied` as "name taken", so another access failure at creation would be reported as "name in use": a misleading text, still a refusal.)
- A client of ours meets that squatter (P-5): if the recorded server process is the squatter's own, `OpenProcess`/`OpenProcessToken` fail (another account: SE_DEBUG_NAME needed) -> OS error; if the squatter opens its process and token to everyone, the SID read is the squatter's -> `PeerSidRejected`. Refused. **BUT there is an order of events in which a client of ours talks to a pipe served by another account: finding M-1.**

## 12. Findings
**M-1 (Major). The server check (P-5) trusts a process number that a squatting server of another account can make point at one of the owner's own processes; a client of ours can then talk to a pipe served by another account.**
- What (READ): `connect_expecting` (:538-557) identifies the server only by `GetNamedPipeServerProcessId` -> `OpenProcess(pid)` -> that process's token user (`other_end_user_sid`, :310-331). Microsoft's page for `GetNamedPipeServerProcessId` says only that it returns "The process identifier": it is SILENT on whose process it is and when it is recorded, and `OpenProcess`'s page is SILENT on reuse. The pipe itself, and its access list, belong to whoever created the name; when the owner's daemon is not running (it is started on demand and exits when idle, 04 §5.3), the name is free for any account (section 5.7).
- Input (an order of events; READ and REASONED, not run): (1) account B creates the predictable pipe name of the owner's data folder in a process X, with an access list that admits everyone, and passes the server handle to a child Y (inherited or duplicated); (2) X exits; Y keeps serving; (3) B waits until X's process number is given to any process of the owner (each hook call starts a new owner process, so numbers are handed out all the time, and B can recreate the pipe until it wins); (4) the owner's hook connects: `GetNamedPipeServerProcessId` returns X's old number IF Windows records the creating (or listening) process rather than the current holder (UNVERIFIED: docs silent), `OpenProcess` opens the owner's own process, its token user is the owner's, `check_peer_sid` passes.
- Exact output (expected, not run): `connect` returns a stream to B's server; the hook sends B every tool request and acts on B's answer (B can answer "allow" to all); the MCP sends B the messages. The builder's stated limit ("between the client's connect and the lookup"; "the DACL still applies") assumes a short window and a compensating access list; on the client side the window is chosen by the squatter and the access list is the squatter's.
- Not new, and bounded: `main` has no server check at all, so today any squatter is trusted; this lane narrows the hole to the reuse route. It matters only on a Windows machine where another account runs programs. Nothing on Windows is handed out yet (06:650).
- Why Major, not a note: brief section 4 lists "a path in the READ Windows code where … a server of another identity is admitted" as NO GO, and the effect if it fires is the whole gate answered by another account. It rests on a Windows behaviour the documentation does not state (as the empty-path finding M-1 of the policy-mode check rested on an unverified host behaviour).
- Smallest fix (needs the coordinator's ruling, since P-5 named the calls): bind the server check to the pipe object, not to a process number. At bind, give the pipe an explicit owner, SDDL `O:<own user SID>D:P(A;;GA;;;<logon SID>)` (`windows.rs:363-365`). In `connect_expecting`, after `open`, read the pipe's owner through the client handle with `GetSecurityInfo(handle, SE_KERNEL_OBJECT, OWNER_SECURITY_INFORMATION, &mut owner, null, null, null, &mut sd)` (vendored `Security/Authorization/mod.rs:74`, constants `SE_KERNEL_OBJECT` :1112, `OWNER_SECURITY_INFORMATION` `Security/mod.rs:496`; both features already enabled), turn it into text with `ConvertSidToStringSidW`, `LocalFree(sd)`, and require `check_peer_sid(owner, own) == Ok` (keep the process check as well if wanted: require both). Microsoft (https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo): "To read the owner … the calling process must have been granted READ_CONTROL access when the handle was opened"; "free the returned buffer by calling the LocalFree function"; it returns `ERROR_SUCCESS` or an error code (not a BOOL). Our DACL grants generic-all to the logon SID, which covers READ_CONTROL; a squatter's pipe that withholds it fails the read and is refused.
