== SUB-QUESTIONS (my recommendation first in each) ==
QA (3a, which writes the gate binds). It binds the REQUEST: every field, changed or not, so a sibling user's all-unchanged save is 403.
 - Why: under the ruling an ORG_ADMIN has no write authority over that user, and this way no new "unchanged" logic sits on a security gate. A wrong "unchanged" verdict there would be a hole.
 - Own-organisation saves keep KS-2287's and KS-2300's resend tolerance exactly as built.
 - The alternative binds only real changes. It needs new change detection for status and the three names.
QB (spec words). Include auth.openapi.ts and the regenerated yaml, as PRs 2267 and 2268 did. The create text would say the new user is placed in the caller's organisation and an organisation-less admin gets 403. The PATCH text would add the own-organisation 403. If they stay out, the spec keeps saying "This route gives the new user no organisation".
QC (3b, the order). The tenant 404 first and my gate last before the write: variant B, measured above.
QD (3d, a body organizationId on create). Today create reads no organizationId from anyone. I recommend IGNORING it: the contract stays the same, and the user lands in the caller's organisation either way. Refusing it would add a new 4xx for a field the route never read. Your call.
QE (3e, the level cap on create). The KS-2287 comment at 686 to 688 and the spec say the cap is BASIC because the new user has no organisation. After this change that reason is false. Under the 20 Nov level ruling (own organisation, up to STANDARD, never self), an ORG_ADMIN could pick up to STANDARD on create.
 - Recommend NO behaviour change: keep BASIC-only.
 - Reword those three comment lines to say the cap is kept pending a ruling. That is a words-only edit inside the KS-2287 block, so it needs your yes.
 - A card for Kam if the cap should be lifted.
QF (3c, self). An ORG_ADMIN in an organisation may change its own name and status, since it is in its own organisation. An organisation-less one is refused, like for any target: the ruling says it "could change no one". The own-role and own-level rules are unchanged. Recommend yes.
 - Pre-existing, listed and not touched: the dashboard resends role on every save, so an ORG_ADMIN saving its own row is ALREADY refused with "Cannot change your own role" (the KS-467 rule fires on any role sent).
QG (the bare admin string). Bind it like ORG_ADMIN, since KS-2287 binds every non-platform caller this file admits. Recommend yes.
QH (the Users page). It is not in the list, so no page edit. The facts comment LISTS these for a board item; none gets fixed:
 - (i) The page shows Edit and Block on rows outside the admin's organisation, and those buttons will now get a 403.
