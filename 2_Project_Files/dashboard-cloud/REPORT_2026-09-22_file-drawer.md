## Design choice on encryption (stated, as asked)
The row scheme (`WED.decryptRow`: AES-GCM ciphertext as a base64 Table column) cannot hold a file — a Table property caps at 64 KB, an entity at 1 MB — so the brief's second option was taken: **one data key per file, used twice.** (a) The row's `ciphertext` is a small meta JSON `{name, note, size, sha256, mime}` under AAD `client|file|id|ts` — an ordinary envelope row, so the page's `decryptRow` and the seat's `decrypt_text` open it unchanged (the file NAME and NOTE are therefore encrypted, never a clear column). (b) The bytes are AES-256-GCM under the SAME key with their own `iv_blob` and AAD `client|fileblob|id|ts` (a blob moved under another row fails to open — proven both in Node and Python). The key is wrapped exactly as a Phase 3 message: Kam's ring (pilot, laptop, ipad) + the addressed seat(s) (`wrapped_keys`, 4 kids for WED/Secuura), and **a Kam upload is refused 400 unless wrapped to the seat** (the same guard his replies have) — so "the seat can read what Kam attached" is true by construction, not by hope (FL2/FL3/FL4, K7). Clear on the row: `client, kind=file, id, ts, view, role, seat, written_by/at, direction shared|upload, size` and `sha256` **of the ciphertext** (integrity of the stored bytes; not prose), `status pending|ready`, `blob`, `iv_blob`, `msg_id`, `synthetic`. Twins: `seat/envelope.py encrypt_file/decrypt_file` ⇄ `common.js encryptFile/decryptFileMeta/decryptFileBytes` (self-test + `09e` both directions).
