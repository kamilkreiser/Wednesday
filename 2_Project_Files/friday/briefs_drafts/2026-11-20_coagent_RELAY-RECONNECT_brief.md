One log line per change of cause, not per try. Status shows the wait (R9). This is the clock for R7 too.
- **R7 (a saved identity that fails a check; P-6).** With the setting ON, when `relay-identity.key` exists and any check of R4 fails:
  - the relay child is NOT started; NO new identity is made; nothing is written; the file is untouched (bytes, mode, times);
  - `invite` answers the existing `relay_unavailable` error [:1157-1160] with the fixed text below; a restored session stays up, DETACHED, with R6's retry running, and `relay_moved_line` stays null;
  - log line and status text, fixed, naming the failed check by category only: "the saved relay identity was refused (<category>). The relay was not started and no new identity was made. Put the file relay-identity.key right or move it away, or restart without --keep-relay-identity; a new identity means the other side needs a new line." Categories: not a regular file; owned by another user; mode is not 0600; larger than 16 KiB; and `IdentityBlobError`'s own texts (`tls.rs:272-306`, which carry no byte of the blob);
  - it heals without a restart: when the owner puts the file right, R6's next try loads it and the guest reconnects by itself; when the owner moves the file away, the next try makes a new one and R5's "new certificate" case follows.
  - Why never a silent fresh identity: the guest still pins the old one (design 09 row 18), so a fresh one cannot connect anyone; it would only hide the damage and leave a state in which the two sides can be brought together again only by a pasted line that nobody was told to make. A deliberately new identity always goes through the `relay.moved` path and says so.
- **R8 (the old path, and the words the second ruling requires).** `join` with a `relay.moved` line [:1240-1260] is not changed: same checks (the session id and the joiner role, [:1244]), same effect. It remains the way to follow a deliberately new identity or a new address. `coagentd`'s usage text and `docs/DAEMON.md` §2 and §7 gain, in plain words: what the flag does; that the default is a new identity for each session, kept in memory only, with nothing on disk; "What is checked: the owner and the permission bits of the file and of the data directory. NOT checked: access-control lists (ACLs) and other extended sharing rules on macOS, and folders above the data directory" (the relay's own help says the same, `crates/coagent-cli/src/args.rs:17-22`); that any program running as the same user can read the file; that a saved identity gives every invitation from this data directory the same fingerprint, so two of them can be told to be the same relay; and R10's limit sentence.
- **R9 (status).** `status` [:1113-1126] gains one object, `relay_identity`: `source` (one of `none`, `memory`, `saved_created`, `saved_loaded`), `refused` (null or R7's fixed text), `retry_in_s` (null or the seconds to R6's next try). No fingerprint field is needed: the pin is already in `session.relays` [:1092]. No other IPC change; `src/ipc.rs` is not touched.
- **R10 (threats: what is claimed, what is a stated limit).**
  - A guest, a hostile peer, or a hostile relay gains nothing from this build: no new frame, message or command exists; the identity is made and handed over locally; a guest's pin changes only by its own owner's `join` [:1240-1260].
  - The relay's key is not a content secret. Design 04 §4.4 [04:408]: "The pin in the invite authenticates the relay's TLS endpoint to joiners. That protects metadata from the network, not content from the relay; content is protected by the pairwise channels regardless." The same in the code (`tls.rs:7-8`).
  - DOCUMENTED LIMIT (help text, DAEMON.md, BACKLOG): whoever copies `relay-identity.key`, or reads the daemon's memory, can stand where the relay stands. Design 06 §4.4 [06:524]: "The thief can present the relay's certificate to joiners and so sit where the relay sits: addresses, traffic graph, sizes, timing, and the power to drop traffic. Not content, and not pairing (the pairing secret is in the invite, never sent to the relay [03 §4.2]). This is why the option is off by default and why the file rules are strict."
  - DOCUMENTED LIMIT (the second ruling): programs of the same user can read the file; access-control lists are not checked.
  - DOCUMENTED LIMIT: a process killed between writing the temporary file and removing its name leaves `.relay-identity.key.<random>.tmp` (0600, inside the 0700 directory) holding the key; the daemon never deletes a temporary file it did not create (`docs/DAEMON.md:96-98`). Same class as every other state file's temporary copy.
  - NOT CLOSED HERE: `relay.moved` lines stay unsigned (`BACKLOG.md:272-276`, G14). They are needed less often now; the entry stays open with one line added saying when.
  - NOT BUILT HERE, to be entered in BACKLOG: the guest's daemon does not tell a changed certificate from an unreachable relay (`link.rs:128-132, :275-278` keep only the stage name; the relay crate's `pin_mismatch` flag is unused), so design 06 §4.3's fixed text is shown nowhere.

If the relay CLI or the relay crate lacks anything you need (the drafter found nothing lacking: `--identity-stdin` exists at `crates/coagent-cli/src/args.rs:23-24, :121` and is implemented at `relay_cmd.rs:131-146`; `generate`, `to_blob`, `from_blob` and `fingerprint` are public), that is a STOP, not an edit.
