## 4. Deliverables

1. **Action model.** `Action { kind: read|search|edit|delete|move|execute|fetch|service|share|other, targets, raw_input_hash, tool_name, session_id, agent_id }` built from a hook `PreToolUse` input by a classifier that maps every tool in the table of 03 section 5.1. Unknown tools and subagent spawns are `other`, tier T2 minimum. The hash covers the exact tool input so a changed retry is a new decision.
2. **Path normaliser (POSIX).** Canonical absolute path for every target: resolve symlinks through the operating system where the object exists, otherwise canonicalise the nearest existing parent; `..`, repeated separators, trailing dots, `~` expansion for the session's user only. Anything it cannot canonicalise with certainty is classed OUTSIDE the workspace. A `PathNormaliser` trait with the POSIX implementation, and a Windows implementation behind `cfg(windows)` that applies 04 section 5.5's rules 2 and 3 conservatively (uncertain means outside; stream suffix, device prefix or reserved name means T3). The Windows code cannot run here: type-check it for `x86_64-pc-windows-msvc` if that target is already installed in the drive-local toolchain (the RELAY seat added it), and say UNTESTED.
3. **Shell recogniser.** A strict recogniser for Bash command lines: the WHOLE line must parse into known-simple forms or it is `execute`. Simple reads (`ls`, `cat`, `head`, `tail`, `wc`, `stat`, `file`, `git status|diff|log|show` with no pager/exec options, and the like) and pure searches (`grep`, `rg`, `find` without `-exec`/`-delete`/`-ok`/output redirection), plus the compound forms B16 recorded when every part is itself recognised (`cd <path> && <search>`, `<search>; echo …` of a constant). Rejected outright: pipes into anything not on a short allow-list of pure filters, redirection, command or process substitution, backticks, variable expansion in command position, `eval`, `xargs`, `env VAR=… cmd`, here-documents, globs that could expand into options. Every path argument goes through the normaliser and decides the tier. PowerShell: one recogniser accepting exactly one read-only built-in with plain arguments (04 section 5.5); everything else `execute`; any external program on Windows is `execute`. The classifier only ever RAISES scrutiny.
4. **Tiers, hard denies, exclusions.** T0-T3 and hard deny exactly as 03 section 5.1, with the credential and gate-configuration pattern lists as named constants in one module, each with a one-line reason. Exclusion globs beat everything including grants. A `.coagentignore` reader is NOT in scope (the caller passes globs).
5. **Decision engine, CONTROLLED.** `decide(action, state, surface, now) -> Decision`, where `Decision` is `Allow{why}`, `Ask{card}` or `Deny{reason}`, `surface` says whether a human can be asked (terminal prompt, console attached, or none), and `state` holds: workspace roots, exclusions, session approvals (each bound to an exact input hash or to a narrow generated scope: "reads under <dir>", "this exact command", "edits to this file", "fetches from <domain>"), resource memory for reads, pause/stop flags, taint. Scope generation for the card's "allow for this session" options is part of the crate and is deliberately narrow. T3 is never batchable and never session-approvable. Expired approvals deny. With no surface, anything that would ask is denied with a reason that says so.
6. **Grant evaluation, APPROVED TRUST.** A `Grant` type per 03 section 5.3 plus `subjects` (04 section 3.6), parsed and validated (expiry at most 8 h after issue, default 60 min supplied by the caller; unknown fields rejected). `decide` consults an active grant only after hard denies, exclusions and T3: those never change in trust. Path, command, domain and tool scopes match on NORMALISED values with a small, documented glob dialect (no regex from the grant). Limits (`max_actions`, `max_edit_files`) are counted in state. `sandbox_required_for_execute` with sandbox unknown or off means execute is asked. On a native-Windows host an execute is never auto-allowed (N3 default). A suspended grant (roster change) behaves as no grant. Signature verification is NOT in this crate (the caller passes a grant it has verified); say so in the type's documentation.
7. `docs/POLICY.md`: the decision order as a numbered list a reviewer can check against the code, the pattern lists, the glob dialect, and every place the engine is deliberately conservative.
