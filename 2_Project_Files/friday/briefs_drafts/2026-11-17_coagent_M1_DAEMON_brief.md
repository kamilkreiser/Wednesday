## 4. Deliverables

1. **Daemon process.** `coagentd --data-dir <dir>`: creates or loads its device identity in `<dir>` (directory 0700, key file 0600, refused if either is wrong or foreign-owned; never under the real home directory tonight: every test and run uses a directory under `coagent/tools/tmp/m1-daemon/`), listens on a `coagent-ipc` socket inside `<dir>`, never listens on any network interface, exits when idle or on signal, leaves no socket behind.
2. **State store.** A small `Store` trait with a file-backed implementation in `<dir>` (atomic write: temp file + rename; no SQLite yet) for: identity, contacts (pinned keys with HOW each was verified), per-(session, slot) verify attempts, shown words and hard stops (so a daemon restart does not reset them: the CORE delta gate's finding), the per-pair outbox for redelivery. Secrets never appear in `Debug`, logs or error text.
3. **Relay child.** The convener's daemon spawns `coagent relay` on `127.0.0.1` with an ephemeral port, reads its address and fingerprint from the child's output, keeps the child alive for the session and stops it at session end; the child is a separate process with no access to the daemon's data directory or IPC socket.
4. **Invite and pairing.** `invite` produces a link (`coagent://join#…` plus the same content as one pasteable line) carrying relay candidates, the relay certificate pin, the mailbox id and the link secret, per 04 section 4.1; `join <blob>` consumes it. Pairing uses `coagent-crypto::Pairing` with explicit key confirmation exactly as the library provides; on success each side stores the other as a contact with provenance `by_code_with_me` and a two-member roster is created and signed by the convener (`coagent-roster`), sent over the new channel, and the channel is inserted with `insert_with_slot`.
5. **Messaging.** Application envelopes over the channel through the relay session channel (slots per PROTOCOL.md; register the slot immediately after `chan.create`, as its Limits section requires); per-pair sequence and ack; an outbox persisted until acked; reconnect with a fresh handshake and redelivery after a dropped connection (03 section 4.5), treating `OutOfOrder` as "reconnect"; both sides see "not connected" for a silent peer. Message types for M1: `chat.msg` with an audience, `request.new` and a reply linked by `re`. Size limits before allocation on everything received.
6. **Local IPC protocol** (daemon <-> `coagent-mcp` and a minimal `coagentd ctl` subcommand for tests): JSON lines over `coagent-ipc`, versioned, with strict size limits, same-user only (the crate enforces it). Commands: `status`, `invite`, `join`, `send`, `inbox_read`, `wait`, `verify_start`, `verify_confirm`, `end`.
7. **`coagent-mcp`.** A stdio MCP server exposing exactly `send`, `inbox_read`, `wait(timeout_s)`. `inbox_read` and `wait` return peer text ONLY inside a tool result, wrapped in a fixed envelope that says it is untrusted data from a named peer (key id and local nickname) and never contains instructions from us beyond that fixed text; nothing from a peer is ever written to stdout outside a tool result, to stderr, or into a tool DESCRIPTION. `wait` blocks up to its timeout (cap: 300 s) and returns a count-only notice when nothing arrived. The liveness invariant of 03 section 3.4 (release peer text only inside a tool call the gate has witnessed) needs the hook, which is M2: implement the release point as ONE function with a `GateWitness` parameter that M1 satisfies with an explicit, loudly named `UngatedM1` value, so M2 has exactly one place to change and a test proves there is no other path to peer text.
8. `docs/DAEMON.md`: process model, data directory layout, the IPC protocol, the message flow for pair/send/receive/reconnect, and every place you chose the conservative reading.
