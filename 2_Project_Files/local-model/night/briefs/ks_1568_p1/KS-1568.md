## What is wrong (one paragraph)

`withConnectorChain` (`index.ts:315`) makes the next rotate of one connector wait for the previous one, so the waiting costs no pooled database client (KS-757's pool trap). The wait is bounded, so a predecessor that never settles cannot hang the connector for ever: the bound is `ROTATE_CHAIN_WAIT_MS`, read per call by `rotateChainWaitMs()` (`:311-314`), default 10 s. The read is `Number.parseInt(process.env.ROTATE_CHAIN_WAIT_MS ?? '', 10)`, and `parseInt` stops at the first non-digit: `10s` reads as **10** and `1500ms` as **1500**. An operator who writes a unit therefore gets a bound of 10 ms (effectively no chain), and the pool pressure the chain exists to prevent comes back. The fix is a stricter read on this one line: the value counts only if it is a plain run of digits (optionally padded with whitespace), `/^\s*\d+\s*$/`, in which case `Number(...)` of it is used; anything else becomes `Number.NaN`, which the next line already turns into the 10 s default. The existing guard on the next line (`Number.isFinite(raw) && raw > 0 ? raw : 10_000`) stays as it is and still handles `0`.
