## What is wrong (one paragraph)

In `webhooks.ts` the Stripe webhook handler claims the event with `claimed = await claimEvent(event.id, event.type, event)` inside a try; its catch logs `logger.error('[Webhook] Refusing delivery — idempotency unavailable', { eventId: event.id, eventType: event.type, error: error instanceof Error ? error.message : String(error) })` (the read is on line 184) and then answers `res.status(503)` with a constant body (`SERVICE_UNAVAILABLE`, message asking to retry the delivery). If the value thrown out of `claimEvent` is a revoked Proxy, `error instanceof Error` itself throws a TypeError inside the catch; if it is an Error whose `message` getter throws, `error.message` throws. Either way the catch throws before the line is logged and before the 503 is sent, so the handler rejects and the request is left unanswered. (`claimEvent` throws its own ClaimUnavailableError for every database failure, so a hostile value reaches this catch only when something `claimEvent` calls outside its own try, such as `logger.warn`, throws one; this is defence-in-depth.) The fix reads the thrown value inside its own inner `try` into a local `reason`, falling back to the constant `unreadable thrown value`, and the log call uses `error: reason`. The response stays the same constant 503; the thrown text is only ever logged. An ordinary Error still logs `error: <its message>`.

## Where

`Blockchain/Dev/services/billing/src/routes/webhooks.ts:184`. CALLERS: this IS the route handler (`router.post('/stripe', ...)`). The catch runs BEFORE any side effect: `claimEvent` either never reached the INSERT (`isDbAvailable()` false, where its `logger.warn` is the call the test makes throw) or failed at it, and the handler returns before `handleWebhookEvent`. **BEHAVIOUR CHANGE the raise PR must state (Stripe-facing):** for a hostile throw out of the claim, Stripe today receives NO response (the request hangs until Stripe's timeout counts the delivery as failed and retries it); after the fix it receives the constant 503 `SERVICE_UNAVAILABLE`, exactly what an ordinary claim failure already gets (503 is a failed delivery Stripe retries with backoff). Persisted state: no webhook_events row is written by this path in either version (the claim did not win), no credits are granted, nothing is marked duplicate, so no paid event is skipped or double-processed by this change; the redelivery is claimed fresh as for an ordinary 503.
