## What is wrong (one paragraph)

Both certification routes default `anchoringStatus` to `'failed'` (`:409` and `:1147`) and set `'submitted'` only when the anchoring service answers ok (`:429`-`:433`, `:1162`-`:1166`). In production a failed leg answers 503 (`:438`-`:443`, `:1170`-`:1175`). Everywhere else the route carries on and saves the certification with `blockchain: { anchorId: null, txHash: null, blockHeight: null, anchoredAt: null, confidence: 'pending-onchain', anchoringStatus: 'failed' }` (`:461`-`:472`, `:1200`-`:1207`) and NO `status` key. Nothing ever upgrades that blob: the read-time healer returns early with no anchor id (`services/anchorStateSync.ts:353`), and `certifications.ts` calls none of `updateDocument`, `pollAnchorUntilConfirmed`, `reconcileDocumentAnchorState` (0 hits). The gateway never reads `anchoringStatus` (0 hits in `api-gateway/src` outside tests); it reads `blockchain.status` (`verification.ts:626`) and, for a STATUSLESS blob only, the `confidence` label (`:748`). So a certification whose anchoring failed is served as `pending-onchain` for as long as it exists. The gateway's one mapping, `confidenceForAnchorStatus` (`verification.ts:244`-`:259`), already turns `'failed'` into `off-chain-only` (`:253`-`:254`), and once a status is present the stale label is ignored (`:748` requires `persistedStatus == null`). Kam's ruling (b): the failed leg SAVES `status: 'failed'`. The success leg is unchanged: it stays statusless `pending-onchain` with its anchor id.
