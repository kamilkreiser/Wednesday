## What is wrong (one paragraph)

`dbSaveApiKey` (`index.ts:292`) sets the key in `memApiKeys` first (`:293`), then runs the INSERT inside a `try` whose `catch` (`:331`-`:333`) only logs `DB save API key failed` and returns normally. The mint route calls it at `:1132` and then answers `201` with the plaintext key (`:1146`, `key: keyValue` at `:1150`) whether or not the row was written. The key lives in process memory, validates, and is listed (`GET /api/keys` reads `memApiKeys` at `:1205`) until the next restart, when it silently stops existing: the caller holds a credential that the platform does not. Re-raising inside `dbSaveApiKey` for every caller is NOT safe: the KS-888 r2 brief-writer measured (`night/briefs/KS-888-r2/README.md`) that revoke (`:1229`) and validate (`:1281`) are `async (req, res)` handlers with no `next` and no `try`, so a throw there is an unhandled rejection. Under node 24 that ends the process. So the rule is:
- `dbSaveApiKey` gains an OPT-IN second parameter `opts: { rethrow?: boolean } = {}`, and its `catch` re-throws only when `opts.rethrow` is set. With no second argument (revoke, validate) it behaves exactly as today;
- the mint route calls it with `{ rethrow: true }` inside its own `try`, and on a failure: deletes the unsaved key from `memApiKeys`, logs one line, and answers `503 SERVICE_UNAVAILABLE` when the fault is an infrastructure one (the same classes as auth's `isInfrastructureDbError`: SQLSTATE class 08, 53 or 57, a socket code, or a pool-timeout message), otherwise `500 INTERNAL_ERROR`. Neither body carries a key, a prefix or an id. Nothing after the save (the KS-577 revoke-on-rotate, the `API key created` log, the 201) runs.
