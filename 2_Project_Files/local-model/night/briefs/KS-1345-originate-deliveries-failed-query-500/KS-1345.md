## What is wrong (one paragraph)

The delivery-history route of the originate webhooks router, `GET /api/webhooks/:id/deliveries`, reads its rows with a query that carries a rejection swallower: a FAILED query (timeout, pool exhaustion, a permissions error) is turned into an empty list and answered `200 { success: true, deliveries: [] }`. A database failure therefore reads as "this webhook has no deliveries", to the client and to the log (nothing is logged), and the route's own catch block, which already calls the router's `fail500` helper with the context `Webhook delivery history read failed (GET /api/webhooks/:id/deliveries)`, is never reached for a rejected query. Its sibling `GET /api/webhooks` had the same defect and was fixed by #1381. Measured with the cells below at the tip: a rejected history query answers 200 and logs nothing.

## The exact change

No diff, no line number and no code is given for the product file: you find the site and write the lines. The behaviour, all of it:

1. **A failed history query is a 500.** When the history query for `GET /api/webhooks/:id/deliveries` REJECTS, the route must answer the router's constant `500 INTERNAL_ERROR` body (the one `fail500` already produces), the thrown text must not appear in the body in any environment, and exactly one `logger.error` call must record it with the route's existing context string and the thrown text. It must never answer 200 with an empty list.
2. **A side effect you must absorb.** Today that swallower also hides a different failure on this route: an id that passes the route's id-format check but is not a UUID (for example `0`) reaches the database cast to uuid, Postgres refuses it, and the swallower turns the refusal into an empty list. Once the swallower is gone that same request would answer 500. It must not: a well-formed id that is not a UUID keeps its CURRENT answer, `200 { success: true, deliveries: [] }`, and the database query is NOT run for it. (Changing that answer to a 404, as the sibling write routes do, is a contract decision for another ticket; this brief does not take it.) The router already has a UUID pattern constant you can reuse; add no import.
3. **Everything else stays.** A malformed id is still a 400. A history query that resolves still answers 200 with its rows and logs nothing. The router's OTHER best-effort read, in the event-dispatch function that fans an event out to the subscriptions, deliberately swallows its own query failure (a fire-and-forget fan-out) and MUST keep doing so. The `fail500` helper, every other route, and the `authenticate()` mount are not touched.

**Do NOT touch**: the event-dispatch function's subscription read (a cell counts the swallowers that remain and wants exactly one); the `fail500` helper; the other routes of the router.
