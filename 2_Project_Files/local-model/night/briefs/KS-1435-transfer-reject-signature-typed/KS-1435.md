## What is wrong (one paragraph)

`POST /api/transfers/:id/reject` (`:737`) parses its body with `rejectTransferSchema.parse(req.body)` (`:739`). That schema (`:408`-`:412`) declares `rejectorId`, `rejectorRole` and `reason` only. zod's default (non-strict) object parsing DROPS unknown keys, so a body whose `signature` is an object or a number passes the parse, the field is discarded, and the reject runs: the transfer moves to `rejected` and the route answers 200. The published contract (`TransferRejectRequest`) declares `signature` as a `string`, so `signature: {}` is a schema-violating body that should be a 400 — Schemathesis' `negative_data_rejection` reports exactly this. The sibling approve schema was fixed for the same mechanism under KS-518 (`:397`-`:403`, comment: *"Declaring it types it (non-string → 400) without changing valid-input behaviour"*, and `signature: z.string().optional(),` at `:403`). The fix adds that same line to `rejectTransferSchema`; a missing `signature` and a string `signature` behave exactly as today, and the route's existing ZodError branch (`:778`-`:780`) answers the 400.
