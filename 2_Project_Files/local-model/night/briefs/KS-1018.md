## What is wrong (one paragraph)
In `services/auth/src/routes/users.ts` three verification-store reads swallow EVERY database error with a bare
`} catch { /* fall through */ }` and then answer from a process-local in-memory map: `getVerificationRequest` (the catch
at line 1183), `findPendingVerificationRequest` (line 1204) and `listUserVerificationRequests` (line 1226). A DB outage
(connection refused, pool exhausted, `08xxx`/`53xxx`/`57xxx` pg codes) is therefore indistinguishable from "no such
request" — the admin review route (line 1309–1310) turns it into a 404 — and nothing is logged. Fix, exactly the
KS-963 shape `userRepo.getUserById` already uses (`repositories/userRepo.ts:408-414`): each catch names the error,
logs it, and RETHROWS an infrastructure error as `ServiceUnavailableError` (503); any other error still falls
through to the in-memory map as today. (The ticket's item 3 — whether the in-memory fallback should exist at all — is
a design decision: do NOT remove the fallback.)
