## What is wrong (one paragraph)

`POST /api/status/:id/revoke` and `/unrevoke` enforce an **admin-class role and no tenant ownership
check at all**, so an `ISSUER_ADMIN` in any tenant can revoke or un-revoke a credential in **another
tenant's** status list — reproduced live, with controls both ways (a foreign caller against a
non-existent list still gets 404, and a non-admin `OWNER` still gets 403, so the 200 was a genuine
authorisation pass rather than a blanket accept). The reason no check exists is structural and is
visible in the file: `status.ts:76` holds status lists in `const statusListManagers = new
Map<string, StatusListManager>()`, a process-local Map with **no tenant linkage**, and the backing
table `credential_status_lists` (`migrations/001_initial-schema.sql:759-765`) declares only `id`,
`issuer_id`, `status_list`, `updated_at`, `created_at` — **no owner column, and nothing in the
service writes to it**. So there is no target tenant to hand `decideTenantAccess`
(`packages/shared/src/security/keyRevokePolicy.ts:141`), and the interlock that sank the KS-578/643
shape applies: adding a tenant comparison without giving lists an owner would refuse *every* caller.
Kam's ruling takes the other road — **narrow the gate to the platform roles now**, which is exactly
the call KS-743 made for the tenant-less `/api/events` routes ("there is no `targetTenantId` to hand
`decideTenantAccess`, so 'platform operator' is the only authorisation that is TRUE of this
surface"). Dropping `ISSUER_ADMIN` from `STATUS_WRITE_ROLES` closes the cross-tenant hole completely
and costs tenant admins the ability to write status until the owner column lands. NOT in this task:
the migration, a repository, or anything that gives a status list an owner — that is the
`bind-creator` follow-up named in the raise notes.
