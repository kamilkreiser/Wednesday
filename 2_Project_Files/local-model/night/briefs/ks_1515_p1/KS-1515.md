## What is wrong (one paragraph)

In `createTimestamp` (index.ts, `case 'rfc3161'`), line 469 reads `eidasQualified = tsaResult.token ? tsaResult.eidasQualified === true : false;` and line 470, the next line, reads `if (tsaResult.mock === true || !tsaResult.token) verified = false;`. So the mock flag already decides `verified` but not `eidasQualified`: a TSA reply `{ token, mock: true, eidasQualified: true }` answers 201 with `verified: false` and `eidasQualified: true`, and with `requireEidas: true` the guard at line 501 (`if (data.requireEidas && !eidasQualified)`) sees a "qualified" value and does NOT refuse. The ticket calls this defence in depth: today the real fallback hard-codes `eidasQualified: false` (`tsa/qualified-tsa.ts:333`, per the ticket), so the combination cannot occur until the TSA module changes. The fix is the ticket's own one line: derive `eidasQualified` from the mock flag as well as the token. The existing cell at test line 85 (`the FLAG decides ... mock marked eidasQualified:true`) uses exactly this input and asserts only `verified`.
