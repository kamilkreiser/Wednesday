## What is wrong (one paragraph)

The revoke handler (`index.ts:1248`, `async (req: Request, res: Response)`, no `next`, no `try`) sets `apiKey.isActive = false` at `:1285` and calls `await dbSaveApiKey(apiKey);` at `:1286`. `dbSaveApiKey` (`:292`) puts the key into `memApiKeys` first (`:293`), then runs the INSERT inside a `try` whose `catch` (`:331`-`:336`) logs and re-throws ONLY when the caller passed `{ rethrow: true }` (`:335`, added by #1322 for the mint). Revoke does not pass it, so a failed save is swallowed and the handler answers `200 "API key revoked"` (`:1290`-`:1293`) although the revoke was never stored: after the next restart the key is live again, and the caller was told it is dead. Passing `{ rethrow: true }` alone is NOT safe: the r2 brief-writer measured (`night/briefs/KS-888-r2/README.md`) that a throw into this handler is an unhandled rejection (no `next`, no `try`), which ends a node 24 process. So the save call goes inside the handler's OWN `try`, and on a failure: the in-memory revoke is KEPT (it is already in `memApiKeys`, so the key stops validating in this process), one line is logged, and the handler answers `503 SERVICE_UNAVAILABLE` for an infrastructure fault (the mint's classifier, copied byte for byte from `:1143`: SQLSTATE class 08, 53 or 57, a socket code, a pool-timeout message) or `500 INTERNAL_ERROR` for anything else. The `API key revoked` log and the 200 do not run. The comment above `:335` still says only the mint opts in; hunk 1 rewrites it so it is true whether or not the validate brief has also landed.
