## What is wrong (one paragraph)

`POST /register` (`routes/auth.ts:158`) lets a caller claim an INVITED stub (KS-74): `createUser` runs first, and because its `ON CONFLICT` clause is narrow it cannot flip the stub's status, so the handler then applies the activation explicitly at `:257` with `await userRepo.updateUser(userId, { status: 'ACTIVE', passwordHash, ... })` and DISCARDS the result. `updateUser` answers `null` when its UPDATE matched no row or its read-back found nothing (under fail-closed row-level security an unresolved tenant setting produces exactly a zero-row UPDATE). The handler then goes on to store a verification token, send the mail, create a session and answer **201 with a token pair, over a row that is still INVITED**. The repository already has the right wrapper, `updateUserOrThrow(id, updates, operation)`, which logs and throws a `ServiceUnavailableError` (503) when the update cannot be confirmed; `POST /reset-password` (`:848`) and `POST /verify-email` (`:892`) in this same file already use it. The fix is to call it here: `updateUserOrThrow` in place of `updateUser`, with the operation name `'Claiming the invited account'` as its third argument. The thrown error reaches the route's `catch (error) { next(error); }`, which hands it to the error handler (503).
