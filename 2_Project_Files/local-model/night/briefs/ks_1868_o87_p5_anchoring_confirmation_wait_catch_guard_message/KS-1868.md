## What is wrong (one paragraph)

The catch of `waitForConfirmation` builds the status text passed to `onStatusUpdate` with the thrown value's message read INSIDE a template literal, unguarded: `` `error: ${err?.message}` ``. A thrown value whose read throws (a revoked Proxy: the `.message` get throws; an Error whose `message` getter throws) or whose `message` is a Symbol (a template literal cannot convert a Symbol to a string) therefore throws INSIDE the catch, so the whole poll REJECTS on the first such attempt instead of counting the failed attempt (`errored += 1` has already run) and carrying on to the next attempt, as it does for an ordinary Error. The fix is the house guard placed before the call, inside the existing `if (onStatusUpdate)`: read the message once inside a `try`, keep `undefined`/`null` as they are (the template printed them as `undefined`/`null`), coerce anything else with `String(...)`, and fall back to the constant `'unreadable thrown value'` when the read or the coercion throws; then `` `error: ${reason}` ``. `errored += 1`, the backoff and the result are unchanged.

WHAT AN ORDINARY ERROR GETS (the rule for taking the site): a rejection of `getTransaction` counts one failed attempt, reports `error: <message>` to `onStatusUpdate` (when given), sleeps and tries the next attempt; the final result carries `errored`. Today (hostile value): the catch throws while building the status text (only when `onStatusUpdate` is given), so the poll REJECTS to its caller on that attempt: the remaining attempts are never made and no result with `errored` is returned.
