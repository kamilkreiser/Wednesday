## What is wrong (one paragraph)

In `routes/verification.ts` the POST /api/verification/verify-file handler, when no document row is found, asks anchoring whether the hash is on-chain. It gates on `if (chain?.verified) {` (line 712), which is truthy for any non-empty value, so a reply whose `verified` is the STRING `'false'` passes; the handler then answers `verified: true` and builds a blob that hard-codes `anchored: true`. `confirmStalePendingAnchor` at line 454 already uses the strict form (`chain?.verified !== true`). Second, the blob handed to `presentBlockchainHonestly` (lines 716 to 723) lists `anchored`, `network`, `txHash`, `blockHeight`, `cardanoScanUrl` and `confirmedAt` but never `simulated`, so a reply that declares itself simulated is presented as on-chain: `presentBlockchainHonestly` (lines 54-71) decides on `Boolean(b.simulated)` or a placeholder-looking `txHash`, and `simulated` never reaches it. The fix: the gate becomes `chain?.verified === true`, and the blob gains one field, `simulated: chain.simulated,`, after `confirmedAt: chain.confirmedAt,`, so the existing rule decides. Everything else is unchanged. The presenter has only two simulated signals, the placeholder `txHash` and the `simulated` flag: anchoring removes the first (`anchorReadback.ts:116`) and this site drops the second, so neither file looks wrong on its own; and the site then returns top-level `verified: true` and `status: 'anchored'` as literals, so the honesty marker is the only load-bearing field.
