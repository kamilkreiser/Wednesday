## What is wrong (one paragraph)

After KS-1029, `PATCH /api/gdpr/dsr/:dsrId` answers "DSR not found" with two statuses depending on the spelling of the id: a non-canonical id is refused before the lookup with `404 NOT_FOUND 'DSR not found'` (`routes/gdpr.ts:408-410`), but a canonical id that names no row falls through to `res.json({ success: updated, message: updated ? 'DSR updated' : 'DSR not found' })` (`:413`) and answers `200 {success:false, message:'DSR not found'}`. `GET /dsr/:dsrId` answers 404 for both (`:366`). The change: when `updateDSRStatus` returns false, answer the same `404 {success:false, error:{code:'NOT_FOUND', message:'DSR not found'}}` the id guard sends, and send `{success:true, message:'DSR updated'}` otherwise. A database error still rethrows to the 500 handler (KS-754), the body checks still come first. The two KS-1029 control cells that pinned the old 200 (U1 and A1) are updated in place.
