## What is wrong (one paragraph)

Platform-S signs a file detached and wants the SHA-256 of the `.p7s` anchored with the sign event (KS-1454). `anchorDocumentSchema.metadata` (`anchorSchema.ts:178-215`) declares only `documentType`, `timestamp` and `identityCommitment`; zod strips every other key, so a `metadata.signatureHash` that S sends is silently dropped and the sign anchor looks like a plain one. `buildFlatAnchorMetadataPayload` (:265-319) is a fixed whitelist and has no `signatureHash` entry, so even a declared field would not reach the ledger. The change: (1) declare `signatureHash` in `metadata` as an optional string matching `^[a-f0-9]{64}$` (lowercase hex only, the ticket's pattern); (2) add a rule at the end of the existing `superRefine` that adds a custom issue when `metadata.signatureHash` is present and `metadata.documentType` is not `'sign'` (the ticket: 400 on any other verb, 'a requirement, not an option'); (3) add one conditional spread after the `identityCommitment` spread in the payload builder, `signatureHash` anchored verbatim under `secuura`. A 64-character lowercase-hex string is exactly 64 bytes, the Cardano string cap, so `toCardanoMetadatum` (`cardano/cardanoMetadatum.ts:59-62`, `> 64` bytes chunks) leaves it one string. `POST /api/anchors` calls `anchorDocumentSchema.parse` (`index.ts:477`) inside a try whose catch handles `z.ZodError` (:582), so a failed rule is the route's validation error, as for every other refusal here.
