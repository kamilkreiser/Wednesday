## What is wrong (one paragraph)

`check-startup-migrations.sh` guards its parser with `if ! command -v python3 > /dev/null 2>&1; then` (`:77`), which checks that python3 is PRESENT, not that it WORKS. When a python3 is on PATH but exits non-zero (gate47 measured a stub exiting 127; a macOS `/usr/bin/python3` shim with no developer tools installed is the same shape), the guard passes, the parse pipeline at `:83`-`:101` fails, `2>/dev/null || echo "UNPARSEABLE"` (`:101`) swallows the interpreter failure, and the `UNPARSEABLE)` arm (`:104`-`:107`) prints "/health body is not JSON — migration check SKIPPED" and exits 2. gate47 measured the result (report :218): `deploy.sh` exits 0 "passed with 1 check(s) SKIPPED" over a `failed: 2` body, with the cause misattributed to the body. python3 ABSENT already fails closed (rc 1, `:77`-`:81`, Wednesday's gate44 ruling); a BROKEN python3 is the same host defect and must do the same. The fix probes python3 itself (`python3 -c 'import json'`) inside the existing guard, before any parsing, and names both causes in its message. A genuinely non-JSON body with a working python3 still reaches `UNPARSEABLE` and rc 2 (the existing cell P5 pins that and must stay green).
