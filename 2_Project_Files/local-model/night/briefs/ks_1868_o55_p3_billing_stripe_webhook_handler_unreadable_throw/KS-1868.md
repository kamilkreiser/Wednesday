## What is wrong (one paragraph)

In `webhooks.ts` the Stripe webhook handler, after winning the idempotency claim, runs `handleWebhookEvent(event)` and `finaliseEvent(...)` inside a try; its catch starts `const message = error instanceof Error ? error.message : String(error);` (line 215), then logs it, calls `await releaseClaim(event.id, message)` (which sets the row to 'failed' so a redelivery can re-claim it) and answers the constant `res.status(500).json({ success: false, error: { code: 'INTERNAL_ERROR', message: 'Webhook handler failed' } })`. If the handler throws a revoked Proxy, `error instanceof Error` itself throws a TypeError inside the catch; if it throws an Error whose `message` getter throws, `error.message` throws. Either way the catch throws on its first line, so nothing is logged, the claim is NOT released and the 500 is never sent. The fix declares `let message: string;` and reads the thrown value inside its own inner `try` into it, falling back to the constant `unreadable thrown value`; every later line of the catch (the log, `releaseClaim`, the 500) is UNCHANGED and now runs, with `message` being the constant. An ordinary Error still gives `message = <its message>`.

## Where

`Blockchain/Dev/services/billing/src/routes/webhooks.ts:215`. CALLERS: this IS the route handler (`router.post('/stripe', ...)`). **MONEY-ADJACENT BEHAVIOUR CHANGE the raise PR must state (Stripe-facing and persistence):** for a hostile throw out of `handleWebhookEvent` (for example `addCertificationCredits` rejecting) today (1) Stripe receives NO response and times out, (2) the webhook_events row stays 'processing', (3) Stripe's redelivery loses the claim (`ON CONFLICT ... WHERE status = 'failed'` does not match 'processing') and is answered `200 {received:true, duplicate:true}` WITHOUT processing, so a paid event whose handler failed is skipped; (4) only an admin POST /webhooks/replay recovers it. After the fix (1) Stripe receives the constant 500 (retried with backoff), (2) the row is set to 'failed' by `releaseClaim`, (3) the redelivery re-claims the row and is processed, which is EXACTLY what an ordinary Error already does today (cells C1 and C2 are green at the tip). The change therefore makes the hostile-throw path identical to the ordinary-Error path; it does not introduce a new retry behaviour. Unchanged and not touched by this brief: `handleCheckoutComplete` grants the credits and then makes further calls (log lines); a value thrown AFTER a successful grant is released and re-processed on redelivery today for an ordinary Error, and after the fix for a hostile value too, i.e. the same existing double-grant window an ordinary Error already has; whether that window should be closed is a design question outside this brief.
