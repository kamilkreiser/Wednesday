## What is wrong (one paragraph)

`POST /api/keys/validate` ends by bumping `apiKey.usageCount++` on the copy this process holds in memory and then calling `dbRecordApiKeyUsage(apiKey)`, whose statement is `UPDATE svc_api_keys SET last_used_at = $2, usage_count = $3 WHERE id = $1` with `$3 = k.usageCount`. The value written is the process's own (possibly stale) copy plus one, so two validates of one key in different processes, or two concurrent validates, overwrite each other: measured by the KS-1370 gate on the merged change (twenty concurrent validates left the count at 9-12) and re-measured here on a real PostgreSQL 18.3 (twenty concurrent read-modify-writes left `usage_count = 1`). Counting in the statement itself, `usage_count = usage_count + 1`, makes the database the one counter; `last_used_at = GREATEST(last_used_at, $2)` makes the timestamp monotonic for the same reason. The statement then takes two parameters (`$1` the id, `$2` the timestamp), so the parameter array loses its third element in the same hunk.
