## What is wrong (one paragraph)

In `index.ts`, `saveKeyAndRetirePriors` mints the new key and retires the connector's prior keys in ONE transaction; the retire runs under the savepoint `ks1549_retire` so that a failed retire rolls back alone and the mint stands (KS-577 + KS-1549: `null` means the retire failed, the new key still stands, and the route reports `priorKeysRevoked: null`). The catch at :397-403 runs `ROLLBACK TO SAVEPOINT`, then logs `log('error', 'KS-577: revoke-on-rotate FAILED ...', { connectorId, tenantId: k.tenantId, keepKeyId: k.id, error: err instanceof Error ? err.message : String(err) })` (the read is on line 400) and returns `null`. If the UPDATE rejects with a revoked Proxy, `err instanceof Error` itself throws a TypeError inside the catch; if it rejects with an Error whose `message` getter throws, `err.message` throws. Either way the catch throws before the line is logged and before `return null`, which aborts the callback. The fix reads the thrown value inside its own inner `try` into a local `reason`, falling back to the constant `unreadable thrown value`, and the log call uses `reason`. Nothing else changes: an ordinary Error still logs `error: <its message>`.

## Where

`Blockchain/Dev/services/security/src/index.ts:400`. CALLERS (git grep at the tip): the only caller is the register/mint route `POST /api/keys` at :1395 (`priorKeysRevoked = await saveKeyAndRetirePriors(apiKey, data.connectorId)`, only when `data.rotate && data.connectorId`), inside a try whose catch (:1399-1407) drops the in-memory key and answers 503/500 `The API key could not be saved, so no key was issued`; on success the 201 body carries `priorKeysRevoked`. **BEHAVIOUR CHANGE the raise PR must state:** for a hostile throw from the retire UPDATE, a rotate today FAILS (500, no key issued, nothing committed, the prior key still live and nothing persisted); after the fix it MINTS (the transaction COMMITs the new key), the prior key is left active, and the 201 body reports `priorKeysRevoked: null`. That is exactly what an ordinary DB error from the retire UPDATE already does (the KS-577 contract: the old credential is still valid, the operator is told).
