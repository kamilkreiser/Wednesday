## Scope

**Closes KS-1639's recommendation, with one deliberate difference, flagged.** The ticket's snippet is `typeof r.is_active === 'string' ? !/^(f|false|0|no)$/i.test(r.is_active.trim()) : Boolean(r.is_active)`. That snippet reads the EMPTY string as active (the regex does not match '', so `!false` is true), whereas today `Boolean('')` is false; it would un-revoke a key whose flag arrives as ''. This brief therefore tests for the TRUE forms instead: `/^(t|true)$/i.test(r.is_active.trim())`. 'f', 'false', 'F', 'FALSE', ' f ', '' and any unrecognised string read inactive; 't', 'true' (any case, padded) read active. The ticket also says "decide at the same time whether the text form should be accepted at all (the alternative is to refuse a non-boolean outright)". This brief takes the first of its two options (accept the Postgres text forms, fail closed on anything else); refusing outright would be a product call and is NOT done here. Every row the live code paths produce has a real boolean (the column is BOOLEAN), so nothing observable changes today.

## What is wrong (one paragraph)

`rowToApiKey` (`converters.ts:158-185`) maps `isActive: Boolean(r.is_active),` (`:171`). `Boolean()` of any non-empty string is `true`, so a row whose `is_active` arrives as the Postgres text form of false (`'f'`, `'false'`) produces an API key the service treats as LIVE. The same mapper already honours `'t'` as active (cell G10 in `row-converters.test.ts`), so it supports the text encoding in one direction only, and the direction it fails in is the unsafe one: a revoked key reads as active. On every current provisioning path the column is BOOLEAN and node-postgres hands back a JS boolean, so `'f'` cannot arrive today; the shapes that would deliver text are a `::text` cast, a `row_to_json` round-trip, a different driver, a hand-built fixture. The fix replaces line 171 so that a STRING value is active only when it is a text form of true, and anything that is not a string keeps `Boolean(...)`.
