## What is wrong (one paragraph)

In `oauth.ts` the outer catch of `POST /authorize` (line 805) logs `logger.error('OAuth authorize POST error', { error: error.message })` and the outer catch of `POST /token` (line 1109) logs `logger.error('OAuth token error', { error: error.message })`; each then answers the constant `500` with code `INTERNAL_ERROR` and message `server_error`. If an awaited call in the try (for example the client app lookup `getAppByClientId`) rejects with a revoked Proxy, the property read `error.message` itself throws a TypeError inside the catch block; if it rejects with an Error whose `message` getter throws, `error.message` throws. Either way the catch throws before the line is logged and before the 500 is sent. Express 4 does not catch a rejection of an async handler, so the request gets NO response and Node sees an unhandled rejection. The fix reads the SAME expression `error.message` into a local `reason` inside its own `try`, and a `catch` sets the constant `'unreadable thrown value'`; the log call then uses `reason`. The 500 responses are untouched. This is the inline guard already merged in `routes/auth.ts` (PR 1911, e.g. lines 308-313); no helper is added.

## Where

`Blockchain/Dev/services/auth/src/routes/oauth.ts`: line 805 and 1109. CALLERS: both are Express route handlers on `oauthRouter` (mounted under /api/oauth), reached over HTTP by OAuth clients. The catches decide nothing about authorisation: an authorization code is minted, and tokens are issued, only on the success paths inside the try, which are untouched; the app lookup is the first await on both paths in the cells (a rejection there means nothing was minted). WHAT AN ORDINARY ERROR GETS (the rule for taking the site): the ERROR line with the message and the constant 500 `server_error`. After the fix an unreadable thrown value gets exactly that; today it gets no response and an unhandled rejection. Nothing is minted before or after in the cells. The sibling catches of this file that read `error?.code` / `/regex/.test(error?.message)` first, or that put `error.message` into the response body (lines 531, 1259, 1283, 1296, 1353, 1382, 1407), are NOT in this brief. **BEHAVIOUR CHANGE the raise PR must state:** for an unreadable thrown value only, the two routes log a constant reason and answer the constant 500 (as for an ordinary Error) instead of leaving the request unanswered. Persisted state: none changes in the cells; a rejection later in the try (after a code or session write) would leave the same persisted state as for an ordinary Error. Recommended tier 1 (OAuth authorize and token endpoints).
