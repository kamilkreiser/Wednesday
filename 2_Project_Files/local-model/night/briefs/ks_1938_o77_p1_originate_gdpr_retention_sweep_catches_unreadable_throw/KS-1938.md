## What is wrong (one paragraph)

In `services/gdprService.ts` the GDPR retention sweep `enforceRetentionImpl` selects every `auto_delete` policy and, for each policy, runs the DELETE or anonymising UPDATE, the `data_deletion_log` INSERT and the `last_enforcement_at` stamp inside a PER-POLICY `try`. That `try`'s catch logs `Retention enforcement failed` with `error: err instanceof Error ? err.message : String(err)`, and the whole loop sits in an OUTER `try` whose catch logs `Retention enforcement error` with the same expression. If the rejection value is a revoked Proxy, `err instanceof Error` itself throws a TypeError inside the per-policy catch; if it is an Error whose `message` getter throws, `err.message` throws. The exception then LEAVES THE LOOP, the outer catch logs the new TypeError (or the getter's Error) instead, and **every later policy is skipped for that run**: no DELETE or anonymisation, no deletion-log row, no `last_enforcement_at` stamp. An ordinary Error is logged and the loop goes on to the next policy. (KS-1938, found by gate 104, G104-F1: measured there with a stateful database stand-in, base == head.) The fix reads the SAME expression into a local `reason` inside its own `try`, and a `catch` sets the constant `'unreadable thrown value'`; each log call then uses `reason`. This is the inline guard already merged in this service's sibling files (`routes/certifications.ts`, KS-1844; `services/auth` `routes/auth.ts`, PR 1911); no helper is added. Nothing about which rows are deleted, which statement is issued or which policy is attempted changes: the DELETE/UPDATE/INSERT code is untouched.
