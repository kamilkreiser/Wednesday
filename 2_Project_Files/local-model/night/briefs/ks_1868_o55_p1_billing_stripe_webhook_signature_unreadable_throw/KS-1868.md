## What is wrong (one paragraph)

In `webhooks.ts` the Stripe webhook handler verifies the delivery with `stripeService.constructWebhookEvent(req.body, signature)` inside a try; its catch logs `logger.error('Webhook signature verification failed', { error: String(error) })` (the read is on line 166) and then answers the constant `res.status(400).json({ success: false, error: { code: 'BAD_REQUEST', message: 'Invalid signature' } })`. If verification throws a revoked Proxy, `String(error)` throws a TypeError inside the catch; if it throws an Error whose `message` getter throws, `String(error)` (Error.prototype.toString reads `.message`) throws. Either way the catch throws before the line is logged and before the 400 is sent, so the handler rejects and the request is left unanswered. The fix reads the thrown value inside its own inner `try` into a local `reason` using the SAME expression `String(error)`, falling back to the constant `unreadable thrown value`, and the log call uses `error: reason`. The response stays the constant 400 `Invalid signature`; the thrown text is only ever logged, never sent. An ordinary Error still logs `error: Error: <its message>` exactly as today.

## Where

`Blockchain/Dev/services/billing/src/routes/webhooks.ts:166`. CALLERS: this IS the route handler (`router.post('/stripe', ...)`), the only route the gateway forwards to billing. This catch runs BEFORE the idempotency claim, before `handleWebhookEvent` and before any database write, so no webhook_events row, credit or payment state exists to change. **BEHAVIOUR CHANGE the raise PR must state (Stripe-facing):** for a hostile throw from signature verification, Stripe today receives NO response (the request hangs until Stripe's own timeout counts the delivery as failed and schedules a retry); after the fix it receives the constant 400 `Invalid signature`, exactly what an ordinary verification error already gets (Stripe treats any non-2xx as a failed delivery and retries it as for the ordinary case). Nothing is persisted either way, no paid event is processed, skipped or marked duplicate by this change. A hostile value here is defence-in-depth: `constructWebhookEvent` is Stripe's own SDK.
