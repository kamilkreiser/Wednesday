## What is wrong (one paragraph)

The registration for `GET /api/referrals/{code}` (`referral.openapi.ts:469`-`:489`) declares its 200 body as `schema: ReferralCodeSchema` (`:480`): the flat `ReferralCode` record, which requires `id`, `code`, `ownerUserId`, `uses`, `active` and `createdAt` at the top level. The handler (`routes/referrals.ts:95`, `router.get('/:code', ...)`) answers something else: at `:105`-`:116` it sends `res.json({ success: true, data: { code, isActive, isExpired, customLabel, referredReward, referrerReward } })`. Schemathesis flagged the pair as `response_schema_conformance` on the 2026-09-29 `pr` sweep (KS-1015 comment, seed `1939481015`; a develop control run reproduced it). The handler leaves out `id` and `ownerUserId` ON PURPOSE: the comment at `:104` reads `// Don't expose sensitive info for public lookup`. The KS-1015 comment gives the direction verbatim: "the spec should change to match the runtime ... Adding those fields to the handler to satisfy the spec would be the wrong fix." So the spec's 200 becomes an inline `{ success, data }` envelope, in the same shape this file already uses for the sibling `POST /api/referrals/generate` 201 (`:439`-`:456`, the KS-498 envelope). `customLabel` is OPTIONAL and not nullable: the row mapper (`services/referralService.ts:116`) sets `customLabel: r.custom_label || undefined`, so JSON omits it when unset and never sends null.
