Summary
- Test only. No product file changes: one path changed, api/tests/HpsmPoc.Api.Tests/Hosting/ForwardedProofTests.cs (40 lines added, 6 removed).
- Fixes the intermittent red of ForwardedProofTests.The_web_front_end_value_is_gone_from_the_request_once_the_pipeline_has_read_it, which failed the api job on hosted CI.

Cause
- The test's watch filter (a test-only startup filter) ran `await nextMiddleware(context);` and only then wrote its reading into a plain field.
- TestServer's SendAsync completes once the response has started, and the 404 body is written inside the app's pipeline (UseStatusCodePages). So SendAsync can return before the filter's code after the pipeline has run.
- The test then read the field. It got either nothing yet, `(False, null)`, or the previous request's correct reading, `(False, "198.51.100.7")`.

Why it is not a product race
- ForwardedProofGate holds only the ForwardedClientAddress it was built with: a sealed record whose proof digest is init-only. It decides per request on that request's own headers (ForwardedProofGate.cs:20-22).
- The gate and the forwarded-headers options are built once at start-up (Program.cs:134 and :136, plus the PostConfigure at :46-50). Nothing writes them per request.
- No product code writes the connection address, and no product static is mutable.
- Every wrong value the test ever showed was "not yet written" or "the previous request's right answer", never an address that no request produced.
- With the fix, the same three assertions pass every run. A scratch product mutant that keeps X-Forwarded-For on a wrong value still fails the fixed test 5 of 5, so the fix did not blind the check.

Fix
- The filter hands each reading over through an unbounded channel, written at the same place as before (after the pipeline). The test awaits it.
- The three original assertions are unchanged apart from `api.Watched` becoming `await api.WatchedAsync()`. A new `Assert.Equal(0, api.Unread)` checks that each request gives exactly one reading.
- The 30 second WaitAsync only turns a reading that never arrives into a failure (TimeoutException). It cannot make the test pass.
- New forcing test: it holds the filter after the pipeline until the response is back, asserts the reading is not yet available, then releases the hold and checks the reading. A try/finally always releases the hold.
