## VERDICT: AGREE WITH CHANGES

The pattern is right: a small outbound-only connector in each office, joined to the Azure server through Azure Relay, is the best default for "seamless and security aligned" when the server is in the client's Azure. The designer's recommendation is not wrong. But the design as written overstates four things (blast radius, "no Internet-facing port", cost, and how closely the lab copies the product), leaves the root CA key reachable by the wrong parties, quietly rewrites a ruling of Kam's, and stands on one unproven fact (the printer accepting calls from the connector's address). It must not be put to Kam as settled until the changes in F1 to F8 are in and the half-day printer test has run.

## Findings, ranked

### F1 (HIGH, security) The "blast radius" claim is circular: the allow-list is pushed by the side it is meant to contain
- B2165:76 says a compromised Azure side reaches "only enrolled printer IPs on 443/7627/631 (connector allow-list)". B2165:87 says the allow-list is one "the server pushes after onboarding". The Azure server is the party doing the enrolling, so a compromised server pushes whatever list it likes. The only hard limits left are review point 3 (B2165:93): ports 443/7627/631 and private addresses. That is every internal HTTPS service in the office on 443, not "enrolled printers".
- **Change:** the ceiling must be set on site and not be changeable from Azure: the client's IT gives the connector the printer subnets (or exact addresses) at install, the server's pushed list can only narrow inside that ceiling, and a pushed target outside it is refused and alerted. With that, the claim becomes true.
- The comparison with a VPN at B2165:12 and B2165:76 ("a VPN would give the Azure network reach into the whole office") is overstated: a site-to-site tunnel is limited by the client's own firewall rules to the printer subnets and ports, a control their security team already knows. Fair wording: both can be scoped; the VPN is scoped by the client's firewall, the connector by our new code.

### F2 (HIGH, security) "No Internet-facing port" is true of the VM and the office, but the design adds an Internet-reachable meeting point guarded by a key
- Microsoft: "By default, Relay namespaces are accessible from internet as long as the request comes with valid authentication and authorization" (https://learn.microsoft.com/en-us/azure/azure-relay/network-security, opened 18:21). Anyone anywhere holding a Send credential for `<site>-to-site` can open connections to the office printers; anyone holding Send on `<site>-to-server` reaches the server's HTTPS port (including its admin console) from the Internet. B2165:12 and review point 1 (B2165:91, "prove with an external port scan") would pass while this door exists.
- The same page gives the two controls the design does not use: namespace **IP firewall rules** (allow only the office's outbound address and the server) and **private endpoints** (the server VM reaches Relay privately inside its VNet).
- **Change:** (a) Entra roles as the default, not the option: Microsoft documents the built-in roles Azure Relay Listener / Sender, assignable at "a specific Relay entity like a hybrid connection" (https://learn.microsoft.com/en-us/azure/azure-relay/authenticate-application, opened 18:21); the server VM uses its managed identity (no key at all on the Azure side); (b) a private endpoint for the server side and an IP firewall rule for the office side; (c) SAS keys only as the fallback for sites that will not onboard to Arc, per site and per direction, with a written rotation job. Whether SAS can be switched off entirely on a Relay namespace: UNMEASURED (not on the pages opened).
- B2165:45 puts a public IP on the VM with inbound denied. It works, but a security reviewer at a client will ask for no public IP at all; a NAT gateway is the usual answer and its price is still UNMEASURED (my query at 18:23:10 also returned 0 rows).

### F3 (HIGH, ruling) The design re-records P-4 as the option Kam did not tap
- P-4 (`datasec-oxpd-final-server-location-p4-1127`, ruled 18:05:44) is choice **a**, whose text is "A machine on each site, governed through Azure". His note (RELAYED, B2165 commission line 6): "we will encourage clients to deploy through azure marketplace. this will be an azure deployment. If they choose local (not phase 1) it will still be in their site. for this reason, we are spinning our mock client environment in azure".
- The tap and the note point different ways. B2165 follows the note (server in Azure) without saying the tap says otherwise; its candidate table marks "server in the office, governed through Azure" as "Phase 2, not Phase 1" and "Mirrors Phase 1: no" (B2165:77, :80), which is the literal text of the option he chose; and Q20 (B2165:231) proposes as a default to record "P-4 as (i) server in Azure + connector". That is rewriting a ruling by default. The same applies to q05 a "On each site's network" (B2163:17), which the design never reconciles.
- **Change:** one question to Kam before any design record changes: "P-4: you tapped (a) a machine on each site, and wrote that Phase 1 is an Azure deployment. Do you mean the server runs in the client's Azure and only a small connector sits on site?" My reading of his note agrees with the designer's; it is still his to say. (Observation, not a ruling: the connector design is the one shape that satisfies both halves, a machine on each site governed through Azure, with the server in Azure.)

### F4 (HIGH, unproven) The whole recommendation rests on a printer behaviour nobody has measured, and the design is internally inconsistent about it
- B2165:129 (section 2c, written first) **rejects** Relay because the printer "sees the agent's address, not the server's: a translation by proxy ... breaks the no-NAT rule". B2165:133 excludes point-to-site VPN for the same reason. B2165:9 then recommends exactly that behaviour. Both texts stand in the same document.
- What the HP source actually says (MEASURED, C2:154): "all OXPd .NET/Java services listen on device port 7627, not configurable; NAT **port** remapping not supported". That is about the port, not about who the caller is. Calls into the device are authenticated by HTTP Basic admin (02:249 row "Trust: server → device"), and the device endpoint is `https://{device}:7627` (C1:79), so the 7627 leg is TLS. I found no HP statement that the device checks the caller's address. So the connector is **plausible**, and section 2c's rejection is the weaker reading; but "the printer accepts 1.x calls from the connector's address" remains UNMEASURED, as the design says (S14b).
- **Change:** delete or mark superseded the rejection text in 2c and 2(d); state the HP wording precisely (port remap); make S14b the gate for everything else (see F9 for doing it without the Azure spend).
- A second-order loss the design does not mention: through a byte-passing connector the server no longer sees the printer's address on callbacks (every callback arrives from the sidecar). C1:383 and C1:496 warn that identifying a device by source address "breaks behind NAT or a proxy". OXPd 2 callbacks have a per-device credential; for OXPd 1.x none is built (02:613, item 2). **Change:** the connector prepends the original caller address (PROXY-protocol style header) for the sidecar to hand to the server, for audit, lockout and device binding; and the missing 1.x callback credential becomes a prerequisite, because the connector's LAN port accepts any machine in the office.

### F5 (HIGH, security) The mock CA root key is not "offline" and is readable by the VM and the agent
- B2165:43 and :48 store the root key "offline, secret, never on the VM" as a Key Vault secret, in the same vault the VM reads "by managed identity" under a **vault access policy** (B2165:53, Q9).
- Microsoft (https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-access-policy, opened 18:22): with access policies, "users with the `Contributor` ... role ... can grant themselves data plane access by configuring a Key Vault access policy"; access policies assign permissions "at Key Vault scope" (the whole vault, not one secret); "Azure RBAC is the recommended authorization system"; and from API version 2026-02-01 RBAC is "the default access control model for new key vaults".
- Consequences: (1) the VM identity's "get secret" covers every secret in that vault, the root key included, so "never on the VM" is not enforced; (2) the agent login (Contributor on the group) can grant itself the root key; (3) a key in an online vault is not offline; (4) Q9's default (access policies, "no card") deviates from Microsoft's current default and from "follow all security ... rules" (K11 note, RELAYED). The issuing CA's key has no stated home at all.
- **Change:** RBAC vault (one role-assignment card for Kam, which is also what a client's Owner does at Marketplace install); the root key not in Azure at all for the mock (made, used once to sign the issuing CA, kept on encrypted removable media or destroyed, as a client's offline root would be); the issuing CA key in a **separate** vault the VM cannot read; only the server certificate and key in the VM's vault.

### F6 (MEDIUM, cost) The A$27.74 a month is the idle price; real print and scan traffic changes the answer
- MEASURED 18:21:29 (retail API, AUD, australiaeast, `relay_prices.json`): Hybrid Connections Listener Unit A$0.019/h; Data Transfer A$0 to 5 GB then **A$1.4212/GB**. The designer's meters and arithmetic are right: 0.019 × 730 × 2 = 27.74; VPN 217.83 + 15.55 + 5.18 = 238.56; lab total 105.18; 66.71 with the VM off outside 217 h. The A$50 card threshold is correctly applied (every variant is over it).
- What is missing: every scan upload, print job and Print-URI fetch crosses Relay (B2165:62-65). Break-even against the A$239 VPN is about **153 GB a month** ((238.56 − 27.74) / 1.4212 + 5). ESTIMATE: a 500-printer site at 100 pages a day per printer and 0.5 MB a page is about 550 GB a month, about **A$775 a month** in Relay data, three times the VPN. A 20-printer office is about 22 GB, about A$24. So the connector is the cheap choice for small and medium sites and the expensive one for large sites. Whether the 5 GB allowance is per namespace or per subscription: UNMEASURED.
- "Two connectors per site give availability" (B2165:82) costs a third listener: Microsoft, "Adding listeners to an open relay results in additional relay hours" (https://learn.microsoft.com/en-us/azure/azure-relay/relay-faq, opened 18:20). A$41.61, not A$27.74.
- Limits (same page, MEASURED): 25 concurrent listeners per hybrid connection; **5,000 concurrent relay connections per namespace**. One namespace per client with many sites can hit 5,000 at the morning sign-in peak; the template should make a namespace per site or the design should size it. Relay SLA and throughput: UNMEASURED (no figure on any page opened).
- **Change:** put the per-GB line and the break-even on Kam's card; state "VPN or the client's existing Azure link for large sites".

### F7 (MEDIUM, seamless) "Three ordinary things" understates the client's work, and the Windows form matters more than Q19 allows
- Today's Workpath customer does **no** on-site network or server work: apps on the printer, all traffic outbound, one Marketplace offer (B2163 section 3). Against that baseline the connector is a new always-on host per site that the client must run, patch and monitor. It is still far less than a VPN (firewall change control, address-plan clashes), so the direction is right; the wording at B2165:11 is too rosy.
- The outbound list is longer than "443 to `*.servicebus.windows.net`": the image registry for pulls and updates; the Log Analytics endpoint for the connector's own log (B2165:87); Entra sign-in if Entra auth is used; and if Arc is used, Microsoft's list of about a dozen endpoints including `login.microsoftonline.com`, `*.login.microsoft.com`, `management.azure.com`, `*.his.arc.azure.com`, `*.guestconfiguration.azure.com` (https://learn.microsoft.com/en-us/azure/azure-arc/servers/network-requirements, opened 18:22). Arc onboarding also needs someone with Azure rights on the client side. Microsoft does allow naming one namespace instead of the wildcard ("allowlist a specific namespace ... you'll also need to allowlist the gateways", Relay FAQ), which a security team will want.
- The Marketplace template installs only the Azure half. How the on-site connector gets its identity (a one-time enrolment code from the admin console, or Arc) is not designed. Without it the install is not seamless.
- Q19's default ("Windows service only if a client asks") runs against the reason q14 was ruled "both equally" (02:793: an appliance "for customers without container skills", and a Windows installer). The machine a print team already has on site is usually a Windows print server. **Change:** connector ships as container, appliance and Windows service on day one, or Q19 goes to Kam as a card, not a default.
- Internal DNS (`printsuite.<domain>` → connector) is the same work as the ruled design (02:795): no extra burden, correctly stated.

### F8 (MEDIUM, lab fidelity and K11b) The azbridge lab proves the path, not the product, and it is not "full mimic"
- K11b was ruled **c "Azure and VPN now"** with the note "full mimic of target environment now" (RELAYED). The design builds neither the VPN nor the product connector for the 23 Dec working copy; it runs `azbridge` and records "a deviation" (B2165:108). The designer does flag the VPN swap for confirmation (Q18): good. But it should say plainly to Kam that the lab would run a stand-in tool for a product part that does not exist yet (5 to 6 lock-days, after 23 Dec).
- What azbridge does mirror (MEASURED, https://github.com/Azure/azure-relay-bridge opened 18:20): TCP tunnels over the same Relay service, both directions, bytes "forwarded end-to-end", Entra or SAS auth, Docker and macOS supported. So it is a fair test of: does the M577 accept calls from the connector's address, do callbacks and the CA work through Relay, and what the delay is. Worth running.
- What it does not mirror: fixed forwarders per printer and port instead of an allow-list with a pushed target; no audit log; no CONNECT sidecar; no caller-address header. "Not covered by Azure product support" is correctly quoted (B2165:101). Latest release v0.16.1, 13 Nov 2025, last push the same day, not archived (GitHub API, 18:23:10): alive but slow-moving.
- Lab risks the design does not list: (1) the server runs in a container, and a loopback alias of the printer's address on the VM host is reached from a container only if azbridge binds beyond loopback (its "-g" option); UNMEASURED; (2) Docker on the Mac hides the printer's address from the forwarder and needs port 443 published on the Mac; (3) the default DNS trick (a public record pointing at a private address, B2165:47 and :104) is commonly dropped by home routers' DNS-rebinding protection; whether Kam's router does: UNMEASURED; it also is not "a name in the customer's DNS" (q22 a) and publishes an internal address; (4) both routes still depend on the untested printer-to-Mac path (owed 118).
- ".NET `HttpClient` supports a CONNECT proxy natively: no core change" (B2165:86): **UNMEASURED** against the built code. The local OXPd checkout is at the 20 Nov initial commit (`origin/main` 7e1a01c), so I could not read the device clients; the design itself says the certificate pin lives in four separate copies (02:613 item 1), each of which would need the proxy setting. General fact: the tunnel is used for `https://` targets only.

### F9 (MEDIUM, order of work) The decisive test can be run cheaper and sooner than the plan says
- S14b needs the printer to accept an OXPd 1.x call from an address that is not the server's, and to call back through a pass-through. That can be tested on the lab network alone with any TCP forwarder between two machines (or two addresses), no Azure, no Relay, no card: A$0, a couple of hours once the printer-to-Mac route (owed 118) works. Azure Relay then only has to prove delay and reliability. **Change:** run that first; it decides connector versus VPN before the spend card is even needed.

## Question 4, plainly: is a VPN or another pattern better?
- **For a client with no existing private link to Azure** (most small and medium offices, and every current Workpath customer): the connector is better. No firewall change, no address clashes, nothing opened inbound, and it costs a tenth as much at low volume.
- **For a client that already has a hub VPN or ExpressRoute into Azure**, or a large site (over roughly 150 GB a month of print and scan): the existing link or a VPN is better: nothing new to install on site, no new vendor software for their security team to vet, flat cost, and it is the transport the server already speaks. The design calls this a "supported alternative"; it should be an equal first-class option chosen at install.
- **Other patterns checked:** Azure Arc alone carries no application traffic (designer correct). App Service Hybrid Connections are one-way (designer correct). Microsoft's own printer product, Universal Print, uses an on-site outbound connector for printers that cannot reach the cloud: the closest Microsoft precedent, and a better citation than HP's fleet proxy (from my own knowledge of the product; not opened today, so UNMEASURED here).
- **Nothing found that beats the connector for Kam's three goals.** The honest caveat is that it makes Datasec the author and maintainer of a network tunnel, which is security-critical software with its own review, signing and patch duty.

## Five lines for Kam
1. The design is the right one: a small program in each office calls out to Azure and carries the printer traffic both ways, so the client opens nothing on their firewall. I agree with it, with changes.
2. Before we rely on it, one cheap test on your printer decides it: will the M577 take calls from the connector's address instead of the server's? We can run that on your own network for A$0 before spending anything in Azure.
3. Four security fixes are needed first: the office, not Azure, sets which printers the connector may touch; the Azure meeting point is locked to the office and the server; the certificate master key is kept out of Azure and away from the server; and logins use Microsoft identities instead of shared keys.
4. The cost is about A$28 a month per office when quiet, but grows with printing and scanning (about A$1.42 a GB); big sites, and clients who already have a private link to Azure, should use that link or a VPN instead. Both should be offered.
5. One thing only you can settle: on P-4 you tapped "a machine on each site" and wrote "this will be an azure deployment". We read that as server in Azure plus a small connector on site; please confirm, because the design record currently assumes it.
