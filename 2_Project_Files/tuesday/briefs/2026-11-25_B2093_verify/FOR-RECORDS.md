## Info for records (not this ticket's acceptance)
1. **First-present, not first-parseable.** A job whose `Job_Start_Time` is present but not a date (`garbage`) while `Job_Start_Time_UTC` is a good stamp reads as undated (null); the same for `_jobDate`. No store fills the bare field, so this needs a producer that does.
2. **Shapes the helper takes as dated** (probe, gate): the text `0` and `1` read as the years 2000 and 2001 (V8's lenient parser, as B2075 found for RD-975); `true` reads as 1 ms after the epoch; an array holding one ISO text reads as that date; a number is read as milliseconds (an epoch in seconds reads as January 1970); the number `0` is undated.
3. **Shapes that still fail the run:** a BigInt, a Symbol, an object with no prototype or a throwing `toString` as a start field makes `new Date(raw)` throw, and the insights function returns its "Failed to generate insights" answer, as at BASE. None can come out of JSON or SQLite text.
4. **The Log Analytics parsers fill `Job_Start_Time_UTC` from `TimeGenerated` (the ingestion time) when a row has no start time** (`getDateTime('jobStartTime') || row.TimeGenerated` and its siblings in `backend/azureLogAnalytics.js`), so a Log Analytics row is rarely undated here; RD-306's rule says "undated stays undated" for `created_at` only.
5. The hour is the server's local hour. In a UTC container an Australian site's off-hours are judged in UTC. Pre-existing for `Job_Start_Time`; not changed.
