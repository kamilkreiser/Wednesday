1. **A refresher can be called after its refresh has already timed out (a side effect of D20, MEASURED by S15).** The refresher's call now waits in the thread pool's queue. If the bound passes before a pool thread picks the call up, the refresher still runs later. When it runs, its cancellation token is already cancelled and the renewal state it receives is all zeros, because the broker's `finally` (`TokenBroker.cs`, the `ZeroMemory(renewal)` after the await) has already cleared the array the lambda captured. The callers are unaffected: they get `RefreshTimedOut`, the late answer is disposed, nothing is stored and no `NewToken` is raised. For this to happen in production, the pool would have to be starved for the whole `RefreshTimeout` (30 s by default). Suggested README `## Limits` addition next to the D20 line: "a refresher may be called after its refresh has timed out, with its token already cancelled and its renewal state cleared". A refresher should check its token before it uses the renewal state. Whether WP1.4's refresher does that is UNMEASURED.
