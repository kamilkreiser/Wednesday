RD407 DIAGNOSIS: CAUSE FOUND — since the reboot, OS sleeps on this Mac overshoot about 2x. The product's 510 ms retry schedule now takes about 1 s of real time and outlives the test's 910 ms fake "missing" window. This is a test/environment timing issue, not a product defect; the gate never opened.

Diagnostician: Tuesday's read-only seat, 2026-11-11, about 08:50 to 09:20 AEDT. Main `1c6bd644`, tree `5774a71e`.

## BLUF

- **Cause.** The test fakes "settings.json is missing" for a wall-clock window: `missingName(file, { forMs: PAST_BUDGET_MS })`. That is 910 ms, measured with `Date.now()` from the first failed read (test lines 41-42 and 119-129).
  - The product's retry loop (`_readRawWithEvidence`, jsonStorage.js about line 2991) sleeps through a **nominal** schedule of `[2,4,8,16,32,64,128,256]` ms using `Atomics.wait`. Those add up to 510 ms, and `waitedMs` adds up the requested delays, not the time that actually passed.
  - On this machine since the 05:41 reboot, each sleep overshoots badly, so the eight retries take about 850 to 1,100 ms of real time.
  - The fake window therefore ends while the product is still retrying. The last retry reads the real, intact settings file, and the product does what a store that "came back" should get:
    - M2: the write resolves.
    - R1 and R3: `answer: true`, `gate: require-session`.
  - The test expected "still missing after the budget": `STORE_UNREADABLE` and `deny-unknown`.
- **Product defect?** No defect in auth behaviour. Every failing cell failed toward **fail-closed / the real data**. R1 and R3 received `require-session`, which means authentication is enforced; none received `allow-open-mode`. M2 resolved only because the real store, with every protected key, was read back before the write. Nothing in the failing runs could make the gate open in production.
- **Production side note (availability, not auth).** The product calls its budget "510 ms", but it is really "eight sleeps". On a host whose timers overshoot, one confirmed-missing read blocks the event loop for about 1 s instead of 510 ms. The 1 s `CONFIRMED_MISSING_TTL_MS` cache bounds how often that happens. The fail-closed outcome for a store that stays missing does not change; the wait is only longer.
- **Why hosted CI and the pre-reboot runs pass.** Their sleeps are close to nominal. Pre-reboot here, M2 took 615 ms and R1 683 ms (`jest-u-header.json`, `jest-p-header.json`); that is about 510 ms plus setup, well inside 910 ms. Why this Mac's timers overshoot since the reboot is not proven (see Ruled out). It is OS-level: Python's `time.sleep` overshoots the same way.

## Ruled out, and how

- **Persisted stamp, temp dir or state surviving the reboot.**
  - Every cell builds a new `fs.mkdtempSync(os.tmpdir()/nexusai-rd407r2-*)` and deletes it in `afterAll`.
  - R1 asserts `sentinelPreexisting: false`, and the received precondition was `{ sentinelPreexisting: false, unpatched: true }`, so the precondition held.
  - The `roles-census-*/.auth-enforcement-stamp.json` log line belongs to another suite's fixture; this suite only uses its own temp dirs.
- **Uptime, boot time, process start time, timezone, date.** I grepped the code for any dependence. `authEnforcement.js` has none: its only clock use is `Date.now` as a 5 s cache TTL default. The jsonStorage retry path uses `Date.now` only for the 1 s confirmed-missing TTL. Dates in the fixture are fixed strings.
- **Branch contamination, or a change on main.** The failure reproduces on main's own tree in a fresh clone, and disappears there when only sleep accuracy changes.
- **Load from concurrent jest runs or the cwd/`--rootDir` difference.** My runs were alone under the lock at load about 2.9, with explicit `--config` and `--rootDir`. The defaults failed and the controls passed under identical conditions.
- **Node or runtime change at reboot.** The node binary is dated Nov 9 (v26.13.0), the same as before. Python shows the same overshoot.
- **DNS, network, Spotlight or disk I/O on the external drive.** The test injects ENOENT in memory and the files sit under `os.tmpdir()`. The busy-wait control removes only the sleep, not the I/O, and the cells pass. So I/O is not what crosses the threshold.
- **Not proven: why the OS overshoots since the reboot.**
  - Measured at 08:5x:
    - `kern.timer.coalescing_enabled: 1`.
    - `pmset`: on AC power, `lowpowermode 0`, no thermal warning.
    - Heavy post-boot background work: `mediaanalysisd` about 99% CPU, `DesktopServicesHelper` about 85%.
  - Running node under `taskpolicy -l 0 -t 0` (this process only) did not remove the overshoot.
  - Candidates are post-boot indexing / media analysis and the kernel's timer coalescing for this process tree's QoS class. I did not change any machine setting to test this, by instruction.

## Recommended fix (ticket)

**Test change (primary).** The past-budget cells M2, R1 and R3 should not depend on how long the product's sleeps take. Two options:
- Inject "missing for the whole call": use `forMs: Infinity` or `observations: Infinity`, then `restore()` after the call returns. This is the "store that really went missing" case the header describes.
- Or inject a count larger than one plus the schedule length plus any evidence reads.

The deliberate "comes back within the budget" cases (M1, R2, R4) already use counted observations and are not affected. The test's own M3/M4 rule ("Counted, not timed — a stall on a loaded machine is not a retry") should apply to the past-budget cells too.

**Product change (optional hardening, not a security fix).** Make the budget honest in wall time. Run the retry loop against a monotonic deadline (`process.hrtime`/`performance.now`, about 510 ms), and report `waitedMs` as time actually waited, not the sum of requested delays. On hosts whose timers overshoot, that caps the synchronous event-loop stall near the documented 510 ms. Keep it fail-closed: the deadline only decides when to stop retrying, and the outcome after the deadline stays `STORE_UNREADABLE` / `deny-unknown`.

**Interim.** Reds on this Mac limited to rd407-r2 {M2, R1, R3}, with real durations above about 910 ms, are environmental (sleep overshoot). ANSWER-2's main-tree comparison is a valid way to classify them. Hosted CI remains the deciding check.
