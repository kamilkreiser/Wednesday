# B1955 DIAGNOSIS -- OXPd Contracts cell C7 red on hosted Windows at the A2-F2 head

**Verdict: TIMING-FLAKY ON HOSTED WINDOWS** -- independent of A2-F2. Qualification: the defect is NOT the 5 s bound. It is an ordering race in the cell. The client treats the SignalR handshake answer `{}` as "connected", but ASP.NET Core writes that answer *before* it adds the connection to the hub lifetime manager. A `Clients.All` send that lands in the gap is never delivered to that connection, so no wait length will make it arrive. The race is inferred from the framework source and the run evidence. It has NOT been reproduced (see TESTED).

Scratch (all evidence): `/Volumes/Datasec_DEV/TUESDAY/2_Project_Files/fleet/state/s314/c7diag/`

## FOUND

1. **What "arrived within 5 s" waits on.** `HubTestClient.ReadInvocationAsync(5 s)` (`GatewayStub.cs:149-177`) reads WebSocket records until it gets a type-1 invocation frame, or returns null when a 5 s linked CTS fires. It is a receive wait on a socket that is already open and handshaken. It is not a start, not a poll, and not a retry. `AssertInvocation` turns the null into "no hub message arrived within 5 s" (`GatewayStubTests.cs:114`).
2. **The race (from source).** The test connects `first` and then `second` (`GatewayStubTests.cs:74-75`). Each `ConnectAsync` returns once the handshake answer `{}` is read (`GatewayStub.cs:134-142`). Then the test POSTs `/api/send` (`:78`), which calls `hub.Clients.All.SendCoreAsync` (`GatewayStub.cs:97`). In ASP.NET Core release/10.0 (copies in `c7diag/aspnetcore_src/`):
   - `HubConnectionContext.cs:643`: `await WriteHandshakeResponseAsync(HandshakeResponseMessage.Empty); return true;`. This happens inside `HandshakeAsync`.
   - `HubConnectionHandler.cs:140-150`: only after `HandshakeAsync` returns does it run `await _lifetimeManager.OnConnectedAsync(connectionContext);`.
   - `DefaultHubLifetimeManager.cs:292-294`: `OnConnectedAsync` is `_connections.Add(connection)`. `SendToAllConnections` (`:99-`) enumerates `_connections` at send time. A connection that is not yet added gets nothing, and nothing is buffered for it later.
   So the client can see `{}`, POST `/api/send`, and have the send enumerate `_connections` before the server continuation after the handshake flush has run `Add`. `second` has the narrowest window: only one loopback HTTP POST sits between its handshake and the send. `first` is covered by `second`'s whole connect.
3. **The failing job fits a lost message, not a slow one.** Job 137299375943 ran on image `windows-2025-vs2026`. C7 took `5s 649ms` in total, which is about 0.65 s of setup plus the full 5.0 s window with zero frames. The stack shows line 86 (the first send's read loop). The trace cannot say whether the client was `first` or `second`. The Contracts process started at 17:57:52.8 while UniversalPrint, Core and Jobs test processes ran alongside it: `dotnet test` runs the 14 assemblies in parallel on a 4-vCPU hosted runner. That kind of threadpool contention widens a continuation gap. A frame over loopback that is merely slow would take milliseconds, not more than 5 s.

## Minimal fix shape (follow-up lane, Contracts test paths only)

Make the cell wait for the server's own registration before the first send. Do NOT just lengthen the 5 s timeout: the evidence says a missed send never arrives, so a longer wait only makes the red slower.

- `GatewayStub.cs:18-20`: give `PrinterHub` an `OnConnectedAsync` override. It increments a connected counter held in a singleton that the stub registers (`GatewayStub.cs:51`, next to `AddSignalR()`), and completes a waiter when the counter reaches the target. The hub's `OnConnectedAsync` runs inside `RunHubAsync` -> `_dispatcher.OnConnectedAsync` (`HubConnectionHandler.cs:150/168`), which is strictly after `_lifetimeManager.OnConnectedAsync` added the connection (`:149`). So its signal proves the connection is in `_connections`.
- Expose `GatewayStub.WaitForConnectionsAsync(int count, CancellationToken)`, bounded by the test's guard.
- `GatewayStubTests.cs`: insert `await stub.WaitForConnectionsAsync(2, guard.Token);` between lines 75 and 77, before the first send. The closing send (`:101`) is then safe as well.
- Update the `HubTestClient` doc (`GatewayStub.cs:109-111`) so it says that a handshake answer does not mean the connection is registered.

**A test that proves it (negative and positive control).** Add a test-only `HubLifetimeManager<PrinterHub>` decorator over `DefaultHubLifetimeManager` that delays `OnConnectedAsync` by about 500 ms. Register it as an option on the stub, for example `StartAsync(delayRegistration: TimeSpan)`.
- Negative control: the current cell body (no wait) against the delayed stub must fail deterministically with "no hub message arrived within 5 s". This proves the race exists.
- Positive control: the fixed body against the same delayed stub must pass.
- Then run C7 in a loop (for example 50 times) on the hosted Windows leg, through a workflow_dispatch or the lane's own push, to measure it under real runner load.
