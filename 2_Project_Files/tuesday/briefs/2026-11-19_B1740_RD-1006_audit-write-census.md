## 4. The storage side
- Ring: in memory, `AUDIT_BUFFER_MAX = 10000` entries (server.js:301), oldest dropped at 322-325. No limit on one entry, none on the whole. The loader at 348 re-reads at most the last 10000 entries from disk and caps nothing per entry.
- File: `audit-buffer.json` in the data directory; the whole ring is serialised at 389 (`JSON.stringify(_auditBuffer)`) and written to a temporary file then renamed (390-395, mode 0600); flushed every 60 s and at shutdown (22738-22741). No size limit, no rotation: the file is rewritten whole, so its size equals the size of the ring. The ring is also resident memory.
- Durable log copy: the same entry object is also written by `logger.info('[AUDIT] ...', auditEntry)` at server.js:317, so a long value is written to the log twice. `backend/logger.js:169-179`: error.log and combined.log are winston File transports with `maxsize: 5242880` (5 MB) and `maxFiles: 5`, so the log files are rotated; whether one record larger than 5 MB is cut was not tested. The console transport (logger.js:165) is not capped in the frame; where container output goes is outside it.
- Erasure audit file `erasure-audit.jsonl` (dataErasure.js:37, append at 715): append-only, no cap or rotation found in the frame (the only references to AUDIT_FILE are 37, 416, 715, 1650).
- Scheduler audit (backend/services/schedulerAudit.js): a separate file with rotation at 5 MB or a day change and a 30-day prune (lines 23-24, 66-80): this store does cap itself.
- What bounds an entry today: the global JSON body limit 50mb (server.js:1454-1455), the chat limit (server.js:1440, CHAT_BODY_LIMIT), the SCIM limit 5mb (22374). The request-line and header limit is not set anywhere in the frame (no `max-http-header-size`, `maxHeaderSize` in package.json, Dockerfile, server.js; nginx.conf holds no `large_client_header_buffers`); the base image is `node:24-alpine` (Dockerfile:2) and its default is the runtime's, not measured here. Arithmetic, not a measurement: ring of 10000 times a 50 MB entry is a nominal ceiling of 500 GB; real entries were not measured.

## 8. Design note: options, not decisions
The three shapes, and what each would touch:
1. One shared cap in the writer (`auditLog`, server.js:305-327): clamps every text leaf or the serialised entry before the push at 321 and before the log call at 317. Covers all 55 ring sites, the path, the userAgent and the whole-entry cap in one place; not the 4 erasure-file sites (separate writer, dataErasure.js:713). It is the earlier option (a) of the RD-806 question; the 2026-11-16 ruling chose per-kind field checks (b) instead. Needs the product owner's word on how an over-long value is shown (cut with a marker, or something else): the open question above.
2. Per-field caps at the sites: about 25 sites with an unbounded detail field plus the entry-level fields. The sites that cannot refuse (identity provider claims, SCIM, stored text, the request path, error text) need a cut, not a refusal, so this shape needs a shared cut helper anyway. It changes the RD-994 C3 cell (the 42 direct calls are counted by text) if any call is added or moved, and each new rule wants an over-long cell and a wrong-type cell.
3. A cap at the store: at the flush (server.js:373-401) and the loader (348) and, for the erasure file, at the append (dataErasure.js:715). It bounds the file but not the in-memory ring or the log copy, unless the push is also capped.
Tests that pin a long value inside an audit row, by program (counted by text, not by running): jest `__tests__` (440 files): 27 mention the audit buffer, the export, REQUEST_DENIED or STATE_MUTATION; 8 of those use `.repeat(`; only `rd994-audit-field-guard.test.js` pins a long value against an audit row, and its cells pin that the row does NOT hold the value (they would not change under a cap above the guard's limits). The other 7 use long text for log-line truncation (rd798, rd799, rd800, rd926), token constants (scim-security-controls, entra-provisioning-setup, rd388) and none asserts a long value stored in a row, from the repeat lines read; not every line of the 27 files was read. Other programs: `tests/` (Playwright end-to-end and the UAT runner), `testing/` and the one Python file: 0 files mention the audit buffer or export. Likely touched by option 1: none found; by option 2: rd994 cell C3 and any cell reading a changed row's shape (rd932, rd990, rd966, rd497 read exported rows; their values are short).
NOT known: the real size distribution of entries; whether anything reads `details` back and needs the full value (the export writes details as JSON in one CSV column, server.js:2144-2155); the runtime header limit; what the identity provider caps on its own claims; who consumes the erasure audit file; how option 1 interacts with the 8 KB figure of the earlier question.
