## Findings
- **F1 (Minor; text false as written).** D15 and the Data README say "`SaveChanges` refuses an audit entry that is modified or removed and saves nothing". Code that holds the context can change entries after the guard, by the context's `SavingChanges` event or by a `SaveChangesInterceptor` in its options. P22 measured both: no exception, all 3 rows' actor id changed.
  - **Why Minor and not Major:** like `ExecuteUpdate`, this needs code that holds the context and deliberately uses EF's own API, and the library itself never does it. But the README's list of limits is incomplete, and the sentence about `SaveChanges` is false in this case.
  - **Fix:** name the limit ("any code holding the context: `ExecuteUpdate`, `ExecuteDelete`, raw SQL, a `SavingChanges` handler or a save interceptor"), or close it. One way to close it is to refuse in a `ChangeTracker.StateChanged` handler, which runs again inside `base.SaveChanges`'s change detection. If Tuesday reads "through the library" as any use of `SuiteDbContext`, this is the one item that would be a Major.
- **F2 (Minor).** A stored device firmware or model outside the seat's own text rule is read as a value, 0 of 6 failed closed (P43). The rows were: a control character, a leading space, 129 characters, empty, a non-ASCII model, and a trailing space. Snapshot and match firmware IS checked on read.
  - **The cost:** the read `Device` holds a value that passed no rule, against THE CONTRACT's first sentence. And `UpdateAsync` of that same `Device` is then refused, so the row cannot be changed through the library without changing the text.
  - **Fix:** `DeviceText.Check` on both fields inside `DeviceMapping.ToDevice`, plus a C24 row for each.
- **F3 (Minor; for B1870's C12 and the host's later wiring).** `AddSuiteData` puts the registry and the audit log on ONE scoped context. When `AddAsync` loses a race, the other writer inserts the key between `AnyAsync` and the save (simulated with an interceptor, P23). The add then throws an untyped `DbUpdateException` holding a `SqliteException`, not `SuiteDataException DuplicateDevice`. The failed entity stays tracked, so the next `AppendAsync` on the same context fails too, and the audit row of that failure is never written (audit rows 0).
  - **Fix:** map `DbUpdateException` on the key to `DuplicateDevice` and clear the tracker, as `SaveOrStale` does for a stale update. Or document that the audit log needs its own context.
- **F4 (Minor; records).** The reported offset is `(long)Math.Truncate(TimeSpan.TotalSeconds)` over a double. Two effects:
  - Above 2^30 seconds (about 34 years: the kit's own 1970 device-clock case), an offset of n s + 0.9999999 is reported as n + 1. That happened in 2,058 of 200,000 random checks (P11) and at both `MinValue`/`MaxValue` extremes (P12). It is never more than 1, and never makes `within` wrong.
  - At the edge, `outside` is reported with a whole-second offset equal to the tolerance, for example `outside 300` at 300 s + 1 tick, or `outside 0` at tolerance 0: 12 of 12 such edge cases in P10. The outcome is right, but a reader of the stored row sees `outside, 300` beside a 300-second tolerance.
  - **Fix:** `difference.Ticks / TimeSpan.TicksPerSecond`, and one README line: "the outcome is decided on the exact difference; the offset is truncated toward zero".
- **Record (no finding).** The clock check reads the server's time BEFORE it awaits the source. A slow source therefore adds its own latency to the device offset, and no time bound exists on a source that never answers. The kit asks for neither; this is a limit for the onboarding wiring (WP1.11).
