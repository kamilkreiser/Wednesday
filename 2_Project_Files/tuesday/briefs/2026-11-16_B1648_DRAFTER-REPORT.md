## TICKET TEXT FOR THE NEXUSAI RECORDS PASS (F1; exact; project RD; type Bug; the records seat files it and returns the key to Tuesday for the stamp)
**Summary:** Sign-in can be passed as a viewer with a session cookie that names a built-in object property (constructor, __proto__, toString and nine more) while sign-in is enforced and no user is stored; with a stored user the same cookie answers 500

**Description:**
BLUF: getSession in backend/jsonStorage.js looks the cookie value up in the stored sessions object with a plain property read, so a cookie whose value is the name of a property every object inherits (constructor, __proto__, toString, valueOf, hasOwnProperty and the other names of Object.prototype) finds that inherited value and is treated as a session that never expires. With sign-in enforced and no authorized user stored yet, requireAuth then lets the request through as role viewer; with any stored user the request fails with 500 AUTH_ERROR. It is on main today and was not introduced by the storage-family slice (RD-769's fix there removed only the part that wrote onto built-in objects).

Measurement (local servers only, no hosted instance read):
- Independent security review, 2026-11-16, over HTTP on a local server at main dcac002d and at the storage-family head 0dc6a0d3 (identical): sign-in enforced, no stored user, cookie session_token=__proto__, constructor or toString: 200 on GET /api/auth/check (authenticated true, user null), /api/printers, /api/stats and POST /api/chat; 403 on the admin GET /api/auth/users; prototype and an unknown token 401. With one stored user: 500 AUTH_ERROR on every route.
- In-process at both commits: all 12 names of Object.getOwnPropertyNames(Object.prototype) give a truthy getSession result (viewer with no stored user, a TypeError and so 500 with one). A JSON cookie reaches it too: cookie-parser turns the value j:["constructor"] into an array, and an array key reads the inherited value.

Cause: getSession (backend/jsonStorage.js, the lookup const session = sessions[sessionId]) reads an inherited value; its expiresAt is undefined and new Date(undefined) < new Date() is false, so it is never expired; requireAuth (backend/server.js) then calls getAuthorizedUser(undefined): an empty user list returns undefined and the role defaults to viewer; a stored user makes email.toLowerCase() throw.

Reachable: the enforce route lets an installer turn sign-in on before any user exists, and the first Entra sign-in adds the first user, so every deployment passes through "enforced, no stored user"; the same holds if the authorized-users file reads empty. In that window an unauthenticated client with the cookie session_token=constructor reads viewer data and can use the chat. Whether any hosted instance is in that state is NOT measured here.

Fix shape: getSession returns a session only when the cookie is a string naming an OWN entry of the stored sessions object, and that entry is an object with a string email and an expiresAt that parses to a time; anything else is no session (null), which every caller already answers as signed out (401 SESSION_EXPIRED for an API, a redirect to /login for a page). No change to how a real session is read, expires or is stored; no change to server.js, to any route gate or to any user-facing text. Not a list of reserved names (the engine's list), not a copy of the store per request.
