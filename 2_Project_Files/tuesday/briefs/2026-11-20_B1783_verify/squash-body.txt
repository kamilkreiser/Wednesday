One workflow with four jobs. linux and windows restore in locked mode, build, test and publish the
server host and run the release guard over the published folder; the linux job also builds the
container image and pushes it nowhere. secret-scan runs a pinned, checksum-verified scanner over the
history and the working tree after a planted control, then over every object the checkout holds
(files, commits with their header lines and messages, annotated tags, folder listings with their
names), each copied twice under a neutral name, once behind one plain first line and once behind a
plain block of 43008 bytes. A planted repository that holds a token in 11 places must be found 25
times first, and the job fails when the checkout holds an ignore file of the scanner. rules runs the
53 planted controls with a floor of 53, then the repository rules. A test holds the secret-scan job
and the rules job to their reviewed text by a fingerprint. The runtime list of both packagings is
declared once, in Directory.Build.props.

The second scan does not see: text saved as UTF-16 or UTF-32, compressed content, a secret split
over two lines, the names of branches and tags, an object that only another kind of ref on the
origin reaches (a git note, for example), and a secret across a read cut in a large file that has
blank lines but none within 25 kB of that cut. A rule of the scanner that is keyed on a file name
fires in the scan by name only. No repository setting requires any of the four checks.

Not in this change, and still open on WP0.3: the bundle tool in the pipeline and a test bundle; the
fingerprint of the real development CA (the deny-list holds comment lines only, and the guard warns
and passes on an empty list); code scanning results. Nothing is deployed or released.
