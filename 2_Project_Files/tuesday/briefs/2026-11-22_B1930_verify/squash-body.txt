EfDeviceRegistry.AddAsync now catches the DbUpdateException of its save,
clears the context's tracker and reads the key again: a key now held is
refused DuplicateDevice (another writer won the race between the check
and the save); otherwise EF Core's own exception is rethrown. Either way
the failed row no longer stays tracked, so the next audit append on the
same context is written. Clearing the tracker also drops any other
unsaved change the caller had on that context, as after a stale update.

SuiteDbContext watches ChangeTracker.StateChanged and Tracked. While a
save runs, an audit entry that becomes modified or removed, or starts to
be tracked so, ends the save with AuditEntryChanged; before the commit
nothing is written, so a SavingChanges handler or a save interceptor can
no longer change or remove a saved entry. Still open: an entry being
added (named and asserted in the README), ExecuteUpdate, ExecuteDelete,
raw SQL, a command interceptor, a handler that runs a nested SaveChanges
first, and a SavedChanges handler, which runs after the commit.
