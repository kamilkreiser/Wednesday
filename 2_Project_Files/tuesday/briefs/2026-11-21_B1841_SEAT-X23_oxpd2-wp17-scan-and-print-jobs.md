## THE DECISIONS INSIDE THIS LANE (each Tuesday's default as coordinator; each a Question at the stamp; each a behaviour with a cell)
- **D1 THE SPOOL KEY LIVES IN MEMORY ONLY** (Q1, STOP-CLASS: Stamp S4 states the answer in words). At `CreateJob` the spool draws a 32-byte key from `RandomNumberGenerator` for that job; it is held only in the process's memory, never written to disk, the secret store or any text, and cleared with `CryptographicOperations.ZeroMemory` at the job's wipe and at `JobSpool.Dispose`. A crash leaves ciphertext whose key no longer exists anywhere; D7 removes it at the next start. Why the default departs from the plan's "(key from C15)": no job survives a restart (D7), so a stored key buys nothing but a key on disk, a store write and delete per job, and a dependency on `ISecretStore.ListNames()`, which throws on one unreadable record of any name in its partition (RELAYED: seat X18's measurement, `<project>/1_Project_Definition/Briefs/2026-11-21_B1831_STATUS.md`, section THE STOP AT 16:53). **Alternative A (the plan's words):** the per-job key put through `ISecretStore` under `spool/<job id>` and deleted at the wipe (then T1A, not T1; the library references `Datasec.Suite.Secrets`; cost: as above, and the store's partition is the host's to choose). **Alternative B:** ASP.NET Core Data Protection (`IDataProtector`) as the platform's key (cost: keys the host must configure; a key ring on disk). Cell K01.
- **D2 THE FILE FORMAT** (Q2). A spool file = a 5-byte header (`DSJS` in ASCII and a format byte `1`) and chunks; each chunk = AES-256-GCM (`System.Security.Cryptography.AesGcm`, 16-byte tag) over at most `ChunkBytes` (default 65536) plaintext bytes; nonce (12 bytes) = the file number (4 bytes, big-endian) then the chunk number (8 bytes, big-endian), unique under one job's key because file numbers are unique in a job; associated data = format byte, the 16 job-id bytes, file number, chunk number, and a final-chunk flag byte (1 on the last chunk, 0 otherwise); a file always ends with exactly one final chunk (an empty file is one final chunk of 0 bytes). A reader verifies every chunk before it releases one byte of it, and refuses (`SpoolCorrupt`): a bad tag, a missing final chunk (truncation), bytes after the final chunk, a chunk out of place (reorder, swap), a file of another job or another file number copied in (other key or other associated data), a header other than the one above. Cells S01 to S05. Alternative: AES-CBC plus HMAC (cost: two primitives, own construction). `AesGcm` on macOS is UNMEASURED by the drafter (the secret store's key-file encryptor uses it: `KeyFileXmlEncryptor.cs`, 2 hits, DERIVED that it runs where those tests ran); a `PlatformNotSupportedException` at your first red run is `STOPPED: NEEDS TUESDAY`.
- **D3 LAYOUT AND NAMES** (Q3). The host gives the root folder (`JobSpoolOptions.Root`). A job is the folder `<root>/<32 lower-case hex of 16 random bytes>`; its files `000001.part`, `000002.part`, ... in the order they are written. **No name, path or extension comes from input**: a part's declared file name is discarded (never stored, never printed); a part's declared content type is kept in memory only if it is an ASCII `type/subtype` token of at most 127 characters, else null. On Unix the root and each job folder are made `0700` and each file `0600` as `OwnerOnly.cs` of the secret store does (the pattern re-expressed, never a reference to that `internal` class); on Windows the root's access lists are the installer's (the same limit the secret store's README states). Options are validated: each positive, file cap at most job cap at most spool cap. Cells C01 to C06.
