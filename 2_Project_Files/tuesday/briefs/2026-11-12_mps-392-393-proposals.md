## 1. Deploy ends "not proven" with no line of its own

**Today.** When the deploy call does not report the site as started, the script prints one line to the error stream, then goes on printing success-looking lines ("deployed ... Checking the live wwwroot", "holds exactly the verified package", "HSTS on ..."), and then ends with exit 3 without saying anything. The line it printed earlier reads:

"deploy-from-ci: NOT PROVEN: the deploy call did not report RuntimeSuccessful with at least 1 instance up (status: X, instances up: N). Do not report this deploy as done."

**Proposed.** A last line, printed just before the run ends:

"deploy-from-ci: NOT PROVEN: the site did not report that it started, even though the files match, so this deploy is not finished; do not report it as done, and check that the site is running before you deploy again."

**Alternative.** "deploy-from-ci: NOT PROVEN (see the earlier NOT PROVEN line): the files are on the site, but it did not report that it started. Do not report this deploy as done."

**Why.** The operator reads the last lines first; today the last lines look like success, and the warning is far above them.

## 2. Stop message when the hosted overlay changed

**Today.** If the hosted overlay changed after the first check, two things print, one after the other:

"deploy-from-ci: the hosted overlay changed after PRE-1 passed, so nothing was deployed; the new overlay copy is kept: <path>"

"deploy-from-ci: STOP: PRE-1 did not pass (above); nothing was deployed"

So the operator reads that the check passed, then that it did not. The same last line is also used when the second read of the overlay fails, and that failure message is itself labelled "PRE-1: the hosted overlay read answered HTTP <code>, so the overlay cannot be checked".

**Proposed.** Replace the last (STOP) line, which covers both the "changed" case and the "second read failed" case:

"STOP: the hosted overlay could not be confirmed unchanged just before the deploy (the line above says why); nothing was put on the site. Look at the kept copy named above, then run the deploy again."

**Alternative.** Two separate stop lines, one per case. Changed: "STOP: the hosted overlay changed after the first check; nothing was put on the site. Read the kept copy named above, then run the deploy again." Could not be read: "STOP: the hosted overlay could not be read a second time; nothing was put on the site. Run the deploy again."

**Why.** It no longer says "did not pass" about a check that passed, and it says what to do next. The alternative is clearer but needs the script to tell the two cases apart (a small extra code change).

## 3. What a seed dry run says about the output folder

**Today.** The help text says a dry run "checks everything a real run checks" and that the output folder is "not touched". A real run with an output folder outside the repository refuses ("seed: REFUSED: the output directory is outside the work tree; refused", rc 2); the dry run does not look at the folder and ends rc 0. The dry run ends with:

"seed: dry run: N would be created, M would be skipped, F failed. Nothing was created."

**Proposed.** Say plainly what a dry run does not check (words only, no behaviour change). The dry run's last line becomes:

"seed: dry run: N would be created, M would be skipped, F failed. Nothing was created. The output folder was not checked; a real run refuses it if it is outside this repository's .local folder."

and the help text and the opening note change from "checks everything a real run checks" to "checks everything except the output folder".

**Alternative.** Keep the last line as it is today, and add only: "The output folder (--out-dir) is not checked in a dry run." Help text changes the same way.

**Why.** An operator who sees "dry run OK" and then a refusal on the real run was told something untrue; the words should match what happens.

## 5. Width edges measured without a classic scrollbar

**Today.** The widths where the tiles change layout (698, 918, 1138 and 1357 px) were measured in a browser whose scrollbar floats over the page. A browser with a normal scrollbar (most Windows browsers) loses about 15 to 17 px of width, so the edges sit that much later. Worked out, not measured: six tiles would show 5 + 1 between about 1358 and 1375 px; the same arithmetic gives an Administrator 4 + 1 between about 1138 and 1155 px (the ticket names only the first range).

**Proposed.** First measure the edges in a browser with a classic scrollbar. Then move the two upper edges later by the measured amount (expected: 1357 to 1375 and 1137 to 1155). Result: with either kind of scrollbar, no width from 500 to 1500 px shows a lone tile for any role. The lower edges need no change (they only make tiles a few pixels narrower).

**Alternative.** Change nothing and accept the thin ranges on browsers with a classic scrollbar.

**Why.** It is cheap, and the people most likely to have a classic scrollbar are the Windows users. The cost: on a browser with a floating scrollbar, the 17 px just past the old edges shows three across where one row would have fit.
