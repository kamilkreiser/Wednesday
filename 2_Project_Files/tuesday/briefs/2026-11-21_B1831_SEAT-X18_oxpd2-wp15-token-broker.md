## THE DECISIONS INSIDE THIS LANE (each Tuesday's default as coordinator; each a Question at the stamp; each a behaviour with a cell)
- **D1 THE TOKEN IS OPAQUE** (Q1). A `TokenGrant` holds: the access-token bytes (non-empty), the renewal-state bytes (what the refresher needs to refresh: a refresh token, a cache entry or nothing; may be empty; the broker never knows which), the subject (a non-empty string the grant STATES), and the expiry instant (UTC) the grant STATES. The broker copies bytes and compares the stated subject; it never decodes any of the bytes. Cell O01: grants whose access token is random non-text bytes, 1 byte, or `MaxTokenPartBytes` bytes behave exactly like text ones. Cost: D9's weaker check (THE N-4 READING).
- **D2 THE SESSION KEY** (Q2). `SessionKey` = (device serial, `SessionPlatform` `Oxpd2` or `Oxpd1`, platform session id), each string 1 to 128 characters of printable ASCII without a space, compared ORDINALLY (a serial that differs only by case is another device here; folding case is the registry's, lane B). Anything else is `InvalidArgument` before any state changes. Cell B06.
- **D3 THE HANDLE (OXPd 1.x only)** (Q3). Made at sign-in of an `Oxpd1` session from `RandomNumberGenerator.GetBytes(32)` (256 bits: `02:636` asks at least 128), written as 43 characters of base64url without padding (`System.Buffers.Text.Base64Url`, MEASURED present in the reference pack). The broker keeps ONLY its SHA-256 (in memory and in the record), never the handle; a lookup hashes the presented string and requires the device serial presented beside it to equal the session's (single-device). An `Oxpd2` session has no handle (`02:366`). Every failed lookup (never issued, ended, altered, wrong device, wrong length or alphabet) is the same `SessionNotFound` with the same message. Cells B02, B03. Alternative: a 16-byte handle. Cost: none measurable.
- **D4 REFRESH BEFORE EXPIRY IS LAZY, AT A READ** (Q4). `GetToken` calls the refresher when the access token's remaining life is at most `RefreshMargin` (default 5 minutes) on EITHER clock of D7; otherwise it hands out the held token with no call. No loop. Alternative: Workpath's loop every 4 minutes (`A1:246`): needs a timer in the library (D7's alternative). Cells F01, F02.
- **D5 ON-DEMAND REFRESH AND WHAT A REFRESH MAY ANSWER** (Q5). `GetNewToken` always calls the refresher (an app module calls it after a 401). One refresh per session at a time: a second caller while one is in flight awaits the SAME call and gets the same result (single-flight). The call is bounded by `RefreshTimeout` (default 30 s, on the broker's `TimeProvider`, `Task.WaitAsync(TimeSpan, TimeProvider, CancellationToken)`, MEASURED present); at the bound the token handed to the refresher is cancelled and the caller gets `RefreshTimedOut`; a result that arrives later is disposed and never stored. A result is ACCEPTED only when: it is a grant (not null) with non-empty access bytes, each part at most `MaxTokenPartBytes`, an expiry later than now on both clocks, and a subject equal to the session's user (D9). Accepted: it replaces the held grant (the rotated renewal state is kept, `02:640`), the record is rewritten (D12), and `NewToken` is raised. A refresher that throws, times out, or answers anything else: the held grant stays as it was; `GetNewToken` throws the typed reason; `GetToken` hands out the held token if it is still valid on both clocks, else throws the typed reason; a refresher that answers ANOTHER subject ends the session (D9). Cells F03 to F10.
- **D6 `MaxTokenPartBytes` = 262144** (Q6): an access token or a renewal state longer than this is refused (`TokenTooLarge`) at sign-in and at refresh, so that the record of D12 always fits the secret store's value limit (`LocalSecretStore.MaxValueLength` = 1048576 bytes, MEASURED at `main`: `LocalSecretStore.cs:31`). How large Microsoft's tokens are is UNMEASURED.
- **D7 TIME: TWO CLOCKS, AND A STEP NEVER LENGTHENS A LIFE** (Q7; the lesson of the card decoders' review, where a time rule added at a stamp became a Blocker: RELAYED, `2026-11-20_B1806_verify/VERDICT.md` finding 1). The broker takes a `TimeProvider` (default `TimeProvider.System`). Every deadline is held on BOTH the wall clock (`GetUtcNow`) and the monotonic clock (`GetTimestamp`, `GetElapsedTime`), and a deadline has passed when EITHER clock says so: a wall clock set back cannot keep a session or a token alive, and a wall clock set forward ends them early (fail closed). An access token's monotonic deadline is its receipt timestamp plus (its stated expiry minus the wall clock at receipt). Across a restart only the wall clock exists: a restored record whose last-activity instant or write instant lies LATER than the wall clock at restore is dropped (the clock went back while the server was down). **No timer and no background thread in the library:** expiry is enforced at every call and by `Sweep()`, which the host will call (not wired in this lane). Cells E01 to E06, R05. Alternative: a timer from `TimeProvider.CreateTimer` (MEASURED present) inside the broker; cost: background work in a security library and tests that must drive timers.
- **D8 ONE LIVE SESSION PER DEVICE** (Q8): a sign-in on a device that holds a live session ends that session first (reason `NewSignIn`, `02:639` "a new sign-in on that device"), erasing its tokens from memory and its record from the store, then starts the new one. Cell B04 (E1.4).
- **D9 THE SUBJECT CHECK** (Q1, Q9). At sign-in the caller passes the session user (the identity the platform reports for this device session) beside the grant; the grant's stated subject must EQUAL it (ordinal, exact) or the sign-in is refused (`SubjectMismatch`, nothing kept, nothing written). Every path that hands out a token goes through ONE private method that compares the held grant's subject with the session user again before the bytes leave; a refresh answer of another subject, or a restored record whose subject differs, ends the session (reason `SubjectMismatch`; Workpath "wipes its tokens and signs the device out", `A1:245`). Cells U01 to U04. Alternative for the comparison: case-insensitive. Cost of the default: if the platform and Microsoft's library state the same user in different case, every read ends the session; which forms they state is UNMEASURED (Q9).
- **D10 INACTIVITY** (Q10). - **D12 THE RECORD AND ITS STORE** (Q12). The broker serialises a session to bytes it builds itself (`Utf8JsonWriter`, base64 of the token parts written straight from bytes, MEASURED present: `Utf8JsonWriter.WriteBase64String`; a format number first) and hands them to `ISessionRecordStore` (THIS lane's interface: `Save(id, bytes)`, `TryLoad(id, out bytes)`, `Delete(id)`, `ListIds()`). The broker reads and writes the store ONLY under its lock and only after it has checked that the session is still the current one (so a record is never written after its delete). Cells P01 to P03.
- **D13 WHEN THE RECORD IS WRITTEN AND ERASED** (Q13): written at sign-in, at every accepted refresh, and on activity at most once per `ActivityWriteInterval` (default 60 s; the persisted last-activity instant therefore lags by at most that, which can only end a restored session EARLY); erased at sign-out, at expiry, at a new sign-in on the device, at a subject mismatch, and at restore when not restored. Alternative: write on token change only (then the restart window and the idle check across a restart have no last-activity instant to stand on).
- **D14 NOTHING LEAKS IN TEXT** (Q14). `TokenGrant`, `AccessToken` (what `GetToken` returns: the access bytes and the stated expiry, never the renewal state, never the subject), `SessionHandle` and every event-argument type print a fixed mask from `ToString()`. Event arguments carry: the kind (`SignedIn`, `NewToken`, `SignedOut`), the sign-out reason, the session id, the device serial and the platform; no token, no handle, no subject. - **D15 STORE FAILURES** (Q15). A `SecretStoreException` or any failure of the record store is turned into `StoreFailed` (fixed message, no inner exception). At SIGN-IN a failed write refuses the sign-in: nothing is kept in memory. At an accepted REFRESH a failed write keeps the new grant in memory (the rotated renewal state may be the only one that still works), marks the record stale and retries it at the next activity and at `Sweep`; `GetNewToken` returns the token. At SIGN-OUT and every erase, a failed delete still ends the session in memory, keeps the record id on a retry list (retried at every later store call and at `Sweep`), and the call throws `StoreFailed`. **Named limit:** a record whose delete keeps failing and a restart inside the restart window brings that session back; it is bounded by D11 (10 minutes after its last activity).
