An approved or edited executive narrative can now be edited again. Each re-edit needs the
audit note and re-approves the narrative. The text and review it replaces are kept as the
next numbered row of a new append-only table, narrative_revision. Approve and Reject stay
for a new draft only; a rejected, failed or pending narrative is still not reviewable. The
same roles as a first review may re-edit (Admin, Consultant, the owning Partner); Demo and
other Partners are refused. A report already issued stays exactly as issued; the next
report carries the new text. An erasure of a person whose approval a later re-edit replaced
still finds and withholds the reports made after that approval.

One migration, NarrativeRevisions, generated by the EF tool for each provider (SQLite
20261115075924, SQL Server 20261115075929). Up only creates narrative_revision with its
primary key, two foreign keys, four CHECK constraints and one index; Down only drops it.
No existing table or row is changed. infra/sql/api-identity.sql gains
DENY UPDATE, DELETE ON poc.narrative_revision TO poc_app. No new user-readable word.

Not deployed. No migration is applied anywhere by this merge. Deploy-time effects, for the
product owner's deploy step: run the Assessment migration bundle (one new table), then
re-run infra/sql/api-identity.sql for the new DENY. After a re-edit, the Demo copy of a
report issued before it answers 409 report.changed-since-issue, as for any later change.
Never run the migration's Down on a hosted database once revision rows exist.
