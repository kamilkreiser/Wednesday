## In short
An approved or edited executive narrative can now be edited again. Each re-edit needs the audit note and re-approves the
narrative. The text and review it replaces are kept as a numbered row in a new append-only table, narrative_revision.
A report already issued stays exactly as issued; the next report carries the new text. Approve and Reject stay for a new
draft only. One migration (it only creates that table). Not deployed. No new user-readable word.

Reviewer feedback item: "Narrative: no way to edit the narrative once approved."

## What changes
- Rule (NarrativeReview.cs): Edit is accepted on approved and edited narratives, with the same text, note and length rules
  as a first edit; the result is edited. Approve and Reject are still refused (409) on them; rejected, failed and pending
  narratives stay not reviewable. No new error code.
- Endpoint (ReportingEndpoints.ReviewNarrative): before the narrative row is overwritten, the review it replaces is added as
  revision 1, 2, ... in the same save. Two re-edits sent on one ETag give one 200 and the rest 412, one revision row, never a 500.
- Who may re-edit: the same roles as a first review (Admin, Consultant, the Partner who owns the customer). Demo and a
  Partner who does not own the customer get 403 and nothing is stored.
- Table narrative_revision (Entities.cs, AssessmentDbContext.cs): key pk_narrative_revision (assessment_id, narrative_id,
  revision); foreign keys fk_narr_rev_narrative (to narrative) and fk_narr_rev_reviewer (to app_user), both restrict;
  CHECKs ck_narr_rev_status, ck_narr_rev_number, ck_narr_rev_note, ck_narr_rev_role; one index on review_by. The context
  refuses to update or delete a revision row.
- Personal data (PersonalDataEndpoints.StoredReportsAsync): the export lists a person's superseded reviews under
  narrative_revision, and an erasure also finds reports made after an approval that a later re-edit replaced, so those
  reports are still withheld.
- Screen (ApiNarrative.tsx): a current approved or edited narrative shows the existing Edit button; the existing editor and
  "Save edit and approve" send the edit. Earlier revisions are stored and exported, not shown.
- infra/sql/api-identity.sql: one new line, DENY UPDATE, DELETE ON poc.narrative_revision TO poc_app, and the header names
  the new append-only table.

## The migration (one, not deployed)

its 4 CHECKs, 2 foreign keys and primary key read back from the catalog; running the generated Down and then Up on a migrated

## Deploy-time effects (the product owner's deploy step; nothing here happens on merge)
1. Run the Assessment migration bundle: one new migration, one new table.
2. Then re-run infra/sql/api-identity.sql for the new DENY (the table must exist first).
3. After a re-edit, the Demo copy of a report issued before it answers 409 report.changed-since-issue, as for any later
   change. The owner still downloads the issued report unchanged; a new report gives a new Demo copy.
4. The edited-or-rejected metric counts an approved narrative that is re-edited.
5. Never run the migration's Down on a hosted database once revision rows exist: it would drop them.
A merge deploys nothing: the CI workflow builds, tests and keeps deploy packages only.
