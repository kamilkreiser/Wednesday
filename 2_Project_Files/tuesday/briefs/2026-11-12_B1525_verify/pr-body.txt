## What

Test harness only (RD-982). No backend or static file changes.

rd720 runs rd412-smtp-route once per cell as a nested jest run. Jest sets JEST_WORKER_ID to 1 for an in-band run, so the nested run searched worker 1's port band whichever worker started it. A suite in the real worker 1 that boots a server through bootServer could be handed the same port while the nested server was still booting. The readiness loop accepted any HTTP 200, read the nested server's answer as its own child's, its own child then died on EADDRINUSE, and the next request was refused (seen in rd657 and boot-probe-log-redaction under --maxWorkers=2).

## Changes

- test-server.js: workerBand() honours NEXUSAI_TEST_BAND_WORKER before JEST_WORKER_ID; new nestedJestEnv() returns the top band of the slot (band 16, idle under --maxWorkers=2) and throws if the caller is already worker 16 or already a nested run.
- rd720: passes nestedJestEnv() to the jest run it starts. Its 8 test titles are unchanged.
- rd395-server-harness.js: bootServer accepts a 200 only after its own child's "running on port <port>" line is in the child's output; a foreign answer becomes a named failure ("did not come from this child") instead of a wrong success.
- New rd982-harness-port-band.test.js (4 cells). Expected counts 5581/337 -> 5585/338.
