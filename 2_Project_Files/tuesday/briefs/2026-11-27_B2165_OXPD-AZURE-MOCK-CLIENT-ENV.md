## BLUF 1: the best way for a client's Azure server to reach printers in their office (Kam's question, board 18:13:30)

Kam's words (relayed by Tuesday, verbatim): "the printer sitting here is a good example. clients will have more complex networks but their printers will always be in their office. let me know the best design for this. it needs to be seamless and security aligned. use fable if need be".

**Recommendation: an "OXPd Site Connector", a small container (or the same appliance image) the client runs in each office, that dials OUT to Azure over port 443 through Azure Relay Hybrid Connections and passes the printer traffic through, both ways, without ever opening a port on the office firewall.** Details in section 2A.

- **Seamless:** the client's IT does three ordinary things: run one container or VM in the office on any host that can see the printers; let it out on 443 to `*.servicebus.windows.net` (through their proxy if they have one); add one internal DNS name (`printsuite.<their domain>` → the connector). No VPN, no firewall inbound rule, no routes, no IP-range clash between office and Azure (the common blocker for a site-to-site VPN in "more complex networks"). The Marketplace template creates the Relay pieces in the client's own Azure group with the server.
- **Security-aligned:** both ends only dial out; the Azure server has no Internet-facing port; TLS runs end to end from printer to server (the connector only passes bytes and never holds the server's key); the connector reaches only printers the server has enrolled and only on 443, 7627 and 631 (a VPN would give the Azure network reach into the whole office); every connection is logged to the client's Log Analytics; Relay credentials are per-site, Listen-only or Send-only, kept in Key Vault or replaced by an Azure Arc managed identity. It is the pattern HP uses for its own cloud fleet service (an on-site proxy behind the firewall, B2163 §2a) and the "secondary gateway" a vendor names for OXPd 1 in the cloud (B2163 §2a, Ricoh).
- **How the printer's two-way needs are met:** printer → server callbacks go to `printsuite.<domain>`, which resolves to the connector, which carries the TLS stream unchanged to the server; server → printer calls (7627 for OXPd 1.x, 443 for OXPd 2 and discovery, 631 for IPPS print) go out through Relay to the connector, which opens them to the printer's real address. The URL the printer sees is its own address and port (no port remapping). **The one thing to prove on the M577:** the printer sees the connector's LAN address as the caller instead of the server's; whether OXPd 1.x cares is UNMEASURED and is the first test (spike S14b, half a day). If it fails, the fallback is the routed site-to-site VPN of section 2 (no translation, more client IT work).
- **Cost per client site:** Azure Relay listener A$0.019/h (A$13.87/month) × 2 listeners = **A$27.74/month**, first 5 GB of traffic a month free then A$1.42/GB (retail API, 18:16:28), plus whatever host the client gives the connector. A site-to-site VPN gateway is about **A$239/month** per client (VpnGw1AZ + connection + IP) plus their firewall work.
- **Lab build on Kam's M577 network:** the mock server VM in `oxpd2-dev-rg` + a Relay namespace + the connector as a container on this Mac (Docker present). **Kam's router: no change** (only the printer ↔ Mac route he already ruled, K4/C-84, owed 118). **Kam's hands:** approve the card (mock environment ~A$105/month always on, ~A$67 with the server stopped out of hours; over A$50, so a card), register the `Microsoft.Relay` provider on the subscription (one click as Owner, or a card for us to do it under his login), the domain, the licences. **Days (ESTIMATE):** lab proof with Microsoft's open-source `azbridge` relay tool 1.5 days (lands M-a about Wed 2 Dec); the product connector (allow-list, audit, CONNECT-proxy sidecar, Arc option, Marketplace wiring) 5 to 6 lock-days, after the working copy or beside it with a second builder. Relay alone (without our connector) is not enough: the App Service flavour "provides access from your app to a TCP endpoint. It doesn't enable a new way to access your app" (https://learn.microsoft.com/en-us/azure/app-service/app-service-hybrid-connections), i.e. one direction. Because both ends are ours, the raw Hybrid Connections protocol carries both: each side is a listener for the flows it receives and a sender for the flows it starts ("bi-directional, request-response, and binary stream communication ... Either or both parties can be behind NATs or firewalls", protocol guide). Up to 25 listeners per hybrid connection with random balancing (same page): two connectors per site give availability.

### The recommended design in detail
- **Azure side (Marketplace template, client's resource group):** server VM (section 1), a Relay namespace, hybrid connections per site: `<site>-to-site` (connector listens: server → printer flows; the target `ip:port` travels in the connect path suffix, which the protocol passes to the listener) and `<site>-to-server` (server sidecar listens: printer → server flows). Per-connection SAS rules: the connector gets Listen on `to-site` and Send on `to-server` only; the server the reverse. Keys in Key Vault; or Entra roles (Azure Relay Listener / Sender) on the Arc managed identity of the connector host (the template, deployed by an Owner, can make the role assignments in the client's group).
- **Server side:** a sidecar container on the server VM: (i) a local HTTP CONNECT proxy whose upstream is Relay, so the server's device clients keep the printer's real URL (`https://192.168.8.x:7627/...`) and only set a proxy per site (.NET `HttpClient` supports a CONNECT proxy natively: no core change, an adapter setting); (ii) a Relay listener that forwards accepted streams to the server's local HTTPS port. The server VM needs no inbound rule at all.
- **Office side (the connector):** signed container (and the appliance/Windows forms, C-17 parity: Q19); outbound 443 only; listens on the LAN on the server's HTTPS port for printer callbacks and passes TLS through (SNI-free TCP passthrough, it never terminates); accepts Relay streams for server → printer and connects only to (printer IP, port) pairs in an allow-list the server pushes after onboarding (443, 7627, 631); logs every stream (time, target, bytes, duration, outcome) to the client's Log Analytics; health heartbeat to the server's console (C16 device status).
- **DNS and certificates:** the client's internal DNS: `printsuite.<domain>` → connector LAN IP (or IPs, for two). The server certificate stays on the server (CN/SAN = FQDN, customer CA, 02:796); the CA chain still goes to every printer by `ImportCertificate` (02:635). Nothing in the connector is secret except its Relay credential.

### Security review points (for the security reviewer; each is a test or a design rule)
1. No inbound port on the office or on the Azure server; prove with an external port scan of both.
2. TLS end to end printer ↔ server: prove the connector holds no private key and cannot read traffic (capture on the connector shows TLS only). Server → printer: TLS to the device's pinned certificate (02:639) on 443; if a 1.x service on 7627 is plain HTTP on the device side (UNMEASURED), the LAN leg connector → printer is as exposed as with an on-premises server, and the Internet leg is inside Relay's TLS.
3. Allow-list enforcement: the connector refuses any target not pushed by the server, any port outside 443/7627/631, and any non-RFC1918 target; test with a forged target.
4. Least privilege: per-site, per-direction SAS rules (Listen-only / Send-only) or Entra roles via Arc managed identity; rotation without touching printers; no namespace-wide keys anywhere.
5. Audit: connector stream log + Relay diagnostic logs + server logs correlated by a stream id, all in the client's workspace; the deny-list of fields (02:575) applies to the connector too.
6. Supply chain: connector image signed, SBOM, pinned base image, update channel (compose pull or Arc extension); the connector runs as non-root with a read-only filesystem.
7. Data path and residency: scan images and print data transit Microsoft Relay inside TLS in the client's chosen region; state it in the security whitepaper.
8. Availability: Relay down or connector down = printers fall back to the HP home screen (02:571 "Enable HP home screen if OXPd app fails to load" left ON); two connectors per site; Relay SLA UNMEASURED.
9. Latency: one extra hop through Relay (Australia East); measure sign-in round trips against the 10-second panel script limit and inactivity timers (02 §4 timeouts row) in S14b.
10. The source address the printer sees is the connector's: a printer EWS IP access list must include the connector (install guide line); OXPd 1.x behaviour UNMEASURED (S14b).
11. `azbridge` (Microsoft's open-source Relay tunnel tool, MIT) "is not covered by Azure product support" (https://github.com/Azure/azure-relay-bridge): lab proof only; the product connector is ours on the supported Relay SDK (a new package: supervised fetch, C-61/C-62).

## 2. The printer path (two-way, device port 7627, no address translation) — the lab VPN analysis, now the FALLBACK

### (a) Azure VPN Gateway site-to-site to Kam's router

The VPN Gateway Basic SKU currently supports only the Basic SKU public IP address resource", while Basic public IPs "are being phased out". Whether a NEW Basic gateway can be created today is therefore not established; the build lane tries it once by CLI and falls back to VpnGw1AZ.
- **Policy vs route-based:** route-based is the only kind the portal creates since 1 Oct 2023 (FAQ); policy-based = IKEv1, Basic only, 1 tunnel. Route-based defaults: IKEv1 and IKEv2, PSK, Phase 1 AES256/SHA256 etc., DH group 2 (*About VPN devices*, https://learn.microsoft.com/en-us/azure/vpn-gateway/vpn-gateway-about-vpn-devices). Basic: no custom IPsec/IKE policy, no IKEv1 on route-based (FAQ).
- **NAT:** "network address translation traversal (NAT-T) is supported. Azure VPN Gateway does not perform any NAT-like functionality on the inner packets ... ensure that the on-premises device initiates the IPSec tunnel" (FAQ). So the inner traffic printer ↔ server is untranslated, which is what OXPd 1.x needs.
- **What Kam's router must support (UNMEASURED; ask):** (1) make and model and firmware; (2) site-to-site IPsec with **IKEv2, route-based (VTI)**, or at least IKEv1 policy-based for Basic; (3) PSK auth with AES256 + SHA256 + DH group 2 or 14; (4) can it initiate (it sits behind his ISP: is his WAN address public, static or dynamic, or carrier NAT?); (5) can it route 10.232.0.0/24 into the tunnel **without** NATing tunnel traffic; (6) does it keep the tunnel up (DPD) and survive reboots.
- **Kam's hands:** the whole router-side configuration, and every later change. Most hands of the four.

### (b) A small box on the lab network as the site's VPN end (recommended for the site end)
- A Linux VM on this Mac (bridged onto 192.168.20.0/24) or any small Linux box on the printer subnet runs **strongSwan (IKEv2, route-based, PSK)** against the Azure VPN Gateway, initiates the tunnel (NAT-T, per the FAQ line above, so no inbound port forward on Kam's router), forwards IP with **no masquerade**. Microsoft: "Other software VPN solutions should work with the gateway, as long as they conform to industry-standard IPsec implementations" (FAQ); strongSwan is not in the validated list (only RRAS is named as supported software), so support is ours.
- **Kam's router needs one static route: 10.232.0.0/24 via the box's LAN address.** The printer's default gateway is the router, so without that route the printer's replies and callbacks never reach the box; a box that source-translated instead would break the no-NAT rule. That route is the one irreducible Kam action for any option. The 192.168.8 ↔ 192.168.20 route (owed 118, K4 ruled C-84) is also needed if the box sits on the Mac's subnet; putting the box on the printer's subnet 192.168.8.0/24 removes that dependency (needs a machine there: UNMEASURED what Kam has).
- The local network gateway in Azure holds his WAN address (or an FQDN if it is dynamic: UNMEASURED which); the box must be up whenever the printer is tested (the Mac must not sleep).

### (c) Azure Relay / Hybrid Connections, or another relay
- Hybrid Connections relays "Web Socket connections and HTTP(S) requests and responses"; both parties make **outbound** WebSocket connections on 443 to a rendezvous; the listener is custom code using the protocol (https://learn.microsoft.com/en-us/azure/azure-relay/relay-hybrid-connections-protocol). The App Service flavour gives "access from your app to a TCP endpoint. It doesn't enable a new way to access your app", one host:port per connection, via the Hybrid Connection Manager agent on site (https://learn.microsoft.com/en-us/azure/app-service/app-service-hybrid-connections).
- **Server → printer** could be carried (an on-site agent opens TCP to the printer's 7627 for each relayed connection), but the printer then sees the agent's address, not the server's: a translation by proxy. **Printer → server callback** has no path: Relay "doesn't enable a new way to access your app", so a second, custom reverse listener on site would have to terminate the printer's TLS (the CN would be the agent's), i.e. the "site relay" component 02:249 says a cloud server needs, which no design, ruling or HP source describes, and which is software we would have to build and ship. **Rejected: it does not mirror any documented client pattern and breaks the no-NAT rule.** Relay pricing for australiaeast: not returned by the retail API (UNMEASURED); provider not registered.

### (d) Other options a client would use
- **A VPN appliance in Azure (NVA) instead of the gateway:** Microsoft: "You can deploy your own VPN gateways or servers in Azure from Azure Marketplace or by creating your own VPN routers. You must configure user-defined routes" (FAQ). A B1s Linux VM with strongSwan or WireGuard in the VNet (IP forwarding on its NIC + a route table on `snet-server`: both within Contributor) ↔ the same lab box. Mirrors clients who run FortiGate/Palo Alto/pfSense NVAs; costs ~A$24/month and can be stopped. Less "Microsoft-native" than (a)/(b)'s gateway.
- **Point-to-site from the box:** NOT usable: a P2S client gets an address from the client pool, so printer traffic would need translation on the box (breaks no-NAT). Excluded.
- ExpressRoute: out of scope (commission).
