## BLUF

GET /api/settings/agent and POST /api/settings/agent are removed, with their capability entries, their tests and their two rows in the role-capability inventory. This is the product owner's 2026-11-12 ruling: retire both routes and leave the stored values untouched. The five stored agent preference values stay in the settings file and its backup copies, unread; nothing writes, deletes or migrates them. Nothing else in the server changes.

## Why

The Settings form that posted these preferences was removed in September, and no code reads the five stored values, so the two routes only stored preferences that nothing used.

## What changes

- `backend/server.js`: the GET and POST handlers, their field lists and their field check are deleted (4 lines added, 60 removed). The two shared body checks, `isPlainRequestObject` and `isBooleanSettingValue`, are unchanged and stay, because the business hours write uses them. One comment above them says so.
- `backend/services/capabilities.js`: the two route entries and the pending-gate line for this ticket are removed. Three edits, nothing else.
- Both retired paths now answer 404 from the final handler; with sign-in enforced an anonymous caller still gets 401 first.
- Two tests used the agent write as a generic authenticated write probe (`__tests__/rd436-r4-enforce-stamp-and-status.test.js` and `tests/e2e/rd436-r4-login-after-selfheal.browser.js`). They now post the Settings page's own body to `POST /api/settings/business-hours`, which writes through the same settings storage; a backup generation of the settings file holds the new keys after that write, which is what the probe label says.
- `__tests__/rd563-agent-settings-validate-before-write.test.js` is deleted: it tested only the two retired routes (5 cells).
- `__tests__/rd969-three-routes-empty-request.test.js` loses the agent leg of its last cell; its 8 cells stay.
- `__tests__/rd691-agent-settings-routes-retired.test.js` is new (5 cells): GET answers 404; POST with the complete body answers 404 and the settings file is byte-identical; with sign-in enforced both methods are 401 anonymous and 404 for a viewer and an administrator; seeded values for the five keys survive a GET and a POST of the retired paths; the route text is gone from the server, the capability map and both inventory files.
