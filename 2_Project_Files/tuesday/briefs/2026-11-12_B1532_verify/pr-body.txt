## BLUF

Three routes that answered HTTP 500 now answer properly (RD-969, RD-563). `GET /api/models` threw on every request and now answers 200. `POST /api/settings/agent` and `POST /api/settings/business-hours` wrote some keys and then threw on a missing value; each now checks its whole body first and, on a bad body, answers 400 with the names of the invalid fields and writes nothing. A valid body is stored exactly as before. No role gate is added or changed.

## What was wrong

- `GET /api/models` mapped `[key, model]` pairs over `getEnabledModels()`, which returns a list of objects, so the handler threw on every request.
- `POST /api/settings/agent` wrote `agent_response_style` and `agent_language` and then threw on `useEmojis.toString()` when the flag was missing: a half-written settings file and a 500 with no reason.
- `POST /api/settings/business-hours` read its body field by field the same way and wrote as it went.

## What changes

- `backend/server.js`: two small functions above their routes return the list of invalid field names; each handler answers `400 { success: false, error, invalid: [names] }` before its first `setSetting`. The names come from a fixed list, so the answer reflects no request text. The success path is the same `setSetting` calls in the same order.
- Agent rule: the body is a plain object; `responseStyle`, `language`, `agentRole` are strings; `useEmojis`, `useMarkdown` are a boolean or the text `'true'` / `'false'`.
- Business-hours rule: `weekdayStart`, `weekdayEnd`, `saturdayStart`, `saturdayEnd` and `excludeSunday` are required; a time is blank or `HH:MM` on a 24 hour clock; the Sunday pair is optional while Sunday is excluded (the Settings page leaves it out of its body then) and required and valid when Sunday is not excluded. There is no start-before-end rule.
- `GET /api/models` maps the objects (`id: model.key`). `memoryUsage` and `performance` were never set after the local-model provider was removed and stay omitted from the JSON.
- Two new test files, 13 cells: the refusals leave `settings.json` byte-identical, the Settings page's own bodies still answer 200 and store what they stored before, and an enforced server answers 401 anonymous and 200 / 400 / 400 to a viewer and to an administrator.
- `docs/role-capabilities.json` and `docs/ROLE-CAPABILITIES.md` are regenerated by `scripts/role-capability-inventory.js --generate`; the changed rows are exactly `GET /api/models` (500 to 200), `POST /api/settings/agent` and `POST /api/settings/business-hours` (500 to 400); anonymous stays 401.
- `scripts/verify-expected-counts.json`: 5599 tests in 341 suites to 5612 in 343.
