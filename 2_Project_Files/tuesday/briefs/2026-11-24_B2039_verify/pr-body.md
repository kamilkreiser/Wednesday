## What this changes

Two routes let any signed-in session make the server use a data source's stored sign-in details:

- `GET /api/setup/data-sources` decrypted every enabled source and ran a connection test with it.
- `GET /api/debug/data-sources` decrypted each non-primary source and queried 5 rows. Its answer carries `hasDecryptedSecret`, `workspaceId`, `authMode` and, when the query succeeds, a `sampleRecord`.

Each handler now starts with the same administrator check as its four sibling routes from RD-1011: `if (!(await requireAdminFor(req, res))) return;`. The check is setup-mode aware. It refuses nobody while sign-in is not configured or setup is unfinished, so the first-run wizard keeps working.

**Refusing a viewer the setup list is the coordinator's default, not the product owner's choice.** RD-1021's own question to the product owner ("is a viewer meant to keep the list?") goes to him with this landing. If he answers "keep the list", reversing it means changing three lines in the setup handler, two inventory rows and three test cells.
