TITLE: Design: an account in more than one organisation, with approval-chain rules set per organisation or project

**BLUF:** DESIGN ONLY: nothing is built before Kam sees the design. Kam asked for a GitHub-like model: one account can belong to several organisations, and each organisation or project has its own rules for the approval chain. Today the platform holds ONE organisation per user (a single column), a many-to-many membership table that only two admin routes and the demo seed touch, and approval chains that are chosen by transfer type or document type and never by organisation. This ticket records what exists, measured at develop `ce0a767a3fc4`, so the design starts from the code and not from memory. Priority Medium (3) proposed: it changes the data model (who belongs to which organisation) and touches auth, the signatory gate and the transfer workflows; nothing is broken today.

**Source:** Kam, live board, 2026-11-24 15:18:33, a note on card secuura-nominee-must-belong-ks2345-1124 (he answered outside its options), verbatim: "a nominee can be part of any company.  Rules of the approval chain must be enforced.  Similar system to GitHub.  one account can be part of multiple organisations.  each organisation or project has rules". Related by citation only: KS-2345 (the nominee question, which carries this note), KS-2343 (who may approve a workflow step; Kam ruled that the KS-2038 party rule governs), KS-2339 (PR 2294, the signatory write gate), KS-2038 (the party rule).

**What exists today** (develop `ce0a767a3fc4`, read 2026-11-24 by Seat S 121st through the GitHub API; nothing was run). Paths are under `Blockchain/Dev/`.

1. **One organisation per user.** `migrations/001_initial-schema.sql` line 531: `ALTER TABLE users ADD COLUMN IF NOT EXISTS organization_id UUID REFERENCES organizations(id);`. `migrations/030_auth_user_columns.sql` line 21 adds the same column with no foreign key. The users table also carries a tenant (`tenant_id`, `migrations/030_auth_user_columns.sql` line 28), a second axis that this ticket does not touch.
2. **A membership table exists.** `migrations/001_initial-schema.sql` lines 75 to 88: `organization_members` has organization_id, user_id, a NOT NULL role, permissions (JSONB), status, invited_by and joined_at, with `UNIQUE(organization_id, user_id)`. By shape it is many-to-many.
