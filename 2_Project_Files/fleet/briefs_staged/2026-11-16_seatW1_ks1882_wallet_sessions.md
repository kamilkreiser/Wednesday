## THE CHANGE (the minimum; the rulings are the spec)
**The rule (D1).** A session may be read or ended by (i) a person whose `userId` matches the session's recorded owner, or (ii) a platform administrator (`isPlatformRole(req.user.role)`, already imported at `server.ts:22`: SYSTEM_ADMIN / SUPER_ADMIN, either casing, ASCII fold, a non-string refused). A session may be SIGNED against by the owner only: no administrator arm (an administrator can read or disconnect, as KS-1845 lets them list; asking a stranger's wallet to sign is not an administrator job). Match the owner like `services/transfer/src/services/transferAccess.ts` `sameId` (ASCII fold, so an upper-case copy of the owner's id matches; the Kelvin sign U+212A and the dotless i U+0131 never do): write the match as a pure function in a new `src/utils/sessionAccess.ts` (`mayReadOrEndSession(user, ownerId)`, `maySignWithSession(user, ownerId)`), unit-pinned, not inline in `server.ts`. A non-string or empty `userId`, a session with NO recorded owner, and an unknown id all fail the owner arm. Every refusal answers the route's OWN 404 bytes, byte-identical to the unknown-id answer, before any other work and before any query (do NOT use a 401/403: different bytes, and a 403 confirms the id exists).
**Where the owner lives (D2).** A second `Map<string, string>` (`sessionOwner`) beside `memConnectedWallets`, set in `POST /api/wallets/session` from `req.user.userId`, deleted when the session is deleted. NOT a field on the stored session (it would print in the 201 body, the GET body and `GET /api/wallets/sessions`; pin the exact key lists, Q 1st's control R5-C2, which must stay green). **No migration, no column, no change to `dbSaveWalletSession`'s SQL.** Consequence, stated plainly in the PR: a session that is not in this process's map when the request arrives (a row restored by `loadFromDb` after a restart, or read through GET's database fallback) has **no known owner and is refused to every caller except a platform administrator**; for the owner it reads as gone. Sign already returned 404 for those (it never read the database); GET and DELETE now do too for the owner. If more than one replica runs, a session made on one is invisible to its owner on another (UNMEASURED; the durable fix is the owner column, KS-2042, Kam's).
**The doors (D3 and the order of work).**
- GET: look up (memory, then the database fallback exactly as today); `if (!session || !mayReadOrEndSession(user, owner))` answer the existing 404 bytes. A DB-only session has no owner, so only a platform administrator reads it.
- DELETE: look up the session first (memory, else a read of the row if the database is available, so an administrator can end a database-only session); `if (!session || !mayReadOrEndSession(...))` answer the 404 bytes **with no UPDATE issued**; only a permitted caller reaches the save, the map delete and the `UPDATE`. This ALSO closes KS-2042's first item for refused and unknown callers (name it in the PR body; KS-2042's other two items stay open). The existing "unknown id answers 404" behaviour for a permitted-nothing caller is preserved: an unknown id by an administrator still answers 404 and issues no UPDATE (a change from today's UPDATE-then-404: say so, pin it).
- SIGN: keep the 400 validation first (it depends on the body only, so it leaks nothing); then `if (!session || !maySignWithSession(user, owner))` answer the 404 bytes.
- CREATE: record the owner. **A verified token with no usable `userId` (missing, empty, non-string) cannot own a session: `POST /api/wallets/session` answers 401 through the shared `UnauthorizedError('Authentication required')` path (the shape `requireRole` uses in `packages/shared/src/middleware/index.ts`; MEASURE the exact bytes through the real `errorHandler` before you pin them) and creates nothing** (D3, W3).
