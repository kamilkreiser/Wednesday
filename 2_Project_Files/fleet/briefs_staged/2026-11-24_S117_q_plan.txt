## Two facts for the contract choice

1. The interceptor's CSRF branch (`frontend/issuer/src/services/api.ts` lines 220 to 227) tests `code` at the top level of the response body (`data?.code?.startsWith('CSRF_')`). Every CSRF refusal the gateway sends nests the code under `error` (`services/api-gateway/src/middleware/csrf.ts` lines 385, 409, 429, 439 and 459, each inside an `error: {` object), so the branch, which reloads the page, never matches. A CSRF 403 falls to the last line and is rejected sanitised.
2. `sanitizeError` (`frontend/issuer/src/utils/errorHandler.ts` line 66) does not pass the server's words on. It maps the code or the status to a fixed sentence from a table (lines 17, 18, 32 and 42 hold four of them; the status switch is lines 85 to 116). Showing `err.message` at a site therefore shows that sentence: a 403 gives "You do not have permission to perform this action.", every 409 gives "This document has already been certified.", and a 500, 502 or 503 gives "Service is temporarily unavailable. Please try again later." It reads the server's code at the top level of the body (`error.response.data.code`, line 77), which the gateway's nested `error.code` never fills, so the status switch does the work.

So the two directions this ticket's "Suggested direction" names each have a price. Passing the response through lets a site read the server's own text, and gives up what the interceptor's last-line comment says it is for ("Return sanitized error to prevent information leakage", line 274). Reading `err.message` is safe but is a fixed sentence by status, and a 409 always reads as "already certified".
