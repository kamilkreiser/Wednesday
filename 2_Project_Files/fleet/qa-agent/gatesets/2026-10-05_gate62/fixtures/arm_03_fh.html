🛡️ Post-run gates — judging the RUN, not its assertions (KS-517 · KS-684)

Three gates run after a Schemathesis sweep and feed the exit code alongside the check results. They exist because every assertion-based gate shares one blind spot: a check that never ran cannot fail, so a run that tested nothing scores clean everywhere. Each of these answers “did this run have the standing to say anything?” rather than “what did it say?”
The three gates
Authenticated coverage (KS-517) — a sweep that loses its session still calls every operation, but the requests die at the auth middleware and never reach a handler. Measured from schemathesis-metrics.jsonl. Caught 240/309 operations stuck at 401.
Run validity (KS-684) — declares a run INVALID when errors dominate: more than 10% of operations erroring, or 5+ operations sharing one identical error message. Read from the run’s own JUnit XML, deliberately not from the report’s parsers, so the gate can disagree with the report. Reconstructed against the 2026-08-24 incident (310 of 318 operations = 97.5%) → INVALID.
Report reconciliation (KS-517) — the HTML report’s headline numbers must equal Schemathesis’ own console summary. Enforces the three-way parity MUST: console = results.json = HTML report. Fails closed — a missing artefact is “cannot verify”, never a pass.
The same blind spot in Akto — a template that was selected but never ran (KS-710 · KS-717)
Akto’s version of “a check that never ran cannot fail”. The test-id catalog is generated from the template files, and check-test-ids diffs that render against the committed catalog — both sides file-derived, so it is structurally incapable of noticing that Akto never loaded a template. A selected-but-absent id produces no testing_run_result document at all, and Akto reports vulnerable 0 exactly as it does for a template that ran and found nothing. Measured on the full OWASP run, 2026-08-28, Akto 2.22.2: 207 ids selected, 193 exercised, verdict PASS. Re-measured on slot 2, 2026-09-28, Akto 2.35.6 (KS-1286): 194 templates initiated, 50,018 result docs across 347 endpoints — the regenerated catalog is byte-identical to 2.22.2’s, and 207→194 is KS-717 dropping ids Akto could never execute rather than lost coverage.
Catalog vs loaded library (KS-717) — a live assertion in SECUURA_STACK_SLOT=1 npm run test:setup reads yaml_templates straight from Mongo (src/setup/loadedTemplates.ts, slot-aware via AKTO_PREFIX) and diffs it against the catalog in both directions, failing on drift either way. Accepted differences are ticketed entries in KNOWN_CATALOG_DRIFT, and the test also fails when a listed entry stops drifting — an exemption cannot outlive its reason.
Excluded from the catalog — an id Akto can never execute must not be selected. 8 Threat-Protection rules carry no execute: block (KS-710); 5 carry upstream’s inactive: true, which Akto stores but its engine skips via fetchOnlyActive (KS-717 §3). 1 more (BYPASS_CAPTCHA_REMOVING_COOKIE) Akto refuses to store, because its info.references: is empty and Jackson cannot coerce that to a list. Catalog 207 → 199 → 194 ids.
Reported, never silent — load-templates names every file Akto rejected and Akto’s own actionErrors; generate-test-ids reports exclusions and, separately, files with a YAML defect Akto tolerates and we now tolerate too (which ARE catalogued — LFI_IN_HEADERS_LINUX had never executed once). The HTML report renders exercised / selected with the shortfall named, not a bare count.
Outcome taxonomy — five categories, shared across all three surfaces
The taxonomy is closed and shared: a category exists in the console, in results.json and in the HTML report, with the same label and the same count, or it is a design error. results.json is the source of truth; the other two are renderings of it.
PASS — exercised, no violation
FAIL — exercised, violated a check
UNVERIFIED — should have run, did not; gates the run (KS-478)
OUT OF SCOPE — excluded by mode, not by accident (KS-519)
SKIPPED — a precondition was never met (KS-684)
SKIPPED is new in KS-684. Previously the banner rendered a strict PASSED/FAILED binary, so API_TOKEN not found turned four healthy suites — GDPR IDOR (KS-258), live integration (KS-416), anchoring integrity (KS-489-D) and state-machine preconditions (KS-478) — into FAILED on the 2026-08-24 run, sending readers after defects that did not exist. An unmet precondition is not a test result. A SKIPPED suite now contributes neither a pass nor a failure to OVERALL, and each row carries its reason — the two skip causes (“no credentials configured” vs “the platform did not answer”) stay distinguishable because they need different remedies. Counting a skip as a pass would be the opposite and worse error.

11. RFC 3161 Timestamp Token Verification (KS-1404)

What changed. services/timestamping accepted an unsigned timestamp token as valid. The old verifyRealToken walked the ASN.1 tree and returned valid: true whenever any OCTET STRING equalled the expected document digest — no signature check, no certificate chain, no TSTInfo parse, no algorithm-OID check. A second path accepted a JSON {"hash":"…"} token outright. Both are closed.

11.1 The verification chain, in order

KS-1404 ITEM 2 (Seat D 5th): the verifier binds the signer certificate via signingCertificate(V2) and builds the chain from the token's own certificates to a pinned root. The signer is selected by an exact SignerIdentifier match — issuer+serial or subjectKeyIdentifier — and the previous ?? certs[0] fallback is gone, so a token whose SignerInfo names nothing it carries is refused rather than checked against whichever certificate happened to be first. The token's other certificates are passed to the chain engine as untrusted intermediates; trustedCerts remains the configured anchors alone, so carrying an intermediate can never create trust. rsaEncryption (digest taken from digestAlgorithm) and RSASSA-PSS (parameters parsed, never defaulted) are accepted, because those are the algorithms the pinned providers measurably use.

A defect of this PR, found and fixed inside it, and the cell that caught it. The first version of the chain fix passed certs: [signer, ...intermediates]. pkijs treats the LAST element of certs as the end-entity — its own documented example is certs: [rootCa, intermediateCa, leafCert] — so an intermediate was validated as the leaf, and a token whose signer chained to nothing was ACCEPTED whenever some certificate it carried chained to an anchor. The order is now [...intermediates, signer]. CHAIN-3 is the only cell that fails on the reversed order, and it stays in the suite for that reason.
  1. Strict DER — definite, minimal lengths, nothing trailing. BER indefinite-length encoding is refused: a genuine token re-wrapped as 30 80 … 00 00 was accepted before this change.
  2. ContentInfo is id-signedData; SignedData's eContentType is id-ct-TSTInfo.
  3. TSTInfo is parsed, and the message imprint is read from messageImprint.hashedMessage — never searched for in the tree.
  4. Exactly one SignerInfo, whose signed attributes carry contentType = id-ct-TSTInfo and messageDigest = digest(eContent).
  5. The signature over the signed attributes re-encoded as SET OF, against the signer certificate's public key.
  6. The signer certificate carries EKU id-kp-timeStamping, is valid at genTime, and chains to a configured trust anchor.

11.2 Fail-closed, and what that means operationally

Trust anchors come from TSA_TRUST_ANCHORS_PEM (PEM text, or a path to a bundle), committed as config. Unset or empty means every real DER token verifies false with reason no trust anchor configured. Stored tokens continue to verify through the database-row branch (same hash and byte-identical proof), which this change does not touch. Compose and per-environment wiring is a separate step, so which environments have an anchor in effect is not covered here.
