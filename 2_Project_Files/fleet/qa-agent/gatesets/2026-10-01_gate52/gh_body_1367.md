Refs KS-1015

One carve out of the KS-1015 sweep, not the whole of it. KS-1015 covers 28 unowned
check/operation pairs; this is ONE of them, `GET /api/referrals/{code}`. It narrows the
ticket and does not close it.

## What was wrong
The published contract declared the flat `ReferralCode` record (id, code, ownerUserId,
uses, ...) as the 200 body. The handler (`services/referral/src/routes/referrals.ts`,
`GET /:code`) answers `{ success, data: { code, isActive, isExpired, customLabel,
referredReward, referrerReward } }`. Schemathesis flagged the 200 as
`response_schema_conformance`.

`id` and `ownerUserId` are left out of the response on purpose — this is a public lookup —
so the spec follows the runtime rather than the other way round. `ReferralCodeSchema` stays
exactly where it was for the owner list (`GET /api/referrals/user/{userId}`), which still
returns the flat record.

## What changed — 3 files
- `services/referral/src/referral.openapi.ts` (+21/-1): the 200 content becomes the
  success/data envelope with the six fields the handler sends, `customLabel` optional,
  `.passthrough()` on the data object.
- `services/referral/src/__tests__/ks1015-referral-lookup-spec-declares-envelope.test.ts`
  (+76, new): renders the document the generator publishes from the shared registry and
  asserts the envelope. No server, no database, no network.
- `docs/openapi/secuura-api.yaml` (+30/-1): regenerated by `npm run generate-openapi`.
  Not hand-edited.
