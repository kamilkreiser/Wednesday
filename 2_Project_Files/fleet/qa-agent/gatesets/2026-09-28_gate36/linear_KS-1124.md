## BLUF

Two READ ONLY findings in originate's `blockchain`-blob writers, recorded by the tier-2 gate on the #967 → #968 stack (KS-1071 / KS-1070) as Option B's blast radius — the gateway now honours a statusless blob's `confidence:'pending-onchain'` literal by ruling, and these are the producers of that literal. Neither is the PRs' change; both are pre-existing and identical at base. **F4:** `routes/certifications.ts:406-469` (and `:1131-1191`) sets `anchoringStatus='failed'` by default and `'submitted'` only if anchoring accepted (`:429`); in production a failure 503s (`:435`), but in non-prod it **persists** `{anchorId, txHash:null, blockHeight:null, anchoredAt:null, confidence:'pending-onchain', anchoringStatus:'failed'}`, and `:510` copies `certification.blockchain` verbatim onto the NEW document created at certify. The gateway reads neither `anchoringStatus` nor `anchorId`, no poller exists in `certifications.ts` (0 `updateDocument` / `pollAnchorUntilConfirmed` references), and `reconcileDocumentAnchorState` needs `bc.anchorId` (`anchorStateSync.ts:298`), which is `undefined` on the failed leg — so that document answers **pending-onchain at base,** `51e74ea7a` **and** `1b7c03a22` (the row was driven) for as long as it exists. **O1:** `routes/documents.ts:764-774` (the thread-token mint callback) writes `blockchain: { ...(create-time blob = nothing), threadToken }` via `updateDocument`, which **replaces** the blob (`documentRepo.ts:510-514`: `{...doc, ...updates, updatedAt}` — `updates.blockchain` replaces `doc.blockchain` wholesale). The auto-anchor accept write (`:880`) is also fire-and-forget; whichever resolves later wins. If the mint lands after the anchor accept, the document's `txHash` / `status` / `anchorId` are lost until the poller rewrites — and the confirmed-path rewrite (`anchorStateSync.ts:206-216`) does not carry `threadToken` back; only the failed path (`:160`) does. Gateway effect of the `{threadToken}`-only blob: off-chain-only at every SHA (driven, harmless); the race itself is originate's.

## Recommendation

One logical path — originate's statusless `pending-onchain` producers and the blob-replacing writers — so one ticket; split only if the two fixes land separately:

1. **F4:** on the failed leg, do not persist `confidence:'pending-onchain'` (write no `confidence`, or a `status` the gateway's closed mapping reads as off-chain-only), and/or make the gateway's Option-B arm read `anchoringStatus`; add a certifications cell asserting a failed submission never presents pending-onchain through the gateway. Prove the row first with the gate's Sweep B shape.
2. **O1:** merge rather than replace in the mint callback (spread the CURRENT persisted blob, not the create-time local), and carry `threadToken` through the confirmed-path rewrite as the failed path already does; a cell that lands the mint after the accept write and asserts `txHash` / `status` / `anchorId` survive. Prove the race first (it was READ, not reproduced).
