Refs KS-1404

Real RFC 3161 verification for the timestamping service. The previous `verifyRealToken` walked the
token for the presence of the expected hash and returned `valid: true` for any token merely
CONTAINING that digest — with no signature check at all. An unsigned, forged token was accepted.

## The change

Strict DER (BER indefinite length refused recursively, trailing bytes refused); ContentInfo is
id-signedData and eContentType is id-ct-TSTInfo; TSTInfo is PARSED and the imprint read from
`messageImprint.hashedMessage` rather than searched for; exactly one SignerInfo, whose signed
attributes carry `contentType` and `messageDigest` = digest(eContent); the signature is verified
over the signed attributes re-encoded as SET OF; EKU id-kp-timeStamping; validity at `genTime`.

New in this PR:

- **ESS binding.** Exactly one of `signingCertificateV2` (`1.2.840.113549.1.9.16.2.47`) or
  `signingCertificate` (`...2.12`) must be present in the SIGNED attributes. Its first ESSCertID(v2)
  hash must equal the hash of the SELECTED signer's DER, and `issuerSerial`, when present, must
  match. Carrying BOTH forms is refused as ambiguous. pkijs 3.4.1 exports no ESS classes (verified
  against the installed package), so the attribute is parsed from its ASN.1 directly.
- **Signer selection.** Exact `SignerIdentifier` match in both legal forms (issuer+serial, or
  `subjectKeyIdentifier`). The `?? certs[0]` fallback is REMOVED — no match is now a named refusal.
  The only remaining occurrence of that string is the comment recording the prior behaviour,
  verified with a comment-excluding filter plus a control proving the filter can report a live line.
- **Chain.** The token's own `certificates` are passed as UNTRUSTED intermediates, with
  `trustedCerts: anchors` the only trust, so carrying an intermediate can never create trust.
- **Algorithms.** `rsaEncryption` (`1.2.840.113549.1.1.1`, digest taken from `digestAlgorithm`) and
  `rsassaPss` (`...1.1.10`, parameters PARSED, never defaulted — absent or unreadable parameters are
  a refusal). Nothing broader than what the measurement below supports.

Also: node-forge is out of this service (`GHSA-86w9-cpqp-85rv` has no upstream fix), pkijs 3.4.1 and
asn1js 3.0.10 are in at exact pins, the dead GHSA 86w9 audit-baseline row is removed, and a local
DER writer produces request bytes byte-identical to the previous output, pinned by a cell.

**Behaviour change, named:** a mock token NOT stored in the DB no longer verifies (DB-row-only
mocks). `isQualified` is dropped.

### A security defect in this PR's own first draft, caught by its own cell

The chain was first built as `[signer, ...intermediates]`. pkijs treats the **LAST** element of
`certs` as the end-entity, so that order validated an *intermediate* as the leaf: a token whose
signer chained to nothing would have been ACCEPTED. The order is now `[...intermediates, signer]`.
**CHAIN-3 is the only cell that fails on the reversed order** — it caught this defect.

## The PSS proof — the measurement the design depended on

Does pkijs 3.4.1's `CertificateChainValidationEngine` verify an **RSASSA-PSS ISSUER** signature?
**YES.** Three arms, in-process, pkijs 3.4.1 + asn1js 3.0.10 at the declared pins, node v24.7.0:

- **PSS** — a root signing an intermediate, both `rsassaPss`: `engine.verify()` **true**, resultCode 0.
- **PKCS#1 positive control** — the identical shape with sha256WithRSAEncryption: **true**, code 0.
  Without it, a PSS failure could have been the harness rather than pkijs.
- **PSS-TAMPER negative control** — the PSS chain with one signature byte XOR 0xff: **false**,
  code -1, `No valid certificate paths found`. Without it, "PSS verifies" could have meant the
  engine never looked at the signature. It looked.

Run from a scratch directory with a `node_modules` symlink, so the worktree was never written to —
`status --porcelain` 0 and HEAD unchanged after the run, both re-measured.
