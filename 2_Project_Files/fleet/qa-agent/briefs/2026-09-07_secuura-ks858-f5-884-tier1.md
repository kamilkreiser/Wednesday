**(3) THE THREE ROWS THAT CHANGED, and one of them was a judgement call Wednesday ruled on.**
`POST //api/auth/verify-email` went **404 → 200**. Wednesday ruled that a GO because the newly-resolving
path arrives INSIDE the guard stack — evidenced by `//api/gdpr//erasures` going **404 → 401**, i.e.
reaching the gate and being refused. **Test that ruling adversarially.** Is there ANY path that now
resolves where it previously 404'd and arrives with a guard SKIPPED rather than applied — an ordering
difference, a mount whose predicate sits below the normalisation but whose sibling sits above it, a
route reached before authentication that was previously unreachable? **That is the one way this fix
could be worse than the bug**, and it is what the whole ruling rests on.

**(4) THE CURIO SPELLINGS AND QUERY STRINGS — the "no new reachability" half.**
Claimed byte-identical forwarding for `%76erify-email`, `verify-email;x=1`, `verify-email%2Fx`,
`%2F%2F`, and byte-identical query strings including
`?redirect=https://example.com//a//b`. **The query half is where a path-collapsing middleware most
often over-reaches** — press it with `//` in a query value, in a fragment, in an encoded parameter, and
in a URL-valued parameter (an open-redirect target is the sharp case).

**(5) THE DOUBLE-APPLY.** The builder measured the existing `/api/gdpr`-scoped collapse at
`proxy.ts:682` as inert because the new middleware runs first and a second collapse is the identity —
and that `req.url` is restored. **Verify the ORDER is what makes it inert, and that nothing else in the
stack restores or rewrites `req.url` between them.** An inert-today interaction that depends on
ordering is a finding if the ordering is not pinned by a test.

**(6) THE RED-PROOFS.** 9 new cells; claimed red-proofed twice (collapse neutered → 4 failed/5 passed
with 9 RAN; query protection removed → 2 failed/7 passed, both query cells and nothing else).
Re-derive both. **Each tamper must red ONLY its own clause.** And ask the question the fleet keeps
