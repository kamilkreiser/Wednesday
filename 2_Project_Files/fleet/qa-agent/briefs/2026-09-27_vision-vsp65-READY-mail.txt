WHAT CHANGED (server/db.js only, plus tests and one BACKLOG line)
- The pool now has query_timeout 30000 ms and connectionTimeoutMillis 15000 ms. DB_QUERY_TIMEOUT_MS / DB_CONNECT_TIMEOUT_MS override them; a bad value (0, -1, 1.5, abc, 30s, Infinity) throws at boot instead of running unbounded. Neither setting exists in production, so the defaults apply.
- LOUD: a hit bound surfaces as DbTimeoutError, code DB_QUERY_TIMEOUT or DB_CONNECT_TIMEOUT, message "DB_QUERY_TIMEOUT: Postgres did not answer a query within 30000 ms (VSP-65)", with pg's original error as cause. The route or lastResortHandler logs it with its ref, as before.
- A client whose query timed out is DISCARDED on release, even when the caller calls release() with no error. All six pool.connect() callers do that (quotes generate, admin backup, reminders dispatcher, seed, seedCollateral, dbRestore). Without this, the stalled connection goes back into the pool with a query that never finishes.
- How: BoundedPool extends pg.Pool and overrides connect() only. pg-pool's own query() goes through connect(), so connect-pg-simple's pool.query path is covered too.
- Why 30 s: the slowest real query is the backup's per-table SELECT *. The last full prod dump on disk (production-full-20260226) is 96,690 bytes, and locally the ten dump queries take 40.5 ms in total (slowest 25.3 ms, 108 rows). So the bound has >1000x headroom.

RED-PROOF: real Postgres 16.15 (local vsp-dev-db) behind a TCP proxy that goes silent on cue, forwarding nothing either way and closing nothing, i.e. a half-open connection. Bounds are shrunk to 1500 ms in the test, with an 8000 ms budget per request. File: test/db/pool-timeout.test.js.

BEHAVIOUR CHANGES FOR THE GATE TO WEIGH
- connectionTimeoutMillis also caps WAITING for a free client when all 10 are busy. Before, a request waited forever; now it gets a DB_CONNECT_TIMEOUT 500 after 15 s.
- dbBackup.dumpTable() catches per-table errors, so a timed-out table is written into the backup as an error entry, not a failed backup. Pre-existing semantics, now reachable. Not changed.
- dbRestore (CLI) runs under the same 30 s bound per statement. Its catch does ROLLBACK on the same client, which on a stalled connection times out too and masks the first error. Pre-existing pattern, bounded now. Not changed.
- statement_timeout (server-side) NOT added. It can't see a half-open connection (the server never gets the query), which is the ticket's case. It would add server-side cancellation to every statement, a separate decision.
