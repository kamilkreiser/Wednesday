FIX
- schema.sql: each index is made only when missing (to_regclass first, so a replay's own indexes are never re-checked for ownership), and a failure to make one warns instead of failing the boot. That's VSP-71's pattern (WHEN OTHERS, per gate 11's G11-P2), for 15 of the 16 indexes.
- The exception is idx_reminders_rule_key (UNIQUE). The dispatcher's ON CONFLICT (rule_key) needs it, so it gets the existence check but no excuse: missing and unmakeable still fails the boot.
- initDb: one warning naming any guarded index still missing. The names are read from schema.sql's own blocks, so the two can't drift.
- initDb: one warning naming every public table the portal's role can't SELECT/INSERT/UPDATE/DELETE, and every sequence it can't USAGE, plus the fix (restore as the portal's role, or GRANT). Each privilege is asked separately, because has_table_privilege with a comma list is true if ANY is held. A CASE is used because Postgres doesn't short-circuit WHERE; the first draft raised 42809 on tables.
- backup-db dump header: "-- Replay as the portal's own database role (DATABASE_URL's user): the role that replays owns every table (VSP-78)."

DESIGN CHOICE, OPEN TO VETO: the access check WARNS, it does not fail the boot.
- First version (788477f, on the branch history) failed the boot. The full db suite then reddened two VSP-71 cells, whose fixture moves `session` to another role with no grant back.
- In production a boot refusal over one table would take down paths that still work (lead submission needs no session). It could also crash-loop the next deploy while production's roles are unread.
- Cost of warning: with NO grants the boot resolves and every data request 500s, with a clear line in the log. That's the pre-existing state on main for any table-level grant loss. If you'd rather the boot fail in the no-grants case, it's a one-line change back plus the two VSP-71 fixtures gaining a GRANT.
