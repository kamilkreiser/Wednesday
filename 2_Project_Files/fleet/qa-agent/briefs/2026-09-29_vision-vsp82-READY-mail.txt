CLIENT BEHAVIOUR, ESTABLISHED BEFORE BUILDING (your VSP-69 rule)
- Where client reminders come from: the only client path is POST /api/reminders (server/routes/reminders.js). Its due_at comes from the PRO dashboard as new Date($('remDue').value).toISOString() (public/pro/js/pro-dashboard.js:278). remDue is a datetime-local, so due_at is always on the millisecond grid (in practice the minute).
- The rules (quote_expiry, poc_commencement) write date + 09:00 and are internal ntfy. stale_follow_up writes NOW() (microseconds) and is internal ntfy.
- For a due_at on the ms grid, due <= floor_ms(now) exactly when due <= now. So the old truncated cutoff and the exact one decide every client reminder identically. What a client receives, including when, does not change.
- The one thing that changes: stale_follow_up's internal push is handled in the tick that first finds it (today up to ~45% wait 5 minutes).
- Not covered by that argument: an API caller sending due_at with sub-ms digits. No such caller exists in the repo; for one, the fix sends at most one tick EARLIER than today, never before due.

FIX: dispatchDue() reads SELECT NOW()::text and compares due_at <= $1::timestamptz (the gate's first shape). The per-reminder transaction, SKIP LOCKED, ordering and the 50 cap are unchanged.
